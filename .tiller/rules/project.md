## 文档与操作约定

- 正式发布前不承担旧版本兼容要求。2026-10-20 用户明确要求：“不需要兼容旧版本，后续也不需要，等正式发布后才会考虑旧版本兼容”。本项目当前及后续开发均按届时的当前契约实现，不为历史格式保留兼容分支、迁移入口或兼容测试；正式发布后再确定兼容政策。历史资料和已发生的执行记录保留，遇到不支持的格式明确拒绝，不静默修改或伪造迁移。各类独立记录分别使用其当前协议版本，不机械统一版本号。开发中已固定的管理运行环境不属于候选产品的兼容承诺，继续隔离使用。

- 本项目测试代码、长期用例与执行证据遵循[项目测试约定](testing.md)；初始化通用规则不替代项目测试框架和验证范围。
- 文档以中文为主；命令、字段名、文件路径、错误码等使用英文。
- 新建工作目录推荐 `YYYYMMDD-主题`，日期取创建日、接续保持原名；已有工作保留历史路径。模块目录仍用稳定能力名称，不加日期或排序编号。
- 开发交付按下方“默认提交与评审流程”执行；草稿、未完成任务及范围外仓库不自动提交或推送。
- 示例项目放在独立的外部仓库，tiller 文档只链接过去，不在本仓库创建 `examples/` 目录。
- 将 tiller 的设计写成自身设计，不引用外部项目作为来源或参照。
- 本次实现中的工作标识、状态文件与操作约定见工作设计；超出该范围的待定事项按决策记录推进。
- 通用入口维护 `resources/entry.md`，根 `AGENTS.md` 通过接入安装；不要在根入口区段外另写通用正文。2026-10-15 用户已授权[统一入口](../work/20261015-unify-entry/work.md)，本项目特有约束继续保存在本文件。

## 默认提交与评审流程

2026-10-20，用户要求“在开发完成代码后，提交完成后自动创建 MR，这个加到流程里面”。本节是对 tiller 本项目后续已授权开发任务的持续交付约定，覆盖必要验证通过后的提交、推送，以及 PR/MR 创建或更新，无需逐次重复询问。当前仓库为 `ChukiChen/tiller`，远端为 `origin`，目标分支默认 `main`，源分支为该任务的开发分支；用户明确指定其他目标时以其指令为准。不将此授权扩展到其他仓库、强制推送或历史重写。

1. 完成当前任务的必要实现、资料和验证，核对真实结果及遗留项，再检查待提交文件。按 Lore 格式提交属于本任务的内容，不混入无关修改、凭据或本机临时文件。
2. 将提交普通推送到已核对的远端源分支，并核对远端提交与本地 HEAD 一致。仅有本地提交或推送结果未知时不能宣称 PR/MR 已创建；先查询远端事实再决定重试。
3. 推送成功后，查询同仓库、同源分支和同目标分支的未关闭 PR/MR。已有请求则复用链接并按最新变更更新标题及正文；没有则自动创建。GitHub 使用 PR，GitLab 使用 MR。结果未知时先查询，避免重复创建；已经合入或关闭的历史请求不自动重开。
4. 标题说明具体问题和结果，正文包含范围、主要变化、实际测试与失败修复、剩余限制和关联工作。依据真实状态选择普通或草稿请求；未满足必要验证时不伪装成可合入。保存平台返回的 URL、源提交和目标，最终答复提供链接；宿主支持关联附件时同步关联。
5. 平台访问、凭据或接口不可用时，保留已完成的提交与推送，报告具体阻碍和未完成的 PR/MR 步骤；不能只给创建页面链接就宣称已创建。可用的 CLI 受控操作优先使用；旧工作格式明确拒绝时，记录限制后在本授权范围内通过宿主执行，不手写受控机器记录。

自动创建或更新 PR/MR 不等于用户验收、合入或发布。实际合入继续核对具体源提交、目标、评审和检查结果，并取得相应人工确认；不自动开启合并、删除分支或发布。

## 合并后的同步与收尾

2026-10-20，用户在确认 PR 已合并后要求“补充收尾流程”，接受已展示的“核实合并 → 安全快进更新本地 main → 归档必要资料 → 检查遗留事项 → 移除 worktree → 报告结果”顺序。本节授权执行者在本仓库满足以下条件时完成同步及任务 worktree 清理，无需逐次重复询问；不包含删除本地或远端分支，也不扩大为验收、发布或其他仓库操作。

1. **触发时机**：执行者完成获准合入后、收到用户已合并的通知时，或接续工作发现对应 PR/MR 已合并时，立即核对并推进收尾。仅写入规则不会建立后台监听；无人执行期间，网页合并不会自动更新本地文件或删除 worktree。
2. **核实合并事实**：查询对应仓库、PR/MR、源提交、目标分支、实际合并提交和时间；关闭不等于合并。确认本任务提交已包含在合并结果中；压缩或变基合并不能只按原提交祖先关系判断，应结合平台回执和内容核对。任务分支若又有新增提交，不将这些内容视为已经合入。查询失败或状态不明确时保留副本，报告待核实项。
3. **同步本地主副本**：通过 Git 登记定位主副本及目标分支，先检查未提交、未跟踪内容、未结束操作和其他任务占用，再 fetch 已核对的远端。主副本位于目标分支且干净、无本地独有提交时，只允许快进到取得的远端目标提交，并核对目标包含合并结果及同步后的 HEAD。分支不符、存在修改、超前或分叉时保留原状并报告，不自动切走其他任务、stash、reset、rebase 或强制覆盖。源码更新不等于 CLI 安装或工程资源升级；检查实际入口，必要时用既有依赖构建，安装和资源升级遵循各自规则，不能覆盖固定的历史运行环境。
4. **先归档再清理**：盘点任务副本中的共享记录、回执、忽略文件和本机资料。共享唯一成果必须逐文件持久保存；必要的候选包、验证日志和运行环境资料保存到待清理目录以外的唯一归档路径，核对清单与摘要，并记录恢复位置。不得将凭据、依赖目录等机械加入 Git，也不得假定 Git 干净就没有需要保存的忽略文件。归档不得只指向将被删除的目录。
5. **核对清理条件**：确认对应任务 worktree 无未提交、未跟踪的未归档成果、未推送提交、未结束操作、运行中的执行者或其他工作引用；检查主副本入口及有效绑定不依赖待删除路径。未完成验收或其他后续事项若仍需要该副本，则保留并说明用途；已归档且可脱离副本继续的验收不必占用开发目录。有任何缺口，只暂停依赖它的清理，已完成的同步不回退。
6. **按清单移除副本**：列明精确路径和分支，核对 Git 登记及归档后，从待清理目录之外移除本任务 worktree；宿主管理的副本使用其归档能力，并先保存该能力不包含的忽略文件。保留主副本、工作历史、本地和远端分支。默认不强制删除；普通移除失败时调查具体残留，不以强制操作跳过保护条件。
7. **记录与报告**：保存合并回执、同步前后提交、归档位置及核验、实际移除路径、保留分支和遗留事项；分别报告已合并、已同步、已清理、待验收和未发布。可用的受控命令优先使用；格式不兼容时记录实际限制，不手写机器状态或补造历史许可。后续必要共享文档变更走新分支和新 PR，不向已合并请求继续追加，也不为记录一次收尾反复制造无内容变化的 PR。

## 自身开发与产品实现

`.tiller/` 保存开发 tiller 自身所用的工程资料。CLI 源码、测试及对外分发的规则和模板分别在 `src/`、`test/`、`resources/` 中维护，与自身工程资料分开。分发资源修改后应核对自身已接入资源的版本和内容，不能用模板静默覆盖项目修改。

自举使用已确认的规则开展真实工作并留下验证依据。人工补足的步骤、尚未实现的工具能力和未通过的检查应如实记录，不把文档齐全或目录存在视为能力已实现。自举启动与验收的未定事项见决策记录 Q13。

## 性能与实现复杂度

2026-10-20 用户要求优先优化流程推进速度，并明确“后面的实现需要考虑性能问题，不能简单的进行代码堆砌”。后续已授权开发持续遵循：

- 设计同步说明关键路径、输入规模、重复读取和外部进程调用成本；避免把整体验证嵌入逐文件循环。
- 优先删除重复工作、批量处理及复用已有能力；新增抽象或缓存须说明实际收益、生命周期、容量和失效边界，避免无收益的层次堆叠。
- 使用完整用户操作的端到端耗时评估体验，分别记录实际执行与流程校验开销；为已知热点保留调用次数或规模增长回归，不能只看单个函数或测试程序耗时。
- 保留必要的来源、路径、范围、并发及写入前后新鲜度校验，通过减少重复计算提高效率；不以跳过检查换取性能。
- 验证范围按改动影响选择，通过后及时启用；新问题或新修改才扩大或重复检查，不把无关回归或额外改造无限追加到当前交付。
