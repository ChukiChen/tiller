# tiller 项目规则

本文件规定开发 tiller 自身时适用的约束，由根目录 [AGENTS.md](../../AGENTS.md) 引导读取，不作为其他项目的默认规则。

## 当前基线

- tiller 当前产品与分发资源版本为 0.5.0；`package.json`、CLI 常量和 `.tiller/project.json` 的 `resourceVersion` 必须一致。版本号只在正式发布正式包时修改。
- 默认工作流为 `start`、`resume`、`confirm`、`verify`、`check`、`accept`、`close` 与 `reopen`；`review`、`release` 和 `pr` 按需使用。默认人工节点只有需求、设计和交付验收。
- `.tiller/specs/` 是当前产品需求、设计和长期决定的依据；历史过程只从 Git 追溯，不在工作树恢复旧快照或过程目录。
- 每次会话先读[决策记录](../specs/decisions.md)，再按任务读取相关规格、背景与用例；候选方案不等于已确认决定，仍有歧义时先澄清。
- 只修改当前任务声明的范围。顺手发现的问题记录到任务记录，不扩大本次修复。

## 文档与操作约定

- 单次任务只维护 `.tiller/task/<id>/task.md`；任务标识日期取创建日，接续保持原名。模块目录使用稳定能力名称，不加日期或排序编号。
- 文档以中文为主；命令、字段名、文件路径和错误码使用英文。
- 本项目测试遵循[项目测试约定](testing.md)。不删除、跳过或弱化测试换取通过；验收条件必须先有全局用例和可定位测试。
- 需求、设计和交付验证按当前任务记录执行；长期结论在任务完成后回写规格或决定，普通实现细节不重复记录。
- 示例项目放在独立的外部仓库，不在本仓库创建 `examples/` 目录。tiller 的设计写成自身设计，不引用外部项目作为来源或参照。
- 通用入口维护 `resources/entry.md`，根 `AGENTS.md` 通过接入安装；不要在根入口区段外另写通用正文。

## 提交与评审

- 默认流程只保留需求、设计（standard 任务）和交付验收三类人工节点。本地提交只在当前任务授权时执行；推送、创建或更新 PR/MR、合入和发布必须分别取得明确授权。
- 提交主题、PR/MR 标题、分支名和说明按[决策记录](../specs/decisions.md)及使用指引生成；草稿、未完成任务和范围外仓库不自动提交或推送。
- 独立评审的阻塞发现写入任务记录并保持阻断，直到显式解决。发布使用只读准备检查；真实合入和发布仍需单独授权。
- 合入或清理前核对源提交、目标、验证结果和未保存内容。只删除已确认无用的本地分支；不强制推送、不重写历史，删除远端分支必须另有授权。

## 自身开发与产品实现

`.tiller/` 保存开发 tiller 自身所用的工程资料；CLI 源码、测试及对外分发的规则和模板分别位于 `src/`、`test/`、`resources/`。分发资源修改后应核对自身已接入资源的版本和内容，不能用模板静默覆盖项目修改。

实现和文档必须如实反映已具备的能力；人工补足的步骤、未实现的工具能力和未通过的检查不得写成已通过。产品范围或关键行为变化先更新需求、设计和决定，再同步实现、用例与入口资料。

## 性能与实现复杂度

- 设计说明关键路径、输入规模、重复读取和外部进程调用成本，避免把整体验证嵌入逐文件循环。
- 优先删除重复工作、批量处理及复用已有能力；新增抽象或缓存须说明实际收益、生命周期、容量和失效边界。
- 用完整用户操作的端到端耗时评估体验，分别记录实际执行与流程校验开销；为已知热点保留调用次数或规模增长回归。
- 保留必要的来源、路径、范围、并发及写入前后新鲜度校验，通过减少重复计算提高效率；不以跳过检查换取性能。
- 验证范围按改动影响选择，通过后及时启用；新问题或新修改才扩大或重复检查。
