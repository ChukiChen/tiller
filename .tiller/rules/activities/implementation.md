# 实现

规则标识：ACT-IMPL。修改代码、配置或测试时使用，并读取[验证依据](../quality/verification.md)。

产物组织和创建、登记、接续遵循[工作记录约定](../core.md#工作记录约定)。

开始实现前按[实施规划与任务拆分](../core.md#功能分块与实施安排)核对已确认规划、当前任务标识与范围、规格依据、前置任务的实际验证证据及完成条件。空项目先完成并验证最小可运行骨架；骨架属于普通任务，已有项目复用基础。规划不足或未确认时先补齐确认，前置任务必要验证未通过时不能进入依赖任务；不能跳过分块直接一次实现全部产品。

按[项目开发规范](../core.md#项目开发规范)核对适用约定及其确认，骨架任务中落实并实际执行适用检查；已有项目按[已有项目接手](../core.md#已有项目接手)引用现状与验证基线，比较本次结果，区分已有失败和新增回归。不以规范补充为由自动进行整库格式化或无关重构。

1. 读取当前需求、相关方案、实际代码及目标范围的项目规则，确定应改变的行为与不应改变的行为。核对对应需求和设计的有效用户确认、实际来源、内容、范围及条件；设计未确认不编写代码与测试。可以登记引用已确认的简短方案，不强制复制为工作内设计文件；核对登记对象与实际来源，但不能以缺少文档、任务简单或已有一般授权豁免确认。
2. 按现有结构完成最小完整变更，复用项目模式；避免无关改动、覆盖用户工作或在没有依据时增加依赖。跨仓库变更分别核对约定和权限。
3. 按影响选择测试、类型检查、构建及其他必要质量检查。缺陷修复或高风险行为增加有意义的回归验证，避免只重复实现细节的测试。
4. 检查实际差异并运行适用验证，读取退出状态与结果。失败先查明原因再修复，变更后重新核对受影响范围。
5. 当场将实际成果、需求对应、产物版本或内容摘要、验证环境、执行结果及未覆盖项记录到当前任务，再按依赖和授权选择下一任务。失败或缺少必要检查时不能标为已验证；最终整体测试不能倒填成早期任务放行证据。同步受影响的规格和项目知识，区分技术验证、过程合规与用户验收。

同一轮可连续执行多个任务，但不能合并它们的进入和验证节点。中断或并行改串行时重新核对当前任务与依赖；并行只用于依赖满足且责任明确的任务。已约定人工检查点须等待真实决定，其他已授权任务无需增加逐项人工审批。

开始修改前按[隔离开发约定](../core.md#隔离开发与评审合入)核对工作活动目录、资料归属和基线交接。提交前核对精确文件清单及既有暂存内容，推送及建立评审分别检查授权；不在主目录混入其他工作，不因实现获准自动推送。

有效确认范围内的编码、测试、修复与技术评审自主推进。需要扩大业务范围或改变已确认行为、接口及关键方案时，展示变更影响并重新确认受影响范围，再执行依赖操作；不把顺手改动当作原授权。发现已有越过节点的代码时如实保存，报告缺失确认并暂停相关后续实现，不能补造先前批准。不能用编译成功证明业务正确，也不能因尚无自动测试就宣称全部通过。
