# 验证依据

规则标识：QUALITY-VERIFY。定义测试范围、执行检查或判断完成时使用。

## 本次验证

- 验收条件使用稳定编号，例如 `AC-1`。需求确认后先把每项转为全局用例，再按 `test_ref` 写测试并实现。
- 每项条件至少映射一个存在的用例编号；该用例必须有具名测试，且本次验证的 `test_ref` 必须与用例一致。
- 记录用例编号、验证命令、实际结果、退出码、提交和代码树摘要；命令执行与外部报告结果分开标明。
- 失败、跳过、未运行和环境限制不能写成通过。套件正常退出不自动等于每个用例通过。
- 代码、测试或范围变化后，旧验证过期，需要重新执行或明确说明影响。

## 测试范围

按实际影响选择单元、接口、集成、场景、性能、安全、可靠性、兼容性和易用性检查；不适用项说明理由。长期用例按稳定模块和跨模块场景组织，不为小改动强制建立整套验证文档。

模块用例位于 `.tiller/cases/modules/<模块>/{behavior,interface,performance,security}.json`，模块名须与 `.tiller/specs/modules/` 一致；跨模块端到端路径位于 `.tiller/cases/scenarios/`，每条声明经过的 `modules` 和 `test_ref`。类型文件按需建立，不建空文件。

每个用例至少包含稳定 `id`、标题、需求/模块引用、`test_ref` 和源码路径。新用例用 `criteria` 保存 `<任务>#AC-N` 来源；历史空值只提示。`test_ref` 使用 `文件::测试名`；文件、具名测试和引用路径必须存在，编号跨文件和场景唯一。

## 记录方式

默认由 `verify` 和 `check` 维护 AC→用例→测试→当前验证的覆盖。`case add` 自动分配编号并校验模块与 AC；`verify` 从测试引用自动记录命中的用例编号；`check` 阻塞缺失、失效、错配、未回指当前 AC 或过期映射，报告各模块各类数量、场景和未覆盖模块，并在改动涉及模块时提示回归其用例和经过它的场景。任务记录只保留可重跑的命令与结果，不保存原始日志、全文快照、自举工程或安装包。需要详细证据时从 Git 取回或重新运行。
