# 开发规范设计

> 状态：讨论稿
> 依据：[开发规范需求](requirements.md)、[总体设计](../../design.md)、[工作推进设计](../workflow/design.md)
> 本文描述完整规范方案，不将设计正文直接作为已启用的项目规则。当前通用规则、六类文档模板与有限结构检查已落实，见[首个交付实现约定](../../../work/initial-delivery/design.md)；其他强制控制与扩展能力仍由[决策记录](../../decisions.md) Q8、Q9、Q10、Q20、Q21 管理。
> 2026-10-15：人工确认规则已同步到 0.2.0 入口、分发资源及自身接入规则，外部 Java 工程已显式升级。实现及验证见[人工确认工作](../../../work/human-confirmation/work.md)，交付待用户验收；独立来源认证与宿主写入拦截未实现。

## 1. 设计思路

将规范组织为“适用条件、执行动作、所需依据、完成条件、失败处理”五部分，并通过项目入口让 AI 在相应时机读取。工作推进根据这些条件选择下一步，验证与反馈提供判断依据。

规则说明要求；模板帮助编写产物；检查器核对可验证条件。三者通过规则标识关联，避免模板、提示和程序各自定义一套完成标准。程序只能检查其实际取得的信息，语义判断和授权来源仍需可追溯。

本设计分开处理规则引导与程序约束：前者通过 AI 读取并执行规则实现，后者只在接入的操作入口中执行检查。规则加载成功不等于行为必然符合，更不等于所有外部操作已经被拦截。

## 2. 规则资源与工作入口

### 2.1 资源组织（候选）

```text
AGENTS.md                          # 通用入口与最小执行约定
.tiller/rules/
├── index.md                       # 规则来源、版本、适用范围与读取索引
├── core.md                        # 开始、推进、变化、恢复、结束的共同动作
├── activities/                    # 按活动读取的规则
│   ├── requirements.md
│   ├── design.md
│   ├── implementation.md
│   └── delivery.md
├── quality/                       # 产物质量与检查依据
│   ├── documents.md
│   └── verification.md
├── project.md                     # 项目自定义约定，可引用既有规范
└── templates/                     # 可选的项目自定义模板
```

这里描述初始化后可接入的规则资源组织，不要求全部复制到每个工程。tiller 分发资源与自身开发资料分开，资源索引可以引用工程已应用版本的可读内容。项目已有路径和格式可保留，入口记录实际位置；当前 `.tiller/rules/project.md` 继续保存本仓库专属规则，不被通用资源覆盖。

通用入口只有一个维护来源 `resources/entry.md`；各工程（包括 tiller 自身）通过初始化或显式升级取得相同 tiller 区段。项目入口可另有自定义正文，不能为了整文件相同而覆盖它。详细资料组织、决定同步和迁移规则分别归入共同规则及文档质量规则；不在自身入口重复维护。0.2.1 的整理范围与验证见[统一入口工作](../../../work/20261015-unify-entry/work.md)。

首次接入建议按[初始化文件清单](../initialization/design.md#24-初始化文件清单候选)建立必要规则读取链路，所选规则正文随工程保存或使用可核验的等效引用。专项执行规则可以预先接入，具体项目产物仍按需产生；共享入口不依赖某台机器的全局安装路径。

模板文件及产物映射沿用[工作推进设计第 5 节](../workflow/design.md#5-产物与模板设计)，不在本文重复维护目录清单。内置规则与模板使用工程已应用的资源版本，不能因 CLI 升级自动改用新版本。

### 2.2 AI 读取与接续

1. 工具适配将通用入口接入宿主支持的指令读取位置；入口保留最小动作要求，并指向规则索引、项目约定和工作记录。
2. AI 开始或接续时，读取共同动作规则与适用的项目规则，定位本次工作、所用依据和未完成事项。
3. 根据当前活动、产物及目标仓库读取专项规则；跨仓库工作逐范围核对局部约定。切换活动或目标时补读相应规则，不依赖最初的一次读取覆盖全部工作。
4. 在工作记录中保存采用的规则来源及版本；上下文缺失或规则变化时重新读取，不能只依据“此前已读”的说明继续。

最小入口明确“先读适用依据、核对当前确认节点、按目标与授权选择事项、修改后核查产物、记录结果与下一步、交付前核对证据和验收”。入口直接写明需求确认后设计、总体设计后形成并确认实施规划、逐任务满足条件后实现、验收与发布分别确认，阶段内自主推进。长篇规则按需引用，不把完整设计文档作为每次任务的必读指令。

必要规则无法读取时，提示具体位置、受影响动作与补充方式；不影响资料讨论的缺口可保留，但缺失规则不能作为放宽权限的理由。不同宿主的实际入口、上下文限制与接入方式由工具适配详细设计确定，不能假设所有工具都会自动读取同名文件。

### 2.3 功能分块指引

本节正式环节名称为“实施规划与任务拆分”，对应 RULE-12；保留原标题兼容历史引用。共同规则中的“功能分块与实施安排”作为唯一详细规则来源，明确规划形成与确认、任务选择、前置依赖、即时验证和整体覆盖。入口与规则索引负责引导，设计、实现和交付活动按各自时机引用，模板仅提示关联必要信息。

规划位置、任务信息、确认依据和推进循环见[工作推进设计](../workflow/design.md#23-功能分块与项目骨架)。规范检查关注任务是否构成可验证增量、规划与规格确认是否有效、依赖是否具备当时的验证证据，不以文件数量或固定工时强制粒度。单任务可简要规划，任务与模块、工作记录不强制一一对应，骨架为普通任务而非独立阶段。

实现活动在进入任务前核对条件，完成当前任务验证后立即保存对象、时间、方法、实际结果和未覆盖项，再判断依赖任务。失败或缺证据不放行依赖任务；发生执行方式变化、中断或规划实质变化时先核对影响。发现越序如实记录，不能用最终结果倒填历史；规则不替业务项目选择框架或预建公共组件。

0.3.3 已分发基础分块指引，0.3.5 在可读规则中明确独立规划确认和逐任务检查；当时未新增任务状态机或规划确认 gate，规划确认仅记录实际来源。0.4.0 已确认增量新增规划确认、激活和逐任务门禁，具体设计及验证以[工作推进设计](../workflow/design.md)和[门禁工作](../../../work/20261019-task-delivery-gates/work.md)为准，仍不自动拆分或调度任务。已有工作不自动改写或迁移，不追认过去过程；程序核对已声明依赖和证据，不能自动判断拆分质量或证明全部宿主行为合规，实际 AI 执行仍须场景验证。

### 2.4 项目专属规范的建立与检查

对应 RULE-13。初始化仅提供通用流程规则，不推断项目技术栈，也不预填专属规范。新项目在总体设计阶段按已选方案形成最小必要约定，并在相关骨架实现前取得确认；已有项目按[接手流程](../workflow/design.md#24-项目接手与规范建立)先读取既有规范和配置。来源不足时保留待定项，不把观察到的代码风格直接提升为正式要求。

项目规范由自维护的 `.tiller/rules/project.md` 承载，内容较多时可引用独立 `coding.md` 或原有规范路径；这里是设计建议，不新增必须生成的模板或受管文件。通用 `core.md` 和 `index.md` 由产品升级维护，不能成为项目自定义规则的唯一保存处。总体设计引用规范，规范引用实际工具配置，避免在多处复制可执行参数。

| 约定类别 | 按需明确的内容 | 检查方式与事实来源 |
|---|---|---|
| 代码组织 | 命名、目录、分层职责和依赖方向 | 引用项目结构、格式化或静态检查配置；职责边界补充人工评审 |
| 行为与诊断 | 错误处理、日志、接口与兼容约定 | 引用对应设计；由适用测试与评审核对，不从现有代码自动推定要求 |
| 依赖管理 | 使用已有依赖、版本与新增依赖约束 | 引用实际清单和锁文件，检查具体变更及项目授权 |
| 验证与交付 | 测试层次、必要检查、评审及适用 CI | 记录命令入口、作用范围、预期判定和证据位置；无自动检查时写明评审要点 |

规范至少说明来源、适用范围、具体要求及验证方法。必要配置在骨架或基础补齐工作中实现并运行，记录具体版本、环境、命令和结果；库、命令行或服务选择各自适用方式，不强制安装统一工具套件。格式化默认先检查差异，批量写入、历史告警清理及依赖新增须在明确范围内安排，不因规范生成自动执行。

确认可与总体或变更设计共用一次审阅，但必须展示被采用的规范内容和范围，必要时将规则文件一并作为设计确认对象；仅链接未经审阅的新规范不视为已确认。后续实质变化复核受影响确认与验证，沿用有效内容无需重复审批。多仓库分别记录局部规则，发生冲突按已有规则协调机制处理。

执行者区分“规范已明确、配置已存在、检查已执行、检查已通过”，失败、未执行和无法判断保持可见。0.3.4 仅提供规则与设计模板提示，实际项目规范由执行者按项目事实编写，检查使用项目工具；未新增规范自动生成器、格式化运行器或语义合规认证。

## 3. 规则表达与选择

### 3.1 一条规则的内容

| 信息 | 作用 |
|---|---|
| 标识、版本与来源 | 关联规范要求、模板、检查及历史使用情况 |
| 适用对象与触发时机 | 说明对哪个范围、哪种活动或动作生效 |
| 所需依据 | 输入产物、当前规则、授权及待核对的事实 |
| 执行动作 | 明确需要做什么，不仅描述“保证质量”之类目标 |
| 满足条件与证据 | 说明如何判断动作完成、允许继续或允许交付 |
| 不满足时的处理 | 说明阻止哪些依赖动作、保留什么、需要怎样补足 |
| 可简化内容与能力说明 | 区分必要信息、可调整形式，以及自动检查或人工判断范围 |

候选用 Markdown 表达正文，索引或结构化元信息承载稳定字段，序列化格式按 Q8 确定。规则由明确版本的规范内容定义，自动检查绑定该规则版本；两者不一致时报告不兼容，不使用旧检查冒充新规则验证。

例如“报告实现完成前”的规则可表述为：核对约定要求与实际变更，运行适用检查并读取结果，将证据关联当前产出；必要检查失败、缺失或过期时，不把相应范围标为完成，记录问题并回到处理环节。文件存在只能证明产物已保存，不能证明行为正确。

### 3.2 适用范围与冲突

按管理范围、目标仓库、活动及交付类型选取规则。共同规则提供一般要求，项目规则补充项目约束，局部约定只在其声明范围内适用；不把 tiller 自身的语言、文档阶段或 Git 限制带入其他项目。

多个适用规则能够同时满足时共同采用；表述不同但可对应时保留来源并建立映射。无法同时满足时呈现冲突，不以文件位置或“更具体”为由静默放宽授权或完成条件。用户明确调整约定后，记录调整对象、范围及影响；规则选择不能覆盖宿主的上级指令或实际权限限制。

业务资料、测试数据和工具输出提供事实，不因被读取而成为新的操作授权。规范要求的流程动作仍须在当前用户授权内开展，提出草稿不等于批准实现。

## 4. 按时机执行的共同动作

以下为完整规则内容设计；当前通用资源已实现，覆盖及具体位置见本次交付工作，其他专项能力按需扩展：

| 触发时机 | 要求采取的动作 | 继续条件或处理方式 |
|---|---|---|
| 开始新工作 | 读取项目规则与已有依据，明确目标、范围、交付类型和必要验收条件 | 信息可逐步澄清；影响当前操作的歧义未解决时，不执行依赖它的操作 |
| 接续已有工作 | 核对记录、实际产出、未结束操作及所用规则版本 | 先处理差异，复用仍有效的成果，不重复已经发生的外部操作 |
| 选择下一事项 | 核对依赖、人工确认及其来源、授权、适用规则及可用能力 | 条件满足则继续；否则展示具体待确认内容或阻碍，独立且已授权事项仍可推进 |
| 编写需求或设计 | 按总体、模块或变更层次选择指引，引用依据，区分事实、假设和待定选择 | 需求与设计分开，草稿保持状态；不要求为了写文档先有完整规格 |
| 制定实施规划 | 依据已确认需求和设计拆分任务，检查覆盖、依赖、验证及待细化项并展示确认 | 未确认只完善规划；已有有效规划可复用，单任务可简要表达 |
| 修改代码、配置或测试 | 核对规划及相关需求、设计的有效确认、当前任务边界和前置验证证据 | 任一必要条件不足时不开始对应实现，简短文档不豁免确认；骨架按普通任务推进 |
| 完成当前任务 | 检查实际差异，执行适用验证，立即保存当时对象和结果，再判断下一任务 | 必要验证缺失或失败不进入依赖任务，不用最终测试倒填早期通过 |
| 检查或评审失败 | 记录问题、原因与影响，修复或明确继续条件 | 处理后复验；没有新依据或措施时停止无效重试 |
| 要求、方案或规则变化 | 查找受影响产物、决定及证据，更新后续安排 | 旧结论先判断适用性，不能直接继承为当前通过 |
| 暂停、终止或交接 | 停止发起对应范围的新操作，保存实际进展、未结束操作与下一步 | 不默认回滚，不将终止视为通过；恢复时重新核对 |
| 发布前 | 核对产物版本、目标环境、发布授权和失败处置依据 | 任一必要条件未满足时不发起发布，结果未知时先查询后决定 |
| 报告交付完成前 | 对照本次范围核对产物、证据、发布情况、资料同步和遗留项 | 必要条件全满足才报告完成；部分完成及未验证内容分别呈现 |

触发条件由工作推进结合当前活动判断。AI 经由宿主直接修改内容时也应遵循这些规则，但是否存在程序拦截要单独说明。入口指令保留关键动作，专项资源解释质量要求，不能只提供一个“请遵循工作流程”的链接。

### 4.1 规则资源的具体修订

| 资源 | 0.2.0 已调整的内容 |
|---|---|
| 通用入口、`core.md` | 将“已有授权无需逐阶段重复确认”改为“复用仍有效的具体确认；到达未确认节点须先呈现内容并等待用户决定”；核对来源、范围和内容 |
| `activities/requirements.md` | 需求起草、澄清与内容确认分开；输出审阅内容及进入设计所需决定 |
| `activities/design.md` | 先核对对应需求确认；设计完成后提出确认，不自动进入实现 |
| `activities/implementation.md` | 可用简短设计或已有设计，但仍须核对有效确认；范围内编码、测试和修复自主执行 |
| `activities/delivery.md` | 技术检查通过、用户验收、发布确认及实际发布结果分别报告 |
| 质量规则与文档模板 | 标注内容、确认对象、待决项与下一步；不预填“已确认”，检查记录与用户来源一致 |

确认语义和记录结构以[工作推进设计第 4 节](../workflow/design.md#4-推进机制与状态判断)为单一依据。例外必须关联用户明确授权，规则不按任务大小自动跳过节点。更新时检查根入口的区段外通用条款和项目自定义规则：发现矛盾需展示并协调，不能只更新受管区段后宣称整个入口一致。

| 资源 | 已实现职责 |

| `resources/rules/core.md` | 增加“工作记录约定”小节，集中说明工作入口、产物命名、按需创建、引用登记、机器记录维护及历史处理；收窄“简单工作可合并”的含义 |
| `resources/entry.md` | 直接列出最少文件约定与命令使用要求，并链接共同规则中的完整约定；自身和其他项目继续从同一资源安装 |
| `resources/rules/index.md` | 明确新建及接续工作前必读该约定，按当前阶段选用专项规则 |
| 需求、设计及文档质量规则 | 引用共同约定，核对产物角色与来源；设计新增或采用前检查需求确认，不再各自推测文件名 |
| 实现与交付规则 | 检查登记对象、依据和当前证据，按产物区分文档验收与整体软件交付；辅助 README 不替代工作入口 |

入口明确以下最少要求：

> 新建或接续工作前，读取共同规则中的工作记录约定。命令已支持的文档工作使用对应命令创建或登记；过程入口使用 `work.md`，本次新写的需求和设计分别使用 `requirements.md`、`design.md`，已有规格通过明确引用接入。`record.json` 由命令维护，不自行编造；`README.md` 可以补充导航，不能替代上述产物。缺少适用命令时记录限制和人工处理范围，已有资料先检查再接入。

“简单工作可合并”仅允许计划、进展、检查摘要及交接等过程信息合并到 `work.md`；独立证据要求和需求、设计、确认边界不改变。具体文件职责以[工作推进设计第 3.3 节](../workflow/design.md#33-工作入口与产物约定已实现)为依据，不将全部候选产物变成每项工作必须生成的文件。

更新通过 0.2.2 资源版本和显式升级计划接入，保护工程自定义正文与历史。规则与本节配套命令一同分发；初始化成功只证明读取链路建立，真实创建及接续行为需另行验证。现有工程规则升级不替代工作记录接入，也不批量重命名已有目录。

### 4.3 隔离开发与合入规则接入

对应 RULE-11 的新增规则设计，尚未写入分发资源。入口增加活动目录检查及合入确认提示，共同动作明确操作授权；设计、实现、评审和交付活动分别引用[工作推进第 11 节](../workflow/design.md#11-隔离开发与评审合入)，不复制另一套状态定义。

- 开始实现前读取初始化方式、工作绑定和 Git 身份。当前工程使用本仓库活动目录；独立管理分别定位共同记录和业务 worktree，仅涉及一个仓库也不切换模式。
- 核对需求设计的有效确认和资料交接；存在未提交、未跟踪资料时先核对计划。不能把文件同名、目录存在或创建 worktree 成功当作基线完整。
- 提交前检查精确文件清单；推送和创建、更新评审分别核对授权。可复用明确的一次授权，不能把设计批准扩大为所有 Git 操作许可。
- 合入前展示具体源/目标提交、依赖、检查和评审意见并取得有效人类决定。验收、合入和发布各有范围；已生成 MR 或测试通过不表示合入获准。
- 中断先核对实际结果；结束先保存共享记录与唯一成果，再按明确清单清理副本和分支。多仓库部分成功保留剩余项，不自动回退。

Markdown 规定 AI 读取、判断及报告的行为；CLI 在自己的 prepare、commit、push、review、merge、cleanup 写入口核对机器条件。身份和语义来源仍按实际复核能力报告，不能把规则文字当作全局拦截。分发时须升级资源并保留项目自定义内容，不仅修改本项目文档就宣称其他工程已经遵循新规则。

## 5. 产物质量与模板衔接

| 产物类别 | 质量检查重点 | 允许的简化 |
|---|---|---|
| 总体需求与设计 | 覆盖约定产品问题与范围，需求和方案对应，待定内容可见，总体能索引已存在的详细资料 | 不预先展开所有模块，不强制产生尚未需要的详细方案 |
| 模块及变更需求与设计 | 行为边界、异常与验收可检查，方案支撑要求，变更影响与既有规格关联 | 引用已有内容，单次变更只描述差异；需求与设计不混写 |
| 实施规划与过程记录 | 需求覆盖、任务边界、依赖、验证、待细化项、规划确认和即时证据明确 | 单任务可合并到工作入口，不省略确认和检查，不要求独立计划文件 |
| 代码、配置与测试 | 变更符合要求与项目约定，行为和受影响路径有适用检查，失败及未覆盖范围可见 | 复用项目实现模式和测试能力，不引入统一语言或代码骨架 |
| 测试与评审证据 | 对象、版本、环境、执行范围、实际结果及问题处理可核对，内容变更后复核适用性 | 引用已有报告，保留能说明结论的必要信息 |
| 验收、发布与交接 | 逐项要求与证据关联，发布计划和实际结果分开，成果可定位、限制和遗留项明确 | 未包含发布时省略发布执行记录，但明确未发布 |
| 运维反馈 | 问题关联交付版本与实际现象，影响、处理决定和后续结果可追踪 | 简单反馈并入已有记录，需新增工作时再细化 |

规范中的必要信息独立于模板章节。项目可以更换模板或使用现有文档格式，只要检查依据能够定位；模板检查不应只匹配固定标题。指引提示未知项、可省略项和内容边界，不预填通过结论，也不将生成完成作为内容确认。

复用时核对来源版本、适用范围和必要信息；已有结构不能承载要求时，先补充或调整相关部分，保留用户内容。模板与规范更新按工程资源版本管理，已生成文档继续作为项目内容维护。

## 6. 检查与约束的实现边界

### 6.1 三类检查方式

| 方式 | 能提供的判断 | 边界 |
|---|---|---|
| AI 按规则核对 | 理解任务、发现语义缺口、分析影响、提出方案与评审意见 | 可能遗漏或误判，不能因表示已读规则就保证遵循 |
| CLI 或项目工具检查 | 文件、引用、版本及记录一致性，测试与构建的实际结果 | 仅覆盖已实现的检查和实际取得的数据，不能凭结构检查证明需求完整 |
| 人工判断或外部依据 | 需要人决定的取舍、使用体验或无法自动取得的结果 | 记录具体对象、决定和来源，不能自动替代所有必要技术检查 |

每条检查结果关联规则版本、检查对象、输入内容标识、执行方式、时间、结果与证据位置，说明适用范围。工具故障或信息不足归为无法判断，不归为通过。证据变化或无法核实时要求复核，不信任孤立的通过标记。

### 6.2 受控操作中的检查

0.2.0 在 `work complete` 写入完成结论前核对文档、适用证据及绑定二者的有效人工验收；条件未满足时拒绝该完成更新，并返回缺失项。设计模板创建同样核对前置需求确认；其他进入实现或发布的动作由规则要求执行者核对，尚无可拦截全部宿主操作的命令。拒绝放行不能妨碍保存草稿、失败、部分进展和恢复记录。

检查读取当前内容并在写入前比较版本；期间内容变化则重新核对，避免依据旧结果写入完成。语义判断与人工授权需有适用的来源记录，不能由执行者自行设置一个布尔值代替。即便记录齐全，也只声明已检查的范围。

纯 CLI 不能认证输入来自人，结构通过、执行者已复核和程序已认证分别返回。AI 在当前对话中可核对实际用户输入，保存 `reported-review` 的确认及验收结论以完成正常交付，但不能报告为程序独立认证或自动放行；缺少实际来源复核时不得写入已验收结论。换工具接续须重新核对来源或取得新的确认。命令参数、交互终端和文件中的角色标签都不能冒充可信来源适配，具体边界沿用工作推进设计第 4.4、9 节。

AI 绕过 CLI 直接改写记录或调用项目工具时，CLI 无法据此保证操作被阻止。重新读取时应检查记录与实际内容是否一致；更强控制需要宿主操作拦截或交付系统接入，具体机制由工具适配及 Q9、Q10 确定，不默认安装钩子或修改项目发布流程。

### 6.3 能力缺失与替代验证

必要检查不可用时返回具体原因、覆盖缺口与可接受的补充依据。已有规范允许等效人工或外部验证时，可按其条件记录实际结果；没有适用替代方式时保持未验证，不为了结束工作自动降级要求。若用户明确改变交付范围或验收条件，保留变化依据并重新判断，而非把原检查改为通过。

## 7. 定制、版本与恢复

项目定制通过独立规则或对既有资料的引用接入，保留来源。格式简化只改变表达，不改变必要信息；不适用需由工作范围支持；改变已约定条件需关联明确决定。这些选择记录在当前工作，不默认成为全部后续工作的共同规则。

工作记录固定实际采用的规则资源版本和项目规则内容标识。显式更新时比较旧规则、项目自定义内容与新规则，沿用初始化的冲突保护和恢复机制；无法取得旧版本时说明限制，不猜测一致。影响正在进行的工作时，在下一项依赖操作前评估并重新检查相关产物。

跨仓库保留各自的规则集合与版本，公共目标不替代局部约束。中断恢复重新核对这些依据、实际内容和未结束操作；历史验证保留原对象和规则版本，新规则不自动改写旧结论。

## 8. 接入与行为验证

初始化建立实际可读取的规范入口，工具适配确认宿主的加载和调用方式，工作推进负责按触发时机选择规则，验证与反馈执行或汇集检查，项目记录保存使用依据和结果。开发规范只定义共同语义及检查要求，不复制其执行状态。

验证先检查入口和引用，再在支持工具的新会话中开展受控样例工作，检查实际读取及动作：

- 只请求总体需求草稿，验证产出范围与状态，不进入编码。
- 已有有效实施规划与相关需求、设计确认，前置任务验证满足条件，验证范围内可以持续实施及检查，而不逐操作等待确认。
- 学生服务只确认技术方向时，验证先提交具体需求并等待；需求确认后只形成设计，设计确认后才实现。
- 自写批准状态、来源无法访问、过期确认或泛化“继续”指令，不放行依赖操作；明确范围的用户例外不扩展到其他节点。
- 规划未确认时不进入任务；单任务简要规划也须确认，规划批准不替代未展示规格批准。
- 骨架仅通过静态检查、前置任务失败或未验证时，不进入依赖任务，独立事项可继续。
- 同轮多任务必须逐项验证并当场记录；集中测试只能证明最终对象，过程偏差不能事后补成合规。
- 必要测试失败、证据过期或产物为空，验证不能据此报告完成。
- 要求变化或跨仓库冲突，验证仅阻止受影响操作并保留依据。
- 中断后恢复和切换工具，验证能找到规则、现状及下一步。

程序约束另测：完成写入是否在条件不满足时被拒绝，失败记录是否仍可保存，并发修改能否识别，以及绕过入口后的覆盖限制是否如实报告。多次运行记录采用的规则、工具版本、输入和偏差，用于发现规则表达问题；有限样例通过不构成对未来行为的保证。

这些是完整接入验证方案。0.2.0 已执行受控接口检查，并以两次独立上下文验证学生服务需求等待及接续，实际覆盖和限制见[验证记录](../../../work/human-confirmation/verification.md)；未覆盖场景仍需补充。tiller 自举也必须记录实际采用和执行的方式，不能仅凭这些文档存在判定自举完成。

## 10. 测试与验证规则接入

对应 RULE-14、AC-36、AC-37。通用要求集中在既有 quality/verification.md，共同动作和活动规则按时机引用；不新增受管规则文件，不改变六类需求/设计模板的数量。项目自行维护 testing.md 或引用原有规范，受管资源升级保护项目资料。

总体需求模板提示可检查的质量目标；总体设计模板提示九类适用性、环境、执行方式与项目约定；模块和变更模板提示当前任务场景、需求关联及受影响回归。模板不预填业务用例、技术通过或用户确认。YAML 用例、索引和执行记录由[验证模块设计](../verification/design.md)规定，声明式描述不扩展为执行语言。

规则要求测试随各阶段产生并即时验证，CLI 检查登记范围及受控命令。快照仅覆盖明确绑定输入，退出成功不生成逐用例通过，报告不替代断言评审、真实 AI 行为验证或人工验收。受控检查不能阻止宿主直接修改，也不独立认证结果来源。
