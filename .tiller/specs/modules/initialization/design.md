# 工程初始化设计

> 状态：讨论稿
> 依据：[工程初始化需求](requirements.md)、[总体设计](../../design.md)
> `.tiller/` 名称、五类基础目录、独立管理工程层级及已有本地仓库接入已确定；当前元信息、入口区段与恢复约定见[首个交付实现约定](../../../work/initial-delivery/design.md)，完整迁移与扩展适配仍由[决策记录](../../decisions.md)管理。

## 1. 设计思路

两种初始化方式共用一套处理过程：确定范围、了解现状、准备变更、完成接入、验证结果。区别在于管理信息保存在哪里，以及需要关联哪些仓库。

初始化通过 CLI 组织接入，不另建开发规范、项目记录或工具适配机制。遵循[全局技术方案与运行环境](../../design.md#6-技术方案与运行环境)，采用已确认的 TypeScript + Node.js 方案，将命令入口、初始化业务和文件等基础操作分开。

命令入口负责参数与执行意图，业务部分生成和执行变更计划，基础操作部分完成文件比较、写入及适配接入。首次初始化、重复检查和显式工程更新共用这些能力，按操作意图区分行为。参数完整时可非交互执行；缺少必要信息时返回可处理的问题，不隐式迁移工程。

基础接入不依赖模型调用。AI 可以辅助补充工程背景和解释语义冲突，范围核对、文件比较和结果检查采用确定性规则。执行前检查运行环境与目标权限；路径、参数传递及文件操作遵循全局跨平台约定。

## 2. 两种方式与目录布局

### 2.1 当前工程接入

管理根目录就是当前工程，管理信息随工程维护。入口引用工程已有规则和资料，新增内容集中保存，避免散落到业务目录。

采用总体设计定义的目录布局：

```text
current-project/
├── <已有代码与文档>
├── <AI 工具入口>
└── .tiller/
    ├── specs/           # 工程需求、设计与长期决策
    ├── rules/           # 开发规范与项目规则
    ├── context/         # 项目背景及资料索引
    ├── work/            # 具体工作的变更说明与过程记录
    └── local/           # 本机信息、缓存及恢复副本
```

已有工程资料可迁入 `.tiller/specs/` 或通过引用复用，保持单一维护来源；迁入时保留原内容并更新引用。初始化不预先生成全部模块和开发阶段的产物。

### 2.2 独立管理工程

独立管理工程是共同的工作根目录，`.tiller/` 与业务仓库容器 `repositories/` 位于其中、彼此平级。`.tiller/` 保存共同规格、规则、背景和跨仓库工作记录；`repositories/<仓库标识>/` 内的各业务仓库保留自身代码、专属资料和独立的 Git 历史。旧直接子目录布局保留兼容，不自动搬迁。

```text
management-project/
├── <AI 工具入口>
├── .tiller/
│   ├── specs/
│   ├── rules/
│   ├── context/
│   ├── work/
│   └── local/
└── repositories/
    ├── repository-a/    # 独立业务仓库
    └── repository-b/    # 独立业务仓库
```

被管理仓库不必各自建立一份相同的总体记录。确需在仓库内补充工具入口时，由适配部分提出局部变更，沿用同一个管理依据，并遵守该仓库的授权与已有约定。

目录包含关系不改变版本管理边界。若管理工程本身使用 Git，新布局统一忽略 `/repositories/`，避免将业务代码再次纳入管理工程的版本记录；旧布局保持各自目录的忽略项。

元信息保留 `repositories` 作为稳定标识列表，`repositoryPaths` 保存标识到工程相对路径的映射。例如 `repositories: ["service-a"]`、`repositoryPaths: {"service-a": "repositories/service-a"}`。文档、确认和交付记录使用标识，不使用存放路径作为身份。0.3.1 初始化及显式升级写入映射；旧版本无映射时仅按原直接目录解释，升级生成原路径映射，不移动仓库或改写历史。

推荐显式传入 `--repo repositories/service-a`。简写 `--repo service-a` 在约定分组目录存在时使用该目录；只有旧直接目录存在时兼容接入；两处同时存在时要求明确 `repositories/service-a` 或 `./service-a`。新映射限制为 `<id>` 或 `repositories/<id>`，拒绝重复身份、危险路径和 Git 身份不匹配，暂不开放任意多层目录。

初始化不自动提交文件。业务仓库如何进入该目录，包括复用已有仓库、远程获取或迁移，以及空管理工程的处理，仍待确定；不因目录约定而直接移动用户的现有仓库。

### 2.3 内容归属与创建时机

五类目录遵循[工程资料组织](../../design.md#7-工程资料组织)。初始化建立管理入口和必要信息，模块与具体工作开始时再创建对应资料：

- `specs/modules/<module>/` 保存持续维护的模块需求与设计；目录名称不带排序编号。
- `work/<work-id>/` 按一次工作组织，可包含本次变更的需求、设计、计划、进展及验证记录，引用涉及的模块规格和版本。
- 一项工作可涉及多个模块与仓库，一个模块可关联多次工作，不为每个模块复制同一项工作的记录。
- `rules/` 与 `context/` 分别接入开发约定和项目事实，复用已存在的依据，不复制规格内容。
- `.tiller/` 根目录保存共享管理配置、版本和初始化结果摘要，具体文件名与格式待定。`local/` 保存本机覆盖配置、缓存、锁、运行日志和恢复副本，并从版本管理中排除。

初始化应检查 AI 读取入口与资料索引能否到达上述内容，同时保留项目的既有忽略规则。可共享的进度、决定和验证证据必须保存在受版本管理的资料中，不能只存在于本机日志。不存在必要内容时如实说明，不用空文档冒充已完成的规格或工作。

接入结果向[工作推进](../workflow/design.md#8-初始化与其他部分的衔接)提供范围、规则、资料引用、可用性及资源版本。总体或模块规格尚未形成时，后续工作可以从编写这些资料开始；初始化不预先实例化全套模板，也不要求先完成具体任务才能通过接入验收。

规则来源、版本和读取索引按[开发规范设计](../standards/design.md#2-规则资源与工作入口)接入，工具适配负责验证目标宿主的实际读取方式。入口可读与规则行为符合要求分别验证，不以接入成功声明所有操作已受强制控制。

### 2.4 初始化文件清单（候选）

以下清单描述完整设计。当前已获准实现的接入文件、版本及恢复约定见[首个交付实现约定](../../../work/initial-delivery/design.md)；超出该范围的适配与迁移机制仍由 Q16、Q21 等问题管理。路径均相对于管理工程根目录，两种初始化方式共用同一清单。

“必须接入”表示相应信息和入口必须可用，已有内容满足要求时优先引用或复用；不要求所有项目都按本表重命名已有资料。

| 对象 | 创建或接入时机 | 内容及处理规则 |
|---|---|---|
| `AGENTS.md` 或目标工具的等效入口 | 必须接入 | 新文件提供通用读取与执行入口；已有文件只补充必要引用，保留原有规则；具体处理见第 5.1 节 |
| `.tiller/usage.md`、`.tiller/run.cjs` | 0.3.2 起必须接入 | 通用使用指引与跨平台 Node 启动器；使用说明不是项目背景，不命名 installation.md；初始化和显式升级维护，冲突不覆盖 |
| `.tiller/project.json` | 必须接入 | 保存管理身份、方式、范围、格式与资源版本、文件归属及接入结果；已有受支持元信息先读取复用，不能直接覆盖未知文件 |
| `.tiller/index.md` | 必须接入 | 面向人的统一资料导航：链接规则索引、已有背景和规格、工作记录入口；未形成的资料标明尚无，不创建指向不存在文件的链接 |
| `.tiller/rules/index.md` | 必须接入 | 列出已接入规则的来源、版本、适用范围、实际位置和读取顺序，关联既有项目约定 |
| `.tiller/rules/core.md` | 必须接入 | 开始、继续、变化、恢复和交付前的共同执行动作，采用明确版本的发布资源或等效已有规则 |
| `.tiller/rules/activities/requirements.md`、`design.md` | 接入所选规范资源时 | 需求和设计的编写动作、总体与模块层次、草稿及确认边界；支持初始化后先开展文档工作 |
| `.tiller/rules/activities/implementation.md`、`delivery.md` | 接入所选规范资源时 | 实现、检查、发布和交接的操作要求；规则可预先接入，但不表示项目已有这些产物或操作授权 |
| `.tiller/rules/quality/documents.md`、`verification.md` | 接入所选规范资源时 | 文档质量与证据检查要求；实际可执行检查能力另行记录，不因存在规则文件就宣称检查器已安装 |
| `.tiller/rules/project.md` 或已有项目规则 | 有实际约定时引用或创建 | 引用已有规则优先；只有明确的项目约定需要保存时才创建，不预填 tiller 自身的语言、Git 或开发阶段限制 |
| `.tiller/context/project.md` 或已有背景资料 | 有可靠背景时引用或创建 | 保存已有事实与资料来源，未知信息保持未知；不依赖模型调用生成项目介绍，也不与管理元信息重复维护范围 |
| 忽略规则 | 必须核对 | Git 工程确保 `.tiller/local/` 被忽略；独立管理工程还排除被管理的业务仓库目录，保留用户现有规则 |
| `.tiller/specs/`、`.tiller/work/` | 初始化提供分类入口，内容按需创建 | 复用已有规格与工作；不生成总体需求、模块文档、虚构工作或验证结果 |
| `.tiller/local/` | 发生本机操作时 | 按需保存锁、日志、资源缓存、变更前副本等；只在本机维护，不作为共享事实的唯一来源 |
| 项目自定义模板 | 项目明确需要时 | 使用已有模板或按开发规范设计接入，不默认创建 `.tiller/rules/templates/` 或复制全部模板 |

本方案建议将上述共同规则、活动规则和质量规则作为一组可读资源接入，记录实际应用的版本和内容摘要；已有等效规则可以引用。选择的资源缺项或不可读时，应明确受影响的可用范围，不能把没有接入的活动宣称为可用。

为了使工程换机器后仍能读取基本规则，建议将所选规则正文随工程保存。共享索引不得依赖某台机器的全局安装绝对路径；引用工程外资源时，必须明确可解析的版本与取得方式，并核对目标环境可用性。

内置模板仍属于分发资源，按工作需要和工程已应用版本选取，不在初始化时实例化为项目文档。资源不可取得时说明限制，可按已接入的产物指引人工或由 AI 编写并记录实际方式，不虚报模板生成成功。

### 2.5 目录、索引与版本管理

五类目录保留统一的逻辑位置，缺少实际内容的目录可以按需建立，不为保留空目录生成占位规格或工作记录。索引区分“尚无资料”和“已有资料不可读取”：前者可引导开始编写，后者说明具体缺口。重新检出后空目录不存在，不构成接入损坏。

`.tiller/index.md` 保存导航，不复制规范正文、规格内容或完整工作进度。工作产生或资料迁移时按实际结果更新引用；当前进展仍由对应工作记录维护。没有工作时明确说明尚无工作记录，不建立虚构的当前工作。

共享元信息、索引及接入的规则应能随工程保存。检查发现现有忽略规则排除了必要共享资料时，说明冲突并形成明确的调整方案，不静默删除用户忽略配置。不使用 Git 的工程呈现本机数据与共享资料边界，但不自动创建仓库或提交文件。

### 2.6 与隔离开发的衔接

初始化的 `project` / `workspace` 方式持续作为工作定位依据，不按本次参与仓库数量变更。根 `.tiller/` 与原业务仓库的位置保持本节布局；具体工作的 worktree、分支及评审请求由[工作推进第 11 节](../workflow/design.md#11-隔离开发与评审合入)按范围和授权创建，初始化不提前创建这些对象。

初始化仅保证共享资料可版本管理、本机 `local/` 排除跟踪、原业务仓库保留独立身份；不自动提交资料，也不默认将独立管理目录变成 Git 仓库。管理工程是否使用 Git 须按实际状态报告，工作推进据此选择管理资料的独立分支或共享快照方式。

活动目录的本机定位由工作推进显式登记，不能借重复初始化把管理 worktree 中缺少的业务目录重新创建，或把业务 worktree 当成新的管理工程。已有工程接入新能力须显式升级；初始接入成功不表示具备远端凭据、评审适配、合入权限或完整交付证据。

### 2.7 使用入口与本机定位

共享入口为 `node .tiller/run.cjs`，使用方式集中在 `.tiller/usage.md`，由 AGENTS 与资料索引链接。启动器保留调用者目录，透传参数、输入输出及退出结果；从其他目录调用须明确目标。

优先检查工程 `.tiller/local/cli/node_modules/tiller`、工程 `node_modules/tiller` 和 `.tiller/local/runtime.json` 记录的已知 CLI。登记绑定本机工程根与实际 CLI 路径，初始化和升级应用后自动记录，`runtime bind` 显式更新、`runtime status` 只读检查。登记不随仓库共享，不把存在文件等同于可运行安装。

Git worktree 先核对 Git 工作副本身份，再查同仓库的登记目录以复用安装；不盲目遍历父目录或把复制的 `.git` 当作登记。缺少或失效安装时输出恢复指引，不自动联网或从配置执行命令字符串。

0.3.2 的受管资源增加指引和启动器。旧版按原资源集合读取，显式升级时添加新文件及索引链接；已有不同正文、预览后变化或用户修改作为冲突保留。初始化后的项目规格和工作仍按需生成。

受管区段和分发的规则、使用指引、启动器允许 LF/CRLF 换行等价，以兼容 Git 检出转换；实质正文变化仍报告冲突。此约定不放宽工作产物或人工确认依据的内容摘要。

## 3. 管理信息

以下为逻辑信息，不限定序列化格式；文件名称与格式对应 Q7、Q8。

| 信息 | 主要内容 | 用途 |
|---|---|---|
| 管理范围 | 管理标识、初始化方式、管理根、明确纳入的仓库 | 区分当前工程和独立管理工程，防止操作范围漂移 |
| 仓库关联 | 稳定标识、名称、用途、定位信息、专属资料引用 | 将同一工作的操作和结果关联到正确仓库 |
| 工作依据 | 适用规范、背景资料、已有记录和读取入口 | 支持首次进入与新会话接续 |
| 变更记录 | 涉及对象、操作意图、修改前依据、完成情况、修改后核对结果 | 防止覆盖已有内容，支持失败后核对与继续 |
| 接入结果 | 总体及各范围的状态、阻碍、待补充信息、下一步 | 呈现实际可用范围，不把部分成功当作全部成功 |
| 版本信息 | 执行的 CLI 版本、工程记录格式版本、已应用的规范与适配资源版本 | 分别判断程序、格式及资源兼容性 |
| 更新依据 | 源与目标版本、迁移步骤、旧资源基线、变更前副本、步骤结果 | 识别自定义内容并支持核对恢复 |

仓库定位信息用于找到工作副本，仓库标识用于持续关联。移动路径不应自动产生另一份身份；同一远程地址也不能直接证明两个工作副本是同一个操作目标。发现重复或歧义时先呈现差异，再确定关联。

可共享的项目事实与依赖本机环境的定位信息应区分，不能把某台机器上可访问的状态当作其他环境也可用。前者保存在共享资料与元信息中，后者放入 `local/`；具体字段和格式仍待确定。

初始化记录只记录接入状态，不代替后续任务的进度或交付结论。事实、推断和未知信息分别呈现，无法确认的项目用途保留为未知。

### 3.1 元信息的具体承载建议

建议以 `.tiller/project.json` 承载共享管理元信息，便于 CLI 确定性读取；工作过程继续采用工作推进设计中的可读记录方案。下列为逻辑字段组，尚未固定 JSON 字段名和完整模式：

- **身份与范围**：管理标识、初始化方式、仓库标识及工程相对位置；根目录位置由当前文件所在工程解析，本机绝对路径不进入共享记录。
- **版本与资源**：工程格式版本、应用的规则和适配资源版本，以及执行此次接入的 CLI 版本；分别记录，不用一个总版本替代。
- **文件归属**：相对位置、引用或生成方式、资源来源、旧基线版本和内容摘要、可识别的管理区段；摘要只能用于比较，不能代替升级需要的原文基线。
- **接入过程与结果**：本次范围、逐项处理结果、各范围可用性、资料检查及实际工具接入验证的证据引用、阻碍与下一步。必要验证未完成时保留未验证，不因文件写入成功直接变为可用。

共享记录是接入结果的维护来源，终端输出及索引仅呈现其结果，不建立第二份可独立修改的状态。恢复所需原件和旧资源基线可保存于本机恢复资料或由可靠的版本资源取得；缺失时报告限制，不能根据摘要重建原文。具体模式、迁移策略和记录并发控制仍需在实现前确定。

## 4. 接入流程

| 步骤 | 处理内容 | 输出与继续条件 |
|---|---|---|
| 确定范围 | 读取用户意图和已有管理信息，定位工程及指定仓库 | 得到明确的方式与目标；歧义未解决时不写入不确定目标 |
| 了解现状 | 读取相关代码概况、资料、规则、工具入口及已有初始化记录 | 得到可复用内容、缺失项与冲突；不扩展扫描到未指定仓库 |
| 检查兼容 | 核对工程格式、已应用资源与 CLI 支持范围 | 区分可直接复用、需迁移和不受支持；没有明确更新意图时不执行迁移 |
| 准备变更 | 区分新增、引用、局部修改、无需修改和冲突对象 | 每项变更可追溯到目标与依据；授权内无歧义的操作可以继续 |
| 完成接入 | 先建立管理依据，再接入工具入口，逐项核对实际结果 | 保存已完成及未完成项；局部失败保留原因和影响范围 |
| 验证结果 | 核对范围、资料可读性、入口及记录一致性 | 得到各范围状态与总体结果，明确下一步 |

已明确的授权继续有效，不为每个步骤重复请求确认。规则冲突、模式变化或范围歧义需要单独解决，不能借初始化默认作出选择。

独立管理工程可以记录已接入的仓库和失败的仓库，但既定范围保持完整。哪些工作可以开展由实际可用范围和依赖决定，涉及失败仓库的工作不能被当作已经具备条件。

接入结果通过通用入口和规则索引衔接[项目接手与规范建立](../workflow/design.md#24-项目接手与规范建立)。已有代码的调查与基线验证属于后续工作，新项目的专属规范随总体设计形成、随骨架落实；初始化不会自动扫描业务、补写总体规格或执行构建测试。已有文档、规范和检查配置由后续工作核对并引用，初始化不预建空项目规范或伪造通过状态。

## 5. 已有内容与规则共存

对每个可能修改的对象，记录发现时的内容依据，并在写入前再次比较。若期间发生变化，重新评估，不按旧结果覆盖。

| 现状 | 候选处理方式 |
|---|---|
| 所需资料已经存在且适用 | 引用已有资料，避免复制与重复生成 |
| 缺少资料或入口 | 在明确范围内新增，未知内容如实标记 |
| 已有 AI 工具入口 | 保留原有内容，优先补充指向 tiller 工作依据的引用 |
| 已有入口与接入要求冲突 | 说明冲突及影响，受影响操作暂停，等待明确处理方案 |
| 已有 tiller 管理信息 | 核对身份、范围和内容后复用，不直接重建 |
| 不认识的格式或无法确认归属 | 保留原内容，报告不兼容或归属不明 |

入口的合并方式由对应适配部分决定。不能因为文件由 tiller 曾经生成就覆盖后续人工修改，也不能仅凭文本比较宣称已经识别所有语义冲突。

采用 `AGENTS.md` 入口时，通用工作原则与项目专属内容按总体设计分开维护。新增入口应引导读取适用的项目规则和已有资料；整理已有入口时，保留原有约束及其适用范围，迁出的规则必须仍能从入口到达并在执行前读取。升级只处理能够明确识别归属的受管内容，不能将整个已有入口视为可覆盖模板。

### 5.1 通用入口的接入方式

入口的读取路径建议为：工程入口 → `.tiller/index.md` 与规则索引 → 共同规则及适用项目规则 → 已有规格和相关工作 → 当前活动规则。必要动作仍在入口简要表达，不能只放一句“遵循 tiller”。

通用入口统一在 `resources/entry.md` 中维护；初始化以该资源生成 `AGENTS.md` 的 tiller 区段，tiller 自身也使用相同生成结果，不另外维护一份通用正文。入口保留资料导航、必要执行原则及人工确认边界，详细资料维护要求放入已有共同规则和文档质量规则，并从入口可达。

工作记录约定的接入见[开发规范设计第 4.2 节](../standards/design.md#42-工作记录约定的接入已实现)：入口保留最少文件及创建要求，链接共同规则中的完整约定。该方案已获用户确认，并在 0.2.2 同步实现规则与配套命令；实际接入与验证进展见[工作记录](../../../work/20261015-work-artifacts/work.md)。初始化不预建工作目录或阶段产物，工程升级不批量迁移历史工作。

入口不存在时，以通用入口资源新建；入口已存在时，保留原文，只补充读取路径和必要的通用动作。当前实现使用 `tiller:entry:start` 与 `tiller:entry:end` 两个注释标记识别 tiller 补充区段。既有其他工具标记和区段保持不变。自身原有的重复通用正文按本次明确授权单独整理，不将这种删除行为放入其他工程的通用升级逻辑。

标记只能帮助定位，不能证明区段未经用户修改。重复初始化或更新时仍比较旧基线、当前内容及目标内容；标记缺失、重复、范围不清或用户修改冲突时保留原文并呈现问题，不整文件覆盖，也不重复追加多份入口。已有有效引用可以复用，不为了统一样式重写用户文件。

将 Codex 作为首个接入验证对象，使用目标运行方式实际支持的工程指令入口；当前以管理根目录的 `AGENTS.md` 接入，但其实际加载行为和可读范围必须在目标环境核验。本文不假定所有工具或从任意业务仓库启动时都会读取管理根入口，也不默认安装专用技能、钩子或修改用户全局配置。

独立管理工程先验证从管理根开展工作的入口链路；若还要求直接从业务仓库开始工作，需另行验证各仓库入口能定位共同依据。确需补充局部入口时，仅修改已授权仓库并保留其规则，不能以管理目录包含仓库推断拥有写入授权。

## 6. 重复初始化与中断恢复

采用“先记录变更意图，再执行并核对结果”的过程。继续初始化时，以当前文件和访问情况核对记录，而不是直接从上次标记的位置往后运行。

| 核对结果 | 后续处理 |
|---|---|
| 实际内容已经符合预期 | 复用结果并补齐记录，不重复写入 |
| 操作尚未发生且原有依据未变 | 继续该项操作 |
| 实际内容与原有依据、预期结果都不一致 | 标记为冲突，保留当前内容，重新评估 |
| 文件已写入但结果记录尚未保存 | 根据实际内容核实完成情况，再补记结果 |
| 模式、仓库范围或目标身份改变 | 呈现差异，不自动转换、移除仓库或迁移历史记录 |

单个文件写入应避免留下截断内容；多个文件和仓库之间不假定能够整体原子完成。局部失败时保留明确的未完成状态，不通过批量回滚删除用户已有内容。若记录本身无法保存，应直接返回失败及可确认的实际结果，不宣称恢复依据完整。

对同一管理范围的并发初始化应串行执行或明确拒绝重叠操作；写入前的内容核对仍需保留，以识别其他参与者的编辑。

## 7. 结果与可用性判断

每个管理范围分别记录以下状态，状态名称为候选：

| 状态 | 含义 |
|---|---|
| 待处理 | 尚未接入或尚未检查 |
| 未完成 | 已有部分结果，仍有必要操作或验证未完成 |
| 受阻 | 存在无法访问、冲突、授权不足或能力缺失等阻碍 |
| 可用 | 该范围所需的工作依据和入口已验证可用 |

只要既定范围中仍有必要项待处理、未完成或受阻，就不能报告总体完成。结果分别列出已可用范围、阻碍和非阻断的待补充资料；仓库用途未知可以作为提示，缺失必要规则或无法读取入口则不能忽略。

可用性检查分两层：

- **资料检查**：管理对象与预期一致，引用能够定位，必要信息可读，已有内容得到保留。
- **接入验证**：在目标 AI 编程工具的新会话中，能够找到管理入口、适用依据和下一步；多仓库场景还需验证相关仓库资料可达。

仅建立文件或通过资料检查，不代表完成接入验证。无法实际验证时标明尚未验证及原因，由后续自动或人工验证补足。初始化不以执行业务测试、发布操作来证明入口可用。

### 7.1 首次接入的检查清单

| 检查 | 核对内容 | 失败时的结果 |
|---|---|---|
| 对象与范围 | 当前工程或独立管理工程身份明确，全部指定仓库仍在范围内 | 范围不明时不写入目标；访问失败保留仓库及原因 |
| 文件与归属 | 第 2.4 节的必要信息已接入，已有内容和管理边界保留 | 缺项或冲突对应范围保持未完成，不整体覆盖 |
| 引用与资源 | 入口到已接入规则和资料的引用可解析，资源版本一致 | 区分不存在的未开展资料与损坏引用，列出能力缺口 |
| 共享与本机信息 | 共享文件未被误忽略，本机目录及独立业务仓库按约定排除 | 说明忽略规则冲突，不擅自改变用户的版本管理边界 |
| 目标工具读取 | 新会话能实际找到范围、适用规则、已有记录与下一步 | 保存未验证或失败及原因，不仅凭工具声称理解即报告可用 |
| 重复执行 | 同范围再次接入保留文件、用户修改与历史，不重复添加入口 | 差异保持可见，按冲突或恢复流程处理 |

接入验证记录目标工具及运行方式、工程内容标识、读取路径、实际观察和结果。无法自动启动目标工具时，可由用户或测试人员按同一检查步骤验证并保存依据；CLI 文件检查通过与工具接入验证通过分别呈现。

### 7.2 首次文档工作与接续验证

以下作为初始化、开发规范和工作推进的组合验证方案，不新增“初始化必须完成一次业务开发”的条件，也不等同于完整自举验收：

1. 在选定的测试工程中接入 tiller，保留已应用资源版本、原文件依据及第 7.1 节结果。单工程和独立管理工程分别验证，独立方式使用已明确关联的仓库，不借此决定空管理工程的政策。
2. 开启新的 AI 会话，仅提出“为这个项目起草总体需求，先明确尚缺信息，不开始编码”。检查实际读取入口、规则和已有背景的过程，确认没有把 tiller 自身规则当作目标项目的专属要求。
3. 在用户提供必要信息后，形成总体需求草稿及可接续的最小工作记录，索引关联真实产物。记录已明确事项、待定问题和下一步，不预填模块实现、测试或发布结论。
4. 在保留记录后中断，再开启新会话，仅要求继续该工作。检查其能否从已有记录恢复目标、依据和进展，不要求用户重述已保存信息；已有多个候选工作时先定位，不能随意选择。
5. 完成约定的文档检查，交付草稿并明确确认状态及剩余问题。检查其没有自动进入设计、编码或发布，也没有将文档编写完成当作产品已实现。
6. 再次初始化，核对工作记录、草稿、用户修改及入口保持；增加必要规则不可读、旧证据或空产物等反例，确认缺口不会被当作通过。

证据记录对应的输入、实际读取及操作、文件变化、引用和结果；工作保存在测试工程已有的共享记录中，本机日志仅作辅助。没有工作记录工具时可按同一约定人工或由 AI 维护，但需注明实际方式，不能据此宣称 CLI 的工作推进能力已实现。

组合验证对应初始化 AC-05、AC-06、AC-09、AC-18，工作推进 AC-08、AC-17、AC-23，以及开发规范 AC-01、AC-04、AC-07。其余多仓库、总体设计编写、升级和平台场景仍按原验收计划执行，不因该样例通过而省略。

新增人工确认设计落地后，还需使用没有“先别编码”额外提示的学生服务请求验证默认规则：只确定技术方向时停在需求确认，需求确认后停在设计确认，中断后保持等待。单工程与独立管理工程分别核对入口和对应仓库规则；该结果与文件接入检查分开报告。

## 8. 升级与迁移

### 8.1 程序升级与工程更新

CLI 安装与升级通过 npm 分发机制处理。包安装过程不扫描或修改工程。之后访问工程时，先检查记录格式和资源版本；兼容工程可按原版本继续使用，需要更新时提供影响说明与明确入口。当前 0.3.6 支持 0.1.0、0.2.0、0.2.1、0.2.2、0.3.0、0.3.1、0.3.2、0.3.3、0.3.4、0.3.5 工程的兼容读取及显式升级；旧版资源的写入限制以兼容检查为准，未知版本拒绝写入，其他迁移路径未实现。实际验证及剩余范围见[实现进度记录](../../../work/20261016-implementation-progress/work.md)。

普通初始化重试不等于升级授权。工程更新以明确的目标版本和范围执行，不在每次运行时追随最新模板。规则与适配资源的升级也需检查兼容性，即使记录格式未变，也不能省略自定义内容比较。

### 8.2 兼容判断

CLI 声明可读、可写的记录格式范围，以及支持的迁移路径。实际判断组合版本，而不是只比较版本号大小。

| 检查结果 | 行为 |
|---|---|
| 格式与资源兼容 | 复用现状；有新资源不代表必须立即改写 |
| 需要迁移且有受支持路径 | 生成明确源版本、目标版本及影响范围的更新计划 |
| 格式过新、版本未知或无适用路径 | 阻止不支持的写入，保留资料并报告限制；只呈现能安全读取的信息 |
| 上次迁移未完成 | 进入该次更新的核对恢复，不直接创建第二条迁移链 |

历史工程缺少版本信息时，不根据文件名猜测版本；需要可靠识别依据或明确的导入方案后才能迁移。模式转换、仓库增删和管理目录改名不因升级自动发生。

### 8.3 保护用户修改

资源更新比较三份内容：上次应用的资源基线、工程当前内容、目标版本资源。

- 当前内容与旧基线一致时，可以按计划更新，并保存恢复依据。
- 用户修改与新版修改互不冲突时，可合并后验证；规则含义有歧义时仍需明确处理，不能只靠文本合并判定正确。
- 修改重叠或无法可靠取得旧基线时，保留现状并报告差异，不把目标模板整体覆盖到工程。

原本属于用户的文件及被引用的业务资料不视为生成物。迁移仅处理计划明确涉及的管理内容，必要的历史记录格式转换需保留原记录和关联，不能重建为空记录。

`.tiller/specs/`、`context/` 和 `work/` 中的工程资料属于项目内容，不因位于管理目录内就允许被新版模板覆盖。`rules/` 中的发布资源与自定义规则按来源区分，继续使用基线比较；恢复副本位于 `local/`，共享版本与更新结果不能只保存在该目录。

### 8.4 执行与恢复

1. **准备**：核对源版本、目标、范围与当前内容，检查支持的迁移路径；取得同范围的排他执行权，避免初始化与更新重叠。
2. **保留依据**：保存必要的变更前副本、资源基线及迁移计划，确认可以读取。建立失败则在写入前停止。
3. **执行**：逐项比较当前内容与计划依据，按依赖更新并保存步骤结果。中断后复用第 6 节的实际内容核对机制，不盲目重复迁移。
4. **复验**：检查迁移后的格式、引用、历史关联和工具入口。记录实际格式变化与资源应用结果，但在必要复验完成前保持整体更新未完成。
5. **完成或恢复**：通过后保存最终版本与结果；失败则明确保留的实际状态，允许继续或按恢复计划处理。

多仓库更新逐范围保存进展，保留此次源版本和目标，不把部分完成标成总体完成。混合状态下，只允许经过兼容核对的操作；旧的“可用”结果不能自动证明新状态可用。

恢复前比较文件与本次更新写入后的内容。内容未变且存在副本时可恢复；已被后续编辑的对象不覆盖，报告冲突。新增文件只有在仍与本次生成内容一致时才可移除。恢复过程也记录进展，失败后不能宣称已完整回退。

需要降级时，仅在存在适用恢复或逆向迁移依据并完成兼容检查的情况下处理；不保证所有版本都能无损降级。备份保留时长、命令形式与具体版本策略见 Q19。

### 8.5 人工确认规则的接入与已有工程更新

以下方案已用于 0.2.0 的规则接入和 0.1.0 → 0.2.0 显式升级，实现与验证见[人工确认工作](../../../work/human-confirmation/work.md)。此次交付待用户验收，其他版本迁移仍需单独设计：

1. 新工程接入明确版本的入口、共同规则、专项规则和模板，使用同一套确认语义。初始化不创建虚构的需求确认、设计确认或验收事件。
2. 已有工程先只读生成更新计划，列明源资源版本、目标版本、受管文件差异及已识别的入口区段外矛盾表述。使用 `tiller upgrade [path] --plan` 与 `tiller upgrade [path] --apply <plan-id>` 分开预览和执行。正在进行工作的语义影响及未被匹配的规则冲突仍需执行者核对，CLI 不声称完成全面语义检查。
3. 按第 8.3 节做基线比较。未修改的受管资源可按计划替换；用户编辑及归属不明的入口保留并展示冲突。规则语义冲突须处理后再报告新版规则可用，不能仅凭文本合并成功判定完成。
4. 应用前再次核对计划所依据的内容，沿用锁、恢复副本与分步进度；内容变化则计划失效。复验成功后更新资源版本，部分失败不得记录整体升级成功。
5. 历史 `record.json` 的完成记录保留原含义，不转换为人工批准。缺少确认来源的进行中工作显示待核对；用户可以针对当前内容作新决定，但迁移不补造过去的审批。`confirmations.json` 按工作推进设计独立版本化，未知格式禁止相关写入。
6. 自身工程及外部测试工程分别核对已应用版本；两者已显式升级，保留业务与历史内容。另以独立临时 Java 工程验证入口读取、等待确认和中断接续。安装新 CLI 本身不代表任何已有工程已经应用新规则，实际结果见[验证记录](../../../work/human-confirmation/verification.md)。

人工确认首次实现使用 `0.2.0`，统一通用入口使用 `0.2.1`；工作产物及历史接入实现使用当前 `0.2.2`，支持已知 `0.1.0`、`0.2.0`、`0.2.1` 基线显式升级，尚未发布。旧版 CLI 不能兼容新版资源时应拒绝写入；不得仅添加新规则文件而继续对外声明使用原资源版本。当前升级对修改过的受管正文保守报告冲突，不提供语义合并；入口、忽略文件和索引受管区段仅允许 LF/CRLF 等价比较，区段外内容保留。规则接入与来源核验、宿主拦截能力分别报告，升级规则不会凭空增加宿主能力。

## 9. 与其他模块的协作

| 模块 | 初始化使用的能力 | 初始化回传的信息 |
|---|---|---|
| 开发规范 | 适用规则与必要的工作条件 | 已有约定、适用范围及冲突 |
| 项目记录 | 管理事实、资料引用与记录方式 | 范围、仓库关联、初始化结果 |
| 工具适配 | 入口接入方式及能力限制 | 目标环境、入口变更和验证结果 |
| 工作推进 | 接收初始化后的工作起点 | 可用范围、阻碍与下一步，不包含虚构的开发进度 |
| 验证与反馈 | 结果证据的记录与呈现方式 | 初始化检查依据、失败原因与待复验项 |

这些是职责约定，不预设接口签名或独立进程。其他模块尚未工具化时，可先按相同约定由文档与人工操作提供支持，结果需注明实际执行和验证方式。

## 0.3.6 验证资料接入

长期验证资料使用可选的 `.tiller/verification/`，由 `verification init` 按需建立最小配置和索引；工程初始化不生成业务用例。项目专属 `.tiller/rules/testing.md`、用例和执行证据由项目维护，升级保留其内容。组织与接口见[验证设计](../verification/design.md)，实际保护验证见[测试管理工作](../../../work/20261019-testing-verification/verification.md)。
