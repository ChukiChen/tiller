# 工程初始化需求

> 状态：讨论稿
> 对应总体需求：[R8 初始化与管理范围](../../requirements.md#r8-初始化与管理范围)、[R9 升级与持续使用](../../requirements.md#r9-升级与持续使用)，关联 R2、R3、R5、R6。

## 1. 目标与范围

工程初始化帮助开发者建立使用 tiller 的起点：明确管理对象，让 AI 能够找到适用的开发依据，并了解开始工作前还缺少什么。

本模块覆盖两种初始化方式，以及接入已有工程、重复初始化、升级兼容、工程管理资料更新和未完成时的处理。初始化完成不等于完成项目分析、具体开发任务或交付验证。

## 2. 使用场景

| 场景 | 用户意图 | 预期结果 |
|---|---|---|
| 当前工程接入 | 在正在开发的工程中使用 tiller | 当前工程具备明确的开发依据和工作入口，已有内容得到保留 |
| 独立工程管理多个仓库 | 从独立管理工程统一开展涉及多个仓库的工作 | 能辨认管理工程与各仓库的关系，并区分共同信息和仓库专属信息 |
| 已有工程再次初始化 | 检查或补足已有的初始化结果 | 已有工作继续保留，不重复建立另一套管理信息 |
| 未完成后继续 | 处理缺失信息、访问失败或接入冲突后继续初始化 | 能知道已完成什么、剩余什么，并继续处理 |
| 升级后继续使用 | 使用新版 tiller 处理已有工程 | 能了解兼容情况和必要更新，保留自定义内容与历史记录 |

## 3. 用户提供的信息

| 信息 | 用途 | 缺失时的处理 |
|---|---|---|
| 初始化方式 | 确定在当前工程中接入，还是建立独立管理工程 | 无法从明确意图判断时，先澄清，不自行选取 |
| 目标工程 | 明确接入或建立管理能力的位置 | 目标不明确时，不修改可能无关的工程 |
| 被管理仓库 | 独立方式下明确仓库范围及可定位的信息 | 范围不明确时先澄清；指定但不可访问的仓库保持可见 |
| 项目背景与已有约定 | 理解工程用途和已有的开发要求 | 优先从已有资料了解，无法确定的内容标为未知 |
| 使用的 AI 编程工具 | 检查能否在该工具中找到初始化后的工作依据 | 未明确或不受支持时，说明对接入结果的影响 |

能够从工程中可靠获取的信息，不应要求用户重复填写。推断的信息应与已确认事实区分；不影响接入的背景信息可以保留待补充。

## 4. 使用过程

1. 用户选择初始化方式并明确管理对象。
2. tiller 了解已有内容与约定，呈现缺失信息和接入冲突。
3. 在明确的范围与授权内完成接入，需要用户决定的事项单独提出。
4. 用户查看初始化结果，了解当前可以开始哪些工作，以及仍需处理什么。
5. 存在阻碍时，用户补充信息或处理问题后继续，无需丢弃已经保留的工作。

接入后应能找到下一项工作的起点：已有项目进入[现状与开发依据建立](../workflow/requirements.md#flow-22-接手已有项目并建立开发依据)，新项目进入总体需求及设计编写，并在设计阶段明确[项目规范](../workflow/requirements.md#flow-23-衔接项目规范建立与实现)。初始化成功不代表已理解业务代码、补齐规格或验证项目可运行。

## 5. 功能需求

### INIT-01 明确管理范围

初始化应区分当前工程接入与独立管理工程两种方式，并呈现实际采用的方式和管理对象。

管理方式应作为后续工作可读取的依据，不能仅按一次工作涉及的仓库数量推断。独立管理工程中的工作即使只涉及一个业务仓库，也不自动改为当前工程集成方式。

独立方式应区分管理工程与被管理仓库。不能仅因某个仓库位于附近或可以访问，就自动将其纳入范围；访问失败也不能导致指定仓库被静默移出范围。

业务仓库可以集中组织在管理工程内的独立区域；共同资料与业务仓库保持清晰边界。仓库身份应与存放位置分开，后续工作能按稳定身份定位实际仓库。新增布局不应隐式移动既有仓库或使已有引用指向另一份内容；歧义与位置冲突应明确报告。

### INIT-02 接入当前工程

在当前工程中初始化后，开发者与 AI 应能够找到该工程的背景、适用规则和后续工作的起点。

已有代码、文档、开发约定及工作记录应保留。已有资料能够满足需要时，应复用或关联，不要求重新描述同一份内容。

### INIT-03 建立独立管理工程

开发者应能够建立独立管理工程，关联多个仓库，并辨认每个仓库的用途、接入情况及其专属资料。用途尚不明确时应标明未知，不编造说明。

共同目标和跨仓库工作应有统一的管理依据；各仓库仍可辨认自身的规则、工作与结果归属。某项共同工作的管理范围不能被误解为对所有仓库的操作授权。

### INIT-04 识别已有内容与冲突

接入前应识别已有的开发规则、项目资料和 tiller 管理信息，区分可复用内容、缺失信息及相互冲突的要求。

接入不能直接覆盖已有约定。无法确定如何兼容的冲突应说明涉及的内容和影响；处理前，不将受影响范围标记为可用。

### INIT-05 提供可用的工作起点

初始化后，开发者与所使用的 AI 编程工具应能够找到管理范围、适用规则、已有记录和下一步。重新开始会话后，也应能找到这些信息。

独立方式下，应能够从共同管理信息找到相关仓库的工作依据。工具无法读取必要信息或缺少必要接入能力时，应明确说明限制，不能仅凭管理信息已建立就宣称接入可用。

### INIT-06 保留重复初始化前的工作

对同一范围再次初始化时，应识别已经完成的接入，保留已有要求、决定、进度和验证记录，不重复建立相互竞争的管理依据。

初始化方式或管理范围与已有信息不一致时，应明确指出差异，不把再次初始化自动当作模式转换或范围变更。

### INIT-07 处理异常与中断

无法定位或访问目标、信息不足、规则冲突、接入不受支持，以及执行中断时，应说明具体问题、受影响范围和可继续处理的事项。

若已经发生部分变更，应能够辨认已完成和未完成的内容；再次继续时核对现状，不盲目重做。局部成功不能被表述为全部成功，也不能掩盖其他仓库尚未接入的事实。

### INIT-08 呈现初始化结果

结果应包含初始化方式、实际管理范围、已经建立或复用的工作依据、接入可用情况、未解决问题及下一步。

只有既定范围内必要的工作依据可找到、必要入口可用，且不存在阻碍接入的未决问题时，才能说明该范围初始化完成。背景资料不完整与接入不可用应分别说明。

### INIT-09 判断版本兼容性

使用新版 tiller 接入已有工程时，应区分程序已经升级与工程管理资料已经更新，呈现当前兼容情况及必要的处理事项。程序安装或更新本身不应自动修改工程。

工程资料版本较新、版本未知或缺少支持的迁移路径时，应保留原内容并说明限制，不尝试以重新初始化覆盖问题或自动降级。能够安全读取的范围可以呈现，不支持的写入应被阻止。

### INIT-10 更新工程管理资料

更新前，应明确目标版本、受影响内容和恢复方式。更新应保留业务代码、历史工作记录及用户自定义内容；与新版规范或入口发生冲突时，先说明差异，不以新模板直接覆盖。

执行迁移前应建立必要的恢复依据，无法建立时不开始迁移。

更新中断或部分失败时，应能辨认实际完成范围，并在核对当前内容后继续或恢复。更新后的修改不得被恢复操作覆盖；无法安全恢复时，应明确指出阻碍。只有必要迁移与接入复验均通过，才能报告工程升级完成。

### INIT-11 跨平台接入与更新

在 tiller 支持的操作系统上，两种初始化方式、重复初始化及工程更新应满足相同的需求与验收条件，包括中文和含空格的工程路径。

环境依赖缺失或平台限制影响接入时，应在操作前能检查的范围内识别并说明；执行中发生的文件占用或权限问题按失败与恢复要求处理，不将部分变更报告为成功。

### INIT-12 建立工程资料入口

初始化应提供统一的工程资料入口，区分产品规格、开发规则、项目背景、具体工作记录和本机临时信息，帮助开发者与 AI 找到相应内容。

已有资料应保持单一维护来源；迁入或引用时保留内容及关联，不重复维护同一份规格。尚未开展的模块和工作不应被自动填充为已存在的需求或过程记录。共享资料应可随工程保存，本机临时数据不混入共享记录。

### INIT-13 发现并持续使用操作入口

接入后，开发者和 AI 应能通过工程资料找到可用的命令入口，不依赖临时补写说明或已存在的全局命令。初始化应区分资料接入成功与命令实际可用，并说明不可用时的恢复方式。

重新打开项目、更换终端或进入同仓库隔离副本后，应能重新核对并使用可用安装；换机器、移动或移除安装后，不得将过期的本机路径视为共享事实。通用说明由产品维护、自动接入并随显式升级更新，保留用户修改。

验收覆盖已有本机安装、无全局命令、隔离副本、安装失效与恢复、升级冲突及共享资料不包含本机绝对路径；接入不生成业务规格或人工批准。

## 6. 验收标准

| 编号 | 验收场景 | 通过条件 | 对应需求 |
|---|---|---|---|
| AC-01 | 在已有工程中首次初始化 | 能找到该工程的管理范围和工作依据；原有代码、文档和约定保留 | INIT-01、INIT-02、INIT-04 |
| AC-02 | 建立独立管理工程并关联两个仓库 | 两个仓库均可辨认，共同依据与仓库专属信息可区分，仓库内容和记录归属不混淆 | INIT-01、INIT-03 |
| AC-03 | 工程旁存在未指定的仓库 | 未指定仓库不被自动纳入或修改 | INIT-01 |
| AC-04 | 已有规则与接入要求冲突 | 能看到冲突及影响，原规则未被覆盖，受影响范围不被标记为可用 | INIT-04、INIT-08 |
| AC-05 | 初始化后重新开始 AI 会话 | 无需重述初始化时已保存的信息，即可找到范围、适用依据和下一步 | INIT-05 |
| AC-06 | 对相同范围再次初始化 | 原有工作记录保留，不产生另一套管理依据；方式或范围不同则明确提示差异 | INIT-06 |
| AC-07 | 指定的一个仓库不可访问 | 该仓库仍列在既定范围中，失败原因与影响可见，不宣称全部成功 | INIT-01、INIT-07、INIT-08 |
| AC-08 | 初始化中断后继续 | 能核对已完成与剩余内容，保留原有记录，并在问题解决后完成接入 | INIT-06、INIT-07 |
| AC-09 | 缺少关键信息或工具无法读取必要依据 | 说明缺失项或能力限制，不虚报相应范围可用；可明确下一步处理事项 | INIT-05、INIT-07、INIT-08 |
| AC-10 | 项目背景不完整但接入所需信息齐全 | 未知背景保持可见，不编造事实；结果区分可用的接入能力与待补充资料 | INIT-03、INIT-08 |
| AC-11 | CLI 更新后访问兼容的旧工程 | 报告程序与工程版本状态，未执行工程更新时工程内容保持不变 | INIT-09 |
| AC-12 | 更新存在自定义规则和历史任务的工程 | 展示目标及影响，保留自定义内容和历史记录；冲突未解决时不覆盖或宣称完成 | INIT-04、INIT-10 |
| AC-13 | 旧 CLI 遇到较新格式、未知版本或不支持的迁移路径 | 保留现状，阻止不支持的写入，说明限制，不重建或降级工程 | INIT-09 |
| AC-14 | 更新中断或多仓库部分更新失败后继续 | 保留源版本、目标和实际进展，不提前报告总体完成；核对后可继续完成并复验 | INIT-07、INIT-10 |
| AC-15 | 更新后出现人工修改，再尝试恢复 | 能区分更新产生的修改与后续修改，不覆盖后续内容；无法恢复的对象及原因可见 | INIT-10 |
| AC-16 | 各支持平台的中文及含空格路径 | 两种方式的接入、重复执行和更新获得一致结果，引用和入口可读取 | INIT-05、INIT-11 |
| AC-17 | 运行依赖缺失、写入受阻或无法建立恢复依据 | 可提前识别的问题在写入前报告，执行期失败不虚报成功；必要恢复依据缺失时不开始迁移 | INIT-07、INIT-10、INIT-11 |
| AC-18 | 建立资料入口或接入已有工程资料 | 各类资料可区分并可找到，共享信息与本机数据分开；已有资料保持单一来源和有效引用，未开展的工作不生成虚构内容 | INIT-02、INIT-03、INIT-05、INIT-12 |
| AC-19 | 独立管理工程的一项工作仅涉及一个业务仓库 | 后续仍能读取原管理方式及共同资料归属，不自动改为当前工程集成；初始化不预建该工作的开发副本或评审请求 | INIT-01、INIT-03、INIT-05、INIT-12 |

验收需检查初始化前后的工程内容、结果说明，并验证实际能否找到和读取工作依据；仅有生成成功的提示不足以证明通过。

## 7. 与其他模块的边界

工程初始化负责建立和维护接入起点，包括工程管理资料的版本检查、更新与恢复，使用开发规范、项目记录和工具适配提供的能力。CLI 程序的安装与升级由分发机制承担。初始化完成后，具体任务的推进、跨仓库依赖协调和交付判断由相应模块承担。

具体工作的独立开发环境、变更评审与合入由[工作推进](../workflow/requirements.md#flow-17-隔离开发并区分两种管理方式)负责。初始化提供明确管理方式及可用依据，不预先为尚未开展的工作创建开发副本、工作分支或评审请求，也不因接入成功认定已经具备远端操作授权。

本模块的验收不要求实际完成一项功能开发或发布；完整自举仍需通过真实开发工作另行验证。
