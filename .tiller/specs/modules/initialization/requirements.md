# 工程初始化需求

## 1. 目标

让空目录或已有工程在一条命令内得到可执行的最小 tiller 结构，并让受管资源可安全升级而不覆盖用户内容。

## 2. 初始化

- 初始化支持当前工程与独立管理工程；仓库范围必须显式、可验证。
- 空工程应得到完整性规格、模块说明、项目背景、全局用例、规划、入口规则和当前平台合并请求模板。项目与模块的需求/设计骨架包含完整业务章节标题和简短写作提示，不放长示例。
- 初始化时选择托管平台；缺省生成 GitHub 模板。之后切换平台需要显式调整项目元信息并补齐对应模板。
- 维护入口文件的固定区段、本机数据排除和工程导航；已有区段外内容和已有骨架不覆盖。
- 重复初始化只补缺失骨架；入口冲突时拒绝并保持原件。
- 初始化完成后输出工程状态和入口位置；入口直接使用 PATH 中的 `tiller`。
- Python pytest 工程在初始化时可被识别并选用对应验证方式；用例骨架与该方式一致。
- 有 Git 提交时，初始化在独立的本机工作树中建立固定初始化分支，提交受管改动并自动尝试同标题 PR/MR，但不自动合入。
- 有 Git 时可把受管产物只写入初始化 worktree；成功后默认分支工作区对受管文件无未跟踪残留（含项目元信息）。无 Git 降级时仍可写 primary。用户改写或已跟踪文件保留，也不使用粗暴的全目录清理。
- 初始化提交在同一变更集中保留用例空目录；工程已有但为空的源码与测试目录补占位文件，不创建不存在的业务目录。
- PR/MR 创建失败仍保留本地 worktree 和提交，并返回可复制命令；初始提交或本地记录已存在时不重复制造冲突分支。
- 初始化基线合入后或显式结束该初始化编号时，默认清理它的本机目录、本地分支和远端分支；保留分支需显式声明，删除失败不阻断收尾，也不影响其他任务的本机数据。
- 跟踪元信息保留可解析到 squash 前 PR head 的稳定引用；fresh clone 在 init 已合入且分支已删除时，仍可用该引用与平台合入记录证明基线，不得依赖本机 merged 标记或已删除分支。
- 初始化编号的 close 必须先证明合入；证明失败时返回稳定错误并保留 init 事实，不假报已关闭。
- 初始化提交标题必须可区分，禁止两个完全同名提交；init PR/MR 标题包含初始化编号，避免重复初始化与历史同名记录混淆。

## 3. 受管资源

- 项目元信息记录模式、每个业务仓库的标识与位置、受管文件规范化摘要、创建时间和资源契约。工程和单个仓库都可以声明验证运行方式与测试前准备。仅含标识的旧清单仍可读取。当前工程方式不登记业务仓库。
- 受管文件包含入口区段、规则、使用指引和平台对应的合并请求模板。摘要必须能区分用户修改与换行风格差异。
- 资源版本必须是当前契约或直接兼容的上一版本；未知版本拒绝读取和写入。

## 4. 升级

- 升级先提供只读预览；应用时在锁内重新核对后原子写入。
- 摘要一致且未修改的受管文件刷新到分发内容；用户修改、缺失、区段异常均列为冲突，不覆盖。按当前平台补齐缺失模板，GitHub 项目不得新增 GitLab 模板。
- 冲突提示包含首个差异位置；预览计划绑定当前输入，文件变化后旧计划失效。
- 成功后更新项目元信息中的摘要和资源契约；保留验证等用户配置；不迁移业务资料、历史任务、旧确认或旧审计。
- 事务失败保留恢复依据，可以恢复；不得只更新文字而跳过复验。
- 可按受管文件采纳当前内容摘要，保留用户修改并消除误报漂移；采纳不重写文件，也不替代升级预览。

## 5. 验收方向

- 空仓库初始化后具备任务、规划、用例与规格入口。
- 已有文件不被覆盖，重复初始化幂等。
- 兼容资源可刷新未修改文件，用户修改必须保留并给出差异。
- 初始化生成的用例骨架说明测试先于实现的测试设计、测试与用例编号的关联方向，以及无关联待实现状态。
- 有 Git 提交的工程可观察到初始化 worktree、固定分支/提交/PR 标题和失败降级命令。
