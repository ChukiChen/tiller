# 工作推进需求

## 1. 目标

用一条任务记录承载需求、设计、确认、验证和交付自检，让 AI 在明确边界内连续推进，用户只在有意义的节点决策。

## 2. 开始与接续

- `start <task-id>` 必须提供标题、目标正文和至少一条编号 AC，生成目标、范围、验收条件结构；可指定类型、规模、范围、规划条目和 PR/MR 标题摘要。
- 小改动默认 `small`，标准/大功能使用 `standard`。standard 任务 `start` 必须声明至少一个 `--target`；small 缺省范围为 `.`。标准代码任务必须补设计并确认。
- `resume [task-id]` 返回当前记录、确认、验证、规划归属、推导阶段和回退原因；无参数时列出当前任务及其阶段，不列历史 work。
- 任务范围和基线必须记录；开工前已有改动不得冒充本次越界。

### FLOW-02 明确要求与交付边界

需求写清目标、范围、正常/异常行为和可观察验收条件。确认前校验目标、范围和 AC 非空；聊天原话不能代替正文，缺少依据时停在澄清。

### FLOW-03 选择必要工作与验证安排

按规模选择 small 或 standard，不做无关阶段产物。每条 AC 在实现前转为全局用例，并规划可定位测试。

### FLOW-04 在授权范围内持续推进

只修改声明的文件范围。顺手发现的问题记录到任务记录，不扩大修复。Git 检查分别报告越界和未提交改动；没有 Git 时明确降级为提示。

### FLOW-05 处理失败与阻碍

同一问题连续两次修复失败就停止自动尝试，报告现象、已尝试方法、证据和两到三个可选方案，等待用户决定。

### FLOW-06 处理要求和方案变化

需求、范围、AC 或设计变化后重新计算确认对象；旧确认失效，不复用旧提交上的批准。无法继续时保留当前记录，不覆盖无关修改。

### FLOW-09 依据验证结果判断交付

最新验证必须通过、测试存在且未过期；`verify --run` 必须实际执行，node:test TAP/spec 输出要命中具名测试且为通过。套件退出码不能代替每条 AC 的用例结论；失败、跳过、未运行和环境限制分别报告。外部报告默认阻断，只有理由完整且显式使用 `--allow-reported` 才可交付。

### FLOW-15 在关键节点取得人工确认

需求、设计（standard）和交付验收是默认人工节点。确认对象是任务记录中已写明的结构化正文；自动保存确认部分、确认人、时间、提交和摘要。`--by` 缺省取 Git `user.name`；用户原话可选，只作附注，AI 不得代写或补造。

### FLOW-24 在各环节形成测试依据并保存执行事实

需求确认后先改全局用例，再写测试、实现和执行命令。`verify` 只接受 `--run "<命令>"`，记录即执行；外部报告使用 `--reported --command --result --reason`。bugfix 先用 `--expect-fail` 在任务基线工作树留下失败先行记录，再保存当前通过。验证保存 AC、用例编号、测试、命令、结果、退出码、核实状态、提交和代码树摘要；不保存原始日志和全文快照。

## 3. 规划拆分

- 大功能可先建立 `.tiller/plans/<id>.md`，写总体目标、关联 specs 和条目。
- 条目包含编号、标题、`small|standard`、依赖、覆盖需求和可选子规划引用；编号稳定，依赖可多值，子规划只作指向。
- 规划确认绑定完整正文，可省略原话并记录确认人；正文或条目变化后需重新确认。
- `start --plan --item` 继承条目粒度并记录归属；依赖未验收时阻塞开工。
- `plan status` 列出条目状态、关联任务、未覆盖需求和阻塞依赖。规划不是默认人工节点。

## 4. 任务记录

`task.md` 是唯一当前记录，包含结构化需求、设计（标准任务）、规划归属、确认、验证和自检。需求与设计独立摘要；完成后长期结论同步到 specs，超大设计先用 plan 拆分。记录不得出现密钥、token、凭据或本机绝对路径。

## 5. 提交与 PR/MR 草稿

### FLOW-29 统一提交、分支与 PR/MR 格式

提交主题为 `类型(模块): 中文摘要`，类型限 `feat/fix/docs/refactor/test/chore`，模块来自 specs，摘要用中文且不带任务链接。PR/MR 标题沿用该格式并在末尾加 `[任务编号]`；标题摘要优先取 `pr --summary`，其次取 `start --summary` 写入的任务元数据，再取任务基线后最早的规范 feat/fix 提交摘要，最后退回任务标题。主模块按范围声明顺序取首个，无法推导时省略括号；说明固定关联任务、变更内容、验收条件、验证结果、影响与风险五段，关联任务用纯文本路径，变更内容按提交时间正序。分支为 `类型/任务编号[-简短描述]`，只使用小写字母、数字、连字符和一个斜杠。

`pr <task-id>` 从任务类型、摘要、范围、AC 状态、验证记录、设计和任务基线后的提交生成 Markdown 或 `--json` 草稿，同时给出建议分支。每条 AC 单独一行并带条件摘要，其下用普通嵌套列表列出该条件的全部验证记录（测试、命令、结果、提交）。分支描述依次取 `pr --slug`、`start --slug` 写入的任务元数据、当前分支匹配描述。它不调用 GitHub/GitLab、不联网；标题、变更内容和风险仍需人工复核。`check` 检查当前分支和任务基线后的非合并提交主题，格式问题只提示，不阻塞。

## 6. 任务阶段与结束

### FLOW-25 从事实推导任务阶段

阶段顺序为已开始、需求已确认、设计已确认（small 可跳过）、已验证、已验收、已关闭/已放弃。阶段从记录中的确认、验证、验收和关闭事实推导，不另存状态字段；需求、设计或验证失效时显示回退后的阶段与原因。

### FLOW-26 关闭、放弃与恢复

已验收任务用 `close --reason` 收尾，未验收终止用 `close --reason ... --abandon`；两者记录原因和时间。已关闭与已放弃都是终态，不能继续确认、验证或验收；`reopen --reason` 显式恢复后才能继续。规划条目不把放弃任务算作进行中或已验收。

### FLOW-27 结构化正文与去原话确认

`## 需求` 使用目标、范围、验收条件三级标题；standard 的 `## 设计` 使用方案、取舍、影响与风险。确认需求校验前三段，确认设计要求方案与影响非空，取舍为空只提示。确认记录包含确认部分、确认人、时间、提交和摘要，原话可选；需求与设计分别失效。

### FLOW-28 旧任务兼容

旧 task.md 的纯文本需求、顶层验收条件和旧 quote 确认继续可读且有效。只有新任务标记结构化格式；写入旧任务时保留其正文结构与旧确认样式。

## 7. 验收方向

- 小改动可只生成一份 task.md 并完成需求确认、实现、验证。
- standard 任务在设计和设计确认前不能进入实现完成态。
- 规划依赖、正文变化、范围越界和无效确认会阻塞或明确提示。
