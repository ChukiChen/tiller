# 工作推进需求

> 状态：讨论稿
> 对应总体需求：[R2 连续推进工作](../../requirements.md#r2-连续推进工作)、[R3 控制执行范围](../../requirements.md#r3-控制执行范围)，关联 R1、R4、R5、R6、R7、R8。

## 1. 目标与范围

工作推进帮助开发者与 AI 围绕同一目标，从提出工作、明确需求和方案，持续推进实现、测试、评审、验收与发布，并将使用反馈带入后续改进。

工作既可以面向产品整体，形成或完善总体需求与总体设计，也可以面向具体模块或功能。总体资料的编写、讨论和修订本身就是可独立开展和交付的工作，不以已有代码或模块规格为前提。

本模块描述各环节之间的衔接、继续条件和异常处理，使参与者能够知道当前做到了哪里、接下来做什么，以及凭什么判断本次工作完成。它适用于单仓库和跨仓库工作，也适用于 tiller 自身开发。

完整流程覆盖从产品构想到交付，但每项工作的完成范围由目标和验收条件确定。形成需求或设计、交付代码、具备发布条件与实际发布成功应分别说明；实现或发布不在本次范围内时，不据此阻止约定交付，也不自动进入这些环节。

## 2. 使用场景

| 场景 | 用户意图 | 预期结果 |
|---|---|---|
| 建立或完善总体需求与设计 | 从产品想法形成整体依据，或调整已有产品范围与方案 | 总体需求与总体设计分开形成并可迭代，已确认事项与待定选择可区分，可作为独立成果交付 |
| 制定实施规划 | 总体需求与设计确认后，决定如何分步交付本次范围 | 任务覆盖、边界、依赖、验证条件与待细化项可审阅，经确认后逐任务推进 |
| 从总体细化具体模块 | 选择当前需要开展的能力，补充其详细需求与设计 | 模块资料关联总体要求，总体引用已形成的详细资料，无需提前展开所有模块 |
| 开发软件或功能 | 从初步想法得到可交付结果 | 要求逐步明确，方案、实现和验证围绕同一目标衔接 |
| 修复或改进已有项目 | 解决缺陷、调整功能或重构 | 结合已有依据开展必要工作，验证问题解决及受影响行为 |
| 长期接手已有项目 | 将已有代码纳入持续开发 | 核对现状和验证基线，复用或补足总体规格与项目规范，再进入增量开发 |
| 为新项目建立开发规范 | 在技术方案确定后统一开发约定 | 总体设计阶段形成规范，相关方案确认后在骨架任务中落实检查 |
| 继续已有工作 | 中断或更换参与者、工具后接续 | 能核对现状，复用有效结果，继续处理剩余事项 |
| 为同一工作逐步补充产物 | 先形成需求，再依据有效确认补充设计和后续记录 | 工作身份及已有依据保持连续，不因进入新环节拆成无关联的新工作 |
| 检查或接入已有手写工作 | 发现工作结构与约定不一致，或希望接续历史资料 | 先看到缺口和兼容情况，再明确接入映射；原内容、历史及确认事实得到保留 |
| 执行中调整要求 | 根据新信息改变目标或范围 | 能了解影响，更新依据并重新验证受影响结果 |
| 协调多个仓库 | 完成依赖多个仓库的共同交付 | 各仓库的职责、依赖、授权及结果可区分，整体结论有依据 |
| 在当前工程中隔离开发并提交评审 | 独立推进一项变更，保持其他工作的内容不受影响 | 本仓库的需求、设计、实现和验证随同一项变更追溯，经确认后合入目标版本 |
| 在独立管理工程中协调评审与合入 | 管理多个业务仓库共同完成的变更 | 共同工作记录集中维护，分别关联各仓库的开发、评审及合入结果，部分成功不冒充整体完成 |
| 发布后改进 | 处理使用反馈和运行问题 | 问题关联原交付，形成可跟进的后续工作 |

## 3. 开始工作所需的信息

| 信息 | 用途 | 不明确时的处理 |
|---|---|---|
| 工作意图与预期结果 | 理解要解决的问题及本次交付目标 | 可先开展澄清，不把猜测作为实现要求 |
| 涉及的项目与范围 | 确定相关模块、仓库和范围边界 | 在影响操作对象时先澄清，不扩大到未指定范围 |
| 已有规格、背景与规则 | 复用项目知识并识别约束 | 优先查阅已有资料；区分未知、冲突和不影响当前工作的缺口 |
| 验收条件与交付范围 | 判断结果是否满足要求、是否包含发布 | 随需求澄清明确，在依赖这些条件的操作前解决歧义 |
| 授权及已有进展 | 区分可自主推进、需要人工决定和已经完成的事项 | 核对现有授权和记录，不要求用户重复提供已明确的信息 |

这些信息可以在推进过程中逐步补充，不要求用户在开始讨论前一次性填写完整。尚无总体或模块规格时，可以先开展相应需求与设计工作；尚未确定模块或业务仓库时，不为起草总体资料强制补齐这些信息，也不编造依据。

## 4. 典型使用过程

### 4.1 从产品想法形成整体依据

1. 用户描述产品意图、目标用户和要解决的问题，通过讨论明确范围、主要场景和预期结果。
2. AI 根据已有信息起草总体需求，用户可以补充、纠正或调整；文档区分已明确要求与待定问题。
3. 需要形成方案时，在相关总体需求经用户确认后起草总体设计，说明主要构成、职责与协作关系，并明确适用的项目开发规范；无法确定的选择保持可见，不把候选方案当作已确认决定。
4. 按本次约定检查并交付总体需求或设计。需要进入实施时，依据已确认的总体需求和设计形成实施规划，拆分任务、核对覆盖和依赖，展示具体安排并取得用户确认。
5. 按规划选择近期任务，复用或细化相关模块、变更需求与设计，补足对应确认后实现和验证；总体引用长期资料，任务关联实际交付依据，不预先细化所有任务。

用户可以只要求起草总体需求、只完善已有设计，或继续讨论已有草稿。草稿编写完成、内容已经确认与产品已经实现应分别判断，不要求一次性确认所有内容，也不因文档形成就自动开始编码。新项目后续实现以骨架为首个普通任务，落实已确认规范的必要检查；已有项目的接手、基线及资料补足遵循 FLOW-22。

### 4.2 从具体需求到功能交付

以在已有项目中增加一项功能为例：

| 环节 | 用户参与 | 预期结果与衔接条件 |
|---|---|---|
| 提出工作 | 说明问题、使用场景和期望 | 辨认新工作或已有工作，找到项目依据及需要澄清的信息 |
| 明确需求 | 查看具体需求，确认目标、关键行为、边界和验收条件 | 相关需求经确认，关键未决问题解决后，进入对应设计 |
| 形成方案 | 查看设计和影响，确认接口约定、关键选择及验证安排 | 相关设计经确认，具备制定本次实施安排的依据 |
| 实施规划 | 审阅并确认任务范围、需求覆盖、依赖、完成条件与人工检查点 | 局部工作可用单任务简要规划；已有整体规划可引用，核对本次任务及所缺依据 |
| 实现与测试 | 查看进展，按需补充信息 | 逐任务核对依据、确认及依赖，再实现、即时验证和记录；验证失败不进入依赖任务，阶段内自主修复与评审 |
| 评审与验收 | 查看交付内容、评审结论和验证依据，作出验收决定 | 检查结论与人工验收结论可区分；用户接受后才能标记相应范围已验收 |
| 变更合入 | 审阅拟合入的具体变更、目标及检查结果，确认合入 | 按授权合入并核对实际结果；评审通过、已验收、已合入与已发布分别呈现 |
| 发布与交付 | 发布前确认具体对象、环境、影响及失败处置 | 经确认后执行对应发布，交付内容与验证对象一致，实际结果和交接信息明确 |
| 反馈与改进 | 提供使用反馈或运行问题 | 问题关联原交付，明确后续处理范围，更新相关项目知识 |

上述环节表达使用主线，关键人工确认节点按 FLOW-15 执行，不要求阶段内每个操作都由用户确认。实现、测试和评审可以反复进行；发现上游问题时，应回到受影响环节调整，并重新判断相关确认是否有效。

### 4.3 各环节的产物要求

以下定义开展相应环节时应形成或复用的产物及必要信息，不规定模板章节、文件名或保存格式。产物既包括文档和记录，也包括代码、配置及实际交付物；不是每项工作都需要产生表中全部内容。

| 环节 | 主要产物 | 必要信息 | 用途与完成判断 |
|---|---|---|---|
| 工程接入 | 初始化结果与工作依据入口 | 管理范围、适用规则、资料位置、可用情况、缺失项与下一步 | 能找到开展工作的依据；复用工程初始化结果，不在每项工作中重复生成 |
| 已有项目调查 | 现状说明、资料差异及验证基线 | 调查范围、资料与代码版本、可验证事实、推断、未知项、检查条件和实际结果 | 足以辨认本次依据及阻碍；未调查、未执行与通过分开，不推断历史批准 |
| 建立项目规范 | 项目专属约定与已有检查配置引用 | 来源、适用范围、必要约定、检查方式、确认依据及遗留项 | 总体设计时明确，实施前确认适用内容；骨架或必要基础补齐时有实际检查证据 |
| 提出与澄清工作 | 工作说明与澄清记录 | 问题、背景、预期结果、范围、已有依据及待解决问题 | 能辨认本次工作及其边界，不把假设当作已确认要求 |
| 明确总体需求 | 总体需求文档 | 产品目标、用户与场景、范围、核心需求、约束与验收方向，以及已有详细需求的引用 | 整体要求清楚，确认状态可辨认；不要求提前展开所有模块 |
| 形成总体设计 | 总体设计文档 | 需求依据、主要构成、职责、协作关系、关键方案及约束，以及已有详细设计的引用 | 能说明整体方案如何支撑需求，候选选择与已定方案可区分 |
| 细化模块或变更需求 | 模块需求或本次变更需求 | 关联的总体或模块要求、具体场景、预期行为、边界、异常情况及验收条件 | 能确定本次要实现和验证什么；变更需求聚焦差异并引用长期规格 |
| 细化模块或变更设计 | 模块设计或本次变更设计 | 对应需求、解决方案、相关接口与数据约定、依赖、影响及验证考虑 | 设计细节足以支撑本次实施，未决选择及其影响明确；仅涉及变更时复用已有设计 |
| 实施规划 | 任务拆分与验证安排 | 需求覆盖、任务边界、涉及对象、依赖、完成条件、验证方式、待细化项与人工检查点 | 展示具体规划并取得确认后按任务推进；单任务可简要表达，规划确认不代替待细化规格的确认 |
| 准备隔离开发 | 开发范围与基线关联 | 管理方式、资料归属、涉及仓库、独立开发位置、工作分支、基线与目标、已有修改及处理依据 | 开发依据可定位，已有修改得到保护，执行位置与工作范围一致 |
| 实现 | 代码、配置或其他实现成果及变更说明 | 实际变更内容、对应要求与方案、受影响范围及尚未完成部分 | 产出可定位且能与要求关联；实现完成不等于验证通过 |
| 测试 | 测试用例或检查项、适用的测试代码与执行记录 | 对应要求、验证对象与环境、预期和实际结果、失败项及未覆盖内容 | 能核查实际执行了什么、结果是否适用于当前产出；未执行项不记为通过 |
| 评审 | 评审意见与问题处理记录 | 评审对象与范围、发现的问题、处理结果、复核结论及剩余风险 | 必要问题已处理或明确待决；修改后的结果按影响复核 |
| 验收 | 验收结论与证据关联 | 约定范围、逐项要求的满足情况、验证依据、未满足或未验证项及必要决定 | 能据此判断本次交付条件是否满足；文档工作按文档要求验收 |
| 提交变更评审与合入 | 变更提交、评审请求及合入结果 | 工作与仓库、源和目标版本、需求设计引用、验证及评审依据、人工合入决定、实际结果及待处理项 | 评审对象与实际变更一致，合入有授权与结果依据；多仓库分别记录并汇总，单个请求完成不代表整体完成 |
| 结束隔离开发 | 保留与清理结果 | 交付记录、未保存或未交付内容、各开发副本的去留及未完成操作 | 清理不丢失唯一成果或共享依据；失败、取消和部分交付仍可追溯 |
| 发布 | 发布安排与执行结果 | 发布对象与目标环境、前置条件、授权依据、失败处置、实际执行及结果确认情况 | 能区分待发布、成功、失败、部分成功和结果未知；仅在发布属于范围时要求 |
| 交付与交接 | 实际交付物与交付说明 | 交付内容及版本、验收依据、发布情况、必要使用或运行说明、遗留事项及后续处理 | 接收方能够找到并使用约定成果，了解边界与剩余事项；交付物可以是文档、源码或可运行产品 |
| 运维反馈与改进 | 运行问题或反馈记录、处理结果及必要的后续工作 | 关联交付、问题现象、影响、可用证据、处理决定与结果 | 反馈能够跟进，需继续处理的事项有明确关联，不因收到反馈就视为已解决 |

决定、进展、阻碍和验证记录随工作持续维护。要求变化时保留变更原因与影响；中断或交接时保留实际进度、未结束操作及下一步；交付时同步受影响的长期规格和项目知识。这些信息可以纳入已有工作记录，不要求分别新建文档。

人工确认也是衔接依据，应能关联被确认的具体内容、适用范围及实际用户决定。产物编写完成、检查通过与用户确认分别判断；表中的产物具备必要信息，不代表已经获得进入下一环节的确认。

同类信息可以合并记录或引用已有成果，但需求与设计仍应分开维护，总体与模块、长期规格与单次变更的归属仍应清楚。可合并的是计划、进展、检查摘要与交接等过程信息，不能因此自行替换约定工作入口或用一份过程说明代替应交付的需求、设计。复用时核对适用范围和版本；本次不适用的产物无需生成，省略会影响后续理解或验收时应说明理由。

## 5. 功能需求

### FLOW-01 建立或接续工作

开发者应能够提出新的工作，也能够明确选择继续已有工作。工作应能关联其目标、项目范围、已有规格及适用规则，避免将不同工作的要求和进展混在一起。

应复用初始化提供的管理范围和资料入口；必要依据不可访问或存在冲突时，说明对当前工作的影响。不影响澄清的问题可以保留待处理，影响操作安全或正确性的问题解决前不执行依赖它的操作。

### FLOW-02 明确要求与交付边界

工作应能够将初步意图明确为问题、预期行为、范围边界和可检查的验收条件，并区分已确认要求、假设及待定问题。

本次交付是需求或设计草稿、经确认的规格，还是包含实现、部署等成果，应明确。已有要求可以引用复用；不能通过默默删除未满足要求或缩小范围，把未完成工作改为完成。

### FLOW-03 选择必要工作与验证安排

应根据工作规模、复杂度、风险和已有成果选择必要环节，说明需要完成的事项、依赖关系及验证方式。需要设计时，方案应能对应相关要求，关键取舍及其影响应可查。

简单修改可以减少步骤和文档，不能因此省略目标、授权边界、适用的人工确认和必要验证。已有有效成果及其确认可以按 FLOW-15 复用，不为走完流程而重复创建；执行中发现复杂度或风险变化时，应调整后续工作并说明原因。

### FLOW-04 在授权范围内持续推进

条件具备且已获授权的工作应能在当前阶段内持续推进，不要求用户逐步催促，也不重复请求仍有效的确认。进入依赖人工确认的下一环节时，应先满足 FLOW-15，不能将一般实施授权解释为所有阶段均已确认。用户应能够查看当前工作、已完成内容、剩余事项和下一步。

需要人工决定、超出范围或授权不足时，应提出具体事项及其影响，暂停依赖该决定的操作。可以独立开展且仍在授权范围内的工作可继续；用户要求暂停或终止整项工作时，应遵守其范围。

### FLOW-05 处理失败与阻碍

信息不足、依赖未满足、执行失败、测试未通过或评审发现问题时，应说明原因、受影响范围和继续条件，并将问题纳入后续处理。

问题处理后，应重新验证受影响的结果。没有可靠处理路径时，应保留已完成内容并明确阻碍，不能无依据地反复重试、跳过必要检查或用完成声明掩盖失败。

### FLOW-06 处理要求和方案变化

目标、需求或方案发生变化时，应能识别受影响的计划、实现、测试、评审、验收及发布安排，并按实际授权更新工作依据。

原有决定、授权和验证结论应重新判断是否仍适用，不能将旧结论直接用于已变化的对象。保留变化前后的关联与理由，不重写历史验证事实；与变化无关且仍有效的成果可以继续使用。

改变已确认的目标、行为、验收条件、接口约定或发布范围等实质内容时，应重新取得受影响范围的确认，再继续依赖它的工作。仅修正文字且不改变含义时，可保留确认并说明依据；影响无法判断时，应先核对，不能默认旧确认仍然有效。

### FLOW-07 支持中断、暂停与恢复

工作中断、更换参与者或 AI 编程工具后，应能够找到目标、依据、实际产出、已作决定、未解决问题和下一步，并核对记录与当前工程是否一致后继续。

恢复时应核对各适用确认节点、被确认内容和用户决定的依据；待确认或已失效的事项仍须处理。仅发现已有代码、文档或完成记录，不能推断此前已经确认，也不能补写并未发生的用户决定。

用户应能够暂停或终止工作。应说明已发生的变更及尚未结束的操作，保留恢复或交接所需信息；终止不等于验收通过，也不默认撤销已有变更。恢复时不盲目重做已有操作，尤其不能重复执行已发生的发布等外部操作。

### FLOW-08 协调跨模块与跨仓库工作

同一项工作应能够关联多个模块和仓库，明确各自承担的工作、依赖、适用规则与授权，并保留统一的整体目标和进展。

部分仓库受阻时，应能判断哪些工作可独立继续、哪些必须等待。整体交付应检查相关仓库的结果及协作效果，不能以单个仓库通过代替整体完成，也不能静默移除失败部分。

### FLOW-09 依据验证结果判断交付

交付判断应对应约定需求、实际产出及适用的测试、评审和验收依据，明确已满足、未满足和未验证的内容。验证依据应能够辨认其对应的产出版本或实际内容。

必要检查失败或证据缺失时，不能宣称相应要求已满足。剩余问题应说明是否阻碍本次交付及判断依据；需要用户接受的取舍应取得相应决定，不能用笼统的风险提示代替处理。

交付对象为需求或设计时，应检查其是否覆盖约定问题与范围、需求与方案是否对应、引用是否有效，以及冲突和未决事项是否明确。文档编写工作的验收不以代码或运行测试为前提，也不能据此声称产品能力已经验证。

### FLOW-10 衔接发布与交接

发布属于本次范围时，应在必要交付条件和授权具备后推进，明确发布对象、目标环境、结果确认方式及失败后的处置要求。开发或测试授权不能自动扩展为发布授权。

应区分准备完成、已发起发布、已确认发布结果及结果未知。发布失败或部分成功时，保留实际结果与待处理事项，不报告全部完成；继续、恢复或回退仍应遵守相应授权并确认实际结果。

交接应说明交付内容、验证依据、必要的使用或运行信息及剩余事项。发布不在范围内时，明确未执行发布及后续所需条件。

### FLOW-11 同步项目知识并承接反馈

变更被接受并交付后，应同步受影响的长期需求、设计和项目背景，保留本次工作与所依据规格、交付内容及验证结果的关联。必要同步尚未完成时，应呈现待办，不能将知识维护声明为完成。

发布后的问题和反馈应能关联原交付，明确是否需要形成后续工作，并保留处理结果。新问题不直接改写原有验证事实；需要修正既有结论时，应留下原因和新的依据。

### FLOW-12 如实呈现工作结果

工作结束时，应说明约定范围、实际交付、验证结论、发布情况、资料同步情况和遗留事项。全部完成、部分完成、受阻、暂停或终止应可区分，不能用同一完成声明替代这些不同结果。

只有约定范围内的必要交付条件均满足，才能报告本次工作完成。人工完成的步骤、无法使用的能力和未执行的验证应可见，不将建议的操作或计划中的结果记为已发生事实。

必要检查通过但尚待用户验收时，应报告交付已准备好、等待验收，不能标记为已验收或整项工作完成。仅交付草稿的工作也应区分草稿交付被接受与规格内容被确认，前者不自动授权设计或实现。

### FLOW-13 形成总体依据并逐步细化

开发者应能够从初步产品意图形成总体需求，再按需要形成对应的总体设计，并在讨论中持续修订。已有资料可复用或完善，不能要求已有完整规格才能开展规格编写。

总体需求应说明产品目标、场景、范围、核心能力与验收方向；总体设计应说明相应方案的主要构成、职责和协作关系。两者分开维护，详细内容在开展相关模块工作时再补充，不要求一次性展开所有模块。

总体需求或总体设计应能够独立交付，并明确内容的确认状态及未决事项。用户仅要求形成草稿时，可交付标明待定问题的草稿；不能将草稿交付等同于方案已确认、获得实现授权或产品已经完成。

进入模块细化时，应关联适用的总体要求和设计，并在总体索引中引用实际形成的模块资料。模块讨论暴露总体缺口或冲突时，应说明影响并协调更新，不能仅修改模块而留下相互矛盾的整体依据。

### FLOW-14 明确并检查各环节产物

工作应能够按第 4.3 节和本次约定确定适用产物，使开发者与 AI 了解每个环节需要形成或复用什么、包含哪些必要信息，以及满足什么条件后可用于后续工作。

应能区分待产生、已有但需补充、可复用和不适用的产物，按实际工作逐步形成，不能为填满清单生成空文档或虚构完成记录。产物可以简化、合并或引用，但不能因此丢失必要信息、混淆需求与设计，或破坏要求、方案、实现与验证之间的关联。

依赖某项产物继续工作前，应检查其实际内容、适用范围和确认状态。必要产物缺失、内容不完整或已经失效时，说明影响并补充或更新；文件存在、模板填完或记录标为完成都不能单独证明环节完成。最终交付应能定位约定产物及其验收依据。

### FLOW-15 在关键节点取得人工确认

默认采用以下节点，只要求确认本次工作实际涉及的范围，不要求提前确认整个产品或全部模块：

| 节点 | 提请用户确认的内容 | 确认后可推进的范围 |
|---|---|---|
| 需求确认 | 目标、范围、关键业务行为、边界、验收条件及待定问题 | 基于已确认需求开展对应设计；阻碍设计的未决问题须先解决 |
| 设计确认 | 对应需求、方案、接口与数据约定、关键取舍、影响及验证安排 | 具备对应实现依据；实际实现还须满足规划确认及任务依赖 |
| 实施规划确认 | 本次任务拆分、需求覆盖、范围、依赖、验证条件、待细化项与人工检查点 | 按规划细化和推进任务，进入实现仍须满足相关需求与设计确认 |
| 交付验收 | 实际交付、需求满足情况、测试与评审依据、缺口和限制 | 将用户接受的范围标记为已验收；不自动取得发布授权 |
| 合入确认 | 拟合入变更、源与目标版本、评审和验证依据、跨仓库依赖及剩余问题 | 在确认范围内合入并核对结果；不自动代表交付已验收或获准发布 |
| 发布确认 | 具体发布物及版本、目标环境、影响、前置条件和失败处置 | 执行对应发布；执行完成后仍需核对实际结果 |

应先形成可审阅的内容，明确本次需要确认什么及确认后的下一步，再取得用户决定。未确认、明确拒绝或确认依据不足时，暂停依赖该确认的工作；可继续完善当前草稿或开展独立且已获授权的事项，不能先实施再补写需求、设计和确认记录。

确认应能追溯到用户的实际表达及其所针对的内容版本或具体内容、范围和结论。AI 自行标记“已确认”、文档生成成功、测试通过、用户未回复或等待时间经过，均不能代替人工确认。用户只确定“Java 接口、增删改查、内存实现”等方向，不代表确认了尚未呈现的业务行为和接口细节。

应结合上下文理解用户决定：“继续”若明确回应当前呈现的确认事项，可以作为该事项的确认；若只是一般推进指令或确认对象不明确，不能解释为对未呈现内容或后续所有节点的确认。确认有条件或只覆盖部分范围时，保留限制，仅在条件满足后推进对应工作；无法确定含义时应澄清。

已有确认在内容、范围和条件仍适用时应复用，不重复审批。用户可以明确要求合并、简化确认节点，或授权在指定范围内由 AI 作出某类决定；应保留这项授权的内容与边界，不能推断为接受未展示的规格，也不能扩大到其他节点。AI 不得以任务简单、文档简短或已有一般开发授权为由自行豁免确认。

记录与实际行为应一致。若发现已经越过节点，应如实呈现已有产物及缺少的确认，将其作为待核对内容，暂停继续依赖该确认的工作；后续取得的确认不能改写为此前已经发生。

### FLOW-16 按统一约定组织并逐步补充工作产物

新建及接续工作时，应能从工程入口找到明确的工作组织约定，知道工作入口、阶段产物和机器记录各自的职责、必要性及创建方式。约定不能只隐含在实现代码或示例中；执行者不能自行用其他文件替代必要入口及产物。

同一目标的工作应保持稳定身份，按实际需要新增阶段产物或关联已有有效资料。只开展需求时不预填设计等后续产物；需求经确认后能够在原工作中补充对应设计，保留需求、确认、进展及历史。已有规格可明确引用，不为满足结构要求复制一份相同正文。产物创建或登记不等于确认、验收或整项工作完成。

已支持的创建与登记操作应通过对应机制执行；机器记录由这些操作维护，不能手工编造状态。缺少支持能力时应明确记录适用限制及人工处理方式，不将未登记的资料冒充已受程序管理，也不借能力缺失跳过人工确认。

检查应能够发现尚未登记的工作及缺少必要入口、登记与文件不一致、产物职责混淆等可判定问题，分别说明结构合规、内容质量和确认状态。可附加导航及辅助材料，不能仅因存在额外文件就判为违规；检查结果不能声称已自动判定全部文档语义。

历史目录、手写记录及旧机器记录应先只读检查，呈现缺口与兼容状态，再依据明确映射接入。检查不自动重命名、覆盖、搬移或补写历史；接入保留原文及已有确认依据，未知的需求确认、验收及完成状态保持未知。接入过程的输入变化、冲突和中断应可检查并安全处理。

### FLOW-17 隔离开发并区分两种管理方式

软件变更应默认在与其他工作相互隔离的开发环境中推进，明确工作身份、涉及仓库、开发基线、工作分支与目标版本。需要接续已有独立环境时，先核对其关联和实际内容；不因目录存在就认定其适用于本次工作。隔离机制及目录由设计确定，不改变已确认的工程管理方式。

准备开发环境前，应辨认已提交成果、未提交修改及未纳入版本管理的必要资料，明确本次采用的内容并保护其余修改。不能假定新环境自动包含原目录的全部内容，也不以准备环境为由擅自提交、丢弃或覆盖已有工作。

两种方式的资料归属与交付关系应分别满足以下要求：

| 方面 | 当前工程内集成 | 独立管理工程管理多个仓库 |
|---|---|---|
| 管理与资料归属 | 本次需求、设计、实现及验证记录归属于当前业务仓库，随其变更交付；主开发位置不再维护另一份相互竞争的本次记录 | 共同目标、跨仓库需求设计及工作进展由管理工程集中维护；业务仓库保留自身专属资料与代码，引用共同依据，不复制另一套整体进度 |
| 独立开发对象 | 围绕当前业务仓库建立或接续独立开发环境 | 仅为本次涉及且获授权的业务仓库分别建立或接续独立开发环境，不将管理工程的副本误认为所有业务仓库的副本 |
| 交付关联 | 工作关联本仓库的变更、评审请求与目标版本 | 同一工作关联各仓库各自的变更、评审请求与目标版本；管理工程自身的资料版本及评审单独记录 |
| 完成判断 | 核对本仓库实际变更、验证及约定合入结果 | 除各仓库结果，还需核对共同资料、依赖关系和组合使用效果，管理工程资料合入不代替业务仓库交付 |

独立管理工程即使当前工作只涉及一个业务仓库，也仍按其实际管理方式处理；不能仅按受影响仓库数量切换模式。多仓库协调应保留管理资料版本与业务仓库交付版本的关联，避免用后来修改的共同资料解释此前已评审的代码。

### FLOW-18 提交变更评审并确认合入

工作应能关联实际变更提交和评审请求，使评审者找到对应需求、设计、变更范围、验证结果、已知问题及目标版本。采用远端协作时，通过项目使用的评审请求（MR 或 PR）交付；创建或更新请求与批准、合入分别记录，不能由请求已存在推断其已通过。

本地提交、推送、创建或更新评审请求、合入和发布的授权应分别可辨认。已获明确授权的阶段内操作可持续执行；设计确认不自动授予未明确包含的提交、推送或远端操作权限，允许提交或创建评审请求不表示允许合入。合入遵循 FLOW-15，平台上的有效人工决定可以作为确认依据，仍须核对其对象、范围及来源。

合入前应核对当前变更、目标版本、必要检查、未解决意见及依赖与人工决定仍一致。内容、目标或依赖变化时重新判断验证和确认是否有效；冲突解决后按影响重新验证，不能用旧结果直接放行。验收与合入确认可以由一次明确决定同时覆盖，但必须辨认两种含义；合入成功本身不构成交付验收或发布授权。

多个仓库分别保留评审及合入结果，按实际依赖协调先后关系。某个仓库被拒绝、受阻或已合入而其他仓库未完成时，应呈现部分状态及处理安排；不能宣称跨仓库整体合入具有不可分割的成功或失败结果，也不自动撤销已合入的成果。

远端不可访问、缺少适配能力或结果未知时，保留本地成果并明确受阻环节。恢复前核对实际提交、推送、评审请求及合入状态，避免重复创建或执行；约定要求远端评审但尚未完成时，不能用本地检查代替。仅交付文档或明确不包含合入的工作，仍按原交付范围判断，不强制开展无关操作。

### FLOW-19 安全结束与清理独立开发环境

工作完成、取消或需释放独立开发环境时，应先确认实际交付状态、未提交或未交付成果、未结束操作，以及工作记录是否已保存在后续可访问的位置。不得因评审请求关闭或任务取消而自动丢弃唯一成果、确认来源或必要证据。

清理范围应明确区分本地开发副本、工作分支、远端分支与共享工作资料，分别核对授权和保留条件；移除一个本地副本不表示其余对象也可删除。存在未解决事项时保留相关内容并说明原因；清理失败不改写已发生的交付事实，接续仍能找到实际结果。

### FLOW-20 从总体依据拆分可交付功能块

本环节称为“实施规划与任务拆分”，位于总体需求、总体设计确认之后，以及任务实现之前。开发者与 AI 应能够将本次范围拆成可实现、可验证的交付任务；此前“功能块”表示同类交付增量。模块表示长期职责，任务可以涉及多个模块或仓库，任务内还可分解技术步骤；不能仅按技术层或文件分工拆解，却无法说明交付结果。

实施规划应说明每个任务的标识、需求与设计依据、预期结果、包含与不包含的范围、涉及对象、依赖、完成条件和验证方式，并列明待细化事项与需要人工检查的节点。应能展示本次需求由哪些任务覆盖，以及尚未安排、细化或受阻的部分，不以遗漏或缩小范围制造完成结论。

具体规划应展示给用户确认，再据此选择任务细化并实施。已有有效规划可核对后复用；局部简单修改可使用单任务简要规划，不强制重新规划整个产品，也不自行省略确认。规划可与其他确认一并审阅，但用户决定须实际覆盖规划内容。规划确认不批准尚未展示的任务需求和设计；进入实现前，应复用充分且已确认的依据，或补足缺口并取得相应确认，不要求预先写完所有任务的详细规格。

按“核对依据、确认与依赖 → 实现当前任务 → 执行验证 → 即时保存结果 → 判断下一任务”推进。必要验证失败、未执行或缺少证据时不得把前置任务视为已就绪，也不得进入依赖它的任务。独立且条件已满足的任务可继续。同一轮可完成多个任务，但须保持真实先后及逐项证据，不能将最终整体测试倒填为早期任务当时已通过。技术验证不默认增加逐任务人工审批；规划约定的人工检查点和既有确认节点仍须满足。

一个任务可关联多项工作，一项工作也可承载多个相关任务，任务与模块、工作记录不强制一一对应。保持同一任务进度及证据的单一维护来源。要求、方案、依赖或验证对象变化后，重新判断受影响规划、确认和证据；改变任务边界、需求覆盖、依赖条件、验证标准或人工检查点时重新确认相应规划，仅在已确认条件内调整执行顺序无需重复批准。中断或执行方式变化后重新核对当前任务、实际产物及未满足条件，不补造历史。

逐任务技术通过与用户接受交付分别判断。整体交付仍须核对需求覆盖、任务间组合验证和剩余事项；发现先实施后验证的偏差时如实保存事实与影响，不以事后补齐文档宣称历史合规。

### FLOW-21 先建立必要的项目基础

空项目应在实施规划中将最小可运行、可验证的项目骨架列为首个普通实现任务，与业务任务使用相同的依赖、确认和验证规则，不将骨架另设为独立流程阶段；依据已确认的相关需求与技术设计建立后续功能开发所需的基础。骨架应能实际构建、运行并完成适用的基础检查；库、命令行程序等以其实际入口或调用验证为准，不强制创建服务。仅生成目录、模板或依赖清单不能证明基础可用。

已有项目先评估并复用现有基础，只补当前工作所缺的条件。后续业务功能和公共组件按实际依赖逐步实现；基础能力应有具体使用对象，不为可能出现的未来需求预建完整框架。骨架未通过必要检查时，依赖它的业务实现不能假定基础已就绪，独立的需求澄清和设计工作仍可继续。

tiller 初始化建立工程管理入口和工作依据；业务项目骨架建立产品自身的技术基础。两者的产出和完成判断应分别呈现，不能把 tiller 接入成功视为业务项目已具备运行条件。

### FLOW-22 接手已有项目并建立开发依据

长期接管已有项目时，应在接入后了解实际代码、文档、已有约定及运行条件，建立本次调查范围内的项目现状与验证基线。调查须限定仓库及目标范围，说明资料来源和时效，保护已有内容和未提交修改，不把管理范围视为修改全部仓库的授权。

应区分实际观察、资料声明、推断与期望行为，记录代码与文档的差异、未知事项及影响。基线应说明已执行的构建、运行和适用检查及结果，区分已有失败、未执行、无法执行和后续新增回归；未覆盖范围不作为通过依据，检查不可用时说明阻碍与补足方式。

在现状基础上检查并复用或补足总体需求，需求确认后完善总体设计及项目开发规范，相关方案和规范确认后，按 FLOW-20 确认实施规划并进入任务增量实现。已有有效依据和具体确认可复用，不要求重写全部资料或预先补齐所有模块细节；现有实现不能自动转为期望要求、正式规范或历史批准。

用户明确的局部工作应先检查整体资料的适用性，记录局部范围、相关依赖和未覆盖部分，再补足本次必要需求、设计与规范。允许按范围精简资料，不允许自行免除人工确认；调查发现影响本次工作的整体冲突时先解决，其他无关历史问题不自动扩为改造任务。

进入实现前应能定位适用规格、规范、基线和有效确认，并说明必要缺口是否影响当前功能块。存在影响正确性或验证的缺口时，只暂停依赖操作，不假称整体接管或全部验证已完成。

### FLOW-23 衔接项目规范建立与实现

新项目接入后应能区分通用执行规则和待建立的项目专属规范。项目专属规范在总体设计阶段依据相关需求、技术栈与结构形成，在开始骨架实现前明确并确认；可与设计一并审阅，但确认须实际覆盖规范内容及范围。

骨架任务应按适用规范建立或复用必要检查能力，实际运行并保存结果，再开展依赖这些基础的业务开发。已有项目优先复用现有规范和检查，只补本次必要缺口；不要求所有项目使用相同工具，也不将配置文件存在视为检查通过。

规范可随模块开发逐步补充，实质变化须明确影响与确认范围。新规范不自动要求全库格式化、重构或修复全部历史告警，必要调整应纳入具体工作。规范内容与执行判断遵循[项目专属规范需求](../standards/requirements.md#rule-13-建立并维护项目专属开发规范)。

### FLOW-24 在各环节形成测试依据并保存执行事实

需求形成可观察验收条件，总体设计明确适用测试类别、目标、方法和项目测试约定；实施规划将必要场景、回归范围和环境依赖分配到任务。当前任务设计细化用例，取得适用确认后编写测试代码与实现，实际执行后当场保存结果，再核对依赖条件。长期用例不与本次执行状态混写，最终测试不能补造此前放行。

用例按稳定设计模块维护，跨模块与系统场景分别组织，复用已有测试框架和原有目录。跨模块场景提前规划，在依赖具备后执行；骨架跑通最小测试入口，初始化不虚构业务用例。交付按测试类别汇总通过、失败、跳过、未执行及不适用，区分任务回归、自动化全量回归和完整交付验证。具体覆盖和证据要求见[验证与反馈需求](../verification/requirements.md)。

### FLOW-25 核对已确认规划与当前任务依据

规划应明确需求覆盖、任务边界、详细规格及待细化项、前置任务和必要产物、验证条件与人工检查点，并绑定真实确认。登记、批准与激活分别记录；任务开始前核对当前规格、规范、确认和前置完成事实。验证必须对应实际开始及当前对象，不能用最终结果倒填开始顺序。中断或依据变化后重新登记继续点；未变化且证据仍适用的独立任务不因其他任务修订而丢失有效结果。

### FLOW-26 区分整体技术条件与有限操作例外

整体交付应核对必要任务、实际产物、需求覆盖、组合验证、检查点及遗留项，并区分技术就绪、过程证据、操作允许与用户验收。例外只能来自真实明确决定，绑定具体操作、当前对象和未满足条件；未知身份、结构、来源或不安全路径不得借例外绕过。例外不改写失败事实，不自动授予依赖任务、合入或发布权限。对象或决定变化后重新核对，历史成功回执不得冒充当前有效状态。

### FLOW-27 明确当前记录边界并保留历史

未知或不支持的记录格式应说明具体问题并保留原件，不补缺省事件、迁移成批准或覆盖历史。旧资料可通过新工作明确引用并重新核对所需确认。同一工作内操作身份不能被不同入口重复使用；写前后依据变化应拒绝伪成功，保留并发修改及恢复事实。当前技术验证、整体验收及发布应绑定同一明确交付对象，文档验收不能替代软件整体验收。

## 6. 验收标准

|---|---|---|---|
| AC-01 | 初始化后提出一项新功能 | 可找到项目依据，明确本次目标、范围和验收条件，未定问题不被当作实现要求 | FLOW-01、FLOW-02 |
| AC-02 | 从明确要求推进到功能交付 | 需求、方案、实现、测试和评审结果可关联；授权内工作持续推进，交付结论能追溯到实际产出和证据 | FLOW-03、FLOW-04、FLOW-09、FLOW-12 |
| AC-03 | 修复一个范围清楚的简单问题 | 复用已有依据，减少不必要步骤和文档，仍明确目标、授权及验证结果 | FLOW-02、FLOW-03 |
| AC-04 | 关键选择未确定或下一步超出授权 | 能看到具体待决事项及影响；依赖该选择的操作未执行，独立且已授权的事项可以继续 | FLOW-02、FLOW-04 |

| AC-07 | 已通过测试后需求发生变化 | 识别受影响成果，更新工作依据，重新判断授权及旧结论适用性，验证变化后的结果并保留历史 | FLOW-06、FLOW-09 |
| AC-08 | 中断后更换参与者或工具继续 | 无需重述已保存的要求即可核对目标、实际产出、问题及下一步，记录与现状不一致时先处理差异 | FLOW-01、FLOW-07 |
| AC-09 | 用户暂停或终止正在开展的工作 | 不再发起被暂停或终止范围内的新操作，已发生变更和未结束操作可查；不自动撤销变更或标记验收通过 | FLOW-04、FLOW-07、FLOW-12 |

| AC-12 | 有未验证要求或存在不匹配交付内容的证据 | 缺口和证据适用范围可见，不将旧产出或局部检查结果作为本次全部通过的依据 | FLOW-09、FLOW-12 |
| AC-13 | 本次只要求交付代码，未包含发布 | 按约定交付与验证，明确没有发布及后续条件；不自行发布，也不因未发布否定已满足的交付范围 | FLOW-02、FLOW-10、FLOW-12 |
| AC-14 | 本次包含发布，但缺少发布授权 | 保留已具备的交付结果，明确待授权事项，不执行发布或报告整项工作完成 | FLOW-04、FLOW-10、FLOW-12 |

| AC-16 | 功能交付后同步规格并收到反馈 | 长期资料与已接受变更一致，原工作历史保留；反馈关联原交付，后续处理可跟进 | FLOW-11、FLOW-12 |

| AC-22 | 简单修改复用已有规格并合并过程记录 | 可辨认复用依据及适用版本，合并后必要信息仍完整；需求与设计不混淆，不适用的产物不强制生成 | FLOW-03、FLOW-14 |
| AC-23 | 必要产物缺失、仅有空模板或已不适用于当前要求 | 能指出缺失和影响，不将文件存在视为通过；依赖这些内容的工作在补齐或更新依据后继续 | FLOW-05、FLOW-06、FLOW-14 |
| AC-24 | 发布交付后出现运行问题 | 发布安排与实际结果可区分，交付物及说明可查；问题关联对应交付，处理结果或后续工作可追踪 | FLOW-10、FLOW-11、FLOW-14 |

| AC-26 | 需求已确认，设计尚待确认，用户给出一般推进指令 | 可完善设计并明确待确认事项，不将需求确认或一般指令扩展为设计通过；明确回应具体设计确认事项后才进入实施 | FLOW-04、FLOW-15 |

| AC-28 | 已确认的行为或接口改变，或仅修改不影响含义的文字 | 前者重新确认受影响范围后才继续依赖工作；后者说明复用依据，不重复确认无关内容；影响不明时先核对 | FLOW-06、FLOW-15 |
| AC-29 | 在等待确认时中断，换工具接续，或发现已有越过节点的代码 | 待确认事项仍保留；已有代码不作为先前确认的证据，不补造历史；先核对产物并取得所缺确认，再继续相关工作 | FLOW-07、FLOW-15 |
| AC-30 | 简单修改复用有效确认，或用户明确简化某个节点 | 复用时核对内容和范围；例外有实际用户授权及明确边界，其他节点仍有效，AI 不自行以简单为由跳过确认 | FLOW-03、FLOW-15 |

| AC-32 | 用户只要求交付需求草稿，并接受草稿交付 | 可以结束约定的草稿工作，仍保留规格待确认状态，不自动开始设计或实现 | FLOW-02、FLOW-12、FLOW-13、FLOW-15 |
| AC-33 | 新建工作后从需求进入设计 | 开始时只有适用产物；需求有效确认后在同一工作补充设计，仅有其他对象或范围的批准不能放行，原需求、确认及历史保持，重复操作不覆盖已有内容 | FLOW-01、FLOW-14、FLOW-15、FLOW-16 |
| AC-34 | 工作只有自行命名的说明文件，或登记产物已被改名、删除 | 只读检查发现入口或登记缺口，定位问题与下一处理方式；不把任意说明文件默认认作必要产物 | FLOW-07、FLOW-14、FLOW-16 |
| AC-35 | 已有可用规格，当前工作仅需引用 | 通过明确登记关联已有对象，核对范围、当前内容与确认；不重复复制正文，不将登记等同于批准 | FLOW-06、FLOW-14、FLOW-15、FLOW-16 |
| AC-36 | 简单工作合并过程说明，同时附带导航文件 | 过程信息可以合并，必要需求与设计仍可分别定位；附加导航允许存在但不能替代必要入口，目录不强制生成全部阶段文件 | FLOW-03、FLOW-14、FLOW-16 |
| AC-37 | 命令支持创建当前产物，或所需操作尚不支持 | 前者遵循约定创建及登记；后者说明限制并留下真实人工处理依据，不伪造机器记录或宣称检查通过 | FLOW-05、FLOW-12、FLOW-16 |
| AC-38 | 检查、接入历史手写资料或旧格式记录 | 检查无写入；明确映射后保留原文、记录和引用，未知确认保持未知；后续可关联当前取得的真实依据而不倒推过去批准；冲突或过期计划拒绝写入，失败可恢复 | FLOW-06、FLOW-07、FLOW-15、FLOW-16 |
| AC-39 | 同一工作有多个产物，只接受其中一个草稿交付 | 验收与完成记录明确对应产物及内容，未验收部分仍可见，不把单个产物完成扩大为整项工作完成或发布授权 | FLOW-09、FLOW-12、FLOW-15、FLOW-16 |
| AC-40 | 当前工程集成模式开展隔离开发 | 开发位置与本仓库、工作分支及基线明确；本次需求、设计、代码和验证记录随本仓库变更交付，其他工作不被覆盖 | FLOW-17 |
| AC-41 | 独立管理工程协调两个业务仓库 | 共同记录集中维护，分别关联各仓库的开发与评审对象，管理资料版本和业务版本可追溯；管理工程资料提交不能冒充业务变更 | FLOW-08、FLOW-17、FLOW-18 |
| AC-42 | 独立管理模式仅涉及一个仓库，或部分仓库已有专属资料 | 沿用实际管理方式，复用专属资料与共同引用，不自动变成当前工程集成或复制整体进度 | FLOW-01、FLOW-17 |
| AC-43 | 原目录存在未提交、未跟踪资料，或复用的开发环境不匹配 | 指出实际差异与采用依据；保留原内容，不假定新环境已具备全部成果，也不擅自提交、清理或覆盖 | FLOW-04、FLOW-07、FLOW-17 |
| AC-44 | 有实现授权但没有推送或合入授权，或已创建评审请求 | 可完成已授权部分，授权不足的操作未执行；评审请求存在、检查通过或允许推送均不能代替人工合入确认 | FLOW-04、FLOW-15、FLOW-18 |
| AC-45 | 合入前变更内容、目标或依赖变化，或存在冲突和未解决意见 | 识别受影响的确认与证据，处理后重新核对；缺少有效确认或必要检查时不能合入，不复用无关批准 | FLOW-06、FLOW-09、FLOW-15、FLOW-18 |
| AC-46 | 多仓库部分合入、评审拒绝或组合验证失败 | 分别记录各仓库结果、依赖及剩余事项；整体未完成，不用管理资料已合入代替业务结果，也不自动回退已合入仓库 | FLOW-08、FLOW-09、FLOW-12、FLOW-18 |
| AC-47 | 推送、创建评审请求或合入时中断、远端不可用或结果未知 | 恢复先核对实际结果，避免重复请求或操作；能力不足及未知状态保持可见，不把本地产出报为远端交付完成 | FLOW-05、FLOW-07、FLOW-18 |
| AC-48 | 已验收但未确认合入，或已合入但未验收、未发布 | 各结论独立；一次决定同时覆盖验收与合入时记录明确范围，合入不自动授予发布权限 | FLOW-09、FLOW-10、FLOW-12、FLOW-15、FLOW-18 |
| AC-49 | 完成或取消工作后清理，尚有唯一成果或未结束操作 | 清理前保留可追溯资料并明确对象与授权；未保存成果不丢失，不把移除本地副本扩大为删除远端分支或工作历史 | FLOW-07、FLOW-12、FLOW-19 |

| AC-50 | 总体依据已确认，准备开始实现 | 先形成并展示实施规划，经确认后逐任务推进；需求覆盖、边界、依赖、验证与待细化项可见，不仅按文件或技术层拆分 | FLOW-15、FLOW-20 |
| AC-51 | 选择功能块，细节不足或已有资料充分 | 缺口按既有节点细化确认，已有充分且有效确认的资料直接引用；总体确认不批准未展示细节 | FLOW-13、FLOW-15、FLOW-20 |
| AC-52 | 空项目开始开发 | 骨架作为首个普通实现任务，实际构建、运行及适用基础检查有证据；接入成功或空目录不代替基础可用 | FLOW-21 |
| AC-53 | 已有项目或需要公共组件 | 复用既有基础，只补实际依赖，说明使用对象，不无条件重建或提前搭建全部框架 | FLOW-20、FLOW-21 |
| AC-54 | 功能块跨模块、仓库或发生依赖变化 | 依据、归属和依赖可查，变化后重新核对确认及证据；阻碍与未完成部分保留，不产生多份竞争进度 | FLOW-06、FLOW-08、FLOW-20 |
| AC-55 | 各块已通过技术验证，准备整体验收 | 核对总体范围覆盖及必要组合验证，缺口保持可见；技术通过不直接等于人工验收 | FLOW-09、FLOW-12、FLOW-20 |

| AC-56 | 长期接管已有代码且总体资料缺失 | 先记录有来源的现状和基线，再补足确认总体需求、设计及项目规范；不把代码行为直接视为需求或历史批准 | FLOW-22 |
| AC-57 | 已有规格充分，或本次仅局部修复 | 核对适用性并复用，局部范围与未覆盖部分可见；不强制补齐全项目历史规格，仍保留必要确认 | FLOW-22、FLOW-15 |
| AC-58 | 基线检查失败或不能执行 | 说明已有问题、条件和影响，后续回归分开呈现；不冒称通过，不自动开展无关修复 | FLOW-22、FLOW-05 |
| AC-59 | 新项目从总体设计进入骨架实现 | 适用项目规范随设计形成并获具体确认，骨架落实必要检查且有实际证据 | FLOW-23、FLOW-21 |
| AC-60 | 采用新规范或多仓库规范不同 | 复用各自有效规则与配置，明确共同和局部范围、变化影响及检查方式；不默认整库整改或将单仓库结果当整体结果 | FLOW-23、FLOW-08 |
| AC-61 | 规划尚未确认，或已确认规划中的任务缺少详细规格 | 前者保留规划待确认，不进入依赖它的任务细化与实现；后者只细化近期任务并取得必要确认，不把规划批准当作未展示规格批准 | FLOW-15、FLOW-20 |
| AC-62 | 骨架只做了静态检查，或前置任务必要验证失败、未执行 | 不进入依赖任务；保存当前阻碍及失败事实，独立且条件满足的工作可继续 | FLOW-20、FLOW-21 |
| AC-63 | 同轮连续实现多个任务，事后才集中测试或补记录 | 区分当前功能验证与当时执行顺序，保留过程偏差；最终证据不倒填为各任务事前验证通过 | FLOW-09、FLOW-20 |
| AC-64 | 局部简单任务、已有有效规划或任务涉及多个工作和模块 | 可用单任务简要规划或引用有效规划，确认与必要证据仍具备；不强制一任务一模块、一工作或每任务额外人工审批 | FLOW-03、FLOW-15、FLOW-20 |
| AC-65 | 中断恢复、并行改串行，或规划范围与依赖变化 | 先核对当前任务、实际产物、依赖证据与确认；实质规划变更重新确认，不受影响安排可复用 | FLOW-06、FLOW-07、FLOW-20 |
| AC-66 | 开发任务从需求推进到交付 | 各环节形成适用验证产物，必要任务验证未满足不进入依赖任务，执行结果与长期用例分开 | FLOW-24、FLOW-20 |
| AC-67 | 局部套件通过但存在未执行类别或跨模块场景 | 按类别和范围报告缺口，不报告整体验证通过或自动验收 | FLOW-24、FLOW-09 |
| AC-68 | 未确认规划、缺任务规格或前置结果失效 | 阻断依赖操作，独立有效任务可继续；激活及开始顺序可追溯 | FLOW-25 |
| AC-69 | 产物或前置事件变化、修订无关任务、中断接续 | 当前证据按实际影响重评，保留历史和独立有效结果，不倒填完成事实 | FLOW-25、FLOW-27 |
| AC-70 | 用户对明确未满足条件作出有限例外 | 操作允许与技术结论分开，失败事实保留；错误身份、来源、条件及过期例外不能放行 | FLOW-26 |
| AC-71 | 局部任务通过、整体验证缺失或验收对象不同 | 不误报整体就绪；整体验收、合入与发布各自绑定当前对象及所需决定 | FLOW-26、FLOW-27 |
| AC-72 | 旧格式、重复操作、并发变化或写后校验失败 | 原件和外部修改保留，历史重放明确未重评，不产生伪成功或覆盖他人内容 | FLOW-27 |

验收应查看实际工作经过、产出与验证依据，覆盖正常交付和异常处理。只有流程说明或空的工作记录，不能证明工作推进能力已经可用。

## 7. 与其他模块的边界

| 相关部分 | 工作推进的衔接范围 |
|---|---|
| 工程初始化 | 使用其明确的管理方式、范围、规则与资料入口；隔离开发、变更评审与合入随具体工作推进，初始化不预先开展这些操作 |
| 开发规范 | 本文明确环节衔接所需产物及必要信息；各类产物的详细质量规范由对应需求细化，模板结构与使用机制在设计中确定 |
| 项目记录 | 保存并关联目标、决定、进展、产出和历史，支持接续与追溯；具体保存方式由设计确定 |
| 验证与反馈 | 使用检查和评审结果判断下一步，将未满足项带回处理；具体检查规则由对应需求细化 |
| 工具适配 | 支持不同工具读取同一工作依据并使用项目既有能力；能力不足时明确限制与待处理事项 |

本需求定义从总体需求与设计形成到开发交付的行为与结果，不规定命令、状态机、文件格式或调度机制，也不替代项目自身的构建、测试与部署工具。初始化接入验收、需求或设计文档交付验收与产品实现验收分别判断，前者通过不代表后者已经完成。
