# 工作推进需求

## 1. 目标

用一条任务记录承载需求、设计、确认、验证和交付自检，让 AI 在明确边界内连续推进，用户只在有意义的节点决策。

## 2. 开始与接续

- 开始任务必须提供标题、目标正文和至少一条普通 `AC-n` 验收条件，生成使用场景、目标、业务范围、关键行为、异常与边界、验收条件结构；可附加类型、规模、范围、规划条目和交付摘要。目标正文可以接入工程内已有的非空 specs；其验收条件节含 `- AC-n: ...` 时直接导入并可省略命令行条件，无 AC 时仍须声明；来源缺失、越界或为空时明确失败。
- 小改动默认 `small`，标准/大功能使用 `standard`。standard 任务必须声明至少一个工作范围；small 默认覆盖当前工程。标准代码任务必须补设计并确认。
- 接续应返回当前记录、确认、验证、规划归属、推导阶段和回退原因；未指定任务时列出当前任务及其阶段，不列外部旧仓遗留记录。
- 任务范围和基线必须记录；交付路径只进任务范围。开工前已有改动摘要存放在本机旁路，不写入共享任务标记，也不得冒充本次越界。
- 初始化基线尚未进入当前主干时，业务任务默认不能开始；证明只使用与本次 expected head 绑定的 local merged marker、祖先或同 head 的平台已合入 PR/MR，不使用 Git tag、`headRef`、tracked `status`，也不按同分支标题兜底。用户可显式跳过并收到提醒；没有初始化基线记录的存量工程默认放行。
- 规格在任务隔离工作树中修改并随任务分支合入；初始化集成由独立初始化编号完成，人工合入后再开业务任务。

### FLOW-02 明确要求与交付边界

需求写清使用场景、目标、业务做/不做/假设、正常/异常行为和可观察验收条件。确认前校验这些关键章节不是空标题或占位；聊天原话不能代替正文，缺少依据时停在澄清。

### FLOW-03 选择必要工作与验证安排

按规模选择 small 或 standard，不做无关阶段产物。每条验收条件在实现前转为带前置条件、步骤、输入、预期结果的全局用例，再建立到实际测试的可定位关联。

### FLOW-04 在授权边界内持续推进

只修改声明的文件范围。顺手发现的问题记录到任务记录，不扩大修复。范围与未提交改动分别报告；没有版本历史时明确降级为提示。

### FLOW-05 处理失败与阻碍

同一问题连续两次修复失败就停止自动尝试，报告现象、已尝试方法、证据和两到三个可选方案，等待用户决定。

验证记录按同一 AC 或同一 CASE 分别计数：连续两次失败且中间没有成功核实后，`verify` 与 `check` 必须明确要求停止自动重试；同一键的成功核实清零。`check` 对任务基线后未回写规格或背景给出可定位路径和简短提纲，但不单凭此阻断验收。

### FLOW-06 处理要求和方案变化

需求、范围、验收条件或设计变化后重新计算确认对象；旧确认失效，不复用旧基线批准。无法继续时保留当前记录，不覆盖无关修改。

### FLOW-09 依据验证结果判断交付

最新验证必须通过、测试存在且未过期；工具必须实际执行声明的测试并独立核实每条验收条件的结论。套件退出码、原始输出、失败、跳过、未运行和环境限制都不能替代通过结论。外部结论默认阻断，只有理由完整且显式放行才可交付。管理多个业务仓库时，按测试所属仓库执行，不能唯一归属时拒绝，不根据文件后缀猜测语言。

### FLOW-15 在关键节点取得人工确认

需求、设计（standard）和交付验收是默认人工节点。确认对象是任务记录中已写明的结构化正文；自动保存确认部分、确认人、时间、基线和摘要，人读段用紧凑表展示，完整字段保存在机器旁路。用户原话可选，只作附注，AI 不得代写或补造。

### FLOW-24 在各环节形成测试依据并保存执行事实

需求确认后先改全局用例，再写测试和实现。测试与用例建立可扫描的稳定关联；验证可以按用例执行全部关联测试，也可以定位单个测试。每次验证保留足以复核结论与重跑的关联事实；正文只展示人读摘要，完整执行证据放在不干扰阅读的机器旁路，原始输出只在本机保存且不提交。外部结论须说明理由；缺陷修复须保留修复前的失败先行证据和当前通过证据。

## 3. 规划拆分

- 大功能可先建立规划文档，写总体目标、关联规格和条目。
- 条目包含编号、标题、`small|standard`、依赖、覆盖需求和可选子规划引用；编号稳定，依赖可多值，子规划只作指向。
- 规划确认绑定完整正文，可省略原话并记录确认人；正文或条目变化后需重新确认。
- 开工时可以挂到已确认条目并继承粒度；依赖未验收时阻塞开工。
- 规划状态列出条目状态、关联任务、未覆盖需求和阻塞依赖。规划不是默认人工节点。

## 4. 任务记录

唯一当前记录包含结构化需求、设计（标准任务）、规划归属、确认、验证和自检。需求与设计独立摘要；终态任务的自检不重复长回归或回写提示，这些提示仍在交付检查输出中。完成后长期结论同步到规格，超大设计先用规划拆分。记录不得出现密钥、token、凭据或本机绝对路径。

## 5. 提交与 PR/MR 草稿

### FLOW-29 统一提交、分支与 PR/MR 格式

交付说明需要统一且可复核：提交主题、PR/MR 标题与说明、主模块、关联任务、变更内容、验收条件和验证结果都应从同一任务事实推导，保持可读并允许人工修订。建议分支应与任务编号一致，描述已包含在任务编号中时不再重复追加；默认交付必须真正创建 PR/MR，离线预览只在显式选择时使用，格式问题只提示，不阻塞技术自检。

系统应能从任务类型、摘要、范围、验收条件状态、验证记录、设计和基线后的历史生成可人工修订的 PR/MR 草稿和建议分支。每条验收条件单独呈现并列出对应验证记录；关联任务保持纯文本可定位。默认 `pr` 在草稿生成后用 tokenized HTTPS git push 推送任务分支，并经平台 API 创建真实 PR/MR；标题、变更内容和风险仍需人工复核。

### FLOW-36 真实 PR/MR 单一交付通道

已验收且任务记录已提交后，默认交付生成五段说明、推送任务分支并创建真实 PR/MR，返回访问地址与编号；只有显式选择离线预览时才不联网。缺 token、平台解析或 API 失败时以中文错误非零退出，不静默降级；平台已有 PR/MR 时明确提示。usage、rules、AGENTS 与 CLI help 的主路径只保留验收、创建 PR/MR（平台 API）与合入，不再示范“只出草稿再手搓 API”。

### FLOW-35 PR/MR 前同步任务记录

验证、自检与相关用例或规格回写会改变交付依据，草稿不得把这些只存在于工作区的事实当作已进入任务分支。交付验收必须先于草稿完成并随任务记录提交；运行交付草稿前先提交验证记录、验收事实及任务范围内的用例和规格回写。

交付草稿无有效交付验收时阻断并提示先验收、提交记录再生成草稿；发现上述记录相对当前提交未提交时失败并列出工程相对路径，不生成五段说明，也不自动提交。仅其他任务自己的记录变脏不阻断本任务；无 Git 或无法读取工作树时只跳过记录门禁并保留提示。合入即交付完成；合入后的结束动作只清理本机，不改写共享任务记录，也不要求补验收或另作收尾提交。

## 6. 任务阶段与结束

### FLOW-25 从事实推导任务阶段

阶段顺序为已开始、需求已确认、设计已确认（small 可跳过）、已验证、已验收、已放弃或历史已关闭。阶段从记录中的确认、验证、验收和关闭事实推导，不另存状态字段；需求、设计或验证失效时显示回退后的阶段与原因。已验收任务按验收基线复查，未验收任务仍按当前工作树；已验收即交付完成，合入后的本机清理不新增共享阶段。

### FLOW-26 关闭、放弃与恢复

已验收任务在合入后清理本机状态，只删除隔离检出与本机数据，不改共享任务记录。未验收终止必须显式放弃，共享记录原因和时间；放弃仍是终态，不能继续确认、验证或验收。已验收任务再次交付可显式恢复，追加恢复事实并重新推导阶段。规划条目不把放弃任务算作进行中或已验收。

### FLOW-27 结构化正文与去原话确认

需求包含使用场景、目标、业务范围、关键行为、异常与边界、验收条件；standard 设计包含方案、失败处理、取舍、影响与风险、验证入口。模板引导业务约束与关键方案，不枚举交付路径、不展开长命令菜谱、不复制规格全文。确认需求校验关键章节实质内容；确认设计要求方案、失败处理、影响与风险和验证入口非空，取舍为空只提示。确认记录包含确认部分、确认人、时间、基线和摘要，原话可选；需求与设计分别失效。

### FLOW-28 历史任务正文

历史记录的纯文本需求、顶层验收条件和历史“范围”章节继续可读；开工前摘要只从当前任务本机旁路加载，确认只使用当前紧凑表与机器旁路。

### FLOW-30 独立评审

评审记录评审人、固定检查清单和稳定编号发现。普通发现不阻塞，阻塞发现须显式解决；存在未解决阻塞项时交付检查与验收失败。评审按需使用，不成为默认人工节点。

### FLOW-31 发布门禁

发布检查只读核对已验收、验收基线可读、项目元数据与受管资源有效、说明文档非空、包名/版本及说明版本一致、任务范围无未提交改动；非包项目跳过包项。日常自检同时返回清单，但发布未就绪不混入技术阻断。真实发布、合入和授权仍由人执行。

### FLOW-32 specs 回写提示

任务基线后没有规格或背景变化时，自检给出告警，由人判断是否为长期结论；该提示不单独阻断交付。

### FLOW-33 过薄文档与过程提示

standard 任务设计字段仅空白或占位、长期决定没有有效条目、本任务涉及模块的设计仅有标题或占位时，自检给出带路径的提示，默认不单独阻断交付。当前分支名未包含任务编号时明确提示，分支命名问题仍只提示。

### FLOW-34 任务 worktree 生命周期

start 为 Git 工程中的任务建立隔离检出，并返回任务检出根路径。本机数据以任务编号聚合到同一任务目录：检查、验证日志、本机清单与开工前摘要不再按类型分散。project 使用工程内独立任务检出；workspace 使用管理仓检出和每个已登记业务仓路径的镜像目录，各仓库使用同一任务分支。start 在创建任务 worktree 后只把任务记录写入该检出（多仓时由管理 worktree 同步到兄弟检出），primary 不留存活种子；后续命令以当前目录或显式路径命中的本任务 worktree 为任务真相，从 primary 解析且主树无记录时可回落到任务 worktree。

任务本机清单与开工前摘要只从当前任务目录读取。目标路径已占用、登记仓库不是 Git 工作副本、缺少提交或 Git 不可用时，start 失败并回滚已建检出，不写任务记录。已验收结束与放弃关闭会强制拆除该任务的全部相关检出，随后删除整个任务本机目录；检出或旁路已缺失时按幂等跳过。其他任务的本机目录保留；任务从未建立检出时仍可结束。

收尾拆除前同时探测主检出任务日志目录与各任务检出内的同编号日志目录。清理后日志已不存在时，`logsRemoved` 表示日志已清理；不得只因主检出日志目录不在而任务检出中的日志随树拆除，就固定报告 false。

### FLOW-37 任务 worktree 根幂等清理

在任务 worktree 根执行合入或收尾时，`resolveTaskCheckout` 同时解析主工程根与任务记录根：记录读写优先当前任务检出，拆树、推送与平台操作继续使用主仓。任务命令从 worktree 写入时不得静默镜像 primary；本任务 worktree 缺少记录时保持清晰缺失，不读取 primary 副本。本地任务分支在主仓和各业务仓删除，避免当前目录已随 worktree 消失而跳过；远端分支已不存在或删除请求表明已清理时安静视为成功。重复收尾对本机已清理任务保持成功；已验收收尾只做本机清理，不改写共享任务记录。

### FLOW-38 doctor 过程卫生自检

`doctor [path]` 独立扫描初始化基线的 effective 合入结论、默认分支上的 specs 脏改或未合入改动、未挂载 worktree 的残留任务分支，并提示进行中任务的 AC 覆盖缺口。基线、默认分支 specs 变更和残留任务分支属于严重项，使命令非零退出；覆盖缺口与历史数据模型别名只作 warning，不阻断。任务级 `check` 的既有门禁保持不变。

### FLOW-39 狗粮路径卫生

任务开工后，任务记录必须在本任务的所有检出中可读，写入失败不得留下半建状态。初始化基线被压缩合入或经网页合入后，启动、过程卫生自检与初始化编号收尾应复用同一套 expected head/平台合入证明：仅当 merged PR/MR 的 head 与本次 expected head 一致或祖先成立时放行，能证明已合入时只写 local marker，证据不足仍阻断。初始化成功后，主检出不保留本次创建且仍未被版本管理的受管文件，仅保留项目元数据这一最小例外，也不误删用户已修改或原本存在的文件。创建 PR/MR 后默认输出可解析的稳定机器结果；交互终端保持可读摘要，草稿预览不联网。远端任务分支已不存在时视为已清理，不提示告警。初始化变更同时保留用例空目录，并为缺失或为空的源码与测试目录加入占位文件。

### FLOW-40 传输走 Git，平台能力走 API

GitHub 与 GitLab 的 commit、分支推送和删分支使用本地 Git；GitHub 默认用 tokenized HTTPS `git push`，仅在失败时可选回退 Git Data API。PR/MR 创建、squash 合入与远端合入状态查询使用平台 REST API；引用稳定 specs 的实现任务不因未重复回写 specs 产生泛化提示，重复验收按当前工作区重新核实。

## 7. 验收方向

- 小改动可只生成一份任务记录并完成需求确认、实现、验证。
- standard 任务在设计和设计确认前不能进入实现完成态。
- 规划依赖、正文变化、范围越界和无效确认会阻塞或明确提示。
- 验证结论、外部放行和缺陷修复证据缺失时不能交付。
- 未清除评审阻塞项会阻断验收；发布清单逐项可判定，已验收任务不被后续代码漂移误伤。
- 初始化基线未进入主干时任务开始被阻断，合入或显式跳过后可继续；初始化编号清理不触碰其他任务的本机数据。


## 3. 任务引用稳定需求与验收条件（TASK-SPEC-AC）

### FLOW-SPEC-AC-1 需求来源锚定 specs
从文件接入任务需求与任务「需求来源」必须指向工程内稳定规格目录。禁止使用关闭时会清理的本机临时需求文件；若正文曾写在临时位置，须先写入稳定规格再引用。文件多行/结构化内容不得被压成单行。

### FLOW-SPEC-AC-2 任务引用 specs 验收条件
任务通过“需求来源”引用 specs 中由路径作用域区分的普通 `AC-n`，验收条件复用同一套正文；不写模块前缀或“对照”平行列表，也不另造仅存在于任务的孤立验收锚给用例使用。

### FLOW-41 合入后不变式与 PATH 单一入口

merge 或 close 结束后，primary 不得因 tiller materialize、任务种子或收尾写入出现未跟踪的任务记录目录；共享任务记录只能在合入后以跟踪文件进入默认分支。默认分支工作区无用户无关脏文件时，必须可从远端快进，不能被残留任务树或其他 tiller 临时产物阻挡。

只给单行短目标时，任务需求仍须生成使用场景、目标、业务范围、关键行为、异常与边界和验收条件，并把短目标写入使用场景与目标，达到可确认的最低完整度；结构化完整需求文件继续优先并以文件正文为准。主路径、狗粮与用例通过 PATH、`npx` 或打包入口调用同一个 tiller。提交 scope 为 specs、workflow、standards 等约定全局/工作流名称时，check 不将其误报为缺失模块；不存在的真实模块 id 仍提示。

### FLOW-42 平台结果可重建与放弃先提交

PR/MR 与初始化合入状态以平台可重建事实为准。创建任务交付前与创建结果不确定时，按 head branch 与 head SHA 查询开放记录，命中即复用，避免响应丢失后的同树重复。已验收但未合入的任务可放弃：先把放弃事件写入主检出任务记录并自动提交，再清理 worktree、本机目录与分支；无法持久化时不清理。requirement-file 保留关键行为的嵌套层级；全局 specs 任务标题使用 `specs` scope；同类非阻断检查提示合并去重。

### FLOW-43 初始化预检与显式自动合入

初始化在创建目标目录、worktree、分支或提交前确认 PATH 上可执行 `git`；Git 不可用时返回安装指引且不留下本次产物。有 Git HEAD 时再检查 origin 与平台 token，失败立即返回设置指引。只有用户显式选择自动合入时，才在 PR/MR 创建后经平台 REST API squash 合入、证明并清理、快进 primary 默认分支；任一步失败停在该步并返回续跑命令，默认初始化仍等待人工合入。
