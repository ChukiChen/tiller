# 工作推进设计

## 1. 任务模型

任务文件包含标题、一行 `tiller-task:v1` 元信息和可读区段。元信息保存 id、类型、规模、创建时间、Git 基线、范围、开工前摘要和可选规划归属。需求、AC、设计、确认、验证、自检从 Markdown 区段读取；元信息与区段都受格式校验。

## 2. 状态与确认

`confirm` 计算对象摘要：

- requirements：类型、规模、范围、需求正文和 AC；
- design：需求摘要和设计正文；
- acceptance：需求、设计、AC 验证结果、提交和代码树。

正文变化导致摘要变化，`check` 将对应确认标为失效。确认记录只接受真实提交或明确的 `no-git`；验收前必须已通过技术自检。

## 3. 验证

`verify` 接受 AC、具名测试、命令和可选 `--run`。实际执行时以退出码决定结果，并保存提交和代码树摘要；仅报告外部结果时标记 `reported`。测试引用通过 `文件::测试名` 与全局用例匹配，命中编号写入记录；测试文件不存在或结果非通过时退出非零。

## 4. 检查

`check` 从任务记录和文件系统重建状态：

- 需求/设计确认是否仍绑定当前对象；
- 每条 AC 是否有最新通过、存在且未过期的测试；
- 用例是否存在并与测试引用一致，`criteria` 是否回指当前 AC 或在本任务修改；
- 用例库结构与模块/场景引用；
- Git 范围内的越界、未提交改动、删除/跳过/弱化测试；
- 记录中的密钥和本机路径。

结果分为阻塞项、提示、逐项覆盖和可写入 `task.md` 的自检清单。`accept` 复用同一检查，防止技术未就绪时写入验收。

## 5. 范围与恢复

范围是工程相对路径集合；默认 `.`。排除任务自己的记录、`.tiller/local/`、`.git/` 和依赖目录。无 Git 时跳过依赖提交差分的检查，但保留文件级代码树摘要。写入使用统一事务，失败可用 `recover`。
