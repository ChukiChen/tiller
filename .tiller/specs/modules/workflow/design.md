## 1. 设计思路

工作围绕明确的交付目标组织，以“读取依据 → 判断可开展事项 → 执行 → 核对产物与证据 → 更新记录”的循环推进。环节之间通过输入、产物和完成条件关联，不以固定阶段序号驱动。

总体需求编写、总体设计编写、模块细化和功能开发都使用同一套机制。区别在于交付对象与检查方式：文档工作检查覆盖范围、内容对应及确认状态；实现工作还需检查实际行为；包含发布的工作还需核对发布结果。

| 参与方 | 处理内容 |
|---|---|
| 开发者 | 提供意图与授权，处理需要人工决定的问题，按约定参与验收 |
| AI 编程工具 | 澄清语义、形成需求与方案、选择下一步、实施变更和分析结果 |
| tiller CLI | 定位管理范围和工作，读取与更新记录，按模板建立产物骨架，检查引用、记录和证据关联，汇总缺口 |
| 项目已有工具 | 执行构建、测试、部署等具体操作，提供实际结果 |

CLI 使用总体设计中已确认的 TypeScript + Node.js 方案。它提供确定性操作，不负责凭空生成产品事实，也不假定具备常驻 AI 调度能力。AI 通过入口规则和适配能力调用这些操作；默认关键节点等待人工决定，阶段内自主推进，实际可强制控制的范围单独呈现。

## 2. 开始工作与接续

### 2.1 确定工作对象

1. 从当前工程入口读取管理范围、项目规则、背景、规格及已有工作索引，核对初始化可用范围。
2. 根据用户明确指定的工作或已有唯一明确的关联，选择接续；存在多个合理候选时说明差异，不仅凭标题相似合并工作。
3. 新工作先明确问题、范围及交付对象，再建立必要记录；接续工作先核对已有产出与记录，不重新生成同一组资料。
4. 按相关模块及仓库读取适用依据，记下实际使用的版本或内容标识。管理范围与操作授权分别核对。

普通讨论不强制建立工作目录。需要保存可接续的交付过程时，建立最小工作记录；已有记录能承载所需信息时直接复用。同一工作在中断和工具切换后保持同一身份，目录命名见第 3.1 节。

### 2.2 先确定本次交付

工作记录说明交付对象是草稿、经确认的规格、代码、可运行成果，还是包含发布的结果，并关联验收条件。这里描述本次目标，不建立固定的任务档位。

起草总体需求时，产品范围尚未清楚可以先澄清；尚未划分模块或业务仓库不阻止在已明确的工程范围内编写资料。必要入口不可读与产品知识待补充分别呈现，前者交回初始化或适配处理，后者由需求澄清继续补足。

### 2.3 功能分块与项目骨架

本节正式环节名称为“实施规划与任务拆分”，对应 FLOW-20、FLOW-21；保留原标题以保持已有引用。涉及代码实现时主线为“总体需求确认 → 总体设计确认 → 实施规划与任务拆分确认 → 逐任务细化必要需求与设计并确认 → 实现及即时验证 → 整体验收”。只交付规格或规划时停在约定范围，不自动启动后续环节。骨架搭建是空项目的首个普通实现任务，不另设流程阶段；已有项目先评估可复用基础。

**记录方式。** 复杂规划写入本次工作 `plan.md`，局部简单任务可将单任务简要规划直接写在 `work.md`；简化不省略展示与确认。多个工作共享规划时，以一处为主，各工作引用任务标识及自身证据，不复制维护总体状态。任务标识在计划内稳定，例如 T01；此前功能块标识仍可沿用，调整名称、顺序或接续不改变标识，拆分或合并保留原任务及替代关系。任务、模块和工作记录不强制一一对应；当前受控任务以规划中的稳定 taskId 登记，并由第 13 节的任务命令推进。

每个任务至少记录：

| 信息 | 说明 |
|---|---|
| 标识与结果 | 可独立验证的交付增量或基础能力、包含及不包含的范围 |
| 需求与设计 | 对应条目、文件及适用版本或摘要；引用已有规格，并标明尚待细化及确认的内容 |
| 涉及对象 | 模块、仓库及关联工作；任务内的技术步骤与交付任务分开 |
| 依赖与顺序 | 前置任务及必须满足的结果、外部条件、可独立推进事项；循环依赖先拆解或协调接口 |
| 产物与完成条件 | 预期成果、验证方法、通过条件及需要人工检查的节点 |
| 当前事实 | 未开始、进行中、受阻、技术验证通过等事实说明，实际产物、当场证据与剩余项；人工验收另引有效记录 |

规划同时维护需求覆盖关系，说明每项本次要求由哪些任务承担、尚未安排或细化的部分。任务太大、无法独立验证或含多个互不相关结果时继续拆分；“写接口、写数据库”等技术步骤可放在任务内，不能代替有明确结果的交付任务。

**规划确认。** 展示规划具体内容、需求覆盖、依赖、验证条件、待细化项及下一步，按第 4 节记录真实决定。当前使用 plan register 保存不可变规划定义和审阅视图，再建立 gate planning 请求，绑定定义、视图及全部规格正文，并引用覆盖范围的设计确认。有效决定取得后，plan activate 激活具体修订；登记不等于批准。可与设计一并展示，但决定须实际覆盖规划；未确认时只完善规划。内容或适用条件变化后重新核对。

**选择与推进。** 按已确认规划选择近期任务，进入实现前核对所选任务的相关需求和设计确认，以及前置任务当时的验证结果。已有足够资料可直接引用；缺口按既有需求、设计节点补足。总体设计或规划获批不批准未展示的任务细节，不要求预先写完全部任务的详细规格。已确认条件内排序、编码、测试和修复可以自主推进，不默认增加逐任务人工审批；规划指定的人工检查点仍须满足。

按“核对条件 → 实现当前任务 → 执行验证 → 即时保存结果 → 判断下一任务”的循环执行。必要验证失败、未执行或证据不足时，记录具体阻碍，不进入依赖任务；独立且条件满足的任务仍可继续。同一轮可完成多个任务，但每项验证与记录必须在依赖任务开始前发生，不能先连续实现全部范围再统一倒填。

**骨架任务。** 根据已确认技术方案及首批功能需要，按需建立目录、依赖管理、构建入口、运行配置和测试入口。实际验证构建、服务启动或库调用、CLI 执行及适用基础检查；不适用项说明原因，仅静态检查不能替代所需运行验证。骨架未验证时暂停依赖它的业务实现，独立讨论和设计可继续。已有项目核对后复用现有基础，公共组件有具体使用依赖时再建设；tiller 接入成功不表示业务骨架完成。

**证据与变化。** 每次验证后立即保存任务标识、实际时间、验证对象的版本或内容摘要、环境、执行方法、结果及未覆盖项，链接原始报告或必要输出。没有提交时可记录内容摘要，不为了生成证据擅自提交。后续产物变化须评估并复验受影响结论，历史证据保留原对象。最终整体测试只能证明其当时对象，不能倒填为早期任务通过；已发生越序时保留偏差，不把补写文档视为历史合规。

中断或并行改串行等执行方式变化后，先核对当前任务、实际产物、依赖及未结束操作。任务边界、需求覆盖、依赖条件、验证标准或人工检查点发生实质变化时，展示影响并重新确认规划的受影响范围；仅在已确认条件内调整顺序无需重复确认。任务技术通过后，整体交付仍核对需求覆盖、任务间协作与必要组合验证，不能由局部通过推断验收、合入或发布获准。

**能力边界。** 0.3.3 的基础分块规则、0.3.5 的规划环节由当前机器门禁进一步落实。CLI 保存规划修订、任务开始/接续/验证顺序，并重核当前前置事件和证据；不自动编写业务代码、执行全部测试或调度下一任务。只保证受控入口取得的数据与操作约束，不能证明宿主未绕过它直接操作。数据契约见第 13 节，真实 AI 行为另行验证。

### 2.4 项目接手与规范建立

对应 FLOW-22、FLOW-23。先判断用户目标是长期接管还是有明确范围的局部工作，不能仅因仓库存在代码就跳过整体依据检查，也不为局部修复强制补写整个产品的历史文档。

| 路径 | 输入与动作 | 产物及进入下一步的条件 |
|---|---|---|
| 已有项目调查 | 在指定仓库和模块范围读取说明、代码、配置、规则及现有工作；检查 Git 状态与基线，不修改无关内容 | 在 `context/` 维护现状与代码导航，引用来源及版本；在当前 `work.md` 记录调查范围、差异、未知项和下一步 |
| 建立验证基线 | 核对项目脚本、环境及副作用后，在授权内执行适用构建、运行和测试；沿用已有检查工具 | 在 `verification.md` 保存实际命令、目录、版本及未提交差异标识、环境、结果和证据；已有失败、未执行和条件缺失分别记录 |
| 长期接管 | 校核总体要求，缺失时从用户意图与可核对事实补足；确认需求后完善总体设计和项目规范 | 长期规格在 `specs/`，规则引用放在 `rules/project.md`；需求、设计及规范的确认覆盖本次内容，必要缺口解决后接到第 2.3 节 |
| 局部工作 | 检查整体资料适用性，说明局部范围、依赖与未覆盖部分，补足相关变更需求、设计和规范 | 当前工作引用相关依据，保留正常确认；未调查全项目不冒称整体接管完成；若局部改动影响整体契约，先协调受影响依据 |
| 新项目 | 总体需求确认后形成总体设计，同期制定适用的项目规范，可一并呈现确认 | 总体设计引用规范实际文件及版本；按第 2.3 节确认规划并安排骨架任务，进入骨架前核对确认包含规范，骨架实际运行适用检查后才允许依赖其结果的实现 |

代码观察、文档声明、推断与预期分别表达。现有代码结构可作为现状设计的事实输入，拟调整结构单独说明，不自动批准重构；从代码推断的业务意图须核实，不能把缺陷转成需求。已有有效资料优先登记引用，未知批准状态保持未知，不能为通过确认检查补造历史。

验证基线仅证明特定版本、环境和范围内的结果。后续与基线比较时记录差异，历史失败不掩盖新增回归，必要检查失败不因“历史已有”直接豁免；缺少执行条件则说明如何补足及阻碍哪些功能块。调查足以识别本次规格、规则、关键依赖、基线和未决问题时可进入相应文档工作，不要求所有历史问题先清零；依赖必要缺口的实现仍暂停。

项目规范的结构、范围和检查映射统一见[开发规范设计](../standards/design.md#24-项目专属规范的建立与检查)。规范确认可并入设计请求，将实际规范文件列为审阅对象或将具体内容纳入审阅；仅写“遵循项目规范”的链接不证明用户已审阅新规则。新内容或实质变更重新核对确认，复用仍有效的确认不另设重复节点。多仓库的共享安排与各仓库规范分别引用，验证记录逐仓库关联，不能用管理工程的检查代替业务仓库结果。

以 0.3.4 分发的共同规则、活动入口与设计模板提示实现上述衔接；现状调查、规范编写和项目检查由执行者开展，CLI 不自动扫描代码、推导产品需求、生成语言规范或运行项目检查。当前工作按固定流程定义登记 outputId 及其角色；需求、设计可使用相应文档模板，其他上下文、规则或证据按真实角色登记或引用，不因文件生成宣称完成。

## 3. 工作依据与记录组织

### 3.1 保存位置

沿用总体设计的五类目录。下列工作文件按需产生，不一次性建立整套文件；统一职责和命名见第 3.3 节，当前文档工作能力及其边界见第 9 节：

```text
.tiller/
├── specs/
│   ├── requirements.md
│   ├── design.md
│   ├── decisions.md
│   └── modules/<module>/
│       ├── requirements.md
│       └── design.md
├── rules/                         # 通用规范、项目规则及可选的自定义模板
├── context/                       # 项目事实与资料索引
├── work/<work-id>/
│   ├── work.md                    # 工作入口、目标、产物索引、进展与决定
│   ├── record.json                # CLI 登记的产物与状态，禁止手工编造
│   ├── requirements.md            # 本次变更需求，需要时创建
│   ├── design.md                  # 本次变更设计，需要时创建
│   ├── plan.md                    # 较复杂的任务与验证安排
│   ├── verification.md            # 测试、评审及验收依据
│   ├── confirmations.json         # 按需创建的确认请求、决定及关联；不是身份凭证
│   └── delivery.md                # 发布、交接与反馈关联
└── local/                         # 本机执行信息，不能作为唯一共享证据
```

新建工作目录推荐 `YYYYMMDD-主题`，例如 `20261015-student-service`。日期取工作创建日，接续、修改内容或切换工具不改变目录名。CLI 接受显式带日期的工作标识及原有不带日期的标识，不自动补日期，也不自动重命名历史工作。模块目录继续使用稳定能力名称，不加日期。

总体或模块的长期规格位于 `specs/`。当前 CLI 可以在工作目录生成草稿，进入长期规格时人工协调单一来源；当前 output 登记可直接关联已有规格，不复制正文。修改已有规格且方案尚未接受时，在工作需求或设计中描述差异；被接受并交付后更新长期规格，迁移保留内容并修复入口，不以本文的长期目标冒充已实现自动迁移。

简单工作的计划、检查结果与交接说明可以合并到 `work.md` 的相应部分；需求与设计保持分开，已有适用规格以引用代替重复文件。工作记录本身可以作为文档编写任务的过程记录，不能代替被要求交付的总体或模块文档。

源码、测试代码、配置和发布包留在项目约定的位置，工作资料只索引产出。多仓库工作使用一个共同工作记录，按仓库标识关联各自成果，不把各仓库源码复制到管理工程。

### 3.2 逻辑信息

| 信息 | 内容与作用 |
|---|---|
| 工作说明 | 目标、范围、交付对象、验收条件与适用授权；界定何时算本次完成 |
| 依据引用 | 规格位置、需求编号、规则及对应版本；说明执行时采用的依据 |
| 任务安排 | 事项、归属、前置依赖、预期产物和检查方式；识别当前可开展事项 |
| 产物索引 | 类型、实际位置、关联要求、内容标识、适用性与确认状态；区分已有、待补充、待产生及不适用 |
| 证据记录 | 被验证对象、环境、检查内容、执行结果、证据位置和限制；支撑完成判断 |
| 决定与变化 | 决定内容、来源、时间、适用范围及变化影响；复用授权并识别失效条件 |
| 当前进展与历史 | 已完成、进行中、阻碍、未结束操作、下一步及关键变化经过；支持中断恢复 |

Markdown 保存可读内容，稳定的索引信息使用结构化元信息。人工确认记录见第 4.4 节，其余完整工作模式仍按 Q8 细化。`work.md` 保存目标、进展和下一步的可读摘要，确认结论从确认记录及实际来源核对得到，摘要中的“已确认”不作为另一份事实源。

版本引用优先使用可定位的仓库版本；未提交内容使用文件内容摘要或可保留的快照标识，并同时记录对象范围。只记录分支名、当前文件路径或“测试通过”不足以证明历史结论适用于当前产出；不为取得版本标识擅自提交代码。

### 3.3 工作入口与产物约定（已实现）

本节定义对应 FLOW-16 的结构，按第 9 节固定流程声明逐步创建或引用产物；历史资料只读检查，旧机器契约拒绝且保留原件。

| 文件或对象 | 职责 | 创建与维护约定 |
|---|---|---|
| `work.md` | 唯一可读工作入口，包含目标、范围、依据、产物链接、进度、待确认项和下一步 | 新工作必需，由创建操作提供骨架，执行者持续更新实际过程 |
| `requirements.md` | 本次需要编写的需求草稿 | 按需由创建或补充操作生成；已有适用需求则登记引用，不复制正文 |
| `design.md` | 本次需要编写的设计草稿 | 对应需求有效确认后按固定流程声明补充，必要时先转换流程；创建不表示设计已批准 |
| `record.json` | 工作意图、固定流程、当前代际、按 outputId 登记的产物及依赖关联 | 由 CLI 创建和维护；不手写、补猜或用 Markdown 状态代替 |
| `confirmations.json` 与 `reviews/` | 实际确认请求、决定、来源及内容快照 | 沿用第 4.4 节，按需由确认操作维护，接续不重建历史 |
| `plan.md`、`verification.md` 等 | 详细过程和证据 | 按实际需要创建；计划、进展、检查摘要、交接说明可合并到 `work.md` |
| `README.md` 等补充材料 | 导航或说明 | 允许存在，不能替代工作入口及所需需求、设计；文件存在本身不算违规 |

新写需求和设计分别使用上述名称；其他产物按流程声明角色与明确路径组织，不要求所有类型都生成需求和设计。既有规格保留原位置和名称，通过带仓库身份的明确引用登记；引用不能让同一混合正文同时承担需求和设计，也不能把工作入口登记为阶段产物。是否覆盖所需语义仍由实际评审判断。阶段验证和交付判断仍需要适用的独立证据；过程检查摘要合并到 `work.md` 不意味着它可绕过现有自证限制。

规则正文集中维护在 `resources/rules/core.md` 的“工作记录约定”小节；入口直接写出最少命名与创建要求并链接该小节，规则索引明确开始及接续时必读。需求、设计、质量规则引用该约定，不各自定义另一套命名。只要求为本次活动创建必要产物，不预先生成全部模板。

适用的创建和登记能力可用时必须使用对应命令。命令不可用或所需操作未支持时，先记录具体限制及人工处理范围；必要时按命名约定维护 `work.md` 和实际文档，但不手写 `record.json`，不宣称已登记、自动检查通过或用户已确认。已有目录不能靠新建同名工作覆盖；当前有效记录可以接续，不支持的记录保留原位并另建当前工作引用适用正文。

## 4. 推进机制与状态判断

### 4.1 每轮推进

| 步骤 | 处理方式 | 产生的结果 |
|---|---|---|
| 核对依据 | 比较范围、规则、授权及输入产物是否仍适用 | 可用依据、待澄清项和失效引用 |
| 选择事项 | 从尚未完成的任务中筛选依赖已满足、适用确认有效、授权有效且无阻碍的事项 | 可执行事项或具体阻碍；未确认时只完善当前草稿或推进独立已授权事项 |
| 准备产物 | 查询产物索引，优先复用，缺少时按适用模板起草 | 新增、引用、待补充或不适用的处理结果 |
| 执行与检查 | AI 或项目工具开展工作，收集实际结果并核对完成条件 | 实际产出、验证依据与发现的问题 |
| 保存与继续 | 更新当前进展、问题和下一步，再次判断依赖 | 下一轮工作、待人工处理事项或交付判断 |

模板生成结束只进入内容编写或检查，不直接满足任务完成条件。依赖未满足的事项保持等待；其他独立事项可继续。没有新的依据或处理措施时不反复执行同一失败操作。

### 4.2 分别表达不同状态

避免把所有情况压缩成一个“阶段”。以下名称是候选语义，不是已确定的存储枚举：

| 对象 | 表达方式 |
|---|---|
| 整项工作 | 进行中、受阻、暂停、终止、完成；同时列出部分完成范围 |
| 单项任务 | 未开展、可开展、进行中、待核查、已完成，或具体阻碍 |
| 文档与其他产物 | 是否存在、是否适用、是否需补充，以及内容是否已确认分别记录 |
| 验证 | 未执行、通过、未通过、无法确定；独立标记证据是否仍适用 |
| 人工确认 | 待确认、已确认、拒绝、有条件、待复核、失效；另行呈现来源核对结果 |
| 发布 | 未执行、执行中、成功、部分成功、失败、结果未知 |

整项工作在有独立事项可推进时保持进行中并呈现局部阻碍；没有可推进事项且仍有必要工作时为受阻。用户暂停或终止时停止发起对应范围的新操作，记录无法立即停止的操作及后续核对方式，不默认回滚。

“完成”只在约定交付、必要验证、用户验收及资料同步均满足后成立。检查完成但待用户验收时显示待验收。草稿交付被接受后，文档编写工作可以完成而文档仍为讨论稿；接受草稿交付不自动确认规格。终止与受阻不能转译成验收通过；恢复由明确的继续意图触发，重新核对当前条件。

### 4.3 关键节点与进入条件

每项工作按交付范围建立确认依赖，不将整个产品锁在单一阶段。设计确认只满足实现的规格条件，进入任务还须核对活动 planning 确认、详细规格、必要规范、依赖和约定检查点。

| 节点 | 绑定的审阅对象 | 控制的后续动作 |
|---|---|---|
| `requirements` | 相关需求正文、范围、关键行为、验收条件及未决项 | 进入对应设计；起草和修订需求本身不受该节点阻止 |
| `design` | 对应需求引用、方案、接口与数据约定、影响及验证安排 | 编写对应代码、配置和测试；已确认范围内的修复与验证无需逐操作确认 |
| `planning` | 不可变规划定义、审阅视图及所引用规格 | 激活明确修订，不自动开始任务 |
| `checkpoint` | 任务或整体操作、检查点定义摘要及实际对象 | 满足相应 start/verify/delivery-ready 人工条件 |
| `exception` | 操作身份、具体未满足条件、当前摘要、理由、允许动作及失效条件 | 有限放行列出的可豁免条件，技术失败仍保留 |
| `acceptance` | 实际交付清单、版本、验证证据、缺口及限制 | 标记对应交付已验收；不隐含发布授权 |
| `merge` | 指定仓库的评审请求、源提交、目标分支及提交、依赖组合、检查与评审结论 | 合入该组具体变更；不代替验收或发布，细则见第 11 节 |
| `release` | 已验收产物、版本、环境、影响及失败处置 | 发起对应发布；发布结果仍需实际核查 |

确认前先展示产物链接、核心内容、待决项和确认后的下一步。用户可以批准、拒绝或提出修改；修改先回到当前环节。有条件决定必须保留条件，涉及尚未确定的新业务选择时继续澄清，不能当成无条件批准。只交付需求草稿时，不创建无关的设计和发布请求；草稿交付验收与需求内容确认分别记录。

下一步成立需要同时满足：输入有效、适用确认有效、操作仍在授权范围内、必要质量条件满足。一般“开发这个功能”不满足具体确认；“继续”仅在上下文明确指向已展示的确认事项时记录为该事项的决定，不覆盖之后尚未呈现的设计或交付。

### 4.4 确认记录与来源

在工作目录按需创建 confirmations.json，严格采用第 9.2 节的当前契约，并绑定固定流程、工作意图及适用阶段；旧格式保留原位并拒绝推进。请求、决定和来源快照追加保存，更正、撤销和替代保留历史。派生状态每次重算，文件中的状态文字不能直接放行。

| 信息组 | 字段及用途 |
|---|---|
| 请求身份 | `requestId`、`gate`、`workId`、`scope`、`createdAt`；范围含目标仓库、模块或需求标识 |
| 审阅对象 | `subjects` 保存仓库身份、相对路径、SHA-256 内容摘要；`upstream` 保存依赖的确认请求及内容标识 |
| 展示内容 | `reviewSummary`、`openIssues`、`nextAction`；明确这次确认什么、哪些问题仍未解决 |
| 用户决定 | `decisionId`、`requestId`、`outcome`、`conditions`、`decidedAt`、`recordedAt`；区分实际决定时间与录入时间，未知时间不伪造 |
| 来源依据 | `source.kind`、`source.reference`、必要的用户原话及对应展示内容引用；记录实际用户输入或由人核对的外部来源，不收集无关对话 |
| 来源复核 | `sourceReview` 记录实际核对者、所读用户输入、对应展示内容、范围解释及核对时间；`sourceVerification` 单独表示程序是否独立认证来源，不由复核者自称认证 |
| 变更与例外 | 被替代或撤销的事件、影响说明；例外另列适用节点、范围、允许动作及终止条件 |

摘要计算采用文件原始字节，路径按仓库身份解析并检查管理范围；多仓库对象分别记录。目录或批量产出使用明确的文件清单及各自摘要，不能只散列目录名。被审阅内容需有可追溯的提交或共享快照；未提交文件可保存到本工作的 `reviews/request-<requestId>/`，不为此擅自提交。当前文件变化不能重写旧快照，内容摘要只证明内容一致，不证明批准来自人。

AI 可以代为记录真实用户决定，但记录者不等于决定者。纯本地 CLI 无法仅凭 `--actor user`、终端交互、用户原话文件或 `approved: true` 证明操作者是人；这些输入只能成为待核对的来源说明，不提供自动放行的凭证。

来源核对分两种路径：当前对话由执行者直接核对真实用户消息与已展示内容，并如实记录这次核对；跨工具接续则需能读取并核对原用户输入，或由用户重新确认具体内容。无法取得来源时显示 `source-unverified`，不能只凭先前 AI 写下的“已确认”继续。用户重新确认产生新事件，不倒填成先前批准。

正常对话采用“人工决定、执行者核对、工具保存”的路径。执行者只有实际读取到用户输入和审阅对象后才可填写 `sourceReview`；CLI 可以保存这项复核及对应验收结论，标记依据为 `reported-review`，同时保持 `sourceVerification: not-independently-verified`。这表示记录了经过执行者核对的决定，不表示程序证明了来源身份。只有独立适配核验成功才可标记 `verified-source`，作为无人值守转换的来源依据。CLI 不能识别同权限执行者伪造整套复核证据，须始终报告这一边界。

将来宿主适配若能从 AI 不可伪造的渠道取得用户决定，可提供独立的来源核验。核验器由已配置的适配能力选择，不能由工作文件声明自己可信；离线核验或跨宿主核验不可用时明确降为来源待核对。该能力尚未实现，本设计不假设所有宿主都支持。

### 4.5 有效性、变化与例外

| 当前事实 | 派生状态与处理 |
|---|---|
| 已展示请求，无对应决定 | `pending`：保留草稿和待确认事项，不继续依赖工作 |
| 用户拒绝 | `rejected`：根据反馈修订；新请求关联原请求，不覆盖拒绝事实 |
| 附带条件 | `conditional`：条件逐项关联证据，满足且来源有效后才可推进获准范围 |
| 决定匹配且来源已核对，内容、范围和上游均有效 | `confirmed`：流程上可满足对应依赖；同时呈现 `reported-review` 或 `verified-source`，不把执行者复核当作程序认证 |
| 内容或来源无法核对、规则变化影响不明 | `needs-review`：输出原因，暂停依赖动作；原决定保留 |
| 已知实质变更、明确撤销或适用范围被替代 | `invalidated`：受影响部分重新提请确认 |

摘要变化先触发待复核，不能仅靠摘要判断业务含义。需求行为、验收标准、设计接口或发布对象等实质变化生成新请求，并沿依赖传播到相关设计、实现与交付判断；未受影响范围可继续。只改错字或排版时，可以追加复核事件，关联前后内容、差异和理由，继承原决定，不能静默替换摘要。纯 CLI 不做语义批准；复核依据不足时继续等待。

合并展示须对实际覆盖的确认对象分别保存真实决定；当前没有按工作类型或 `small` 标签自动省略确认的通用授权。已支持的操作例外按第 13 节绑定具体条件与动作，不能将其扩大为任意节点委托。合并展示仍须保持需求与设计分开；若需在需求确认前准备候选设计，必须先有允许这样做的明确授权。撤销或范围变化后重新判断例外，不能把一次例外写成全项目默认豁免。

### 4.6 写入、接续与越过节点后的处理

创建请求、追加决定及检查均读取当前对象；写入前在同一工作锁内复核记录修订号和文件摘要，变化则返回冲突，不关联到旧请求。采用完整文件替换，失败保留原记录；跨文件操作中断时保留未完成结果。幂等性由请求及事件标识判断，重复输入不能生成多个批准或重复触发发布。

接续先读取工作范围与适用规则，再核对请求、决定来源、当前对象和上游依赖，给出可继续事项、待确认节点及原因。缺少确认文件不视为已确认；`work.md` 与机器记录冲突时先报告并核实，不按较新的“完成”字样选择事实。

已存在越过节点的代码时保留现场，记录已发生的变更和缺少的确认，停止继续相关实现；必要时只开展已授权的现状核对。把现有内容交给用户审阅后取得新决定，不制造“编码前已经确认”的历史。继续讨论或保存失败记录不应被关卡阻止。

## 5. 产物与模板设计

### 5.1 组织与选择

模板由开发规范提供，工作推进依据产物类型、层次及本次目标选择。模板是编写指引和骨架，不是完成后的项目文档。规范定义必要信息和检查要求，模板定义建议章节与填写提示。

规则读取、触发动作及产物质量检查见[开发规范设计](../standards/design.md)。工作推进使用这些依据，不自行维护另一套质量标准；本节保留模板结构与产物位置的映射。

当前文档模板由随包资源提供；工作流程定义与文档模板分开，按 outputId 对应角色选择模板或引用真实正文。模板只是骨架，不替代流程、确认或完成证据。工程资源更换仍走初始化升级的预览、冲突检查及原件保护，不迁移工作记录。精确当前安装与资源契约的收口属于待验证 T7，不承诺旧资源或任意更高版本兼容。

项目自定义模板目录、规范模板接入及模板优先级仍为候选，不能当作当前已实现读取行为。未来若采用，仍须保留来源、版本及必要内容检查；现有文档正文可以继续明确引用，缺少必要信息时补足，不能凭模板优先级豁免要求。

### 5.2 模板目录与产物映射（候选）

下表给出完整产物的模板文件名及结构建议。当前已实现的六类文档模板及草稿位置见[首个交付实现约定](../../../work/initial-delivery/design.md)，其他产物模板尚未实现。目标位置相对于管理工程或目标业务仓库，`work/` 和 `specs/` 均指 `.tiller/` 下相应目录。

| 产物 | 候选模板文件 | 建议内容结构 | 目标或引用方式 |
|---|---|---|---|
| 初始化结果 | 由初始化模块提供 | 范围、入口、可用性、缺失项、下一步 | 引用已有接入结果，不重复创建 |
| 工作说明与澄清记录 | `work.md` | 意图、范围、交付条件、依据、待决问题、产物索引、进展与下一步 | `work/<work-id>/work.md`，简单过程记录可合并其中 |
| 总体需求 | `product-requirements.md` | 定位、问题、场景、范围、核心需求、约束、验收方向、详细需求索引 | `specs/requirements.md` |
| 总体设计 | `product-design.md` | 需求依据、总体思路、主要构成、职责与协作、关键方案、约束、详细设计索引 | `specs/design.md` |
| 模块需求 | `module-requirements.md` | 总体关联、目标、场景、使用过程、功能需求、验收条件、边界 | `specs/modules/<module>/requirements.md` |
| 模块设计 | `module-design.md` | 需求依据、方案、处理流程、接口与数据、异常与恢复、验证对应 | `specs/modules/<module>/design.md` |
| 单次变更需求与设计 | `change-requirements.md`、`change-design.md` | 分别描述行为变化与方案变化，关联规格版本、影响范围及验证要求 | `work/<work-id>/requirements.md` 与 `design.md`，不复制完整规格 |
| 实施规划与任务拆分 | `plan.md` | 任务标识、需求覆盖、范围、依据、依赖、完成条件、待细化项、规划确认与逐任务证据，见第 2.3 节 | 较复杂工作人工维护 `plan.md`，单任务可合并到工作入口；当前没有对应模板创建命令 |
| 实现成果与变更说明 | 不提供统一代码模板；说明并入工作记录 | 代码或配置引用、需求对应、影响与剩余内容 | 成果遵循项目目录与技术栈，工作中保存引用 |
| 测试安排与结果 | `test-record.md` | 要求与对象、用例或检查项、环境、预期及实际结果、未覆盖项 | `verification.md` 的测试部分，测试代码引用项目位置 |
| 评审记录 | `review-record.md` | 对象与范围、意见、问题处理、复核与剩余风险 | `verification.md` 的评审部分，必要时独立记录并索引 |
| 验收记录 | `acceptance-record.md` | 约定范围、逐项结果、证据、缺口、取舍决定与结论 | `verification.md` 的验收部分，关联对应产出 |
| 发布安排与结果 | `release-record.md` | 对象与环境、前置条件、授权、失败处置、执行记录、结果确认 | `delivery.md` 的发布部分，仅在适用时使用 |
| 交付说明 | `handover.md` | 成果及版本、验收依据、发布情况、使用与运行信息、遗留事项 | `delivery.md` 的交接部分，引用实际交付物 |
| 运维反馈与改进 | `feedback.md` | 原交付、问题与影响、证据、处理决定、后续工作及结果 | 关联原交付记录；需新工作时在新工作中保存处理过程 |

每个模板附带用途、适用条件、必要信息、可省略内容和检查提示。身份、依据及确认状态放在共同说明中；实际字段格式待 Q8 确定。记录型模板可作为同一文件的不同部分使用，不因模板数量产生等量文件。

### 5.3 生成、复用与更新

1. 先检查目标是否已存在及是否适用；符合要求则登记引用，需要补充则形成局部修改，不能覆盖已有人工内容。
2. 新建时只填入已有事实和可确认的引用。待定问题明确标记；执行结果、评审结论和通过状态不得由模板预填。
3. AI 根据实际任务编写内容，检查必要信息与上下游关联，再更新产物索引。自动检查存在与格式，语义完整性由评审判断。
4. 模板更新只影响后续选择或明确的迁移工作。已生成文档属于项目内容，不自动重新生成；新规范要求产生的缺口以待补充项呈现。

起草总体需求和设计时分别写入对应文档，总体只引用已经形成的模块资料。模块细化发现总体冲突时，先记录受影响要求与方案，再按决定更新相关资料和引用。仅起草候选方案不意味着自动接受或进入实现。

## 6. 变化、恢复与跨仓库协作

### 6.1 变更影响传播

用“需求 → 方案 → 实现 → 证据 → 交付”的引用关系查找变化影响。某个对象变化后，将依赖它的结论标为需要复核，记录变化原因和涉及对象；确认未受影响的结果可继续复用，无法判断时不维持原通过结论。

先明确变更范围与适用授权，再更新任务、产物及验证安排。过去的证据仍保留原对象与结论，新验证产生新记录，不把历史失败或旧版本通过直接改成当前通过。长期规格同步后保留工作与交付版本的关联。

### 6.2 中断恢复与写入协调

恢复时依次核对工作入口、实际文件内容、未结束操作和外部结果。已完成且依据仍有效的事项复用；已写文件但未登记时核实后补记；实际内容与记录冲突时说明差异并协调处理。

候选采用写入前比较所读版本、单文件完整替换及分步记录，避免按旧内容覆盖其他参与者修改。多个文件和仓库不假定能整体原子更新；中断后的部分完成保持可见。共享进展需协调单一写入者或检测并发冲突，锁只能辅助协调，不能代替内容比较。

测试失败先记录问题，再按原因调整实现或检查安排；环境未改善且没有新措施时停止重复尝试。暂停或终止后保留实际产出和未结束操作，不删除工作历史。记录无法保存时直接报告，不能声称已具备完整恢复依据。

### 6.3 跨模块与跨仓库

在同一工作中按模块及仓库登记任务、前置依赖、适用授权和产物引用。可独立开展的事项不因其他仓库受阻而全部停止；依赖失败仓库或接口未明确的事项不能推进为完成。更新共同文件的并行任务需明确写入责任，发生冲突时先协调。

整体验收同时检查各仓库结果与协作效果，并记录组合使用的各仓库版本。仓库各自通过而协作验证失败时，整体保持未完成。源码不自动迁移，仓库不可访问也不静默从交付范围移除。

## 7. 验证、发布与完成

### 7.1 证据与完成条件

验收记录按本次要求逐项关联实际产物、适用证据和结论，区分已满足、未满足、未验证及不适用。每项必要检查说明覆盖范围，不能用文件格式检查代替行为测试，也不能用局部测试通过代替全部需求满足。

文档任务检查约定内容、需求与设计对应、有效引用、确认状态及未决问题。允许草稿包含待讨论选择，但本次承诺覆盖的内容缺失时仍为未完成。实现任务使用项目工具产生结果，报告检查环境与证据对应版本；修复后的对象按影响重新验证。

完成检查汇总交付范围、必要产物、验证、待决事项、发布结果及规格同步情况。技术检查具备条件后形成验收请求，未获用户接受时保持待验收。阻碍交付的问题保持阻碍；非阻断遗留项说明理由、处理归属与后续安排，需用户接受的取舍关联实际决定。不得自行降低验收条件来得到通过结论。

### 7.2 发布与结果核对

发布前核对目标产物与已验证、已验收对象一致，取得绑定具体产物、环境和失败处置的发布确认。临近执行再次核对内容和前置条件；变化则重新判断确认有效性，不能复用一次批准任意重复发布。先记录操作意图和可核对的标识，再交由已有发布工具执行，结果记录与操作对应。

执行中断或结果未知时，先查询目标环境或外部操作结果；无法可靠确认时保留未知并阻止盲目重试。发布工具支持幂等标识时可复用，不能假定所有发布系统都具备该能力。继续、恢复与回退分别核对权限及实际结果，部分成功不汇总为全部成功。

未包含发布的工作交付约定成果，并标明未发布与后续条件；包含发布的工作必须取得必要的结果确认后才可完成。

### 7.3 交付与后续反馈

交付说明关联实际成果、验收依据、发布情况、必要使用或运行资料，以及遗留事项；同步受影响的长期需求、设计和项目知识后保存完成结论。

后续反馈引用原交付版本，记录问题、影响和处理决定。新处理形成关联工作，不改写原验收记录；若原结论确有错误，追加修正理由与新依据。是否继续原工作或建立新工作按范围和用户意图判断，不把所有反馈自动扩展为已获授权的开发任务。

## 8. 初始化与其他部分的衔接

| 相关部分 | 工作推进读取的内容 | 返回或更新的内容 |
|---|---|---|
| 工程初始化 | 管理范围、入口、资料引用、可用性及资源版本 | 缺少入口、无法访问或兼容性问题；不把具体工作进展写成初始化状态 |
| 开发规范 | 产物要求、模板、质量条件及操作边界 | 实际采用版本、缺口及自定义冲突，不自行放宽规则 |
| 项目记录 | 规格、背景、既有工作和历史 | 当前进展、产物引用、决定、证据及长期资料同步 |
| 验证与反馈 | 检查结果、评审意见及其适用范围 | 待验证对象、问题处理和复验请求，接收结果后判断下一步 |
| 工具适配 | 当前工具可读取的入口及可调用能力 | 需要执行的操作与实际限制，不建立另一套进度事实 |

初始化只需让新会话能找到范围、规则、已有资料和工作入口；没有总体或模块规格时，下一步可以是编写这些资料。模板资源可以可读取而尚未实例化，初始化不预先填满工作文件。

初始化接入验证在目标工具的新会话中实际验证入口、适用依据及下一步可读取，多仓库时还需验证相关仓库资料可达；工作推进验收检查能否真正澄清、产出、恢复及交付。二者分别保留证据，不互相替代。独立管理工程尚未关联仓库时能否报告初始化完成，仍由 Q15 决定；这不妨碍在已明确的资料编写范围内开展讨论。

## 9. CLI 能力与验证安排

### 9.1 按类型选择与固定流程

当前实现对应 TW-01～TW-07；批准来源、逐任务证据及待验证项以[按类型推进工作](../../../work/20261020-typed-workflows/work.md)为准。此处记录实现契约，不将 T7 尚未完成的安装与资源收口、真实 AI 行为、整体验收或发布标为通过。

内置类型为 `requirements`、`analysis`、`research`、`feature`、`bugfix`、`improvement`、`review`、`validation`、`documentation`、`migration`、`operations`。流程是有界 JSON 数据，声明适用范围、阶段、依赖、产物、确认及完成条件，不执行任意脚本。影响事实为 true、false 或 unknown；缺失或未知影响不作为省略必需步骤的依据。

`workflow list|show|check` 读取和检查定义；`show` 可用 `--revision <version>` 选择版本。项目扩展使用 `project.*` 标识，不能覆盖内置标识。候选定义存在不表示可采用；`workflow register --input <file> --plan|--apply <plan-id>` 比较基线、变化和所需确认后启用具体版本。放宽确认、增加动作或改变完成条件须核对精确变化及真实授权，不能借项目定义扩大权限。

`work create <id> --title <title> --workflow <id> --input <file>` 必须显式选择流程，并与输入一致。输入登记 operationId、expectedRevision:0、workflow、可选 workflowVersion、goal、reason、scope、impact、basis、actionSources、expectedOutputs、completionCriteria 及可选 level。动作来源必须真实可读、内容匹配且在工作范围内；登记来源不认证人的身份。创建保存工作入口、记录及 `workflow/definitions/<digest>.json` 固定定义快照，不预填所有阶段文档。目录重名拒绝覆盖，目录中的工作不随目录外候选定义修改而静默升级。

### 9.2 当前记录、产物与确认

当前机器格式严格区分各自版本，不用单个版本号代表所有文件：

| 对象 | schemaVersion |
|---|---|
| 工作 record.json、确认 confirmations.json | 4 |
| 流程定义、阶段 state.json、规划定义、任务记录 | 1 |
| 验证运行、Git 交付 delivery.json、整体 delivery-ready 回执 | 2 |

工作记录保存固定 workflow 的 id/version/digest/path、工作意图、影响及来源、artifacts、links 和操作历史。普通 revision 与 workflowRevision 分开：后者标识当前流程代际，不能因普通产物或关联修订把有效阶段冒认为另一代，也不能把旧代事件用于新流程。

`work add <id> --input <file>` 与 `work output add <id> --input <file>` 接收 operationId、expectedRevision、outputId，以及 source、content 或 template 中的一种和适用 confirmationRefs。outputId 必须属于固定定义；产物按声明角色登记来源、摘要和 origin，不再限定整个工作只能有一份需求和一份设计。引用不复制或改写原文；生成内容仍受文档角色与必要确认约束，不通过文档接口执行代码。新写需求和设计保持分开，登记成功不表示内容已批准。

确认请求携带 workflowBinding，绑定 workflowDigest、intentDigest 及适用 stageId，并按动作核对 scopeBinding、operationBinding、documentBinding 或交付绑定。请求、决定、审阅快照、来源复核和撤销事实追加保存；当前有效性重新计算。`work request-confirmation`、`work record-decision`、`work check-gate` 保留明确对象与来源边界，reported-review 仍表示执行者报告复核，sourceVerification 不因此成为独立身份认证。文档验收绑定具体正文及证据，不自动批准其他产物、软件整体验收或发布。

### 9.3 阶段、转换、依赖与当前格式边界

| 入口 | 当前行为 |
|---|---|
| `work workflow inspect <id>` | 返回固定流程、选择依据与当前意图，不执行后续阶段 |
| `work stage status <id> [--stage <id>]` | 按当前代际核对适用阶段、前置、产物、确认及当前证据 |
| `work stage start|resume|verify <id> --stage <id> --input <file> --plan|--apply <plan-id>` | 绑定控制修订与 attempt，保存真实开始、接续或验证事实；命令不替代实际实现与验证执行 |
| `work workflow change <id> --input <file> --plan|--apply <plan-id>` | 比较旧新意图、定义、产物映射及授权，保存旧记录与转换回执后进入新代际 |
| `work workflow links <id> --input <file> --plan|--apply <plan-id>` | 显式登记跨工作阶段产物依赖，并检查范围、引用和循环 |
| `work workflow dependencies <id> --stage <id>` | 只读重核生产者当前结果及消费阶段的依赖适用性 |
| `work inspect|check|resume <id>`、`work inspect --all` | 检查当前结构或呈现不支持记录的原因；resume 不自动执行下一阶段 |

阶段事件带 workflowRevision，验证必须对应同代际、同阶段的实际开始及 attempt。需要规划任务的阶段委托第 13 节已有机制；只读分析等阶段按自己的声明完成，不强制开发任务。当前所需前置失败、过期或未执行时阻断依赖，独立有效结果仍可使用，不能由最终通过补造较早开始或验证事实。

转换绑定预览所见控制状态、workflowDigest、changeDigest 及 mappedOutputs，保留 `transitions/<operationId>/from-record.json` 和回执。新增能力与弱化条件重新核对真实确认，旧确认不因产物映射自动跨代授权；旧 links 不自动带入新流程，既有预览需要重做。历史阶段和任务记录保留，当前判断只消费与新意图、代际及实际委托相符的事实。

关联明确 consumerStageId 与 producer 的 workId、workflowRevision、stageId、outputId，并绑定生产者 attemptId、eventSequence、source 和 SHA-256。不存在的阶段、越界引用、循环及生产者变化不能被忽略；重新检查应使受影响消费者失效或受阻，不自动回滚其他工作已经发生的外部操作。

`--type` 创建/补充、`work bind`、`work complete`、requirementsBasis 和旧格式兼容写入不属于当前接口。无登记目录只读呈现结构缺口；旧版本、未知字段或不完整当前记录拒绝并保留原件，不采用旧完成标记、不自动迁移或补写批准。需要新流程时另建当前工作，按 outputId 明确引用仍适用正文并取得当前所需确认。工程资源 upgrade 不迁移工作记录。

### 9.4 验证、交付与受控边界

`verification run <id> --suite <id> --input <file> --plan|--apply <plan-id>` 必须携带 workflow 上下文；外部观察先 capture，record 使用实际 captureId 登记结果与证据，不能观察后重新采集当前对象冒充过去结果。workflow 明确 stageId、可选 taskId、actions、confirmationRefs 及适用 operationBinding，证据绑定工作、固定流程、意图、阶段及真实开始事实。任务消费者必须匹配实际 taskId 和工作所有者，不能把无任务阶段观察当作任务证据，也不能将任务验证冒作独立阶段验证。报告核对最新结果及当前输入，失败、过期或未执行不能退回旧通过。

`delivery-check` 汇总固定流程所需阶段、产物、当前验证及适用规划任务；`delivery-ready` 输入绑定 work/stages/tasks 控制快照，预览、写前和写后重核后保存回执。技术就绪、过程证据、操作允许、用户验收与发布分别呈现；只报告或只交付需求的工作按自身完成条件结束，不要求无关代码、PR 或发布。涉及 Git 的实际动作仍遵循第 11 节精确对象与授权。

读写操作分开，路径按工程与仓库身份解析，检查普通文件、共享可见性、大小和摘要；计划、CAS、工作锁及写后重核保护受控写入，失败保留原件、外部修改和恢复事实。历史幂等回执明确未重评当前有效性。CLI 不能阻止同权限宿主直接修改文件或执行外部命令，内容摘要和 reported-review 不能证明人的身份；不宣称全局自动编排、来源认证或全局操作拦截。

记录逻辑、CLI 集成、真实 AI 接续、项目工具协作与安装后闭环分别保留实际证据。T7 目标为 CLI、包与资源精确 0.5.0 当前契约，移除最低版本或任意更高版本可兼容判断；这项尚待正式验证，不影响既有固定管理环境，也不把未运行平台或未执行场景报为通过。

## 11. 隔离开发与评审合入

本节对应 FLOW-17 至 FLOW-19，方案已按实际确认在 0.3.0 实现，0.3.1 补充分组仓库路径支持。实现包含环境准备、Git 交付操作、合入条件检查及恢复清理，不代表自动合入可用或已获交付验收；当前平台适配不能原子保护源和目标，拒绝自动合入。验证边界见[隔离交付验证](../../../work/20261015-isolated-delivery/verification.md#实现验证记录)，当前整体范围见[实现进度记录](../../../work/20261016-implementation-progress/work.md)。

### 11.1 管理方式与工作身份

使用初始化记录中的 `project`（当前工程集成）或 `workspace`（独立管理）方式，不按本次涉及仓库数量推断。每项工作关联稳定的仓库标识、仓库角色、基线提交、开发分支、目标分支和评审对象。独立管理中的管理仓库与业务仓库是不同角色，即使都使用 Git，也分别交付。

主目录是最初登记的工程位置，活动目录是本项工作当前允许写入的 checkout。一个工作同一时刻只有一个共同记录的写入位置；不同分支保留的历史副本不是第二份活动记录。创建隔离环境不自动切换或清理主目录，也不影响其他工作。

### 11.2 两种目录与资料归属

当前工程集成使用以下布局：

```text
my-project/
├── .git/
├── AGENTS.md
├── src/
└── .tiller/
    ├── specs/、rules/、context/、work/
    └── local/worktrees/<work-id>/    # 本仓库的 Git worktree
        ├── .git                     # Git 维护的定位文件
        ├── AGENTS.md
        ├── src/
        └── .tiller/                 # 本分支的共享资料及工作记录
```

开发时本次需求、设计、确认、代码及验证资料都在该 worktree 内维护，并随本仓库分支交付。主目录的 `.tiller/local/` 被忽略，不影响子 worktree 在自己的 Git 索引中跟踪 `src/` 和共享 `.tiller/`。必须从活动目录执行 Git，不能在主目录对嵌套路径执行批量添加。子 worktree 自身的 `local/` 同样忽略，不递归创建下一层 worktree。

独立管理使用以下布局，业务仓库的原目录默认分组到根 `repositories/` 中；旧工程按已登记路径定位，不自动移动：

```text
management-project/
├── .git/                            # 管理资料独立版本管理时存在
├── .tiller/
│   └── local/worktrees/<work-id>/
│       ├── management/              # 管理仓库的 worktree，维护共同资料
│       │   └── .tiller/{specs,rules,context,work}
│       └── repositories/
│           ├── repository-a/        # A 自己的 worktree 和分支
│           └── repository-b/        # B 自己的 worktree 和分支
└── repositories/
    ├── repository-a/                # 已登记的原仓库
    └── repository-b/
```

有 Git 管理仓库时，`management/` 保存本工作唯一活动的共同需求、设计、确认、依赖和整体进展；管理资料使用独立分支及评审请求。业务 worktree 保留各自代码和已有专属资料，共同记录只引用其仓库、路径和版本。管理仓库忽略原业务仓库容器及 `local/`，不把业务源码或 Git 元数据纳入自身提交。管理 worktree 不复制或重新初始化业务仓库。

准备、接续及恢复从 `repositoryPaths` 解析源仓库位置，活动副本仍按稳定标识放在上述 `repositories/<id>` 下。未参与本项工作的业务仓库回到主工程登记路径读取，不在管理 worktree 内猜测同名目录；本机绑定须与登记源路径及 Git 身份同时匹配。管理身份 `.` 不得用于引用业务容器内对象，业务文档使用其仓库标识。

管理工程没有 Git 时，不擅自 `git init`：共同记录仍在管理根维护，通过共享的不可变资料快照及摘要标识版本；界面明确没有管理分支或管理 MR。业务仓库仍使用各自的隔离环境。若项目要求管理资料也经 MR 交付，须先满足管理仓库条件，不能用快照冒充提交。两种情况都保持 `workspace` 模式，仅涉及 A 时也不改用单仓库规则。

### 11.3 基线、创建与记录交接

需求和设计阶段可以先在现有资料位置开展。设计有效确认、实现范围明确后，准备隔离环境；只交付文档且未约定 Git 交付的工作不强制创建。默认分支建议为 `codex/<work-id>`，可按项目规则覆盖；目标分支必须由明确配置或已确认输入提供，不假定为 `main`。分支名通过 Git 校验，冲突时不覆盖或自动占用已有分支。

准备分两步：先生成计划，再按计划应用。计划列出源仓库身份、基线提交、目标、活动路径、分支、已有修改、文件交接清单及授权。应用前复查内容摘要、Git 状态和所有权，计划过期则重新准备。Git 必须有可用的基线提交；尚无提交的仓库先说明缺口，不代替用户创建初始提交。

新 worktree 只取得指定提交的内容。对于本次需要的未提交或未跟踪资料，明确选择纳入基线提交，或在计划中逐文件列出复制到活动目录的相对路径和内容摘要。提交遵循单独授权；复制不改变原文件、不隐式 stash、不带入忽略的凭据和缓存。目标有不同内容、存在符号链接越界、文件仍在变动或无法判断必要文件时，停止相关交接并报告差异。无关修改保留原位。

交接清单表达新增、修改、删除及重命名，记录操作前后摘要；删除只作用于与基线一致的活动副本，原目录保持不动。重命名按旧路径删除和新路径新增核对。文件类型、符号链接、子模块或执行位变化无法可靠迁移时明确阻断，要求先形成获授权的基线或补充支持，不静默退化为普通文件复制。交接后比较完整清单，防止已删除资料从基线重新出现。

完成创建和内容校验后，先写入可恢复的交接事件，再切换活动位置。来源副本保持原内容，标为该工作的历史起点；后续同一工作写入须解析到活动目录，禁止两处分别更新。复制的确认快照及来源保持原内容，基于活动目录重新验证引用；字节不变不等于范围适用，跨仓库对象仍须核对。交接未完成时不得开始依赖它的实现。

复用已有环境须核对 Git common directory、实际 worktree、分支、基线、工作标识及本机登记；路径同名不是同一环境的证据。活动目录不能被另一项工作同时占用。

### 11.4 记录与路径解析

当前 record.json 保存第 9 节的类型化工作与产物，work/<id>/delivery.json 保存 Git 交付事实；tasks.json 与 delivery-checks 另保存任务及整体技术门禁，各自版本见第 9.2 节。文档验收不等于软件交付完成。主要信息如下：

| 信息 | 保存内容 |
|---|---|
| 工作与资料归属 | 工作标识、管理方式、共同记录所属仓库或非 Git 管理根、交接事件 |
| 仓库交付单元 | 稳定仓库标识、管理或业务角色、基线提交、开发与目标分支、远端标识、实际提交及 MR/PR 标识和链接 |
| 资料版本与依赖 | 管理资料提交或不可变快照摘要、各业务提交组合、顺序依赖、验证及评审引用 |
| 授权与决定 | 各动作对应的真实授权来源、适用范围及条件、需求/设计/合入/验收请求引用 |
| 事实与操作 | 单调递增事件序号、操作标识、准备/执行中/成功/失败/结果未知、实际观测结果及时间 |

共享记录使用逻辑仓库标识和相对路径，不写本机绝对路径或凭据。绝对路径、锁、临时计划和操作日志放在主目录 `.tiller/local/`；worktree 的 Git 本机管理目录保存定位绑定。绑定只负责找到主登记和活动目录，不能授予权限。查找时优先核对显式工程与工作参数，再核对绑定和 Git 身份；冲突或绑定缺失时要求重建定位，不能静默选择最近的 `.tiller/`。

路径解析按工作建立映射：单仓库的 `.` 指向活动 checkout；独立管理的 `.` 指向活动管理资料目录，业务标识分别指向各自活动 checkout，未参与仓库仍只读定位到原仓库。不能将管理 worktree 中的相对登记误解为已经复制了业务仓库。恢复到另一台机器时依据共享仓库身份、分支、提交和快照重新登记本机映射，路径缺失不能生成第二份工作历史。

资料版本采取不可变清单，绑定经审阅的需求、设计与确认快照及各业务提交，不要求包含未来才产生的合入回执。管理分支的提交和业务提交分别记录；最终回执作为后续记录追加，不要求一个提交包含自身哈希。共同资料变更导致清单变化时重验关联的业务交付及确认。

待合入内容与其后的控制证据分开：固定源 OID 后产生的合入请求、决定和操作回执，不再提交进该 OID 对应的待合入分支。它们由共同记录位置追加保存，作为待归档控制资料，并关联已固定的提交；不允许混入未经审阅的代码或规格变更。后续归档可使用获授权的资料提交或可核验的持久共享证据存储。归档操作自身的确认及回执引用持久来源，不要求归档提交包含批准自身的记录；来源尚未持久保存则仍待归档并禁止清理，不能借此省略应有批准。

### 11.5 命令与操作授权

当前 `work` 命令提供下列受控接口。所有输入使用版本化 JSON；写操作提供 `--plan` 与 `--apply <plan-id>`，计划绑定输入、对象状态和授权来源。计划通过不是人工批准，应用前仍检查授权和适用关卡。

| 命令 | 输入重点与作用 |
|---|---|
| `work prepare <id> --input <file>` | 仓库、基线、目标、分支及交接文件；创建或核对隔离环境，交接活动记录 |
| `work commit <id> --input <file>` | 指定仓库、精确文件清单、提交信息及授权；检查实际暂存内容，不批量夹带无关变更 |
| `work push <id> --input <file>` | 指定远端、源提交和目标开发分支；正常推送，不默认强推 |
| `work review <id> --input <file>` | 明确 create/update/attach、仓库、源/目标分支和资料版本；建立或关联真实 MR/PR |
| `work merge <id> --input <file>` | 指定评审对象、提交组合及有效合入确认；逐仓库执行和核对 |
| `work delivery-status <id>` | 只读核对本地；显式选择远端查询时报告查询时间和失败，不修改交付状态 |
| `work reconcile <id> --input <file>` | 依据实际 Git/平台结果记录恢复、外部合入或记录交接，不重放未知写操作 |
| `work cleanup <id> --input <file>` | 明确副本、本地分支或远端分支清单，分别核对保存依据和授权 |

隔离环境准备属于已批准实现范围内的本地操作。提交、推送、创建或修改 MR 不因设计批准而默认获准；可在展示实施计划时一次取得授权，列明仓库、远端、开发及目标分支、允许动作和条件，后续在该范围内复用。没有授权时继续可开展的本地实施和验证，将已准备的具体变更及待执行操作展示出来。

合入使用独立 `merge` 确认；验收和合入可以由同一条明确的人类决定分别登记，但不可相互推断。发布及删除远端分支也不由合入隐含授予。本产品方案被确认，不等于用户同时给当前 tiller 仓库授予这些实际 Git 操作权限。

### 11.6 MR、合入检查与整体结论

Git 操作由 TypeScript 调用本机 Git，使用参数数组和明确 cwd，不通过 Shell 拼接。评审平台适配层提供查询、创建、更新、合入及能力说明；GitHub PR 与 GitLab MR 使用统一逻辑对象，但保留平台标识和原始证据。平台地址由明确配置解析，未知平台不猜测。凭据从已有认证设施或环境读取，不进入共享文档、计划或日志；具体适配不增加未获允许的第三方运行时依赖。

没有自动写适配或凭据时，可生成评审材料并由人创建，再 attach 实际对象；只有核验仓库、源/目标及平台状态后才能记录为已关联。单凭一个 URL 不证明已创建、已批准或已合入。授权不足和适配缺失分别报告。

合入请求展示：各仓库及 MR、源提交 OID、目标分支及当前 OID、资料版本、依赖组合、检查证据、未解决意见和拟采用的合入方式。`merge` 的上游为相关有效设计确认；验收是否为合入前置由该工作明确约定，缺省不将二者强制串行，发布仍需验收及发布确认。

确认采用第 9.2 节当前契约及 workflowBinding。mergeBinding 在 Git 对象外绑定整体 deliveryBinding，必要时明确 merge 专属 deliveryExceptionRefs；旧格式保留原位并拒绝，不迁移历史验收为合入许可。平台批准仍须核对具体提交、权限、来源和项目要求，不能用机器人评论或陈旧批准代替。

执行前重新取得源、目标、依赖、检查和评审状态，任一绑定版本变化则原合入请求失效，生成新展示并重新确认；需求设计只在其内容或适用范围变化时失效。存在冲突、必要检查未过或未解决阻断意见时不合入。冲突解决后产生的新提交重新验证，不擅自改写远端历史。

适配层必须明确能否在写入时原子校验已确认的源/目标版本；查询后的相等不等于并发保护。缺少所需条件写入或平台保护时，不执行自动合入，改由具备相应保护的人工平台流程执行并核对结果；无法证明合入的准确范围时保留待复核。记录实际 merge/squash/rebase 后的提交，不假定源 OID 就是最终目标提交。

多仓库按显式依赖顺序操作，合入前记录已通过验证的提交组合；依赖成环时先制定可验证的兼容或分步交付方案。允许某仓库已合入、另一仓库待处理的状态，不承诺跨平台原子事务，也不自动回退已合入变更。整体完成分别核对管理资料、所有约定业务交付、版本组合验证及用户验收；文档已合入、单个 MR 已合入或各自测试通过均不足以代表整体完成。无 MR 的文档工作不虚构评审对象。

### 11.7 中断、归档与清理

每次外部写入前持久化操作标识和输入摘要，完成后保存实际结果。跨仓库不使用本地文件事务冒充远端事务。中断恢复先按仓库、源/目标、提交和操作标识查询远端：确认已完成则补记事实，确认未发生且授权仍有效才允许重试，无法判断则保持 `unknown`。无网络或平台不支持核对时保留现场和人工处理步骤，不重复创建 MR 或报告成功。

锁按主登记及工作共享，创建和复用时另核对仓库分支占用；不同活动目录不能各自取得一把互不相关的同工作锁。中断遗留的锁须核对进程及未结束操作，不按文件年龄直接删除。外部修改造成状态漂移时保留差异并重做计划。

结束前生成可追溯结果清单：需求设计版本、确认来源、各提交与评审结果、验证组合、遗留项和后续责任。回执在合入后追加，保存于共享工作资料；若需另一次文档提交，仍按对应授权办理，不假称已包含在先前 MR 中。

清理前先把活动记录交回可长期访问的位置。优先使用已经包含交付资料的主 checkout；若主目录尚未更新或与交接基线不同，保留 worktree，等待明确同步或逐文件协调，不自动 pull/reset/覆盖。非 Git 管理资料继续留在管理根。共享记录和快照不得只留在将删除的本机 `local/` 中。

计划逐项检查未提交及未跟踪文件、未推送提交、未结束操作、其他工作引用和最终资料可达性。取消也必须先保存唯一成果或取得明确丢弃授权；仅创建本机备份不能当作共享保存。普通清理调用 Git 的 worktree 移除机制，不递归强删，不自动删分支。移除副本、删除本地分支、删除远端分支分别列明权限与检查；受保护分支和其他工作使用的分支不得删除。失败记录已完成部分和剩余对象。

### 11.8 验证与原件保护

采用临时本地 Git 仓库验证两种布局、提交可用性、单业务仓库仍属 workspace、无 Git 管理根、独立管理资料与业务版本关联、未跟踪资料交接、删除和重命名、未支持文件类型、路径含中文和空格、重复准备及身份冲突。验证主目录与其他工作内容不变，交接清单及确认依据一致，共同记录只有一个活动写入位置；固定源 OID 后产生的控制记录不会改变待合入内容，归档仍可追溯。

远端操作用可控适配替身覆盖权限不足、条件写入竞态、超时后实际成功、重复创建、部分合入、检查失败和未知结果；真实平台另做受控验证，不能用替身证明平台权限、原子保护或认证有效。清理测试覆盖未推送提交、唯一记录、占用分支和交接冲突。Windows、macOS、Linux 分别验证实际 Git 行为，未运行的平台明确未验证。

新增共享格式、定位解析、命令、规则和升级须一起交付；工程资源升级先预览并保护自定义内容；不支持的机器契约拒绝且原件不变，不转换旧工作。只有涉及 Git 交付的当前工作才按需建立 delivery.json。通用入口及专项规则提示活动目录与合入关卡，真实 AI 样例验证执行顺序；Markdown 负责工作约定，CLI 只对自身操作实施检查，不能声称阻止宿主直接写入或绕过 Git 命令。

## 12. 测试定义、执行与交付衔接

对应 FLOW-24，数据和命令契约统一引用[验证与反馈设计](../verification/design.md)，不在工作记录中重复维护长期用例。需求验收条件和质量要求进入总体测试范围；总体设计引用具体项目测试约定；实施规划登记当前任务所需用例、环境依赖和回归范围。详细用例随任务设计完善，设计确认后写测试代码，必要检查即时执行并关联工作记录。

工作内 verification.md 记录本次选择依据、对象版本、分类结果、证据引用与未覆盖项。verification run 保存实际套件执行事实，verification record 接入人工或外部用例结果，verification report 汇总当前范围；进程退出成功不代表逐用例通过。受检输入变化需复验；绑定输入之外的依赖及环境由执行者另行核对。

流程阶段按第 9 节绑定实际验证上下文，需要规划任务的阶段才消费任务委托；任务门禁消费验证选择及完整产物快照；前置未有效验证时阻断依赖任务，但不自动调度下一任务。整体检查对照需求、九类适用性及跨模块/系统场景保留缺口，分别报告技术结果、过程证据、验收和发布授权。真实 AI 验证保留实际轨迹，不能以规则匹配替代。新增机器契约见第 13 节。

## 13. 规划、任务与整体门禁契约

对应 FLOW-25 至 FLOW-27，依据[已确认任务门禁设计](../../../work/20261019-task-delivery-gates/design.md)。可解析的命令输入示例统一维护在[使用指引](../../../../resources/usage.md#规划任务与整体交付)，避免复制大块 JSON。

规划 schemaVersion 1 包含 ownerWorkId/revision/scope、需求及排除理由、总体确认 basis、tasks、delivery、changeReason。任务登记详细规格和规范、待细化项、确认引用、显式前置及必要产物、验证选择、人工检查点。delivery.requiredTasks 必须覆盖当前全部任务；移除/延期须新修订明确说明。register 保存不可变定义/审阅视图；planning 请求绑定实际规格；activate 在锁内重核后写激活事件。taskDigests 区分不受影响任务与变化任务，新规划不清空全部历史。

任务 start/verify/resume 输入使用 operationId、expectedRevision，verify 另带当前 attemptId；checkpointRefs/evidenceRefs/exceptionRefs 为明确引用数组。start 不执行代码，verify 不执行测试。start 绑定规格、有效前置完成事件及 start 检查点，不绑定自身预期产物；verify 核对实际完整快照、最新验证及 verify 检查点。resume 创建新 attempt。前置完成事件、规格或开始检查点变化时不能直接 verify；输出变化后历史 verified 失效。移除任务保留 cancelled 历史，定义未变且依据仍有效的任务可跨修订保持当前通过。

任务与规划操作共用 tasks.json 的单调 revision/events/receipts。operationId 在同工作内亦不能与 delivery-checks 回执冲突。重复输入返回 historical 回执并明确当前未重评；不同输入复用 ID 拒绝。写前及写后重核依据；写后失败只撤销本次控制文件，外部修改保留并报告，不回滚业务产物或虚报成功。

人工 checkpoint 绑定 ownerWorkId、taskId（整体省略）、checkpointId、operation、definitionDigest；摘要包含检查点目的及对象，不能只按名称复用。独立 exception 绑定操作/条件 ID/当前技术摘要/理由/允许动作/失效条件，真实决定和来源仍须有效。自动消费只接受 allowedAction 等于 operation、endCondition 为 basis-change-or-revocation；未知文本登记但不放行。技术摘要排除例外决定及自身回执，apply 摘要另含决定指纹。非法路径、结构、身份、来源及缺少真实开始事实等硬错误不可豁免。

例外使 operationAllowed 为 true 时，technicalReady 仍按原技术条件判断。verify 例外写 task-verification-excepted 并保留 failureReasons，不写普通 task-verified；修复后可同一有效 attempt 正常验证。任务依赖不自动继承例外，整体、merge 和 release 各自核对对应例外。required:false 缺项可警告，但显式必要检查仍须通过，已纳入快照的可选产物变化也会使历史失效。

delivery-check 只读返回 scope、technicalReady、processEvidence、issues、exceptions、basisDigest；delivery-ready 另保存第 9.2 节当前版本的不可变回执，不增加 tasks revision，也不自动验收。acceptance 可绑定 deliveryBinding={deliveryCheckId,deliveryBasisDigest}，技术未就绪但明确验收显示 accepted-with-exceptions。release 必须绑定同对象 acceptance；mergeBinding 同时绑定整体对象及 Git 状态。普通文档验收不能代替整体验收。进行中的 commit/push/review 仍按实际授权执行并展示 readiness，整体门禁不扩大提交/远端操作权限。

严格格式统一见第 9.2 节，阶段、任务和整体控制状态共同参与当前判断。未知版本、字段或不完整依据拒绝，旧文件保留原位。验证从观察前 capture 或真实 run 取得 ID，record 不得事后采集当前对象冒充过去结果。自动运行成功、逐项结果、任务技术通过、整体操作允许、用户验收与发布分别呈现。

## 10. 当前轻量用例实现（2026-10-22）

全局用例目录固定为 `.tiller/cases/modules/<模块>/<behavior|interface|performance|security>.json` 与 `.tiller/cases/scenarios/<场景>.json`。模块名取自 `.tiller/specs/modules/` 实际目录；模块文件内的 `module`、`kind` 必须与路径一致，场景还需声明经过的模块和端到端测试。旧根目录 `*.json` 不再读取。

`verify` 按测试引用匹配用例并写入任务验证的 `用例` 字段，不要求手写 JSON。`check` 将每条 AC 的最新验证绑定到存在且 `test_ref` 一致的用例，验证结果、代码树和测试缺失均按阻塞处理；同时汇总模块类型数量、场景和未覆盖模块，并按改动文件给出回归提示。该实现只服务默认工作流，不恢复旧验证重模块、证据包或全文快照。
