# 验证与反馈需求

> 状态：实施依据；实现与实际验证结论由对应工作记录维护。
> 对应总体需求：R4、R5，关联 R2、R3、R6、R7。

## 1. 目标与边界

开发者应能持续维护产品测试范围、长期用例及需求覆盖，复用项目测试能力，查明某次交付实际验证了什么、依据是否仍适用以及尚有什么缺口。

本模块组织验证定义与证据，不替代项目的测试框架，不以用例数量或进程成功证明全部需求成立，也不将技术通过作为用户验收、合入或发布批准。

## 2. 使用过程

| 环节 | 必要信息或产物 |
|---|---|
| 明确需求 | 可观察的验收行为、异常与边界，必要性能、安全等质量要求 |
| 总体设计 | 全局测试范围、类别适用性、方法、环境、完成条件和项目测试约定 |
| 实施规划 | 各任务的验证场景、依赖、回归范围和必要人工检查 |
| 当前任务详细设计 | 基于已确认需求完善用例，明确条件、操作、预期结果及实现方式 |
| 当前任务实现 | 编写或调整测试代码，执行必要验证并立即保存证据 |
| 整体交付 | 核对需求覆盖及各类结果，呈现未验证、失败、跳过和待判断事项 |

用例可从需求阶段起草，预期行为不得由实现反推为已确认需求。详细用例随任务产生，不提前强制生成所有模块用例。测试代码遵循对应设计确认和授权；骨架任务建立并实际运行最小测试入口。已有项目复用已有测试并建立真实基线。

## 3. 功能需求

### VERIFY-01 明确全局验证范围

应分别评估单元、接口与契约、集成、完整场景、性能与容量、安全、可靠性与恢复、兼容性与交付、易用性与可访问性九类测试。每类可辨认适用、不适用或待明确状态及理由。适用类别需有目标、方法、环境和完成条件；适用但尚未执行不能写成不适用。性能指标、风险边界须有需求依据，不预设所有项目通用的达标数值。

### VERIFY-02 按稳定模块维护用例

模块划分以确认后的设计职责为参照，需求定义验证目的，代码位置决定执行位置；模块不与任务、技术分层或仓库强制一一对应。模块内场景、多个模块协作场景、系统整体质量场景分别归属。同一用例正文只维护一份，跨模块场景关联全部相关模块；调用其他模块本身不构成跨模块归属的充分理由。

### VERIFY-03 关联需求、用例与测试实现

长期跟踪的用例应有稳定标识、目的、需求依据、分类、条件、操作、预期结果及执行方式。用例可属于多个测试类别，调整文件位置不改变标识，废弃标识不复用。自动化用例能定位对应测试实现和执行入口；人工用例明确过程及证据要求。允许通过套件关联内部单元测试，但套件关联不表示每条需求均已逐项验证。

### VERIFY-04 支持不同语言及既有测试

项目决定测试框架、目录、命名、测试数据和执行方式；tiller 使用通用关联与结果约定。已有测试和场景描述可以引用接入，不强制转换、改名或复制。用例声明只描述验证，不因存在自然语言步骤就自动获得执行能力。

### VERIFY-05 检查覆盖和定义缺口

应发现重复标识、失效引用、未知模块或需求、自动化入口缺失以及声明范围内的需求覆盖缺口。检查应区分结构有效、具备关联、实际执行与结果符合预期；文件关联存在不能证明断言充分。覆盖仅针对明确登记的范围，不能暗示已经发现全部产品需求。

### VERIFY-06 明确执行范围并保留真实结果

执行前应能审阅入口、目标仓库、运行目录、参数、时间限制及受检输入范围，在对应授权内执行。配置或受检对象变化后应重新核对。超时、启动失败、非零退出和正常退出分别记录；套件正常退出不得自动生成所有关联用例通过。不得自动执行来源不明的文档命令，外部扫描、压测、部署和数据修改仍遵守实际目标与授权。

### VERIFY-07 接入执行证据并判断适用性

结果应关联对象版本或内容摘要、环境、方法、时间、来源及证据。人工和外部报告保留其声明来源、实际覆盖与限制，登记不等于独立核验或身份认证。受检依据变化后旧结果保持历史事实并标示需复验，不静默覆盖旧结果。快照仅覆盖明确采集对象，未捕获的依赖和环境变化需人工判断。

### VERIFY-08 分类报告交付结论

报告应分别呈现各类别适用性、需求覆盖、用例执行和证据适用性，区分通过、失败、跳过、未执行和无法判断。任务回归、约定自动化全量回归、完整交付验证分别说明范围；一次套件通过不能冒充全部完成。必要条件缺失时保持缺口，不把报告生成当作验收、任务放行或发布批准。

### VERIFY-09 验证实际 AI 流程行为

tiller 自身应通过实际过程验证人工确认、逐任务验证、失败依赖阻断及中断接续。证据应包含实际操作顺序和产物，规则文本匹配及 AI 自填通过不能代替行为验证。其他项目按适用性采用，不强制所有项目增加 AI 专项测试。

### VERIFY-10 明确每次任务与整体交付的检查集合

每次判断应明确所选需求、用例、检查、产物、类别和场景范围及理由，不能把全局登记范围或一次套件成功默认当作当前任务完成。必要检查须覆盖当前完整产物，包括源码集合和明确的生成内容；可选项缺失与必要检查失败分别处理。来源、路径或对象身份不明时保留硬阻碍。

### VERIFY-11 先绑定受检对象，再登记观察结果

人工观察或外部结果应引用观察前采集的对象版本；实际执行记录可作为后续逐项结果的采集依据。不得先观察过去对象，再采集当前文件冒充当时版本。检查定义、输入、结果证据或执行期间对象变化后旧结果失效；最新相关尝试失败时不得挑选更早通过。运行检查不能由人工填写通过替代真实执行事实。

## 4. 验收标准

| 编号 | 场景与预期 | 对应需求 |
|---|---|---|
| V-AC-01 | 能辨认九类测试适用性、理由及缺口，适用未测不被归为不适用 | VERIFY-01 |
| V-AC-02 | 模块、跨模块和系统用例归属清楚，同一正文不重复，需求和仓库可追溯 | VERIFY-02、VERIFY-03 |
| V-AC-03 | 两种语言项目能复用各自框架和目录，已有关联场景不被要求重写 | VERIFY-04 |
| V-AC-04 | 重复标识、无效引用及缺失执行入口返回明确问题，关联完整不宣称语义充分 | VERIFY-03、VERIFY-05 |
| V-AC-05 | 实际执行保留正常、失败、超时及启动错误事实，退出成功不自动产生用例通过 | VERIFY-06 |
| V-AC-06 | 执行前配置或绑定输入变化使旧执行依据不可复用；未绑定环境的限制可见 | VERIFY-06、VERIFY-07 |
| V-AC-07 | 外部和人工结果有声明来源、具体用例及证据，不能冒充本次亲自运行或人工批准 | VERIFY-07 |
| V-AC-08 | 当前与历史结果分开，依据变化后标示失效并保留原事实，各类别分别报告 | VERIFY-07、VERIFY-08 |
| V-AC-09 | 初始化不虚构业务用例，需求、设计、规划、实现与交付各阶段产生适用验证资料 | VERIFY-01、VERIFY-03、VERIFY-08 |
| V-AC-10 | 真实过程证据能辨认越过确认或事后倒填，程序测试通过不替代流程行为验证 | VERIFY-09 |
| V-AC-11 | 显式选择或产物集合变化时按声明范围核对完整当前快照，局部通过不扩大为整体通过 | VERIFY-10 |
| V-AC-12 | 缺少此前采集、输入漂移或运行期间变化时，拒绝倒填，保留失败/失效及未捕获环境边界 | VERIFY-07、VERIFY-11 |
| V-AC-13 | 新尝试失败、改检查别名或手填运行通过时，不允许挑选历史通过或把声明当成实际执行 | VERIFY-11 |
| V-AC-14 | 生成二进制核对真实字节及来源；可选缺失可说明，必要检查仍满足；不安全及自身控制对象拒绝 | VERIFY-10 |

## 5. 与其他模块的关系

工作推进使用本模块的覆盖和证据判断下一步，开发规范规定生成时机与质量要求，工程初始化保护并保留项目用例和历史。具体资料、命令及检查边界见[验证与反馈设计](design.md)。

## 6. 当前轻量实现约束（2026-10-22）

全局用例按模块与类型分文件维护，跨模块端到端路径登记为场景；不再使用单一 `flow.json` 或旧验证重模块。每条 AC 必须先映射全局用例，再由用例的具名测试产生当前验证。`check` 校验模块目录、类型白名单、场景模块、跨文件编号、测试引用和 AC→用例→测试→验证链路，并报告模块统计、未覆盖模块和相关回归提示。

验证记录只保留用例编号、测试、命令、结果、提交和代码树摘要；原始日志、全文快照、证据包和安装包不进入记录。来源见[模块用例、场景与用例先行](../../../task/20261022-case-first/task.md)。
