# 验证与反馈需求

## 1. 目标

把每条验收条件绑定到可重复的全局测试设计用例和实际测试，用当前任务验证证明交付，不用日志堆叠或空占位替代结论。

## 2. 全局用例

- 用例按模块和类型保存，覆盖行为、接口、性能和安全；跨模块流程保存为独立场景。
- 模块名必须与规格模块一致；类型按需建立，不建空文件。
- 每条用例包含稳定唯一编号、标题、前置条件、步骤、输入、预期结果、类型、优先级和需求/模块定位；关联 AC 使用所挂需求 specs 中的路径作用域 `AC-n`，可多个。不保存测试实现或执行结果副本。
- 场景额外声明经过的模块，必须至少一个模块。
- 新用例自动分配未被占用的编号，不要求测试已存在；模块不存在时提示先建规格，创建后返回待实现状态与测试骨架。

## 3. 用例先行

需求确认后先把验收条件转为新增或修改的全局用例，再写测试、实现和验证。测试与用例建立可扫描的稳定关联，系统据此形成用例到测试的反查。

一个测试可覆盖多个用例，一个用例可被多个测试覆盖。无任何测试关联的用例显示待实现；测试引用不存在的用例编号产生明确错误。验证可以按用例执行其全部关联测试，也可以定位单个测试。

结果必须由工具实际执行并从独立执行证据判定，原始输出不参与通过判断。目标测试必须精确命中，失败、跳过、匹配为零或无法唯一定位都不能核实，并由自检阻断。测试前准备失败即验证失败；其它测试方式应通过统一的运行接口接入。

运行器现含 `node-test`、`junit-maven`、`junit-gradle` 与 `pytest`。pytest 从私有 JUnit XML 核实，不内嵌 Python，也不自动安装依赖；同一 AC 或 CASE 连续两次失败且中间无成功核实时，检查要求停止自动重试。Windows 上 junit runner 使用 `mvn.cmd`/`gradle.bat` 或等价系统命令解释器入口，pytest 使用 `pytest.exe` 或可执行模块入口；POSIX 保持 `mvn`/`gradle`/`pytest`。启动差异不改变选择器、私有报告、失败或跳过判定，工具缺失必须失败。junit CASE 适配器骨架和仓库辅助脚本不得依赖 `/bin/sh`。

管理多个业务仓库时，按测试文件所在仓库选择运行方式与测试前准备；该仓库写明的项优先，没写明的项沿用工程默认。测试前准备在该业务仓库根目录执行。测试文件不能唯一对应一个已登记仓库时拒绝执行。当前工程没有业务仓库时使用工程默认。Java 测试可以分别通过 Maven 与 Gradle 运行，并且只承认恰好命中的那一条结果；缺失、重复、跳过或额外失败都不能通过。尚未接入的框架仍提交带理由的外部结论。

无法本机执行时，外部结论须写明命令、结果和理由；自检与验收默认阻断，只有显式放行才可通过，PR/MR 草稿须标明未执行。缺陷修复应在任务基线证明原测试失败，再保留当前通过的同一测试证据。

## 4. 检查

自检必须校验：

- 设计确认后每条验收条件至少引用一个存在的用例，且用例具备预期结果等完整测试设计字段；缺少用例编号是错误。
- 验证或验收阶段每个用例至少有一个关联测试；无关联为待实现并阻塞。
- 验证测试覆盖用例、结果通过、当前代码状态未过期。
- 执行记录已核实；外部结论有理由并仅经显式放行；缺陷修复有基线失败先行和当前通过。
- 已验收任务按验收确认中的基线复核代码、测试和范围差异；未验收或验收失效的任务继续使用当前工作树；验收时证据不完整仍失败。
- 用例关联 AC 为需求 specs 中的 `AC-n`；历史“无”、留空与 `task#AC` 只提示迁移，不阻断；不要求回指当前任务 AC。
- 编号跨文件唯一、模块目录合法、类型在白名单、场景模块存在。
- 统计每模块各类型数量、场景及未被场景覆盖的模块。
- 本次改动涉及模块时提示回归其用例和经过它的场景。
- 交付命名不合约定时只提示，不阻塞技术自检。
- 验证日志至少记录显示命令、起止时间和退出码；验证相对当前代码树失效时明确说明“验证已过期”。
- 任务验证正文只展示条件、测试、用例、结果、来源、核实、提交、时间与日志定位；完整命令、退出码和代码树摘要保留在机器可读证据中，核实与过期判定不因展示精简而变化。
- 任务基线后没有规格或背景回写时只告警，不单独阻塞。

历史用例来源允许为空但必须提示；不得批量伪造来源。

## 5. 当前轻量验证边界（2026-10-22）

不恢复旧验证命令、检查/报告子命令、原始证据包、评审快照或全文快照。全局用例是测试设计事实源；执行细节从任务记录中的重跑依据和版本历史获取。

## 6. 验收方向

- 无测试、错配测试、过期树或反向验收条件不成立时自检阻塞。
- 新项目可以从验收条件先建立用例，再写测试并完成端到端验证。
- 目录结构变化和模块回归提示可直接定位。
- 已验收历史任务不因后续代码变化误报验证过期，但保留验收时本就不完整证据的失败。


## 5. 用例与稳定需求锚定（CASE-REQ-LINK）

全局用例与任务验收不得以短暂任务编号为锚。

### VER-CASE-REQ-1 用例不回指任务 AC
新登记用例不得写入 `关联 AC：<任务>#AC-n`。用例通过「需求」字段挂靠 specs；「关联 AC」写该需求文件验收条件中的 `AC-n` 列表。

### VER-CASE-REQ-2 覆盖靠 verify 与稳定条件
`check`/`accept` 的 AC 覆盖以任务对 specs 中同一套 `AC-n` 的引用加上 verify（条件→测试→CASE）为准，不要求用例文件回指 `taskId#AC`。历史 `task#AC` 仅可读，最多 warning。

### VER-CASE-REQ-3 登记用例无任务来源 AC
新用例显式登记一个或多个关联验收条件；编号必须存在于所挂需求 specs 文件的验收条件中，不得把任务编号写入用例，也不要求任务来源 AC。

### VER-TREE-DIGEST-1 验证树按 Git 文本规范化
工作区与提交两侧的 tree 摘要使用同一 Git blob 规则：工作区按 Git clean/filter 折算，提交直接读取 blob 标识；二进制保持原字节。Windows 上的 CRLF 工作区与 LF 提交在没有实质内容差异时产生同一摘要；实现不修改用户 `core.autocrlf`，也不强制改写工作区换行。`verify` 记录、`check` 过期判断、已验收任务的提交复查与 `preExisting` 比较共用该规则。

## 7. 验收条件

- AC-1: 登记用例时校验所挂需求 specs 的验收条件，并把一个或多个关联 AC 写为 `AC-n` 列表
- AC-2: `case add` 拒绝 `任务#AC` 写法；未提供可解析的 specs AC 时不写用例文件
- AC-3: 历史「关联 AC：无」、留空与 `task#AC` 仍可读取，只保留迁移提示，不阻断历史用例
- AC-4: 工作区文本 CRLF 与提交 LF 无实质差异时，verify 记录、check 过期判断、acceptance 提交复查与 preExisting 使用一致 tree 摘要；二进制改动仍被识别

## 8. 跨语言 CASE 桥接入口（VER-ADAPTER）

业务测试使用 tiller 不直接扫描的语言（如 Java）时，标准路径是「可扫描入口挂用例编号 + 内部转调真实测试运行器」：

- 发现仍走既有测试扫描；入口测试名或紧邻注释写稳定用例编号，一个文件可挂多个用例。
- 入口体内调用该语言真实运行器；Maven 用 Surefire 类方法选择，Gradle 用对应测试选择器。
- 入口按可扫描运行器执行，真实 Java 测试按 junit 运行器执行；不得按扩展名自动猜语言，混合工程应显式配置入口与 Java 的仓库/运行器边界。
- 用例登记对 junit 运行器输出带用例编号与转调占位的可扫描骨架，完整类方法映射由工程补齐。
- 真实运行器失败、缺失或结果不可核实即失败；入口存在不构成覆盖证据。纯 Node 或已扫描工程可直接用普通测试名挂用例编号。
