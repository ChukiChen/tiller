# 验证与反馈需求

## 1. 目标

把每条验收条件绑定到可重复的全局测试设计用例和实际测试，用当前任务验证证明交付，不用日志堆叠或空占位替代结论。

## 2. 全局用例

- 用例按模块和类型保存为 Markdown：`behavior`、`interface`、`performance`、`security`；跨模块流程保存为 `scenarios/*.md`。
- 模块名必须与 `.tiller/specs/modules/` 一致；类型文件按需创建，不建空文件。
- 每条用例包含稳定唯一编号、标题、前置条件、步骤、输入、预期结果、类型、优先级、需求/模块引用、源码路径和来源 AC `criteria`；不保存测试引用字段。
- 场景额外声明经过的 `modules`，必须至少一个模块。
- `case add` 自动分配未被标题占用的下一个 CASE 编号，不要求测试已存在；模块不存在时提示先建规格，创建后返回待实现状态与测试骨架。

## 3. 用例先行

需求确认后先把 AC 转为新增或修改的全局用例，再写测试、实现和验证。关联方向为测试引用用例：测试名或紧邻注释包含 `CASE-NNN`，tiller 扫描 `test/**/*.test.*` 和 `*.spec.*` 建立 case→tests 反查。

一个测试可覆盖多个用例，一个用例可被多个测试覆盖。无任何测试引用的用例显示待实现；测试引用不存在的 CASE 编号产生明确错误。`verify --case CASE-NNN` 执行覆盖该用例的全部测试，`verify --test` 与 `--criterion` 继续可用。

结果只从私有报告读取，stdout/stderr 不参与判定。文件与完整名称（嵌套按名称路径）必须精确匹配恰好一个通过事件且无失败；仅引用文件时要求全部通过。报告缺失/损坏、0/多个匹配、失败或跳过都不能核实，并由 `check` 阻断。`verify.prepare` 失败即验证失败；其它框架通过 `src/test-output.ts` 的 `TestRunner` 适配器扩展。

无法本机执行时使用 `--reported --command --result --reason`，理由必填；`check`/`accept` 默认阻断，只有 `--allow-reported` 显式放行，PR/MR 草稿须标明未执行。bugfix 任务使用 `--expect-fail --test` 在任务基线临时工作树走同一适配器和报告路径证明失败，并保留当前通过的同一测试证据。

## 4. 检查

`check` 必须校验：

- 设计确认后每条 AC 至少引用一个存在的用例，且用例具备预期结果等完整测试设计字段；缺少用例编号是错误。
- 验证或验收阶段每个用例至少有一个引用它的测试；无引用为待实现并阻塞。
- 验证测试覆盖用例、结果通过、代码树未过期；
- 执行记录已核实；外部报告有理由并仅经 `--allow-reported` 放行；bugfix 有基线失败先行和当前通过；
- 已验收任务以 acceptance 确认中的提交为检查端点，测试文件、代码树、范围 diff 和测试弱化从该提交读取；未验收或验收失效的任务继续使用工作区/HEAD；验收时证据不完整仍失败；
- 用例 `criteria` 回指当前任务 AC，或该用例在本任务新增/修改；
- 编号跨文件唯一、模块目录合法、类型在白名单、场景模块存在；
- 报告每模块各类型数量、场景及未被场景覆盖的模块；
- 本次改动涉及模块时提示回归其用例和经过它的场景。
- 提交主题和分支名不合约定时只提示，不阻塞。
- 任务基线后没有 specs/context 回写时只告警，不单独阻塞。

历史用例 `criteria` 允许为空但必须提示；不得批量伪造来源。

## 5. 当前轻量实现约束（2026-10-22）

不恢复旧 verification CLI、check/report 子命令、原始证据包、reviews 快照或全文快照。全局用例是测试设计事实源；执行细节从 `task.md` 的重跑命令和 Git 获取。

## 6. 验收方向

- 无测试、错配测试、过期树或反向 AC 不成立时 `check` 阻塞。
- 新项目可通过 `case add` 从 AC 先建立用例，再写测试并完成端到端验证。
- 目录结构变化和模块回归提示可从 CLI 输出直接定位。
- 已验收历史任务不因后续代码变化误报验证过期，但保留验收时本就不完整证据的失败。
