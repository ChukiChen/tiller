# 验证与反馈需求

## 1. 目标

把每条验收条件绑定到可重复的全局用例和具体测试，用当前任务验证证明交付，不用日志堆叠或空占位替代结论。

## 2. 全局用例

- 用例按模块和类型保存：behavior、interface、performance、security；跨模块流程保存为 scenario。
- 模块名必须与 `.tiller/specs/modules/` 一致；类型文件按需创建，不建空文件。
- 每条用例包含稳定唯一编号、标题、需求/模块引用、源码路径、具名 `test_ref` 和来源 AC `criteria`。
- 场景额外声明经过的 `modules`，必须至少一个模块并使用端到端测试。
- `case add` 自动分配下一个 CASE 编号；模块不存在时提示先建模块规格；测试文件不存在时返回骨架建议。

## 3. 用例先行

需求确认后先把 AC 转为新增或修改的全局用例，再按 `test_ref` 写测试，最后实现。验证时运行测试并把命中的用例编号写入 task.md。`verify` 只接受 `--run "<命令>"`，记录即执行；不能另行手填与执行结果矛盾的状态。

node:test TAP/spec 输出必须命中 `文件::测试名` 且通过；仅引用文件时要求测试存在且失败数为 0。无法核实要写入记录并由 `check` 阻断。其它框架通过 `src/test-output.ts` 的解析器注册表扩展。

无法本机执行时使用 `--reported --command --result --reason`，理由必填；`check`/`accept` 默认阻断，只有 `--allow-reported` 显式放行，PR/MR 草稿须标明未执行。bugfix 任务使用 `--expect-fail --run` 在任务基线临时工作树证明失败，并保留当前通过的同一测试证据。

## 4. 检查

`check` 必须校验：

- 每条 AC 至少引用一个存在用例；
- 用例的 `test_ref` 文件和具名测试存在；
- 本次验证测试与用例一致、结果通过、代码树未过期；
- 执行记录已核实；外部报告有理由并仅经 `--allow-reported` 放行；bugfix 有基线失败先行和当前通过；
- 用例 `criteria` 回指当前任务 AC，或该用例在本任务新增/修改；
- 编号跨文件唯一、模块目录合法、类型在白名单、场景模块存在；
- 报告每模块各类型数量、场景及未被场景覆盖的模块；
- 本次改动涉及模块时提示回归其用例和经过它的场景。
- 提交主题和分支名不合约定时只提示，不阻塞；PR/MR 模板、平台选择与 `pr` 输出由具名接口/行为测试覆盖。

历史用例 `criteria` 允许为空但必须提示；不得批量伪造来源。

## 5. 当前轻量实现约束（2026-10-22）

不恢复旧 verification CLI、check/report 子命令、原始证据包、reviews JSON 或全文快照。全局用例是声明事实源；执行细节从 `task.md` 的重跑命令和 Git 获取。

## 6. 验收方向

- 无测试、错配测试、过期树或反向 AC 不成立时 `check` 阻塞。
- 新项目可通过 `case add` 从 AC 建立用例并完成端到端验证。
- 目录结构变化和模块回归提示可从 CLI 输出直接定位。
