# tiller 总体需求

## 1. 产品定位

tiller 是面向 AI 开发的轻量标准工作流与 CLI：先写清目标、范围和验收条件，再在范围内实现，用可定位测试与 Git 记录证明结果。它优先保证确定性、恢复性和低操作成本，不追求重型阶段引擎或审计档案。

## 2. 用户与场景

- 个人或小团队从空目录接入，快速得到可执行的任务流程。
- 已有仓库接入，保留用户规则、背景和业务文件。
- 大功能先拆成有依赖关系的任务条目，再逐项开工。
- 中断后从 `task.md`、Git 和全局用例恢复，不依赖聊天上下文。
- 交付前核对 AC、测试、边界和风险；人工验收仍是独立动作。

## 3. 默认工作流

| 规模 | 必要流程 |
|---|---|
| small | 需求确认 → 实现 → 验证 |
| standard / 大功能 | 需求确认 → 设计确认 → 实现 → 验证 |

默认人工节点只有需求、设计（仅 standard 代码任务）和交付验收。规划、合入、发布按需确认，不是默认门禁。`start` 创建任务，`resume` 接续，`confirm` 记录确认，`verify` 记录可重跑验证，`check` 做交付自检，`accept` 记录交付验收，`close`/`reopen` 结束或恢复任务。

`verify` 只声明 `--test "<文件::测试名>"`，由 tiller 构造并执行精确匹配的 node:test 命令；结果只从私有临时报告读取，stdout/stderr 不参与判定。报告缺失/损坏、匹配 0 个或多个、失败或跳过都不能核实为通过。无法本机执行的外部报告必须写明理由，默认阻断，仅在显式 `--allow-reported` 时放行。bugfix 任务用同一适配器保留基线失败先行与当前通过两侧证据。standard 任务 `start` 必须声明 `--target`；small 缺省 `.`。

交付格式统一：提交主题为 `类型(模块): 中文摘要`，PR/MR 标题末尾加 `[任务编号]` 并保持五段说明，标题摘要按显式指定、任务元数据、最早规范 feat/fix 提交、任务标题回退，主模块取范围首个，关联任务用纯文本；分支为 `类型/任务编号[-简短描述]`。`pr <task-id>` 只读取本地任务与 Git，按提交时间正序生成可人工修订的标题、说明和建议分支，不调用托管平台或联网；`check` 对提交和分支格式只提示。

任务阶段只从记录事实推导：已开始、需求已确认、设计已确认（small 可跳过）、已验证、已验收、已关闭、已放弃。确认失效或验证过期时显示回退阶段与原因，不另存可能漂移的状态字段。

## 4. 任务记录与确认语义

- 单次任务只维护 `.tiller/task/<id>/task.md`；历史 `.tiller/work/` 只读保留，不自动迁移。
- 结构化需求、设计、范围、编号 AC、确认、验证和自检都写入同一记录；start 生成目标、范围、AC 与设计模板，聊天原话不能替代正文。
- 确认绑定已写明的对象及其摘要，自动记录确认部分、确认人、时间、提交和摘要；需求与设计独立摘要，正文变化只使对应确认失效。
- 用户原话可选，只作附注；AI 不得代写或补造。确认人用 `--by`，缺省取 Git `user.name`。
- 验证记录每条 AC 对应的用例编号、测试、tiller 实际执行的命令、结果、退出码、核实状态、提交、代码树摘要和本机日志路径；完整输出写 `.tiller/local/logs/` 且不提交。外部报告单独标明未执行及理由。历史记录继续可读，不提交原始日志、全文快照、自举工程或安装包。
- 已验收任务用 `close` 收尾；未验收终止用 `close --abandon`，二者记录原因和时间。终态任务不能继续确认、验证或验收，需显式 `reopen`。
- 记录不得包含密钥、token、凭据或本机绝对路径；本机数据只放 `.tiller/local/`。

## 5. 全局用例与用例先行

- `.tiller/cases/` 保存跨任务的产品级测试设计：模块行为、接口、性能、安全用例，以及跨模块场景。
- 模块名与 `.tiller/specs/modules/` 一致；类型固定为 `behavior`、`interface`、`performance`、`security`。场景声明经过的模块。用例和场景均使用 Markdown。
- 用例写在测试之前，包含稳定唯一编号、标题、前置条件、步骤、输入、预期结果、类型、优先级、需求/模块与源码引用、来源 AC `criteria`；不保存测试引用字段。历史空来源允许保留并提示，新用例必须绑定当前任务 AC。
- 关联方向是 test→case：测试名或紧邻注释引用 `CASE-NNN`，tiller 扫描测试建立 case→tests 反查。一个测试可覆盖多个用例，一个用例可被多个测试覆盖；无引用显示待实现，引用不存在的编号报错。
- `case add` 不要求已有测试，自动分配未占用的编号并校验模块、类型和 AC。`verify --case` 执行覆盖该用例的全部测试；`--test` 与 `--criterion` 继续可用。
- `check` 在确认后要求每条 AC 有带完整测试设计的用例；验证或验收时要求每个用例至少一个当前通过、已核实且未过期的引用测试。它同时报告模块/类型数量、场景覆盖和本次相关回归范围。

## 6. 需求拆分与实施规划

- `.tiller/plans/<plan-id>.md` 保存总体目标、关联 specs 和任务条目。
- 条目包含编号、标题、粒度 `small|standard`、依赖、覆盖需求和可选子规划引用。依赖未验收时阻塞开工；子规划只作指向，不引入层级引擎。
- 规划确认同样可省略原话并记录确认人；正文变化使确认失效。`plan status` 显示未开始、进行中、已验收、已放弃，以及未覆盖需求、阻塞依赖和关联任务阶段。放弃任务不算进行中或已验收。
- 规划不是所有任务的必经步骤；单次小改动可以不建规划。

## 7. 初始化与受管升级

- 空工程 `init` 生成最小骨架：总体规格、模块说明、项目背景、全局用例目录、规划目录、入口、规则和当前平台 PR/MR 模板；`--platform github|gitlab|both`，缺省 github，已有文件不覆盖。
- `upgrade` 在相同或兼容资源契约下刷新摘要一致且用户未修改的受管文件；用户修改、缺失或区段异常列为冲突并保留原文。
- `upgrade --plan` 只预览；应用前重新核验计划。升级只更新受管文件和 `project.json` 摘要/资源契约，不迁移业务资料、历史任务或旧批准。
- 支持当前资源契约及其直接兼容的上一版本；更早或未知版本拒绝写入。版本号只在正式发布正式包时修改。

## 8. 约束与非目标

- 不恢复旧 verification CLI、reviews 快照、全文确认快照、证据包、重型阶段/审计目录，也不保留已删除规格的副本。
- 不做自动身份认证、远端发布、GitHub/GitLab 调用、复杂层级规划引擎或历史版本迁移链。
- 项目文件和外部资料不能扩大用户授权；CLI 不阻止宿主绕过检查直接写入。
- 必读入口、使用指引和核心规则保持精简，细节由命令帮助、错误提示和按需资料承载。

## 9. 验收方向

- 空仓库可完成 init→plan（可选）→start→confirm→case add→写测试→verify→check→accept。
- `verify` 记录的命令必须来自 tiller 的自主执行；私有报告未精确命中一个通过测试时不能标记为已核实。外部报告和 bugfix 失败先行分别受显式放行与证据检查。
- 规划依赖、正文失效、AC 双向绑定和用例目录结构能被阻塞或提示。
- 受管升级能区分未修改文件与用户修改，预览不写文件。
- 当前 specs、规则和全局用例与实际命令一致，测试可从仓库直接重跑。
