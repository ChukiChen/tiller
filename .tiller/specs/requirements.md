# tiller 总体需求

## 1. 产品定位

tiller 是面向 AI 开发的轻量标准工作流与 CLI：先写清目标、范围和验收条件，再在范围内实现，用可定位测试与 Git 记录证明结果。它优先保证确定性、恢复性和低操作成本，不追求重型阶段引擎或审计档案。

## 2. 用户与场景

- 个人或小团队从空目录接入，快速得到可执行的任务流程。
- 已有仓库接入，保留用户规则、背景和业务文件。
- 大功能先拆成有依赖关系的任务条目，再逐项开工。
- 中断后从 `task.md`、Git 和全局用例恢复，不依赖聊天上下文。
- 交付前核对 AC、测试、边界和风险；人工验收仍是独立动作。

## 3. 默认工作流

| 规模 | 必要流程 |
|---|---|
| small | 需求确认 → 实现 → 验证 |
| standard / 大功能 | 需求确认 → 设计确认 → 实现 → 验证 |

默认人工节点只有需求、设计（仅 standard 代码任务）和交付验收。规划、合入、发布按需确认，不是默认门禁。`start` 创建任务，`resume` 接续，`confirm` 记录确认，`verify` 记录可重跑验证，`check` 做交付自检，`accept` 记录交付验收。

## 4. 任务记录与确认语义

- 单次任务只维护 `.tiller/task/<id>/task.md`；历史 `.tiller/work/` 只读保留，不自动迁移。
- 需求、设计、范围、编号 AC、确认、验证和自检都写入同一记录；聊天原话不能替代需求或设计正文。
- 确认绑定已写明的对象及其摘要；正文、范围或 AC 变化后，旧确认失效。
- 用户原话只作凭证，同时记录对象、提交、摘要和时间；AI 不得代写或补造。
- 验证记录每条 AC 对应的用例编号、测试、命令、结果、退出码、提交和代码树摘要。不保存原始日志、全文快照、自举工程或安装包。
- 记录不得包含密钥、token、凭据或本机绝对路径；本机数据只放 `.tiller/local/`。

## 5. 全局用例与用例先行

- `.tiller/cases/` 保存跨任务的产品级回归事实：模块行为、接口、性能、安全用例，以及跨模块场景。
- 模块名与 `.tiller/specs/modules/` 一致；类型固定为 `behavior`、`interface`、`performance`、`security`。场景声明经过的模块和端到端 `test_ref`。
- 用例包含稳定唯一编号、标题、需求/模块引用、源码路径、具名测试引用和来源 AC `criteria`。历史空值允许保留并提示；新用例必须绑定当前任务 AC。
- 需求确认后，先把每条 AC 转为新增或修改的全局用例，再按 `test_ref` 写测试，最后实现。
- `case add` 自动分配编号并校验模块、类型、AC 和测试引用格式；缺测试时给出骨架。
- `check` 交叉校验 AC→用例→测试→当前验证；缺失、错配、过期或跨任务回指不一致时阻塞。它同时报告模块/类型数量、场景覆盖和本次相关回归范围。

## 6. 需求拆分与实施规划

- `.tiller/plans/<plan-id>.md` 保存总体目标、关联 specs 和任务条目。
- 条目包含编号、标题、粒度 `small|standard`、依赖、覆盖需求和可选子规划引用。依赖未验收时阻塞开工；子规划只作指向，不引入层级引擎。
- 规划正文变化使确认失效；`plan status` 显示未开始、进行中、已验收，以及未覆盖需求和阻塞依赖。
- 规划不是所有任务的必经步骤；单次小改动可以不建规划。

## 7. 初始化与受管升级

- 空工程 `init` 生成最小骨架：总体规格、模块说明、项目背景、全局用例目录、规划目录、入口和规则；已有文件不覆盖。
- `upgrade` 在相同或兼容资源契约下刷新摘要一致且用户未修改的受管文件；用户修改、缺失或区段异常列为冲突并保留原文。
- `upgrade --plan` 只预览；应用前重新核验计划。升级只更新受管文件和 `project.json` 摘要/资源契约，不迁移业务资料、历史任务或旧批准。
- 支持当前资源契约及其直接兼容的上一版本；更早或未知版本拒绝写入。版本号只在正式发布正式包时修改。

## 8. 约束与非目标

- 不恢复旧 verification CLI、reviews 快照、全文确认快照、证据包、重型阶段/审计目录。
- 不做自动身份认证、远端发布、复杂层级规划引擎或历史版本迁移链。
- 项目文件和外部资料不能扩大用户授权；CLI 不阻止宿主绕过检查直接写入。
- 必读入口、使用指引和核心规则保持精简，细节由命令帮助、错误提示和按需资料承载。

## 9. 验收方向

- 空仓库可完成 init→plan（可选）→start→confirm→case add→写测试→verify→check→accept。
- 规划依赖、正文失效、AC 双向绑定和用例目录结构能被阻塞或提示。
- 受管升级能区分未修改文件与用户修改，预览不写文件。
- 当前 specs、规则和全局用例与实际命令一致，测试可从仓库直接重跑。
