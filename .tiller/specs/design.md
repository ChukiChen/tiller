# tiller 总体设计

> 状态：讨论稿
> 依据：[总体需求](requirements.md)
> 本文提出总体方案，尚未确认的选择见[决策记录](decisions.md)。

## 1. 总体思路

tiller 将开发规范、项目记录和验证依据组织起来，让 AI 编程工具能够依据同一套要求持续推进工作。

开发者确定目标和授权边界；AI 编程工具负责理解、设计、实现和分析；tiller 提供工作依据、推进规则和检查支持。项目已有的构建、测试和发布工具继续承担各自的执行职责。

这一区分使 tiller 可以适用于不同技术栈，也避免把某个 AI 编程工具的使用方式写成通用规范。

## 2. 主要构成

以下是职责划分，不限定最终的代码模块或交付形式。

| 部分 | 职责 | 对应需求 |
|---|---|---|
| 工程初始化 | 确定管理范围，协调初次接入及已有工程的版本检查、管理资料更新与恢复 | R8、R9 |
| 开发规范 | 定义各类工作需要明确的信息、产出、授权边界和完成条件 | R1、R3、R4 |
| 项目记录 | 保存管理范围、当前项目知识，以及具体工作的目标、进展、决定、产出和验证依据 | R1、R2、R5、R8 |
| 工作推进 | 根据已有记录和完成条件识别下一步，处理阻碍、中断、要求变化和跨仓库依赖 | R2、R3、R8 |
| 验证与反馈 | 将要求与验证结果关联，呈现未满足项和剩余风险，把问题带回后续工作 | R4、R5 |
| 工具适配 | 提供不同 AI 编程工具读取规范与记录的接入方式，并衔接项目已有的检查工具 | R6、R8 |

自举使用这些相同的部分，作为 R7 的实际验证场景，不单独建立一套自身开发流程。

## 3. 各部分设计

### 3.1 工程初始化

**方案**：支持在当前工程中接入 tiller，管理信息随工程维护；也支持建立独立管理工程，登记多个仓库并统一管理。初始化先确定范围、识别已有资料与规则，再组织开发规范、项目记录和工具适配完成接入，检查可用范围及待处理问题。

再次接入时先核对版本与兼容性。CLI 自身更新和工程管理资料迁移分别处理；升级已安装程序不隐式改写工程。需要迁移时，先明确目标和影响，保留恢复依据，按实际结果更新版本与可用状态。

**边界**：两种方式共用后续工作机制。独立管理工程中，`.tiller/` 保存共同资料，业务仓库默认集中在同级的 `repositories/` 下，各仓库保留独立的版本历史；仓库标识与相对路径分别登记，旧直接子目录布局仍可使用。接入及重复初始化应保留已有内容、规则和工作记录，明确缺失信息、无法访问的仓库及冲突。初始化完成仅表示具备开始工作的基础。

### 3.2 开发规范

**方案**：围绕各类工作定义需要明确的信息、产出、授权边界和完成条件，供 AI 与工作推进共同遵循。按任务需要选择适用环节，并结合项目已有约定，形成当前工作的执行依据。

规范以触发条件、执行动作、所需依据、完成条件和失败处理表达，通过工作入口与专项规则供 AI 读取。规则引导、自动检查和实际可阻止的操作范围分别呈现，具体方案见[开发规范设计](modules/standards/design.md)。

**边界**：规范定义做事的要求，不保存具体工作的进度，也不包含特定工具的加载方式。未决问题与已确认要求分开处理；共同规范与仓库约定发生冲突时，应解决冲突后再推进受影响的操作。

### 3.3 项目记录

**方案**：用文件分别保存项目长期知识和具体工作的过程信息，通过引用关联。独立管理工程保存共同目标、跨仓库依赖和总体进展，各仓库的变更与验证结果关联到同一项工作。

**边界**：各仓库保留自身代码、专属约定和版本历史，不各自维护另一份总体进度。记录提供恢复与验证的依据，但仍需与实际产出核对；历史完成标记不能替代当前事实。

### 3.4 工作推进

**方案**：结合开发规范与项目记录，根据完成条件、依赖和授权识别下一步，由 AI 在授权范围内执行并更新进展。跨仓库工作按依赖协调；中断后核对现状再恢复，要求变化时回到受影响的环节。

总体需求与设计编写、模块细化和功能交付使用同一工作机制，按交付对象选择产物及检查方式。产物按需使用开发规范提供的模板或复用已有资料，文件生成不等于环节完成。具体记录、推进与模板衔接见[工作推进设计](modules/workflow/design.md)。

总体需求与设计确认后，以实施规划明确任务边界、需求覆盖、依赖及验证条件，展示并取得规划确认，再逐任务补足必要规格确认、实现和即时验证。骨架是空项目的首个普通实现任务，已有项目复用基础；单任务可简要规划，不省略确认与检查。具体记录、依赖处理及当前程序边界见[实施规划设计](modules/workflow/design.md#23-功能分块与项目骨架)。

已有项目先按接管范围调查现状和检查基线，再复用或补足总体规格及项目规范；局部任务明确相关依据与未覆盖范围。新项目在总体设计阶段形成项目规范，在骨架任务中落实检查配置。现状、期望、规则和验证记录分别维护，使用已有工具执行检查；具体衔接见[项目接手与规范建立](modules/workflow/design.md#24-项目接手与规范建立)，规则组织见[项目专属规范设计](modules/standards/design.md#24-项目专属规范的建立与检查)。

需求确认、设计确认、实施规划确认、交付验收、合入确认和发布确认作为适用的前置依赖。先展示具体产物及下一步，取得对应用户决定后才推进；阶段内自主执行。确认记录绑定内容、范围及来源，内容变化后重新判断有效性，中断后保留待确认事项。具体机制见[关键节点设计](modules/workflow/design.md#43-关键节点与进入条件)。

涉及代码交付时，通过 Git worktree 和工作分支隔离开发。当前工程的资料与代码随同一仓库交付；独立管理工程集中维护共同资料，各业务仓库分别关联分支和 MR/PR，管理资料单独版本化。提交、推送和评审操作依据明确授权，合入保留人工确认；整体交付核对所有约定结果。目录、记录交接与异常处理见[隔离开发与评审合入设计](modules/workflow/design.md#11-隔离开发与评审合入)。该增量已在 0.3.0 实现，当前适配拒绝无法原子保护源和目标的自动合入；真实平台验证及用户验收仍待完成，当前范围见[实现进度记录](../work/20261016-implementation-progress/work.md)。

**边界**：不要求所有任务走完固定阶段。需要人工决定、缺少前置条件或检查失败时，记录阻碍和待处理事项。执行前明确目标仓库及适用授权，管理工程的授权不能代替仓库自身的授权；完成判断必须引用验证依据。

### 3.5 验证与反馈

**方案**：汇集项目检查结果、评审意见和必要的人工验证，关联相应要求及被验证的产出。发现的问题交回工作推进处理；要求或产出变化时重新判断已有结论是否适用，发布结果与使用反馈进入项目记录。

**边界**：检查通过与满足全部要求分别呈现，缺失证据不能视为通过。跨仓库交付需核对相关仓库的结果及协作效果，不能以单个仓库通过代替整体完成。验证与反馈不替代项目原有的测试和发布工具。

### 3.6 工具适配

**方案**：为 AI 编程工具提供规范与记录的读取入口，使其按管理范围和具体任务获取所需资料；衔接项目已有检查工具，将结果提供给验证与反馈。初始化使用这些接入方式建立入口，后续工作继续复用。

**边界**：只处理工具差异，不改变通用规范，也不维护独立的需求或进度。对宿主工具不支持的能力明确说明限制；加载方式和具体集成机制在详细设计中确定。

## 4. 协作关系

各部分围绕同一项工作协作：

1. **建立环境**：工程初始化确定管理范围，借助工具适配接入规范和项目记录。
2. **开展工作**：工作推进读取规范与记录，由 AI 执行当前可开展的工作，并保存进展和产出。
3. **判断结果**：验证与反馈读取要求及产出，收集检查结果，向工作推进提供完成依据或待处理问题。
4. **继续改进**：变更与反馈更新项目记录，工作推进据此调整后续工作，必要时重新验证。

项目记录贯穿全过程，工具适配提供持续接入；中断恢复和跨仓库协作使用同一套工作依据。

## 5. 职责边界

| 参与方 | 负责事项 | 边界 |
|---|---|---|
| 开发者 | 明确目标、确认需求、设定授权范围，处理需要人工决定的事项 | 不要求逐项手动推动已授权的工作 |
| AI 编程工具 | 澄清、提出方案、实施、分析问题并维护相关记录 | 不自行扩大授权，也不以完成声明替代验证依据 |
| tiller | 提供规范、记录约定、推进规则及检查支持 | 不替代 AI 编程工具或项目自身的构建、测试和部署系统 |
| 项目工具 | 执行构建、测试、静态检查、发布等具体操作 | 单次执行成功不代表全部需求已满足 |

需要判断和创作的工作由 AI 完成；格式检查、关联检查和结果汇总等确定性工作由工具辅助。自动检查只声明其实际覆盖的范围。

## 6. 技术方案与运行环境

### 6.1 CLI 与技术栈

tiller 通过 CLI 提供操作入口，开发者和 AI 调用同一套执行逻辑。入口负责参数、交互、结果及退出状态；各模块负责业务判断；文件、路径、进程与适配操作集中在基础能力中。

技术方案已确认为 TypeScript + Node.js：源码使用 TypeScript，开启严格类型检查，编译为 JavaScript 后运行，通过 npm 分发并暴露 `tiller` 命令。当前实现以 Node.js 22 为最低运行基线，不引入第三方运行时库；Git 仓库识别和共享资料忽略检查使用本机 Git。具体实现与验证见[首个交付实现约定](../work/initial-delivery/design.md)。

基础初始化由 CLI 完成确定性操作，不依赖模型调用；AI 可辅助整理工程背景和解释语义冲突。参数齐全时支持非交互执行，缺少必要信息时返回明确的问题，不在非交互环境中等待输入。

### 6.2 跨平台约定

候选支持平台为 Windows、macOS 和 Linux，具体系统版本、CPU 架构与 Node.js 支持范围需形成兼容矩阵（Q18）。各模块遵循相同的平台约定：

- 路径通过平台路径接口解析，区分可共享的相对位置与本机定位信息，处理空格、中文、大小写及路径越界问题。
- 文件操作使用跨平台接口，保留已有内容的编码和换行；针对文件占用、权限和替换失败提供明确结果与恢复路径。
- 外部程序调用使用明确的工作目录和参数列表，避免依赖某种 Shell 的命令拼接；涉及 Git 时单独检查其可用性。
- 发布包的入口、静态资料定位和安装后执行应在各支持平台验证，不能只验证源码运行。

### 6.3 版本与升级边界

分别记录 CLI 版本、工程记录格式版本，以及工程已应用的规范和适配资源版本。兼容性按显式支持范围判断，不用“CLI 版本较新”代替兼容结论。

CLI 包的安装和更新属于分发层；工程初始化负责已有工程的检查、资源更新和记录迁移。普通读取或重复初始化不自动进行破坏性迁移，也不自动降级较新的工程资料。

需要更新的工程先生成变更与恢复计划，再执行迁移并复验。用户编辑过的规则和入口进行差异协调，任务历史不因模板更新而重建。没有适用迁移路径时，保留工程并说明限制。

### 6.4 验证方式

类型检查、模块测试与 CLI 集成测试覆盖核心逻辑；各支持平台验证实际安装、首次初始化、重复执行、升级和中断恢复。用中文及含空格路径、已有自定义规则、多仓库部分失败等场景检查结果一致性。

验证的是 tiller 自身兼容性，不代表所有被管理项目都天然支持同样的平台。具体兼容矩阵与测试证据随发行版本维护。

## 7. 工程资料组织

### 7.1 目录职责

两种初始化方式都使用 `.tiller/` 作为工程资料的统一管理目录，按用途划分，对应 R2、R5、R8、R9：

```text
.tiller/
├── specs/                  # 持续维护的产品规格
│   ├── requirements.md     # 总体需求
│   ├── design.md           # 总体设计
│   ├── decisions.md        # 项目级决策
│   └── modules/            # 各模块的详细需求与设计
├── rules/                  # 开发规范与项目规则
├── context/                # 项目背景、代码地图及资料索引
├── work/                   # 单次工作的变更说明与过程记录
└── local/                  # 本机及临时数据
```

| 目录 | 保存内容 | 边界 |
|---|---|---|
| `specs/` | 总体及模块需求、选定设计和长期决策 | 描述产品应具备的能力及方案，保留文档确认状态；未确认草稿不能视为正式要求 |
| `rules/` | 做事时遵守的规范、质量要求和操作边界 | 区分 tiller 提供的内容与项目自定义规则，不保存任务进度 |
| `context/` | 现有项目事实、术语、代码位置及外部资料引用 | 说明项目现状，不复制需求、设计或规则；未知信息明确标记 |
| `work/` | 某次工作的变更需求、设计、计划、进展、过程决定及验证证据 | 记录一次交付的范围和经过，不维护另一份完整模块规格 |
| `local/` | 本机定位信息、缓存、锁、运行日志和升级恢复副本 | 排除版本管理，不能作为团队共享事实或验收结论的唯一来源 |

工程配置与版本元信息放在 `.tiller/` 根目录。初始化设计提出 `project.json` 承载共享元信息、`index.md` 提供资料导航的候选方案，具体模式仍待确定，见[初始化文件清单](modules/initialization/design.md#24-初始化文件清单候选)。共享信息引用工程相对位置，本机覆盖信息放入 `local/`。规格、规则、上下文、工作记录及共享元信息随工程版本管理；本机恢复副本不是可跨机器恢复的保证。

### 7.2 模块规格与具体工作

`specs/modules/<module>/` 按产品能力划分，持续维护该模块的需求与设计；`work/<work-id>/` 按一次具体工作划分。两者是多对多关系，也不与代码仓库一一对应。

具体工作可按需要建立 `requirements.md`、`design.md`、`plan.md` 和验证记录。这里的需求与设计只描述本次变化、影响与取舍，通过需求编号、文档引用及版本关联到模块规格，不复制整份模块文档。新工作目录推荐 `YYYYMMDD-主题`，例如 `20261015-student-service`；日期取创建日，接续不改名，已有目录保留以兼容历史引用。CLI 使用显式输入的完整标识，不自动补日期；状态记录约定见工作推进设计及对应实现记录。

例如“支持升级”可同时关联初始化与工具适配模块，而初始化模块还会关联首次实现、路径修复等不同工作。跨仓库工作在同一个工作目录中记录目标、任务归属、依赖及验证结果，不在各模块或仓库中重复记录总体进度。

未接受的变更方案保留在工作记录中。变更被接受并交付时，更新受影响的长期规格，保留工作与交付版本的关联；后续修改规格不能改写旧工作的验证事实。

### 7.3 创建、接入与升级

初始化建立五类目录的管理入口和必要元信息，内容按需产生，不生成空的模块规格或整套工作文档。目录采用稳定名称，不以数字编号表达开发顺序。

`AGENTS.md` 作为通用工作入口，保留资料读取、工作推进、维护与验证原则，引导执行前读取适用的项目规则。项目背景放入 `context/`，项目专属约束放入 `rules/`；不将 tiller 自身的开发阶段、语言或 Git 限制作为其他项目的默认规则。读取入口兼容尚未创建的资料，必要依据缺失时明确说明。本仓库分别使用 `context/project.md` 和 `rules/project.md` 承载这些内容。

接入已有工程时，可以迁入已有工程资料或建立引用，保持单一维护来源。迁入属于明确的文件变更，需要保留内容并修复引用，不能静默搬动用户资料。本仓库将原工程文档迁入 `specs/`，原始草稿保留在 `specs/archive/`。

`specs/`、`context/` 与 `work/` 中的项目内容不属于可用模板覆盖的生成物。升级仅处理明确计划涉及的受管资源或格式转换，保留用户内容、引用和历史。恢复操作依赖的原件可放在 `local/`，恢复依据缺失时不能假定可安全回退。

## 8. 关键取舍

- **采用文件保存工作依据**：便于查阅、版本管理和跨工具接续。代价是记录可能滞后，因此恢复和验证时必须核对实际产出。
- **区分目标、方案与实际结果**：需求说明预期行为，设计说明选定方案，实际产出说明当前实现。出现冲突时记录差异并处理，不用“代码总是优先”之类的统一排序消除冲突。
- **按工作需要选择环节**：简单任务减少不必要的产出，但仍保留目标、授权边界和验证依据。具体裁剪规则在详细设计中展开。
- **区分流程约定与强制控制**：规则要求关键节点人工确认；CLI 检查自身入口的记录和内容关联，宿主外部操作的拦截另由适配能力提供。文件摘要不能证明决定来自人，来源无法核验时不能报告人工确认已验证；具体边界见工作推进设计第 4、9 节，机制仍待设计确认。

## 9. 自举方式（建议）

建议先用已确认的最小规范指导自身工作，再逐步以实际工具替代重复操作。自举不以完整工具集已经存在为前提。

1. **建立起点**：选择适合自身管理范围的初始化方式，明确自身开发采用的要求、记录方式、授权边界和验证条件。当前文档可作为输入，但不因此视为已经完成自举验证。
2. **用于真实工作**：选择一项自身开发任务，使用约定推进，并记录实际产出、验证结果和使用困难。人工补足的操作应如实记录。
3. **改进并验证**：将使用问题转化为改进要求。规范或工具变更后，记录后续工作采用的版本，并验证原有问题是否得到解决。

自举证据应能关联使用的规范、具体任务、交付结果及验证依据。规范变更不能自动把过去未通过的工作改判为通过。

本节是 Q13 的候选方案，具体启动范围和通过标准尚待确认。自身使用与独立外部示例共同检验适用性，外部示例仍位于独立仓库。
