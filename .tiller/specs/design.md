# tiller 总体设计

## 1. 设计原则

文件是事实源，Git 是历史；CLI 只做可重复检查，不承担身份认证。默认路径短、参数少，复杂能力按需启用。任何确认都绑定已写明的对象摘要，任何验证都绑定可重跑命令与代码树。

## 2. 主要构成

| 部分 | 职责 |
|---|---|
| `src/core.ts` | 工程初始化、元信息、受管区段、状态检查 |
| `src/flow.ts` | task 的 start/resume/confirm/verify/check/accept |
| `src/plans.ts` | 规划、条目依赖、确认和状态 |
| `src/cases.ts` | 全局用例读取、校验、`case add`、回归提示 |
| `src/upgrade.ts` | 受管文件预览、冲突判断、原子刷新 |
| `src/cli.ts` | 命令解析、帮助、JSON 输出和退出码 |
| `resources/` | 分发的入口、使用指引、规则和启动器 |

## 3. 默认工作流

`start` 写入完整需求与编号 AC，记录类型、规模、范围、基线和开工前已有改动；标准代码任务补写设计后再确认。`confirm` 保存真实原话、对象摘要、提交和时间。`verify` 按具名测试找到全局用例，运行或登记命令并绑定当前代码树。`check` 汇总确认、AC 映射、范围、测试弱化、安全和未提交改动。`accept` 只在技术自检通过后记录交付验收。

## 4. 规划

规划文件由可读正文和一行规划元信息组成。条目粒度、依赖、覆盖需求、可选子规划引用和确认摘要保存在元信息中；可见正文必须与元信息一致，否则确认失效。子规划仅作条目指向，不递归调度。`start --plan <id> --item <item>` 读取已确认条目、继承粒度并检查依赖是否已验收；未完成直接阻塞。任务元信息保存规划归属。`plan status` 从任务验收记录推导条目状态，并列出未覆盖需求和阻塞依赖。

## 5. 全局用例

目录：

```text
.tiller/cases/
  index.md
  modules/<模块>/{behavior,interface,performance,security}.json
  scenarios/<场景>.json
```

模块文件声明 `module`/`kind`，场景声明 `modules`。每条用例必有 `id`、`title`、`requirements`、`modules`、`test_ref`、`source`；新用例另有 `criteria`。读取时校验路径、模块、类型白名单、编号唯一、具名测试存在和场景模块存在。`case add` 在工程锁内分配下一个 `CASE-NNN`，写入对应文件，缺测试文件时返回建议骨架。

## 6. 用例先行与检查

`verify` 以 `test_ref` 命中用例编号写入 `task.md`。`check` 要求：

1. 每条 AC 有最新验证和至少一个用例；
2. 用例存在、测试引用一致且仍存在；
3. 用例 `criteria` 回指当前任务 AC，或该用例在本任务新增/修改；
4. 最新验证通过且代码树未变化；
5. 用例库结构有效，并报告模块数量、场景覆盖和回归提示。

无 Git 时范围检查降级为提示；有 Git 时同时检查越界、未提交改动、删除/跳过/弱化测试。

## 7. 初始化与升级

`init` 只补缺失骨架，维护 `AGENTS.md` 区段、`.gitignore` 本机排除和 `.tiller/index.md` 导航；已存在且冲突的入口拒绝覆盖。`project.json` 保存模式、仓库映射和各受管文件的规范化摘要。

`upgrade` 读取当前或兼容上一资源契约，按记录摘要判断受管文件是否被用户修改。未修改文件按分发资源或固定区段重建；修改、缺失和异常区段只报告冲突。预览摘要绑定输入、期望结果和元信息；应用时在锁内重新预览并原子写入，成功后更新摘要与 `resourceVersion`。

## 8. 错误与恢复

输入错误返回参数错误；未初始化、版本不支持、冲突、依赖阻塞、未确认、未验证、范围越界等使用稳定错误码并说明下一步。写操作使用事务与恢复日志，失败后可用 `recover` 恢复；不得凭摘要重建缺失文件或覆盖用户修改。

## 9. 验证入口

`npm run build`、`lint`、`typecheck`、`npm test`、`npm run test:package`。构建必须实际编译 TypeScript；局部规则检查不能替代完整测试。
