## 1. 背景与问题

开发者已经普遍在用 Cursor、Claude Code、Codex 这类 AI 编程工具，但普遍停在“让 AI 写一段代码”这一步。常见问题有：

1. **只覆盖编码**：需求、设计、测试、评审、发布、运维基本没有 AI 参与，就算有，也是零散提问。
2. **上下文靠聊天**：需求和决策留在对话里，换个会话、换个工具、换个人就丢了。AI 写着写着就跑偏，也没有办法拉回来。
3. **没有关卡**：AI 产出没经过确认就往下走，出问题之后才发现需求一开始就理解错了。
4. **“做完没有”靠感觉**：没有验收标准，也没有独立审查，测试只是在凑覆盖率。
5. **多仓库、多工具不好协同**：前后端分仓、多人用不同 Agent，规范没法共享。

现有的 AI 工作流方案往往概念多、偏团队和企业场景，或者绑定特定平台和技术栈，个人开发者上手门槛高。

**tiller 要做的**：一套轻量、不绑定技术栈、个人开发者也能马上用起来的 AI 软件工程方法论和工具集，覆盖全流程。

## 2. 目标与非目标

### 2.1 目标

- **G1 全流程**：需求 → 设计 → 编码 → 测试 → 评审 → 发布 → 运维，每个阶段都有明确的输入、产出和关卡。
- **G2 可信**：事实在文件里，不在聊天里。每次决策可追溯，“做完”由命令和独立审查来判定。
- **G3 轻量**：一个人、一个仓库、半小时之内能跑起来；需要时再逐步加上多仓库、并行和自动化。
- **G4 多 Agent**：同一份规范能在 Codex、Claude Code、Cursor 上用，**Codex 作为一等支持对象**。
- **G5 可解释**：每个机制都能讲清楚“为什么”，方便学习和推广。
- **G6 自举**：tiller 本身也必须用 tiller 开发，自身开发是产品的实际使用场景。Codex 是执行开发的 Agent，tiller 提供开发所遵循的方法和工具；自举启动方式和验收标准见 Q13。

### 2.2 非目标

- 不自研大模型，也不做模型网关。
- 不做 IDE 或 Agent 本体，只做 Agent 之上的规范、模板和编排。
- 不绑定语言或框架。
- 第一版不做 Web 控制台、SaaS 或团队权限系统。
- 不追求面面俱到的阶段完备度，先做“最小可用的全流程”。

## 3. 目标用户与场景

### 3.1 用户画像

| 画像 | 特征 | 诉求 |
|---|---|---|
| 主力：后端/前端/全栈开发者 | 用过 AI 工具，没有成体系的方法 | 让 AI 稳定交付能上线的功能，而不只是 demo |
| 次要：小团队技术负责人 | 3–10 人，想统一 AI 使用规范 | 规范能共享、能审计、新人能直接上手 |
| 次要：独立开发者 | 一个人负责全流程 | 让 AI 补上测试、评审、发布这些自己顾不上的环节 |

使用者以中文用户为主。

### 3.2 典型场景

1. **新功能**：在已有仓库里加一个功能，从需求澄清走到上线。
2. **缺陷修复**：带复现和回归测试的 bugfix，走轻量流程。
3. **接手陌生仓库**：先让 AI 生成项目总览和代码地图，再开始开发。
4. **重构**：不改变行为，用测试和契约兜底。
5. **跨仓库需求**：前后端分仓，一个需求同时改两个仓库。
6. **无人值守长任务**（后期）：夜间批量修 lint、补测试、做审计。
7. **tiller 自身开发**：用 tiller 推进自身的需求、设计、实现和验证，让自身开发持续检验方法与工具是否可用。

## 4. 核心理念与原则

1. **文件即事实**：每件工作都有状态文件，Agent 每次会话开始都先读它，不以聊天记录为准。
2. **活文档与过程记录分开**：全局文档只描述“当前是什么、为什么”；“这次做了什么”放在工作项目录里。
3. **人把方向，AI 干活**：每个阶段结束都要人工确认才能往下走；高风险区域先出计划，或者先问人。
4. **有冲突时有明确的优先级**：代码、契约、文档冲突时以谁为准要写清楚。
5. **“做完”靠验证，不靠自述**：每个阶段有退出标准，由命令（test/build/lint）和独立评审判定。
6. **渐进式复杂度**：默认单仓库、串行、轻量流程；多仓库、并行 worktree、长任务都按需开启。
7. **Agent 无关**：规范的源头只有一份，再生成各 Agent 的适配文件。

## 5. 概念模型（草案）

| 概念 | 含义 |
|---|---|
| Project | 一个启用了 tiller 的仓库或工作区 |
| Work Item（工作项）【名称待定】 | 一件要交付的事：一个功能、缺陷或重构 |
| Stage（阶段） | 生命周期中的一步，有输入、产出和关卡 |
| Flow（流程档位） | 一组 stage 的组合，如 feature/bugfix/refactor |
| Gate（关卡） | 阶段之间的人工审批和自动检查 |
| Unit（单元） | 工作项内可以独立实现、只落在一个仓库的一块 |
| Living Docs（活文档） | 项目总览、架构、术语、领域设计 |
| Rules（规则） | 给 AI 的约束：AGENTS.md、分区权限 |

## 6. 功能需求：按生命周期阶段

每个阶段统一描述为：**输入 → AI 做什么 → 产出 → 关卡**。产出路径只是示意，具体目录结构见 7.1。

### 6.1 需求（Requirements）

- F-REQ-1：从一句话需求生成**澄清问题清单**，人把答案直接写在文件里（如在每个问题下写 `[Answer]:`）。
- F-REQ-2：产出 `requirements.md`：背景、用户故事、验收标准（可测试）、非功能需求、不做什么。
- F-REQ-3：每条需求有编号，后续设计、任务、测试都能追溯到它。
- 关卡：人工确认需求；自动检查每条需求都有验收标准。

### 6.2 设计（Design）

- F-DES-1：读活文档（总览、架构、术语）后再做设计，产出 `design.md`，内容包括方案、模块边界、数据和接口变更、备选方案和取舍。
- F-DES-2：设计只写概念、边界、约束和决策理由，不写到方法签名一级。
- F-DES-3：把工作拆成 Unit，标出依赖关系；每个 Unit 只落在一个仓库。
- F-DES-4：有接口或数据结构变更时，契约文件（OpenAPI、JSON Schema 等）是源头，先改契约。
- 关卡：人工确认设计；涉及受保护区域时强制 plan-first。

### 6.3 编码（Coding）

- F-COD-1：按 Unit 生成带退出标准的任务计划，再逐项实现。
- F-COD-2：遵守 AGENTS.md 中的分区权限，生成物和受保护文件不能手改。
- F-COD-3：每个 Unit 完成后更新状态文件，并在提交信息里带上工作项编号。
- F-COD-4（后期）：并行模式下每个 Unit 一个 git worktree。
- 关卡：build/lint/typecheck 通过。

### 6.4 测试（Testing）

- F-TST-1：根据验收标准生成测试用例清单，再写测试（不以覆盖率为目标）。
- F-TST-2：bugfix 必须先有能复现问题的失败测试。
- F-TST-3：输出需求和测试的追溯表。
- 关卡：test 命令通过，每条验收标准都有对应测试。

### 6.5 评审（Review）

- F-REV-1：用**独立会话或子代理**做评审，不复用执行者的上下文。
- F-REV-2：评审清单覆盖需求符合度、设计一致性、安全、测试质量和文档是否需要更新。
- F-REV-3：评审意见落在文件里，修复后再复审。
- 关卡：没有阻断级问题，人工确认。

### 6.6 发布（Release）

- F-REL-1：生成变更说明和发布检查清单（配置、迁移、回滚方案、灰度）。
- F-REL-2：提供 CI 集成示例（如 GitHub Actions 中跑 tiller 检查）。
- 关卡：人工确认发布；tiller 不替用户推送或部署。

### 6.7 运维（Operations）

- F-OPS-1：为线上问题提供排查流程模板：现象 → 假设 → 证据 → 结论 → 修复 → 复盘。
- F-OPS-2：复盘结论沉淀为规则或经验条目（学习闭环）。
- F-OPS-3（后期）：运维手册模板和可观测性检查清单。

### 6.8 项目初始化与接手（贯穿所有阶段的前置步骤）

- F-INI-1：在已有仓库上生成**项目总览四件套**：`overview.md`（项目是什么、整体架构）、`codebase-map.md`（代码地图）、`glossary.md`（术语）；有业务流程时再加 `flows.md`（流程、角色、状态机）。
- F-INI-2：目标是新的 AI 会话**3 步以内**就能找到该读的文档。

## 7. 功能需求：横切能力

### 7.1 状态与事实源

- X-ST-1：每个工作项一个目录（示意 `tiller/work/<YYMMDD>-<slug>/`），里面放 `state.md`（当前阶段、关卡状态、下一步）、各阶段产物和决策日志。
- X-ST-2：`state.md` 是这个工作项进度的唯一事实源，Agent 每次会话开始都要先读它。
- X-ST-3：状态文件格式【待定】：纯 Markdown（人好读），或者 Markdown 加 YAML front matter（机器好解析）。
- X-ST-4：工作项目录默认提交到 git，运行时临时文件放进 gitignore。
- X-ST-5：提供 `truth-and-precedence.md` 模板：代码行为 > 契约/模型 > 活文档 > 过程记录，并配套冲突处理规则。
- X-ST-6（可选）：活文档带新鲜度标记（fresh / stale / unknown），AI 不能自己把文档标成 fresh。

### 7.2 文档路由

- X-RT-1：根目录 `AGENTS.md` 是 AI 的最高约束入口，写明先读什么、按任务类型读什么、哪些区域禁止手改。
- X-RT-2：按任务类型提供阅读清单（如 backend、frontend、testing），避免 AI 什么都读或什么都不读。
- X-RT-3：分区权限分级，初步设想 5 级（implement、plan-first、ask-first、research-only、blocked），是否精简【待定】。

### 7.3 门禁与审批

- X-GT-1：每个阶段结束时有人工审批，审批结果写进 `state.md` 和决策日志。
- X-GT-2：自动检查分两档：advisory（只提示）和 blocking（阻断）。检查内容包括必填章节、追溯完整性、命令通过等。
- X-GT-3：流程档位决定跑哪些阶段，初步考虑 `feature`、`bugfix`、`refactor`、`spike` 四档。
- X-GT-4：人在关卡上的纠正可以沉淀为规则，确认后写回规则文件。

### 7.4 多仓库（v0.3 之后）

- X-MR-1：工作区模式：工作区根目录放 `tiller/` 和规则，各代码仓库作为直接子目录。
- X-MR-2：工作项记录涉及哪些仓库；每个 Unit 只属于一个仓库，git 操作要指定仓库。
- X-MR-3：可选的 `repos` 清单和同步命令（克隆缺失仓库、维护 `.gitignore`）。
- X-MR-4：过程记录和各子仓库的 commit 之间要能关联起来（比如在 state 里记录各仓库的 commit）。

### 7.5 多 Agent 适配

- X-AG-1：规范只有一个源头（tiller 自己的 rules、stages、templates），再生成各 Agent 的适配文件。
- X-AG-2：首批目标：**Codex（一等支持）**、Claude Code、Cursor。适配方式（AGENTS.md、skills、slash 命令、rules 目录）以各工具当时的官方文档为准，开发时再核实。
- X-AG-3：适配层只做“怎么加载”，不改变规范内容；同一工作项可以在不同 Agent 之间接力。

### 7.6 长任务自动化（v1.0 之后，探索性的）

- X-AU-1：任务单（JSON）：目标、授权边界、验证命令。
- X-AU-2：确定性状态机负责流程，AI 只负责每一步里的判断和创作，“做完没有”由命令和独立审计判定。
- X-AU-3：小改动不要背上全套仪式，要支持把多个小工作项打包处理。

## 8. CLI 初步设想（不代表 MVP 一定要做 CLI）

| 命令 | 作用 |
|---|---|
| `tiller init [--agent codex,claude,cursor]` | 在仓库中生成 AGENTS.md、规则、模板和适配文件 |
| `tiller new <描述> [--flow feature]` | 新建工作项目录和 state.md |
| `tiller status` | 显示当前工作项的阶段、关卡和下一步 |
| `tiller check` | 运行自动检查（必填章节、追溯、命令） |
| `tiller approve <stage>` | 记录人工审批（也可以直接在 Agent 会话里完成） |
| `tiller doctor` | 检查安装、适配文件和文档新鲜度 |
| `tiller sync` | 规范源头变了之后，重新生成各 Agent 的适配文件 |
| `tiller workspace sync`（后期） | 多仓库同步 |

- 实现语言【待定】：TypeScript/Node（生态熟、npx 分发方便）、Go（单二进制）、Python。
- 分发方式【待定】：npm / Homebrew / 直接下载二进制。
- 原则：CLI 只做确定性的工作（生成、检查、记录），不调用模型；创作性的工作交给 Agent。

## 9. 交付形态与版本规划（草案）

| 版本 | 内容 | 验收 |
|---|---|---|
| **v0.1 MVP** | 方法论文档 + 模板（AGENTS.md、state.md、各阶段产物模板、truth-and-precedence）+ Codex 适配；**形态待定，见 Q1** | 在一个真实小项目上用 Codex 走完一次 feature 流程 |
| v0.2 | `tiller init/new/status/check` 最小 CLI；加上 Claude Code、Cursor 适配；bugfix、refactor 档位 | 3 个 Agent 上都能走通同一个工作项 |
| v0.3 | 项目总览四件套生成、文档新鲜度、多仓库工作区 | 外部示例仓库中的前后端分仓场景跑通 |
| v0.4 | 规则学习闭环、CI 集成示例、发布和运维模板 | 全部 7 个阶段都有模板和检查 |
| v1.0 | 稳定的目录约定和 CLI 接口，外部示例仓库完整可用 | 对外公开发布 |
| v1.x | 并行 worktree、长任务状态机（探索） | — |

开源仓库计划包含的内容（示意）：

```
tiller/
├── README.md            # 语言见 Q5
├── LICENSE              # 见 Q6
├── AGENTS.md            # tiller 自身开发规范（遵循 tiller，以 Codex 为主要开发 Agent）
├── docs/                # 方法论“是什么、怎么用”
├── templates/           # 各阶段产物模板
├── adapters/            # codex / claude-code / cursor
└── cli/                 # v0.2 之后
```

示例项目不放在 tiller 仓库里，而是一个独立的外部仓库，tiller 文档只链接到它。

## 10. 成功指标（草案）

| 类别 | 指标 | 初步目标 |
|---|---|---|
| 可用性 | 新用户从 init 到走完第一个工作项的时间 | ≤ 30 分钟 |
| 有效性 | 外部示例项目中，需求到测试的追溯完整率 | 100% |
| 有效性 | 换一个会话或 Agent 后不用解释就能接着做 | 外部示例项目里能演示 |
| 社区 | 外部用户反馈的 Issue / 采用案例 | 【待定】 |

## 11. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 流程太重，用户觉得仪式感过强 | 弃用 | 默认用轻量档位，小改动走 bugfix/spike |
| Agent 工具迭代快，适配文件很快过时 | 维护成本高 | 适配层薄，规范只有一个源头，`tiller doctor` 检查 |
| 示例不足 | 外部用户上手难 | 外部示例仓库覆盖每个阶段，文档中链接过去 |
| 一个人开发，范围失控 | 延期 | 严格按版本推进，v0.1 只做 Codex 加模板 |
| 和同类方案比较时显得功能少 | 定位模糊 | 突出轻量、中文、教学友好和全流程闭环 |
| 模板质量依赖模型能力 | 效果不稳 | 每个模板配示例和检查，在真实项目上验证 |

## 12. 待讨论问题

- **Q1 MVP 形态**：v0.1 只做“文档 + 模板 + Codex 适配”（零代码，最快），还是一开始就带最小 CLI（`init/new/status`）？
- **Q2 CLI 语言和分发**：TypeScript/Node（npx）、Go（单二进制）还是 Python？
- **Q3 首批 Agent**：只做 Codex，还是 Codex、Claude Code、Cursor 同时做？各自用什么加载机制（AGENTS.md、skills、slash 命令）？
- **Q4 阶段和档位**：7 个阶段是否就是最终划分？首批档位是不是 feature/bugfix/refactor/spike？
- **Q5 仓库语言**：中文为主、中英双语，还是英文为主加中文文档？（CLI 输出和模板的语言也要一起定）
- **Q6 许可证**：MIT 还是 Apache-2.0？
- **Q7 术语**：工作项叫 intent、task、work item 还是中文名？状态文件叫 `state.md` 吗？目录叫 `tiller/` 还是 `.tiller/`？
- **Q8 状态文件格式**：纯 Markdown，还是带 YAML front matter（方便 CLI 解析）？
- **Q9 关卡强度**：审批是靠 Agent 会话里的人工确认（软约束），还是要 CLI 或 git hook 强制（硬约束）？
- **Q10 权限分级**：保留 5 级，还是精简成 3 级（自主 / 先出计划 / 先问人）？
- **Q11 示例项目**：官方示例项目（独立的外部仓库）用什么真实项目？
- **Q12 多仓库和长任务**：是否确认推到 v0.3 和 v1.x 之后？
- **Q13 自举的启动与验收**：已确定用 tiller 开发 tiller。何时开始、工具尚未成形时怎样执行自身流程、如何留下可验证证据，仍待确定。
