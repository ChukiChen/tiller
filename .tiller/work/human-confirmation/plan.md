依据：本工作所引用的需求、工作推进设计第 4、9 节、开发规范设计第 4.1 节、初始化设计第 8.5 节。用户在看到设计及约束边界说明后要求“继续”，本轮进入实现。设计确认不等于最终交付验收。

## 实现安排

1. 将资源和程序版本更新为 0.2.0。保留 0.1.0 资源基线，支持只读预览及显式应用的工程升级，保护入口区段外内容、自定义规则及历史记录。
2. 更新通用入口、共同和专项规则及文档模板：需求确认后设计、设计确认后实现；验收与发布分别确认，阶段内自主推进。
3. 实现独立确认记录与请求快照、来源和复核记录、内容及上游有效性检查。使用 JSON 输入文件承载复杂请求与决定，避免把大段用户决定放在命令行中。
4. 接入请求确认、记录决定和检查节点的 CLI；文档完成必须绑定对应验收请求，旧完成仅作为历史文档交付记录读取。无来源或无实际复核依据不写新版完成，不声称自动认证来源。
5. 验证缺少确认、拒绝、条件未满足、内容变化、来源变化、接续、越界路径、兼容写入口和升级冲突；正向验证人工决定复核后的正常完成。
6. 更新说明、自身接入及独立 Java 测试工程的 tiller 资源，保留已有业务代码、文档和历史。用新的隔离工作验证学生服务默认等待行为，不覆写已有学生服务实现。

## 分工与依赖

2026-10-15 范围补充：用户建议工作目录加日期前缀，随后要求继续。采用显式 `YYYYMMDD-主题` 推荐命名，保留旧标识兼容；同步命名规则、CLI 校验与示例，验证日期标识的创建、确认、完成和接续。0.2.0 尚未发布，规则按本次最终包内容核对并显式更新两个测试工程的受管规则，不改工作历史。

- 确认模块负责新记录、判断和专项测试，不改工作入口和旧记录接口。
- 初始化升级负责资源版本、基线、预览与应用和专项测试。
- 规则资源负责入口、规则与模板，不直接覆盖已接入的工程资源。
- 主执行负责 CLI、工作完成与接续集成、兼容测试、说明、实际升级和整体验证。

具体接口和记录字段按已确认设计实现，工程细节在实现记录中注明；不引入新依赖。先完成可测试的模块，再集成 CLI，最后在构建后的版本上更新已有工程。

## 通过依据与边界

运行 lint、严格类型检查、自动测试及隔离安装验证，保留实际结果与未覆盖项。真实 AI 行为验证与确定性测试分开记录；若宿主能力不足不能把模拟输入当作真实用户批准或真实 AI 验证。

确认记录中的来源复核是执行者对真实用户输入的记录，不是身份认证；同权限者可绕过 CLI，自动转换及宿主直接写入拦截不在本次实现范围。只能报告本次实际验证的平台。最后呈现交付和证据待用户验收，不自行记录用户已验收。
