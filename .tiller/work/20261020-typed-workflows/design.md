# 按任务类型选择与组合工作流程：设计

状态：原方案已确认；2026-10-20 按用户直接指示取消正式发布前的旧版本兼容要求。对应 [需求](requirements.md)，调整来源见[版本政策](decisions.md#版本政策)，实际确认及进展见 [工作入口](work.md)。决定来源已合并，原请求及过程快照按用户本次清理要求删除；本文保留设计依据。

## 1. 现状与变化

变更前 `src/work.ts` 的工作记录版本为 3，产物角色只有 requirements/design，六种模板表达文档层级；`src/confirmations.ts` 的上游关系主要按开发流程固定，规划、任务、验证和交付已有独立记录。只给现有模板增加类型名称，不能使分析任务真正独立结束，也不能解决确认与授权的差异。

本方案在现有证据和门禁基础上增加“流程定义、工作选择、阶段结果”三部分。类型表达交付目标；影响和操作权限单独核对；宿主负责理解请求并提出选择，CLI 校验显式记录，不声称能从自然语言自动认定授权。已有总体设计仅作为背景，本次变更设计是实施依据候选。

## 2. 类型目录与工作选择

初始内置十一种流程：requirements（需求探索）、analysis（问题分析）、research（技术调研／实验）、feature（功能开发）、bugfix（缺陷修复）、improvement（重构／性能优化）、review（审查／评估）、validation（实现核查／验收验证）、documentation（文档／规则维护）、migration（升级／迁移）、operations（发布／运维）。improvement 必须写清结构保持或性能目标；operations 必须写清发布或具体运维动作，不能用大类名称代替对象。

每份流程定义包含稳定标识、版本、适用与不适用场景、阶段及依赖、产物角色、必要检查、确认要求、允许动作类别和结束条件。内置定义由版本化资源分发；项目扩展放在 `.tiller/workflows/`，使用 `project.<name>` 标识和 JSON 数据，不执行定义中的脚本，不新增依赖。

开始工作时登记目标、类型及理由、仓库范围、已有依据、预期产物、影响事实、允许动作的来源及完成条件，生成可审阅摘要。影响事实包括：是否修改代码或行为、是否访问生产环境、是否写数据、是否涉及凭据和权限、是否具有不可逆影响、是否触达外部服务。未知项明确列出，不能默认低风险。

明确的只读分析或审查请求可直接成为相应调查范围的来源，不为调查强制追加一次“允许开始”的确认。分类不明确或权限有歧义时只暂停依赖该信息的动作。变更型任务仍遵循下一节的确认要求，不能以自动选型代替人工决定。

## 3. 默认阶段与确认矩阵

“复用”须绑定适用范围、对象版本、原决定和证据，变化后重新核对；不是检查存在一个旧文件。单任务规划可简述，但不得自动省略。用户明确合并确认时必须同时展示实际覆盖内容，不记录为分别发生过的批准。首版只合并没有前置冲突、已可合法形成并展示的对象，例如已确认需求下的多个设计：同一真实决定分别绑定各请求，保留同一来源，不虚构独立批准时间。需求尚未批准时，不以之后的合并确认倒推设计编写许可；若用户明确要求联合准备有前后依赖的内容，必须先核对具体阶段例外授权，再按其范围准备，不新增事后批量放行入口。

| 类型 | 默认阶段和最小产物 | 必须核对的确认与结束条件 |
|---|---|---|
| 需求探索 | 目标澄清、需求整理；需求文档及未决事项 | 用户确认需求后结束此范围；交付草稿可先报告待确认，不进入设计 |
| 问题分析 | 现象与范围、证据、假设验证、结论；分析报告 | 只读调查按明确请求开展；报告保留不确定性及建议。无代码修改、合入或发布节点 |
| 技术调研／实验 | 研究问题、比较维度、调查或隔离实验、结论；调研记录 | 已授权且无外部副作用的调查无需开发门禁；超出已有授权的写入、环境配置／业务数据变更、付费、外部系统或破坏性实验须先展示实验计划并取得相应操作授权；明确授权的本地隔离实验临时产物与结果记录正常推进 |
| 功能开发 | 需求、设计、规划、实现、验证；规格、代码和证据 | requirements → design → planning；实现后按约定验收。已有有效依据可引用 |
| 缺陷修复 | 复现、原因、修复范围、方案与单项或多项规划、修复回归；缺陷记录及证据 | 先分析不要求批准修复方案；写代码前需求／修复目标、设计和规划须确认或有效复用。独立 bugfix 不自动减免 |
| 重构／性能优化 | 当前基线、不变行为与改善指标、方案、规划、修改、对比验证 | 目标、设计、规划确认；性能以实测比较，结构修改保留行为回归。不得顺带改变业务行为 |
| 审查／评估 | 范围与标准、检查、复核、报告；问题清单和证据 | 按授权评估，不自动修复；报告区分发现、假设及未覆盖部分，不等同于验收批准 |
| 实现核查／验收验证 | 验收依据、验证选择、实际结果、覆盖结论；验证报告 | 已有依据可复用；具有副作用的测试单独核对授权。技术结论与用户接受分开，受委托验证不能冒充用户验收 |
| 文档／规则维护 | 明确目标与语义影响、起草、审阅、修订；文档和变更说明 | 纯措辞、格式或引用修正可按具体编辑请求处理；改变产品行为、权限或流程义务时走需求、设计及必要规划确认。类型不能掩盖语义变化 |
| 升级／迁移 | 现状、目标与兼容、恢复方案、执行安排、操作、核验 | 目标、方案及规划确认；数据／环境操作另绑具体对象与恢复条件。失败时报告状态，不擅自执行未授权回滚 |
| 发布／运维操作 | 对象版本与环境、前置和恢复检查、操作、结果观察 | 发布沿用具体发布确认及适用验收依据；其他运维按具体操作确认。既有开发证据可引用，不补造另一套开发过程 |

通用检查与人工接受分别保存。报告型工作可达到“已交付、未验收”；只有实际用户接受才标记“已验收”。新流程的 report/delivered 状态不借用现有必须验收才可完成文档的含义。

## 4. 扩展与权限约束

扩展先预览差异、检查阶段依赖无环、产物和结束条件可达，再登记固定版本。类型与文档模板分开：阶段可以引用已有文件，也可按实际需要创建 analysis.md、review.md、verification.md 等产物，不为纯分析制造 requirements.md/design.md。

项目规则或用户明确约束优先于类型默认值。扩展可收紧默认检查；减少适用确认、增加动作权限或改变完成语义时必须形成可审阅的政策变更，引用真实批准后启用。标识重名、版本覆盖、未知动作、缺失来源或绕过核心操作保护时拒绝激活。

操作权限取适用宿主约束、项目约束及有效用户授权共同允许的范围；类型标签不产生权限。提交／推送／创建评审可复用明确的持续授权，实际合入和发布继续绑定具体对象；不由某种任务类型自动开启。检查通过也不等于外部操作已发生。

这只是 CLI 受控操作的检查边界，不是沙箱，不认证自然语言来源、不阻止宿主直接写文件。

## 5. 阶段、组合与转换

每个独立工作有一个主要交付目标，选择一个固定流程版本。阶段状态为待开始、进行中、受阻、已验证或不适用；不适用须符合流程条件并保存依据，不能作为跳过失败的通道。另记工作已交付／待验收／已验收／已取消，不把阶段验证等同于整体接受。

同一请求包含多个独立交付时建立关联工作及依赖，如 analysis → bugfix → operations；前一工作记录结论和证据，后一工作引用对应版本、重新核对动作授权。组合不自动创建所有后续工作，也不自动执行，只有明确目标及范围的部分进入推进。

在未改变交付目标的情况下，排错、测试和修复属于当前阶段内部动作，不新开工作。误分类或目标改变时，转换预览展示新旧阶段、产物映射、证据可复用性、失效确认及新增授权；应用后保留旧修订，不覆写历史。改变权限或批准范围的转换必须重新确认，不能从 analysis 改名 feature 后直接写代码。

接续读取固定定义和当前产物摘要。目录定义更新不自动改变正在执行的工作；升级定义须显式预览并核对影响。依赖结果变化只使相关后续证据失效，不伪造以前失败或自动回退外部操作。

## 6. 数据与接口方案

以下均为拟新增接口，不是当前可执行命令：

- `workflow list/show/check`：列出及检查内置／项目定义；`workflow register --plan/--apply` 登记项目扩展及其批准来源。
- `work create --workflow <id> --input <intent.json>`：创建按类型组织的新工作，读取显式目标、影响、范围及来源；文档模板仍用于生成对应角色文件，不作为任务类型。所有新建工作都必须明确 --workflow；省略时显示可选类型并拒绝创建，不能用旧 --type 参数绕过选型。不保留旧版创建或接续入口。
- `work workflow inspect/change --plan/--apply`：查看选择、版本、阻碍和转换差异；写入使用 operationId 与 expectedRevision 防止重复和覆盖。
- `work stage start/verify/resume --plan/--apply`：对调查、报告、操作等阶段保存开始依据及实际证据；不自动执行程序。开发阶段继续使用已存在的规划与 task start/verify/resume，避免第二套开发任务调度。
- `work output add`：登记或按类型生成产物，产物来源必须指向真实文件；`work delivery-check` 汇总适用阶段、输出及验证，报告型交付与代码交付按所选流程分别计算。

工作记录采用版本 4，保存目标、流程引用、通用产物角色和关联工作；定义快照、阶段事件及转换历史独立保存。候选产品只支持当前契约，版本 3 及其他旧版、未知版本明确拒绝，保留原件，不提供兼容分支、迁移或批准继承。正式发布后再确定兼容政策；本次真实开发工作由隔离的固定管理程序维护，不要求候选产品读取它。

确认记录需支持按流程快照解析必要上游，并为受影响的范围／操作确认绑定具体对象。既有 requirements/design/planning/acceptance/merge/release 含义保留，新增 scope/operation 对象分别承载需要人工决定的范围变化与非发布操作许可。只读请求来源记录不伪装成新的 scope 人工批准；普通阶段完成用证据，不生成无实际决定的确认记录。

确认绑定增加字段后仅使用当前确认契约，不保留旧版解析或双注册表路径；各类独立记录按自己的当前协议判断，不机械统一版本号。不借可配置图削弱合入、发布及来源绑定等独立保护。若发布工作引用另一工作产物，应绑定该工作的交付、验收及版本，不伪造本工作已有开发阶段。具体字段和错误码随各任务细化，但不得扩大以上能力边界。

## 7. 涉及范围及取舍

预计涉及 src/work.ts、确认、规划、任务、整体交付、CLI、资源与相关测试；补充流程定义与阶段记录模块，复用现有路径保护、事务、摘要、确认来源和验证记录。共享规则需明确区分调查、变更和操作，不能继续写成所有活动一律需要开发规格。

继续使用 TypeScript + Node.js，零新增依赖，沿用现有测试框架及九类验证分类。命名、分层、错误和静态检查沿用项目约定。长期规格在方案确认并实际实施后协调更新，不在本轮把候选设计写成既成能力。

不采用仅增加四个类型标签的做法，因为无法覆盖新增类型及独立结束；不采用任意脚本工作流引擎，避免引入另一套执行环境；不采用按改动文件数自动跳过确认，因为无法反映语义和权限影响。第一版只提供声明、记录和受控检查，宿主负责执行，不加入后台调度、自动猜测批准或自动生产操作。

## 8. 验证安排与需求覆盖

| 需求 | 主要验证场景 |
|---|---|
| TW-01 | 十一类均可显示目标、类型、理由及实际适用阶段；缺失范围或影响事实的相关动作受阻；模板类型与流程类型不混用 |
| TW-02 | 新增 project.* 类型可检查和使用；重复标识、循环、无结束条件、未批准的减免和执行脚本被拒绝；定义更新不污染进行中工作 |
| TW-03 | 分析结束不允许修复；显式关联／转换后重新核对权限；依赖证据变化触发相关失效；外部成功不因下一工作失败而自动回滚 |
| TW-04 | 已批准开发内失败修复沿用当前任务；新增范围不得继承旧许可；不重复造完整文档 |
| TW-05 | 同类任务涉及生产、数据或权限时增加具体检查；未知影响不能按低风险放行；文件数不触发豁免 |
| TW-06 | 分析、审查、验证各自凭证据交付，无虚构需求设计或 PR；待验收与已验收分开；开发、迁移、发布各有真实完成条件 |
| TW-07 | 有效确认可复用；对象或范围变化后失效；仅“继续”不能批准未展示内容；用户明确合并确认只覆盖已展示对象 |

单元验证定义、解析和必要条件；集成验证定义→选择→阶段→证据→交付；接口验证 CLI 成功和拒绝路径；回归将原开发、确认、路径和交付场景适配到当前契约，保留有效的行为与安全断言，不再验证旧版接续成功；系统验证分析→修复→发布的组合及多仓库边界；安全验证路径、来源与越权拒绝；可靠性验证中断、并发修订、重复回执、部分成功及旧/未知格式拒绝时原件不变；性能验证大量定义／阶段解析有界且不退化为无界遍历；安装和资源验证采用当前契约，历史版本迁移或兼容不是验收条件，操作系统证据按实际环境报告。另做宿主真实演练，核对执行是否符合规则，不用单元测试冒充实际行为。

原设计与七任务规划已确认并进入实施；本次只按用户直接修订移除兼容要求，保留其余设计与任务依赖。调整后重新登记规划并按当前输入验证，不把历史测试结果改写成新契约已通过。
