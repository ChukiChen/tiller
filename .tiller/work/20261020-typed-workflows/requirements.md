# 按任务类型选择与组合工作流程：变更需求

本文件整理用户已审阅的需求草案，不批准尚未展示的设计、具体节点简化或实现。确认原话和归档顺序见 [需求确认来源](decisions.md#需求确认)。

## 目标与范围

把“按工作类型选择流程”作为正式能力。分类依据是本次交付目标及其影响，据此决定阶段、产物和确认节点，不将所有任务强制走完整开发和发布流程。

现有依据见 [总体需求](../../specs/requirements.md)、[工作推进需求](../../specs/modules/workflow/requirements.md)及[工作推进设计](../../specs/modules/workflow/design.md)。当前版本共用门禁，文档模板类型不是任务流程类型；本次补充任务分类和流程选择，既有讨论稿不因此整体获批。

## 初始类型与流程方向

| 类型 | 主要交付物 | 典型流程 |
|---|---|---|
| 需求探索 | 明确的问题、范围和验收标准 | 澄清 → 梳理需求 → 需求确认 |
| 问题分析 | 原因、证据和处理建议 | 收集现象 → 调查验证 → 分析结论 |
| 技术调研／实验 | 方案比较、实验结果和建议 | 明确问题 → 调研或实验 → 比较结论 |
| 功能开发 | 可使用的新能力 | 需求确认 → 设计确认 → 规划确认 → 实现验证 → 验收 |
| 缺陷修复 | 问题消除及回归证据 | 复现 → 定位 → 明确修复范围与方案 → 修复 → 回归验证 |
| 重构／性能优化 | 结构或指标改善 | 建立基线 → 明确保持项与改善目标 → 方案确认 → 修改 → 对比验证 |
| 审查／评估 | 问题清单及评估结论 | 明确标准与范围 → 审查 → 证据核对 → 报告 |
| 实现核查／验收验证 | 要求与实际结果的对应证据 | 明确验收依据 → 检查或运行 → 记录差异 → 形成结论 |
| 文档／规则维护 | 可审阅的文档变更 | 明确目标与影响 → 起草 → 审阅修订 → 接受；涉及行为变化时补充相应确认 |
| 升级／迁移 | 完成转换且可验证的目标状态 | 现状检查 → 兼容与恢复方案确认 → 执行 → 验证 |
| 发布／运维操作 | 指定环境中的操作结果 | 明确对象与影响 → 前置检查 → 操作确认 → 执行 → 结果验证 |

上表是初始集合，不能成为封闭名单。它表达流程方向，不代表已批准简化任何节点。

## 必要能力与可观察结果

- TW-01 分类与可见选择：开始时说明类型、理由、适用节点及完成条件；不明确时先澄清，不能默默套用完整开发流程。
- TW-02 可扩展：项目可增加类型或调整流程，但须说明适用范围、必要产物、确认节点及完成条件，不能借自定义类型绕过已有约束。
- TW-03 组合和转换：一个请求可以分析、修复、发布；分析完成只代表分析任务完成，转入修改或发布时重新核对对应依据和授权。
- TW-04 阶段内动作：已确认开发范围内的测试、排错和修复不反复建立完整流程；超出范围才转成新任务或调整原任务。
- TW-05 按影响决定深度：相同类型可因影响不同需要不同检查；不凭文件数、“简单任务”等判断自动减免确认。
- TW-06 独立结束条件：分析可结束于结论，审查可结束于报告，开发结束于约定交付，不强制每种类型都产生代码、PR 或发布。
- TW-07 确认边界明确：区分各类型必需节点、可复用的既有确认及可由用户明确合并的节点；具体矩阵在设计阶段展示确认，不由类型名称隐含授予权限。

验收以能否观察到上述选择、扩展、转换、复用、影响判断和对应完成结果为依据；具体测试场景及实现机制在设计阶段细化。

## 边界

类型不自动授予实现、提交、推送、合入、发布或数据操作权限；阶段内自主执行只限有效授权范围。需求确认允许形成设计，不等于批准设计或实施规划。

2026-10-20 用户进一步明确：正式发布前不需要旧版本兼容，后续开发也遵循此要求，正式发布后再考虑兼容政策。当前工作只支持届时明确的当前契约，不保留旧版接续、双版本兼容或自动迁移要求；历史资料不删除，不支持的格式明确拒绝且保留原件。来源见[版本政策调整](decisions.md#版本政策)。其余已确认需求不变。
