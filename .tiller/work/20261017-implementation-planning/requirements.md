# 实施规划与任务拆分变更需求

> 本次方向来自用户讨论及修改指令；长期条款以模块规格为准，不表示全部历史讨论稿获批。

## 问题与目标

真实项目虽列出功能分块，却在骨架独立验证前进入业务实现，最后集中记录结果。总体设计到执行之间缺少明确的实施规划确认环节，计划与实际依赖检查脱节。

本次将实施规划明确为总体需求、设计之后且任务执行之前的环节，覆盖需求、任务结果与边界、依赖、完成及验证条件、待细化事项，并取得对应内容的用户确认。选定任务后按缺口细化需求和设计，充分的已有规格直接引用。

## 范围与关联

- [工作推进 FLOW-20、FLOW-21](../../specs/modules/workflow/requirements.md)：规划、任务拆分、骨架与增量验证，具体条款在模块维护。
- [开发规范 RULE-12](../../specs/modules/standards/requirements.md)：规划检查、任务进入条件与证据要求。
- [工作推进设计](../../specs/modules/workflow/design.md)和[规范设计](../../specs/modules/standards/design.md)：资料组织和可读执行约定。
- 骨架是空项目通常首先执行的普通任务；已有项目复用满足要求的基础，只安排实际缺口。
- 同一轮可连续完成多项任务，但必须逐项验证与即时记录。未通过前置验证不能进入依赖任务；最终测试不能倒填早期过程。人工检查点按明确约定执行，不默认每任务新增批准。

## 本次交付边界

优化规格、分发规则、入口及设计模板提示，并通过资源版本升级同步 tiller 自身。保持六类规格模板和现有命令体系，不新增任务状态机、规划确认类型、自动调度或宿主写入拦截。规划确认暂由可读工作记录保存真实用户来源，不伪装成 CLI 已支持的节点。

不修改学生测试工程，不重写已有审计或确认历史；不提交、推送、合入或发布。后续程序能力需要另行形成详细设计及验证安排。

## 验证要求

1. 总体与模块规格、入口、规则和模板中的流程一致；骨架不成为独立流程阶段。
2. 明确规划确认与需求、设计、验收确认的区别，以及单任务简化与变化接续边界。
3. 新接入工程取得新规则；0.3.4 可显式升级，已有用户规划、工作记录、确认及自定义规则受保护。
4. 资料链接、资源来源与自身安装内容一致；构建、静态检查和影响范围回归通过。
5. 技术检查不冒充实际 AI 已按流程执行；真实行为仍需新增量验证。
