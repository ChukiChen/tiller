# 任务推进与交付门禁变更设计

> 状态：设计草案，待确认；下列新增格式与命令均未实现。
> 对应：[已确认需求](requirements.md) GATE-01 至 GATE-08。确认来源见工作记录；本设计不提供旧记录兼容、转换或迁移。

## 1. 方案与职责

在现有工作推进中增加任务运行记录和统一门禁评估器，复用现有确认、验证、仓库定位、锁和事务机制。规则指引 AI 调用正确入口，程序拒绝不满足条件的受控操作；不创建独立的调度系统。

| 职责 | 输入 | 输出或作用 |
|---|---|---|
| 规划登记 | 当前交付范围、任务、依赖、产物及检查条件 | 可审阅的不可变规划版本，结构与覆盖问题 |
| 确认检查 | 对象版本、范围、真实用户决定 | 有效、待确认、拒绝或失效，不自动批准 |
| 任务门禁 | 规划、规格确认、前置任务及当前实际对象 | 能否开始、能否验证完成及阻断原因 |
| 验证评估 | 指定范围的用例、运行事实、人工结果和证据 | 各必要条件当前是否满足 |
| 整体门禁 | 当前交付范围的任务、产物与组合验证 | 技术就绪、过程证据和验收状态分别报告 |

拟新增任务规划与推进模块，统一门禁评估由同一实现提供给查询、写入和交付命令，避免查询通过但写入漏检。沿用 TypeScript、Node.js 和零新增运行时依赖约束；测试遵循[项目测试约定](../../rules/testing.md)。

## 2. 记录及单一来源

同一工作仍以 work.md 导航，requirements.md 和 design.md 承载规格。新增任务记录，不将它们混入文档产物的完成状态。

```text
.tiller/work/<work-id>/
  work.md                         可读入口与当前事实
  requirements.md / design.md     新写规格，已有正文允许引用
  record.json                     工作身份与文档产物，由命令维护
  confirmations.json / reviews/   确认、展示及快照，由命令维护
  plan.md                         当前规划的生成视图，不是第二份状态源
  planning/<revision>/            不可变规划正文及任务定义
  tasks.json                      活动规划指针、任务执行及追加事件
  delivery-checks/<id>.json       整体检查的不可变回执
  verification.md                 本次验证说明
  verification-runs/<id>.json     实际执行及报告证据
  delivery.json                   Git 交付对象及操作事实
```

planning 下的规划和任务定义通过命令生成，用户输入文件只作为命令参数；以后修改输入文件不改变已登记规划。plan.md 从活动规划生成，手工改动会提示视图与登记不一致，不能据此改变门禁。

每份规划归属一个 ownerWorkId；任务身份为 ownerWorkId + taskId。其他工作通过该身份引用，不能复制执行状态。relatedWorks 只表示关联，不授予其他工作范围或仓库权限；写操作始终定位唯一归属工作。首版依赖图限定在同一规划，跨工作协作的任务也应纳入该共同规划，以避免维护多份相互矛盾的依赖图。

### 2.1 规划定义

| 字段 | 契约 |
|---|---|
| revision、ownerWorkId、scope | 内容版本、唯一工作、仓库及本次交付目标 |
| requirements | 本次需求标识和正文引用；每项必须映射任务或明确的排除理由 |
| basis | 当前总体需求和设计的确认引用；引用包含 workId、requestId、decisionId |
| tasks | 稳定标识、标题、结果、范围、相关模块、仓库、关联工作 |
| dependencies | 前置 taskId 及实际需要的产物/结果标识，拒绝自依赖和环路 |
| artifacts | 产物标识、用途、类型、仓库与路径、必要性及检查条件 |
| verification | 用例选择、类别适用性、必要检查和选择理由 |
| humanCheckpoints | 明确需要用户判断的节点及确认对象 |
| delivery | 必要任务、共享交付物、集成回归和交付遗留项 |

任务定义另含 requirements/design 确认引用、规范正文引用和待细化项。规划允许部分近期之外的任务规格未定，规划结构检查显示缺口而不要求预先补齐；任务 start 时缺必要规格必须阻断。任务完成条件及必要产物不能留待隐式推断。

所有已登记需求必须能说明去向；排除、延期及任务取消属于规划范围变更，需明确理由并重新确认，不能靠 optional 标志或删除任务绕过必要项。规格补充若改变原范围或标准也产生新规划版本。

### 2.2 产物类型

- document：共享文本文件，检查引用安全、存在、正文及占位；内容正确性由约定评审判断。
- source：明确文件清单；可登记有限目录集合，计算排序后的成员清单及内容摘要，增加或删除文件同样使依据变化。无需逐个把目录中所有文件人工列成任务。
- generated：构建或运行产物的声明，检查实际生成证据、来源输入及摘要。可重建的本机二进制不强制纳入 Git，也不允许把 local 里的唯一日志当共享证据；共享证据保存构建入口、输入版本、实际输出摘要及核对来源。仅声明文件存在不能放行。
- reference：另一任务已声明的产物，引用唯一来源并要求与依赖图一致，不复制状态。

artifact.required 默认为 true，非必要项必须有理由。检查器不能执行文档中的任意命令；执行型验证仍由明确配置的验证入口完成。

产物集合与所有摘要入口统一区分受检内容和可变控制资料。本次 tasks.json、确认决定/展示回执、verification-runs、delivery-checks、交付事件以及本机恢复资料不得成为其自身检查的产物输入；集合若包含这些路径，明确拒绝并要求缩小到真实交付内容，不静默过滤后宣称覆盖整个目录。需求、设计、规范等正文可以独立登记。控制资料作为过程证据另行关联和归档，不进入会被自身写入改变的内容摘要。

## 3. 确认与版本

新确认格式在原有需求、设计、验收、合入和发布节点外增加 planning、checkpoint、exception 三类。planning 的前置是覆盖本次范围的总体设计确认；设计保持其需求前置。任务详细规格可以由其他工作提供，引用须包含来源工作身份，并核对文件、目标和仓库范围，不能只比较名称。

planning 确认绑定不可变规划正文、任务定义及被引用规格。请求展示说明所有待细化事项；规划批准不会使任务的需求、设计自动批准。checkpoint 只完成所声明的人工判断；不默认要求每个任务再人工审批一次。

每次规划修改生成新 revision，禁止覆盖旧版本。激活新版本需要有效 planning 确认，并在展示中逐任务列出保留、重做及待核对项。任务定义、规格和实际依赖均未变的任务可保留技术证据；变更任务及其依赖者重核，不按全局 revision 变化一律否定所有任务。新规划确认是当前推进依据，旧执行记录仍引用当时的版本。

重复确认不另设默认要求；已有确认只有在对象、范围、条件及来源仍有效时复用。内容绑定与来源复核仍为 reported-review，不认证用户身份。

## 4. 任务状态与三个检查点

任务操作状态采用 pending、active、verified、cancelled；blocked 与 stale 是根据当前依据计算的结果，不用手工修改状态绕过检查。每次输出同时给出 recordedStatus、effectiveStatus、blockingReasons 和下一步建议。

| 操作 | 必须核对 | 成功写入 |
|---|---|---|
| start | 活动规划确认、当前任务规格确认及规范、前置任务和所需产物当前有效、人工开始检查点 | 新的 attemptId，开始时版本、依赖完成事件和检查摘要 |
| verify | 有真实 start；当前规格和产物、必要验证、完成检查点满足；无未解决的开始依据漂移 | verified 事件，产物摘要、用例/结果记录身份、开始事件与依赖依据 |
| delivery check/ready | 必要任务有效、范围覆盖、共享资料及组合验证完整、约定交付人工检查完成 | check 只读；ready 另写不可变技术就绪回执 |

start 不自动执行代码。verify 不自动运行未知测试，不自动将套件退出成功转成用例通过。缺条件时输出结构化原因，返回非零退出码，并且不写成功状态。只读 status/check 可在未知状态下列出缺口，不要求先伪造完整记录。

同一轮允许 start A → verify A → start B；B 依赖的 A 必须在 B 开始检查时已经有效。独立任务可并行，状态写入串行协调。骨架只是普通任务，其成功条件必须含实际构建、启动或调用证据，不能只用 lint 代替。

验证通过只是登记当前结果，不授予提交、验收或发布许可。技术就绪报告可供用户验收，acceptance 仍需独立真实决定；可以随时报告失败、记录拒绝或附条件意见。

## 5. 验证范围与证据复用

现有报告按整个已登记目录判断，且快照包含完整配置和工作记录；直接把其 ready 布尔值用于任务会导致无关缺口阻断及状态自我失效。本次改为一个共享评估器，任务和整体检查传入显式 selection。

selection 包含需求、用例 ID、必要检查、九类适用性与理由、受影响模块和跨模块/系统场景的选择依据。不能用空列表默认跳过，也不能按目录自动断言范围充分。纯文档工作选择文档检查和人工评审，不强制建立业务用例；代码工作必要需求须有可核对的验证关联。

全局配置损坏、标识歧义或目标仓库无法确定时无法安全解析，应阻断。可定位为无关模块的未执行、类别待定或未覆盖项列为范围外警告，不阻断局部任务。所选任务中的类别适用性、必要回归和排除理由由已确认规划及详细设计约束。

新的逐用例证据快照只绑定其适用内容：用例定义、相关需求/设计、适用规范、套件配置和明确的共享输入。人工用例也必须明确受检对象及输入，不能只登记一张脱离对象的报告。工作身份绑定稳定 ID 和范围，不绑定会变化的整份 record.json、tasks.json、进度 Markdown 或结果目录；规避“登记完成改变记录，证据随即过期”的循环。

自动、外部和人工结果均须绑定执行或观察当时的受检代码/产物版本及必要运行输入。规划为每项必要检查声明被验证的 artifact 标识；verify 要求结果中的输入绑定覆盖对应代码清单及必要配置，并将其摘要与当前交付对象比较，缺失或不一致即拒绝。生成产物同时核对实际输出摘要与构建来源；不能用刚采集的当前代码摘要代替旧报告未记载的受测版本。无法自动完整推导动态依赖时，显式输入清单及遗漏风险交由评审，程序不宣称已发现全部依赖。

每条完成证据引用 workId + runId + caseId 或人工检查 ID，复用验证模块数据而不复制通过状态。关联的后续失败、未执行的新尝试或证据变化使当前结果需重核，不能从历史中挑一个通过结果掩盖较新失败。跨工作结果只在对象版本、范围、环境约束及来源一致时显式引用，不能合并不相关工程的绿色结果。

旧证据没有必要输入绑定时不为其补写快照，也不提供旧格式转换；在新流程中重新执行或按当前对象重新核对并登记真实结果。套件执行与逐用例结果仍分开，产物运行证据须指向实际执行事实或有来源的人工/外部观察。

## 6. 变化、重复与中断

每个事件保存递增序号、操作 ID、attemptId、当前规划及任务定义摘要、规格确认身份、必要输入/产物摘要、依赖完成事件、结果引用与真实登记时间。时间用于展示，顺序和依赖依靠事件引用与锁下校验，不依赖本机时钟证明因果。摘要用于一致性检测，不是防篡改签名。

start 时记录事实，verify 时重新读取全部必要依据。任务自身预期代码变化是执行结果，不把它当作 start 自动失效；已确认规格或前置产物改变则需重核。通过后被绑定代码或证据变化，当前任务转为 stale；下游在继续或验证前必须重核。

已开始任务受影响时，不隐式改写其开始依据。resume 显示差异，用户已授权且条件满足后以新 attempt 登记当前继续点，保留先前事件；重验产生新的当前结果，不把新证据倒填到旧开始之前。下游合法地改动共享文件时，可以复验相关前置的当前契约，再重核下游，保留此前各次验证事实。

写操作统一使用操作 ID 和 expectedRevision；同 ID 同输入且已成功时返回原回执，相同 ID 不同输入拒绝。失败重试需重新检查；成功回执只能证明当时发生，不能替代当前 status。持有唯一管理位置的工程锁，在事务提交前再次比较相关内容；不同时持有多个跨工作写锁，跨工作依据只读并在提交前重核。

文件事务失败沿用现有恢复日志。未知外部执行结果保持 unknown，先核对结果，不自动重跑；普通 start/verify 不执行外部写动作。直接绕过 CLI 的修改只能在以后检查时发现绑定内容变化，无法证明未登记操作的准确时间。

## 7. 整体交付与 Git 操作

统一输出包括 scope、technicalReady、processEvidence、acceptance、issues、exceptions、basisDigest。processEvidence 区分本次受控顺序具备、存在缺口及无法判定；不承诺认证宿主全部行为。发现顺序缺口不得静默视为整体就绪。

ready 回执绑定当前规划、必要任务完成事件、产物/验证摘要及适用确认身份。生成回执不自动建立验收批准。验收请求可展示未就绪内容供用户决定，但登记正式验收状态时需匹配具体交付对象；若有明确例外，标明 accepted-with-exceptions，不改写 technicalReady。

| 交付动作 | 新门禁的接入 |
|---|---|
| 单份文档 complete | 仍检查该文档及其验收，不要求所有实现任务完成 |
| commit、push | 保持既有授权与版本检查，不增加整体完成前置；不会因此标记可合入 |
| review create/update/attach | 允许授权的进行中评审，明确 deliveryReadiness；要登记可合入须整体门禁通过或具备明确例外 |
| merge | plan 与 apply 均重算整体门禁；确认绑定检查摘要、具体源/目标版本及依赖组合 |
| reconcile | 保存观察到的真实合入事实，门禁缺失时报告过程缺口，不补成合规 |
| release 确认 | 绑定该次验收、发布对象及必要交付门禁；本增量不新增部署执行器 |

这里的“可合入”是 Tiller 判断；不宣称所有平台已支持修改草稿状态。当前平台适配不能原子校验源和目标版本，已有自动合入拒绝必须保留，新增门禁通过也不能消除该限制。

固定源提交后的技术就绪、验收及合入控制回执不再混入该源提交，否则会循环改变被批准对象。沿用已有交付控制资料的追加与独立归档方式，归档前保留活动目录；共享资料尚未持久保存时禁止清理，不要求一个提交包含批准自身的后置记录。

## 8. 明确例外

exception 请求绑定操作、任务/交付身份、未满足条件 ID、当前对象摘要、理由、允许动作及失效条件，复用真实用户决定与来源复核。未知结构、非法路径、来源无法核对及对象身份不明不能通过例外绕过。

例外有效时 operationAllowed 可为 true，但 technicalReady 保持原结论，回执标明 allowed-with-exceptions。例外只覆盖列出的条件；其他问题仍阻断。对象或适用条件变化后重新确认；不用自由文本的模糊“以后都可以”当作无限授权，不增加通用 --force 或 skip-all。

## 9. 拟提供的命令

以下为待实现接口，不能用当前 0.3.6 CLI 执行。复杂输入沿用 --input 项目相对文件，计划与应用的摘要不代替用户确认。

| 命令族 | 作用 |
|---|---|
| work plan register <work> --input <file> --plan / --apply <digest> | 验证输入并保存新规划版本，生成审阅正文；尚不激活 |
| work request-confirmation / record-decision / check-gate | 新增 planning、checkpoint、exception 类型，保持明确展示与来源核对 |
| work plan activate <work> --revision <id> --request <id> --plan / --apply <digest> | 核对有效规划确认、差异和保留项，再选择活动规划 |
| work task status <work> [--task <id>] | 只读计算当前任务、依赖、证据及缺口 |
| work task start/verify/resume <work> --task <id> --input <file> --plan / --apply <digest> | 在对应检查点执行受控状态变更；resume 创建新的继续 attempt |
| work delivery-check <work> | 只读整体检查，未满足返回非零码，不自动执行测试 |
| work delivery-ready <work> --input <file> --plan / --apply <digest> | 保存当前技术就绪或有效例外的不可变回执 |

没有单独强制完成或删除依赖的入口。取消任务通过新规划修订完成，不直接删历史事件。普通进度说明可写 work.md，机器状态只能经命令变化。

写操作输出至少包含 operationId、changed、operationAllowed、technicalReady、blockingReasons 和 basisDigest；错误项给出 code、task/artifact/case 身份、原因、可补足动作和是否允许例外。只读检查不创建记录目录。

## 10. 新格式与旧记录边界

本次只为新工作提供完整门禁。拟定 work record 版本 3、confirmation 版本 3、verification run 版本 2、delivery 版本 2；planning 与 tasks 使用首个版本 1。版本变更用于明确绑定任务、选择范围和记录身份，不读取旧数据后默默补缺省字段。具体字段由严格解析器统一定义，未知字段或版本拒绝写入。

新流程遇到旧记录返回 UNSUPPORTED_RECORD_VERSION，说明实际版本和需要的新建入口；不提供兼容读取、adopt/migrate 转换路径或自动继承批准、进度和通过结果。旧文件保持原位，不因升级或命令失败删除。新工作可引用原有需求/设计正文，但须核对适用范围，并建立当前格式下的实际确认与验证。

此限制针对工作、确认、验证结果及交付记录，不扩大为删除项目资料、仓库、测试代码或所有工程初始化升级能力。项目规则资源升级仍保护用户内容；是否支持某一历史资源版本是独立范围。实现时清理受本次替换格式影响的旧解析/迁移分支与对应兼容测试，保留新格式和拒绝旧格式的验证。

开发 Tiller 本增量时仍使用当前可用版本登记本次设计；不能在未实现前伪造新状态文件。新能力可用后，另行新建真实自举工作验证，不将本工作的既有登记迁移成新门禁合规记录。

## 11. 仓库定位与安全范围

单仓库模式中资料和代码位于同一活动分支，依现有交付定位解析。独立管理模式中 planning/tasks 和共同证据留在管理工程，产物及运行入口使用稳定业务仓库标识；一个业务仓库也不切换成单仓库模式。

每次引用检查实际登记路径、工作范围、共享性、链接及遍历风险。禁止通过管理根引用绕过业务仓库边界，不将本机绝对路径写成共享身份。文件集合快照包含成员变化，规模设明确上限，超过时返回限制而非截断成通过。

任务间并发不赋予新增仓库权限。状态和条件文件变动由统一锁及事务处理；跨仓库文件系统和远端状态无法整体原子化，应用前后核对并报告中途变化，不能保证所有宿主写入被拦截。

## 12. 验证安排与需求覆盖

| 测试类别 | 本增量验证重点 |
|---|---|
| 单元 | 图与范围校验、状态计算、摘要、例外匹配、选择范围 |
| 接口 | 输入版本与未知字段、退出码、计划过期、重复操作 |
| 集成 | 确认→规划→任务→验证→交付；共同记录及两种仓库模式 |
| 场景 | 骨架失败阻断下游、补足后重试、独立任务继续、真实 AI 操作与中断接续 |
| 性能 | 有限规模解析与重复检查耗时，明确上限与实测环境；没有经确认的响应时间指标，不预称达标 |
| 安全 | 路径、链接、仓库越权、证据自证、例外扩大及恶意记录 |
| 可靠性 | 并发漂移、事务失败、重复调用、结果未知及当前/历史状态分离 |
| 兼容性 | Windows/macOS/Linux 命令与路径；拒绝旧记录验证不等于支持其兼容 |
| 易用性 | 阻断输出能定位原因与下一动作，用户能区分技术就绪、例外和验收 |

性能先建立容量与耗时基线，若需承诺数值则另明确指标；其他平台未运行时保留未验证。真实 AI 样例在用户授权的测试工程或新建受控临时工程开展，不能以静态文字匹配替代。
