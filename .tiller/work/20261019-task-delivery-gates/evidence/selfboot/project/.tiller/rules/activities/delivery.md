# 交付

规则标识：ACT-DELIVERY。验收、报告完成、发布和交接时使用，并读取[验证依据](../quality/verification.md)。

产物组织和创建、登记、接续遵循[工作记录约定](../core.md#工作记录约定)。

按[实施规划与任务拆分](../core.md#功能分块与实施安排)汇总已确认规划、需求覆盖、任务产物与当时证据，核对遗漏和范围变化，再验证组合行为与整体条件。必要任务未验证或约定人工检查未完成时，不能报告整体技术检查已完成。骨架或各任务通过不等于业务目标已达成；当前功能结果、历史过程合规与用户验收分别报告，不能用整体测试补成逐任务放行历史。

用 `work delivery-check` 只读核对当前完整交付，再按 `work delivery-ready` 的预览与应用保存就绪或带例外的回执。分别说明 technicalReady、operationAllowed、processEvidence 和 acceptance，不能合并成一个“完成”结论。就绪回执只记录当时对象，不自动取得用户验收；当前检查仍须重算。命令和绑定字段见[使用指引](../../usage.md)。

1. 按本次范围逐项关联要求、实际产物和当前证据，区分满足、未满足、未验证与不适用。必要问题未解决时不得报告全部完成。
2. 展示实际交付范围、产物、验证证据、缺口与限制供用户验收；请求可呈现未就绪对象供决定，正式整体验收须绑定当前有效的完整交付对象。明确例外成立时标明 accepted-with-exceptions，保留技术未就绪事实；未验收时报告待验收，不标记已验收或整项完成。文档工作区分草稿交付被接受、规格内容确认及实现状态，不将前者自动用于批准设计或实现。
3. 发布须另行取得针对具体产物版本、目标环境、影响、前置条件及失败处置的用户确认，并绑定同一交付对象的有效整体验收，再使用项目已有发布能力。需要例外时单独核对 release 许可，delivery-ready 或 merge 例外不适用。交付验收不自动授予发布权限；发布不在范围内时明确未发布，不扩展交付目标。规则本身不授予提交、推送或发布权限。
4. 外部结果未知或部分成功时先查询事实，记录具体对象和结果，避免重复操作；恢复和回退分别核对条件与授权。
5. 交接说明提供成果位置及版本、使用方式、验证依据、发布情况、限制和遗留问题；更新已接受变更涉及的长期规格，保留历史证据。

后续反馈关联原交付及实际现象，记录影响和处理决定。新增工作按实际范围与授权推进，不改写旧验收结果；旧结论错误时追加更正依据。

文档交付按登记产物核对验收、当前内容及独立证据，普通文档验收不增加整体任务完成前置，也不能替代发布要求的整体验收。一个产物完成不等于整项软件交付完成；过程摘要可合并记录，不能替代受控完成所需的独立证据。

代码交付同时遵循[隔离开发约定](../core.md#隔离开发与评审合入)：逐仓库关联真实 MR/PR、提交及检查结果，取得有效合入确认后才执行对应合入。源或目标变化、评审阻断及组合验证失败时停止相关合入。恢复先核对事实；完成后先归档共同资料和回执，再按授权清理副本或分支。不得把本地结果、管理资料已提交或一个仓库已合入表述为跨仓库整体完成。

commit、push 不增加整体完成前置，进行中 review 可以保持未就绪并报告 deliveryReadiness；实际 merge 的预览和应用均重算当前整体门禁及专属例外，平台双 OID 原子保护限制继续适用。reconcile 保存真实观察，当前结果不能证明当时已获许可；发现历史门禁缺失时报告过程缺口，不用事后回执补造合规。固定源提交后的控制记录独立归档，未持久保存的共同资料禁止随副本清理。

交付按[验证依据](../quality/verification.md)核对登记范围的需求覆盖，并逐类说明单元、接口、集成、场景、性能、安全、可靠性、兼容性及易用性检查的适用性、实际结果和缺口。任务回归、自动化全量回归及完整交付验证分别说明；局部套件通过、关联完整或报告生成不能提升为全量通过。外部证据标注来源，内容变化后复核适用性，真实 AI 行为仍需过程证据。
