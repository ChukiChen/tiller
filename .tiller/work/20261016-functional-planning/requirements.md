# 功能分块与项目骨架推进需求

## 目标与依据

现有[工作推进需求](../../specs/modules/workflow/requirements.md)描述模块细化、任务安排和最小完整变更，但未明确从总体需求及设计拆分可实现功能块的过程。需让开发范围、顺序、验证及总体覆盖可查。

## 行为与边界

1. 根据适用且已确认的总体需求、设计拆分功能块，关联需求、方案、预期行为、不包含范围、依赖与验收条件。模块是长期职责，功能块是可检查的交付增量，可以跨模块或仓库。
2. 功能分块覆盖本次约定范围；保留未安排、待细化及阻碍项，不把剩余内容当作已完成。先安排整体依赖，再按需细化近期功能块，不一次写全所有模块文档。
3. 空项目将最小可运行、可验证的项目骨架作为首个实现单元，依据已确认的相关需求和技术设计搭建。验证构建、启动及适用基础检查；不以空目录或生成成功代替基础可用。
4. 业务功能和公共组件按实际依赖逐步实现，不预建尚无使用需求的框架；已有项目先核对并复用现有基础，只补缺口。tiller 接入与业务项目骨架搭建分开。
5. 每块先核对需求及设计充分性和有效确认，缺失时按现有节点细化与确认；已有足够且已确认的资料直接引用。块内编码、测试和修复自主推进，新增业务决定或关键方案变化仍需确认。
6. 每块验证后更新实际状态、证据和后续安排，全部块完成仍需核对整体需求覆盖及组合验证，保留用户验收。

## 交付条件

工作推进需求和设计、开发规范及分发规则表达上述行为；空项目、已有项目、跨模块依赖、部分完成与需求变化均有可执行指引。实现进度明确本次为规则及流程落地，不宣称已有自动任务拆分、调度或功能块机器检查。保留原有资料与确认语义，既有工程通过显式资源升级接入。

当前讨论未要求新增任务调度命令、强制每块独立 work 或统一业务脚手架，不纳入本次实现。
