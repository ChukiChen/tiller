# 项目接手与开发规范建立设计

> 依据：[本次需求](requirements.md)。授权来自已展示流程及资料方案后的[用户决定](user-source.md)，不将本文件新增实现细节冒称逐字批准。

## 方案

沿用现有文档与规则机制，保持需求、设计及过程分开：总体需求与总体设计只加概述和详细链接；工作推进新增 FLOW-22、FLOW-23 和对应场景、产物、验收；开发规范新增 RULE-13；初始化明确接入后的工作起点。

通用规则在 `core.md` 增加“已有项目接手”“项目开发规范”，由通用入口、规则索引及活动指引引用，设计模板补充必要提示。项目规范由自维护的 `rules/project.md` 引用已有规范或专属文件，实际工具参数仍由已有配置维护。需求模板不掺入技术选择，不新增受管文件或机器产物类型。

## 执行边界

长期接管先调查及建立基线，依次补足确认总体需求、总体设计和规范，再分块；局部任务记录检查范围及缺口。新项目规范随总体设计形成，可合并展示确认，骨架阶段实际执行适用检查。调查、语义判断及业务检查仍由执行者负责，不新增自动扫描、调度或脚手架能力。

此次资源内容改变，以 0.3.4 发布物形式准备本地包，保存可校验的 0.3.3 原始资源基线，沿用正式升级保护；不发布到注册表。旧版 0.3.2、0.3.3 的受管文件严格检查不能因新版本放宽。自身通过显式计划升级，测试项目保持原状态。

## 验证安排

1. 审阅新项目、长期接管、局部修复、有历史失败和多仓库差异五种路径，核对确认和产物边界。
2. 检查本次 Markdown 链接、标题锚点、需求编号与规则读取链；不通过文案正则宣称语义正确。
3. 构建、静态检查、类型检查及受影响的初始化、资源、版本、升级和启动器测试。
4. 使用旧版基线检查单仓库和独立管理升级、自定义内容及历史工作保护；验证本地包可安装与命令可用。
5. 自身升级后重新运行入口一致性检查，检查旧确认及历史事实保持。真实 AI 在业务项目中的流程行为、跨平台运行和用户验收分别保留待验证状态。
