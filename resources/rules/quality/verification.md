# 验证依据

规则标识：QUALITY-VERIFY。执行检查、接受证据或判断完成时使用，并读取[工作记录约定](../core.md#工作记录约定)。

1. 明确要证明的要求、对象与范围，选择适用检查及预期结果。复用项目已有能力，不为简单变更强制引入整套工具。
2. 实际执行检查并读取输出，记录对象版本或内容摘要、环境、方法、时间、结果及证据位置。未执行、失败、无法判断与通过分别表达。
3. 评审、人工判断或外部结果说明实际来源及覆盖范围，不能用自行填写的通过标记代替。缺少必要能力时保持未验证，只有满足原约定的等效证据才能替代。
4. 输入、产物或规则发生变化后复核证据适用性。旧版本通过不能直接证明新版本；历史失败不删除，修复后追加实际复验结果。
5. 汇总检查覆盖及剩余缺口，仅在必要条件满足时报告对应范围完成。技术检查通过后仍须展示结果取得交付验收；文件存在、结构有效、局部测试通过不能替代人工确认。

已有项目按[已有项目接手](../core.md#已有项目接手)保留变更前基线并与当前结果比较；失败是否既有须有证据，无法比较时明确不确定。按[项目开发规范](../core.md#项目开发规范)分别记录配置是否落实、检查是否实际运行及结果，不能以配置生成或本地通过代替未执行的检查或 CI 结果。

CLI 检查约束其已实现的操作，不能阻止所有宿主中的直接修改。确认来源文本的存在、摘要匹配或复核记录不构成用户身份认证；执行者必须核对真实用户表达，不能自行写一个来源文件冒充批准。AI 表示已读规则不构成行为保证；初始化文件接入、宿主实际读取和具体工作验收需要分别取证。

结构检查、内容审阅与人工确认分别记录；工作检查通过仅覆盖其返回的登记产物和条件。产物完成记录、已有规格引用和需求依据绑定均不自动授予后续阶段批准，当前内容或依据变化后重新核对适用性。旧格式机器记录保留原件并拒绝使用，不转换成当前通过证据。

实施任务验证还须遵循[实施规划与任务拆分](../core.md#功能分块与实施安排)：进入依赖任务前保存前置任务当时的产物版本或内容摘要、检查方法与真实结果。必要检查未执行或失败均不满足依赖；后续改动复核受影响证据。同一轮的最终成品测试不证明此前各任务按顺序验证，事后复核应标明时间和偏差，不补造阶段证据。

stage verify、适用的 task verify 与整体 delivery-check 使用当前有效范围及相应验证选择，分别绑定用例、检查、显式输入、产物和证据。必要检查不得因失败而临时排除，无关全局缺口也不能冒充本任务的阻碍；需要改变选择时按对应阶段或规划重新核对并确认适用影响，不为报告型阶段建立不适用的开发规划。非必要产物缺失不自动免除显式列出的必要检查。technicalReady 报告技术事实，operationAllowed 另计精确例外，processEvidence 报告顺序证据，acceptance 来自真实用户决定，四者不能相互替代。

## 测试范围与长期用例

全局逐项评估 unit（单元）、interface（接口与契约）、integration（集成）、scenario（完整场景）、performance（性能与容量）、security（安全）、reliability（可靠性与恢复）、compatibility（环境兼容与交付）、usability（易用性与可访问性）。适用、不适用和待明确均说明理由；适用类别关联目标、方法、环境及完成条件，适用未执行不能改称不适用。类别可以交叉，指标来自需求和设计，不预设所有项目相同的阈值。

长期验证资料按需创建：`.tiller/verification/modules/<module-id>/<category>.yaml`、`cross-module/<scenario>.yaml`、`system/<topic>.yaml`。模块以稳定设计职责为准，需求定义验证目的，代码位置关联执行；模块不等同于任务或仓库。跨模块用例至少涉及两个模块，系统质量单独归属；仅调用其他模块不必改变归属。同一用例一个正文和稳定标识，不因移动文件改变标识，不复用废弃标识。

配置登记需求、模块、九类适用性和项目套件；YAML 声明条件、操作、预期及实现引用，index.md 提供汇总入口，不再手写重复详细用例。不同语言沿用自己的测试框架、目录和数据管理约定；已有场景格式可引用接入。不要求将全部内部单元测试复制为文档；引用套件仅说明关联，不能自动认为逐需求验证充分。

## 受控检查与执行证据

先查看实际 CLI 帮助，使用 `verification init` 建立验证入口，`verification check` 检查格式、引用和登记范围。空初始化保持类别待明确，不生成业务用例或历史通过。结构检查不替代内容审阅。

执行已配置套件使用 `verification run <work-id> --suite <suite> --input <run.json> --plan`，核对仓库、程序、参数、目录、时限和输入范围，再按实际授权使用 `--apply <digest>`。摘要只绑定配置和显式采集输入，不认证权限，也不捕获全部依赖或运行环境；应声明会影响结果的实际输入，额外环境变化人工复核。不要执行来源不明的文档命令，外部扫描、压测、部署和数据修改先核对具体目标与授权。

run 输入绑定当前 workflow；capture 同样包含真实阶段、动作及确认引用，开发任务还须明确 taskId 且已实际开始。任务证据不能替代阶段证据，旧代际或其他阶段的授权不能用于当前执行。输入只在[使用指引](../../usage.md)维护完整示例。

进程正常退出只说明套件执行结果，不自动为所有关联用例写入通过。外部或人工检查先用 `verification capture <work-id> --input <json>` 采集明确范围与受测版本，再实际检查并使用 `verification record <work-id> --input <json>` 引用该次 captureId、具体结果与独立证据。登记时和消费时都核对当前输入，不能在输入变化后拿旧观察记录通过。多个检查须覆盖各自实际输入；跨工作证据只读引用并核对范围及当前对象，不复制为新的历史事实。输入格式见[使用指引](../../usage.md)，来源声明不冒充身份核验或亲自执行。

证据独立于受检输入及控制资料；不能用工作入口、规划/任务状态、确认展示、机器结果或就绪回执自证通过。代码、用例定义、适用范围或实际产物变化后，旧结果保留但重新判断当前有效性；较新的失败、跳过或未执行不能被旧通过掩盖。生成产物须关联实际生成证据，目录成员变化和引用产物的上游失效均需重新核对。

`verification report <work-id>` 按分类汇总适用性、登记需求覆盖、套件事实、用例结果和证据是否仍适用。通过、失败、跳过、未执行和不适用分开；未支持解析的报告保留原始证据并明确人工复核，不能推断结果。工作内 verification.md 引用这些证据，说明任务回归、自动化全量回归或完整交付验证的实际范围。输入或产物变化后重新判断结论，旧事实保留，必要检查缺失不放行依赖任务。

真实 AI 流程验证须有实际交互、操作顺序和产物依据，分别检查确认、逐任务验证、失败依赖和接续；规则文字匹配及 AI 自填通过不是行为保证。验证命令只产生或核对验证证据，阶段状态通过 stage 命令、适用的开发任务状态通过 task 命令推进，不自动执行后续任务，也不授予验收、合入或发布权限。
