# 验证依据

规则标识：QUALITY-VERIFY。定义测试范围、执行检查或判断完成时使用。

## 本次验证

- 验收条件使用稳定编号，例如 `AC-1`。需求确认后先把每项转为全局用例，再按 `test_ref` 写测试并实现。
- 每项条件至少映射一个存在的用例编号；该用例必须有具名测试，且本次验证的 `test_ref` 必须与用例一致。
- `verify` 只声明 `--test "<文件::测试名>"`，由 tiller 构造并执行精确匹配的 node:test 命令；记录用例编号、实际命令、结果、退出码、核实状态、提交、代码树摘要和本机日志路径。
- 结果只从 tiller 私有临时报告读取，stdout/stderr 不参与判定。文件、完整名称（嵌套按名称路径）必须精确匹配且仅命中一个通过事件，且无失败；仅引用文件时要求全部通过。报告缺失/损坏、0/多个匹配、失败或跳过都不能核实。
- `verify.prepare` 可在 `project.json` 配置测试前准备命令（参数数组），失败即验证失败；`verify.runner` 缺省 `node-test`。新增框架在 `src/test-output.ts` 实现 `TestRunner` 的构造命令与报告解析并注册。
- 外部报告使用 `--reported --command --result --reason`，理由必填；默认阻断，只有 `--allow-reported` 显式放行并在 PR/MR 草稿标明未执行。
- bugfix 任务使用 `--expect-fail --test` 在基线临时工作树走同一适配器和报告路径证明失败，并保留当前同一测试的已核实通过记录。
- 失败、跳过、未运行和环境限制不能写成通过。套件正常退出不自动等于每个用例通过。
- 代码、测试或范围变化后，旧验证过期，需要重新执行或明确说明影响。

## 测试范围

按实际影响选择单元、接口、集成、场景、性能、安全、可靠性、兼容性和易用性检查；不适用项说明理由。长期用例按稳定模块和跨模块场景组织，不为小改动强制建立整套验证文档。

模块用例位于 `.tiller/cases/modules/<模块>/{behavior,interface,performance,security}.json`，模块名须与 `.tiller/specs/modules/` 一致；跨模块端到端路径位于 `.tiller/cases/scenarios/`，每条声明经过的 `modules` 和 `test_ref`。类型文件按需建立，不建空文件。

每个用例至少包含稳定 `id`、标题、需求/模块引用、`test_ref` 和源码路径。新用例用 `criteria` 保存 `<任务>#AC-N` 来源；历史空值只提示。`test_ref` 使用 `文件::测试名`；文件、具名测试和引用路径必须存在，编号跨文件和场景唯一。

## 记录方式

默认由 `verify` 和 `check` 维护 AC→用例→测试→当前验证的覆盖。`case add` 自动分配编号并校验模块与 AC；`verify` 从测试引用自动记录命中的用例编号；`check` 阻塞缺失、失效、错配、未回指当前 AC 或过期映射，报告各模块各类数量、场景和未覆盖模块，并在改动涉及模块时提示回归其用例和经过它的场景。任务记录只保留实际命令、结果和日志路径；完整输出写 `.tiller/local/logs/` 且不提交，需要时从 Git 取回或重新运行。
