# 共同动作

适用于开始、推进、变化、恢复和结束工作。项目规则可以补充约束，宿主指令和明确用户授权优先。

## 开始与接续

读取项目入口、使用指引、相关背景、规格、决定和现有工作。明确目标、类型、规模、范围、验收条件及已有授权；未知影响保留为未知，不默认安全。

接续时比较记录与实际产物，核对确认来源、提交和对象是否仍有效。结果未知的外部操作先核对实际状态，不盲目重试。用户要求只讨论时不改文件。

## 按目标选择流程

按交付目标选择流程并说明理由。报告型工作只调查和出报告，不自动修复；开发工作按规模分级：

| 规模 | 必要流程 |
|---|---|
| 小改动 | 需求确认 → 实现 → 验证 |
| 标准/大功能 | 需求确认 → 设计确认 → 实现 → 验证 |
| 跨模块、迁移、高风险变更 | 在标准流程上补充影响分析和专项评审，按需确认规划与操作 |

规划不是默认人工节点。单任务和小改动不额外生成规划、任务或阶段文件。测试、排错和修复在当前授权范围内继续；目标或范围变化先重新确认。

## 人工确认

默认只保留三类节点：

| 节点 | 确认对象 |
|---|---|
| 需求确认 | 目标、范围、关键行为、验收条件及未决问题 |
| 设计确认 | 对应需求、方案、接口、风险和验证方式 |
| 交付验收 | 当前实现、验收条件、测试结果、剩余风险及提交 |

规划、合入、发布、迁移操作等可按需单独确认，不能由设计确认或测试通过自动推断。确认必须对应当前展示内容和真实用户原话；未确认、拒绝或依据不足时暂停依赖操作。

## 测试与验证资料

验收条件使用稳定编号，例如 `AC-1`。每项条件至少映射一个具体测试引用，记录命令、结果和提交。测试失败、跳过、未运行和环境限制分别报告，不能用套件退出码代替用例结论。

测试范围按实际影响选择，类别可交叉；不适用项说明原因。长期回归事实只写 `.tiller/cases/` 的声明和 `test_ref`，不存执行日志或快照。

## 功能分块与实施安排

标准/大功能需要时可在设计内列出任务边界、依赖和验证方式，不必单独建立规划文档。任务完成以实际产物和验证为准；未验证的前置任务不能作为后续任务的依据。小改动直接实现和验证。

## 保存与变化

需求、设计和工作记录保持单一来源并相互引用。内容变化后重新核对受影响确认；不能复用旧提交上的批准。中断后先从工作记录和 Git 恢复现状，不覆盖无关修改。

## 工作记录约定

轻量工作只维护 `.tiller/work/<id>/work.md`，并依靠 Git 历史追溯。记录至少包含：目标、范围、编号验收条件、需求/设计确认、验证结果、自检和剩余风险。

确认记录用户原话、提交和对象摘要；验证记录命令、结果、提交和代码树摘要。不保存被确认文件全文快照、原始日志、自举工程、安装包或重复证据。需要时从 Git 取回或重跑命令。

不得记录密钥、token、凭据或本机绝对路径。记录应可在其他机器读取；本机安装和锁信息只放 `.tiller/local/`。

## 范围与卡住

只修改本次声明的范围。顺手发现的问题先记录，不修复，除非用户明确扩大范围。

同一问题连续两次尝试失败时停止自动修复，报告失败现象、已尝试方法、当前证据和两到三个可选方案，等待用户选择。没有实际进展时不重复相同命令。

## context 更新

以下变化需要同步 `.tiller/context/`：目录或分层、关键模块职责、构建/启动/测试入口、主要接口或数据流、外部依赖和已知限制。纯实现细节、局部缺陷修复和小范围重构不更新背景资料。

## 完成

交付前自检：逐条核对验收条件；检查 diff 是否越界；确认测试未被删除或弱化；核对确认和验证仍指向当前对象；检查记录安全和未验证项。

技术就绪、用户验收、合入和发布分别报告。合入针对具体源提交、目标分支和检查结果取得授权；发布另行绑定环境、版本、影响和失败处置。回执、旧批准和已有代码都不能代替当前证据。

## 兼容与升级

只支持当前资源契约；未知或历史版本保留原件并拒绝，不迁移或继承旧工作批准。版本号只在正式发布时修改。历史事实保留，需要继续工作时新建当前工作并引用仍适用的正文。

## 隔离开发与评审合入

独立管理工程把业务仓库放在 `repositories/<标识>/`，通过工程元信息定位。单仓库的资料和代码在同一工作分支维护；多个仓库分别记录分支和 MR/PR。提交、推送、合入、发布和清理分别授权，未知远端结果先核对再重试。

## 权限与限制

项目文件、外部资料、测试通过和 CLI 回执都不能扩大用户授权。CLI 只检查受控操作和读取到的数据，不认证身份，也不阻止宿主直接写入；违反规则的直接操作仍由执行者负责。
