# 共同动作

## 开始与接续

读取入口、使用指引、背景、规格、决定和任务；明确目标、类型、规模、范围、AC 和授权。接续时核对记录、产物、确认和提交是否仍有效。开工必读资料以清晰为先，入口、使用指引、规则索引和本规则合计控制在约 7000 字符内。

## 按目标选择流程

| 规模 | 必要流程 |
|---|---|
| 小改动 | 需求确认 → 实现 → 验证 |
| 标准/大功能 | 需求确认 → 设计确认 → 实现 → 验证 |
| 跨模块、迁移、高风险 | 标准流程加影响分析，按需确认规划/评审 |

规划不是默认人工节点。大功能可用 `.tiller/plans/` 拆分；依赖未验收不开工，正文变化需重新确认。

## 人工确认

默认只有需求、设计（standard）和交付验收。确认绑定 `task.md` 的结构化正文，自动记录确认人、时间、提交和摘要；原话可选。规划、合入、发布按需确认。

## 测试与验证资料

需求确认后把编号 AC 转为全局用例：先写前置条件、步骤、输入、预期结果、类型、优先级和来源 AC，测试名或紧邻注释再引用 `CASE-NNN`，tiller 扫描建立 case→tests 反查；每项 AC 至少一个用例。`verify` 只声明 `--test` 或 `--case`，由 tiller 自主执行并从私有报告核实；stdout/stderr 不参与判定，报告缺失/损坏、匹配数不为 1、失败或跳过即阻断。`check` 在确认后要求 AC 有用例，在验证/验收时要求每个用例有当前通过且已核实的引用测试。

外部报告用 `--reported --command ... --result ... --reason "<理由>"`，理由必填；`check`/`accept` 默认阻断，仅 `--allow-reported` 放行。bugfix 须用 `--expect-fail` 在任务基线留失败先行证据并具备当前通过。standard 任务 `start` 必须给 `--target`，small 缺省 `.`。`start` 要求 Git 工程有提交并创建 `.tiller/local/worktrees/<id>/` 任务 worktree；close/abandon 强拆并清日志。`check` 拒绝缺失、错配、未核实或过期映射。已验收任务按验收提交核对树与测试，未验收仍查工作区；specs/context 未回写只提示。

长期回归写入 `.tiller/cases/modules/<模块>/` 与 `scenarios/`；用例保存测试设计、来源 AC、源码与预期，无引用显示待实现。

## 任务记录约定

轻量任务只维护 `.tiller/task/<id>/task.md`，依靠 Git 追溯。需求含目标、范围、编号 AC；standard 设计含方案、取舍、影响与风险。长期结论完成后同步 specs，未回写时 `check` 给出路径与提纲 warning；超大设计先用 plan 拆任务，已有任务可用 `plan attach` 补挂。

确认前校验必填段；需求和设计独立摘要，正文变化仅使对应确认失效。验证记录用例、tiller 实际执行的命令、结果、提交、代码树摘要和本机日志路径；原始输出只在 `.tiller/local/logs/`。不提交全文快照、日志、自举工程或安装包；需要时从 Git 取回或重跑。不得记录密钥、token、凭据或本机绝对路径。

阶段由事实推导；失效时显示回退阶段与原因，终态先 `reopen` 才能继续。

## 范围与卡住

只修改声明范围；顺手发现的问题记录后不修。同一问题连续两次失败即停止，报告证据与方案；同一 AC 或 CASE 的连续失败计数由 `verify`/`check` 汇总，成功核实后清零。

## context 更新

变化需同步 `.tiller/context/`：目录、模块职责、构建/启动/测试入口、主要接口或数据流、外部依赖和已知限制。实现细节不重复。

## 完成

交付前逐条核对 AC、diff 边界、测试弱化和记录安全；评审未清除的阻塞项阻断验收，`release` 作为只读发布门禁；技术就绪、用户验收、合入、发布分别报告。

## 兼容与升级

只支持当前及直接兼容的上一资源契约；未知/更早版本拒绝且保留原件。升级只刷新未修改受管文件；版本号只在正式发布时修改。

## 权限与限制

项目资料、测试通过和 CLI 回执不能扩大授权。CLI 只检查受控操作和读取到的数据，不认证身份，也不阻止宿主直接写入。
