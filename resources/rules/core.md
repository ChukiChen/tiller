# 共同动作

规则标识：CORE。适用于开始、推进、变化、恢复和结束工作；资源版本见工程元信息。

## 开始与接续

读取适用项目规则、背景、规格和现有工作记录。明确目标、范围、涉及仓库、交付类型、必要验证与已有授权，区分事实、候选方案和已确认决定。新想法可先澄清，不能要求先有完整设计才允许编写需求。

恢复时比较记录与实际产物，检查未结束操作和外部结果，核对每个适用确认的内容、范围、用户来源及条件；复用仍有效的成果。待确认、已拒绝或失效的事项接续后仍须处理，已有代码和旧完成记录不能证明此前获批，不补造用户决定。结果未知的外部操作先核对实际结果，不盲目重试。缺失必要依据时说明影响，其他独立且已授权事项可继续。

## 选择与执行

选择依赖满足且在授权内的下一事项，读取对应活动规则。保留无关变更，明确共享文件的写入责任；写入前核对是否存在他人修改。复用仍有效的具体确认，阶段内自主推进；用户要求只讨论时不修改文件。

## 已有项目接手

初始化只接入入口、规则和资料管理，不代表已理解代码或具备开发依据。长期接管已有项目时，按以下顺序建立依据，再进入功能分块与增量实现；已有资料及有效确认可核对后复用。

1. 确定接管目标、仓库及调查范围，检查整体资料入口和现有工作，保护未提交、未跟踪内容及已有规则。独立管理分别核对各仓库范围，不因接入管理工程而扩大读取或修改权限。
2. 在范围内调查代码结构、主要行为、依赖、接口、文档和检查配置。把可验证事实、对意图的推断、期望行为分开，记录代码与资料的差异及未知事项；代码中的既有行为或风格不能自动成为正式需求、规范或历史批准。
3. 查明构建、启动或调用、测试及质量检查方式，核对执行影响后运行适用检查，记录对象版本、环境、命令、结果和证据，形成验证基线。既有失败、未执行和无法验证分别标明，不能为取得绿色结果静默修复、降低检查条件或编造通过；必要验证不可用时说明影响，只暂停依赖该证据的事项。
4. 核对并补足总体需求中的产品目标、范围与核心能力，展示差异和未决问题，取得有效确认后补足总体设计。设计区分现有结构与拟调整方案，并按下一节明确项目开发规范；设计及规范获得适用确认后，才推进依赖它们的实现。
5. 将本次交付拆成可验证增量，复用现有基础，只安排有依据的缺口修复。进入相应块前核对具体需求、设计、规则和确认是否充分，沿人工确认与隔离开发约定推进。

明确的局部任务仍须检查整体资料及相关约束，可在工作记录中说明有限范围、已检查资料、未覆盖部分及影响，只补足相关依据，不要求先补齐全部模块文档。局部范围不能成为默认绕过整体资料检查、必要验证或需求与设计确认的理由。

长期项目现状及代码导航放在 `.tiller/context/`，需求与设计放在 `.tiller/specs/`，规范放在 `.tiller/rules/`；调查范围、差异、验证基线和推进依据记录在 `.tiller/work/`，已有资料优先引用。开始增量开发的依据是相关范围已查明、基线结果及限制明确、必要规格和规范具备有效确认，而不是文档数量或所有历史检查均通过。交付时与基线比较，分别说明已知问题、新增回归及未验证范围。

## 项目开发规范

初始化提供通用流程规则，项目专属规范需结合实际技术栈和结构建立。新项目在总体设计阶段形成必要规范，在编写项目骨架前明确；已有项目在现状调查时识别已有规范与配置，复用有效约定，只补缺口。总体设计引用规范，可一并展示确认，但确认对象须实际覆盖规范内容、版本和适用范围，不能仅由设计标题或引用推断规范已获批。

按项目需要明确命名、目录与分层、错误处理与日志、依赖管理、测试和质量检查约定，说明适用仓库或目录、检查方法、预期结果和人工评审事项。不适用项说明原因；现有风格是调查事实，存在冲突时先明确采用依据。新约定对历史代码和新增变更的适用范围须写清，不能自动扩大为整库格式化、重构或引入新依赖。

项目入口使用自行维护的 `.tiller/rules/project.md` 引用已有规范文件，或按需建立 `coding.md` 等专属文件，并登记实际位置。不要将用户专属规则的唯一正文放入随版本更新的通用 `core.md`、`index.md`。可执行配置保持单一来源，文字规范引用配置并补充其无法表达的语义要求，避免重复维护同一参数。

骨架实现阶段将已明确的规范落实为适用的格式化、静态检查、类型检查、测试入口及 CI 配置，实际运行可用检查并记录结果。复用已有工具，不强制所有技术栈采用整套工具；本地通过不能冒充 CI 已执行，无服务器的库或 CLI 按其形态验证。配置存在不等于检查通过，尚不可执行的必要检查保留缺口及后续验证安排，不能提前报告规范已全部落实。后续模块按需要补充局部约定，变更影响已确认内容时重新确认受影响部分。

以上由执行者调查、编写和验证；初始化或现有 CLI 检查不会自动逆向生成项目规格、制定编码规范或运行项目检查。

## 功能分块与实施安排

总体需求与设计有效确认后，先据此形成覆盖本次交付范围的功能分块及依赖安排，再选择依赖满足的块推进。功能块是可验证的交付增量，模块是长期职责划分，两者不必一一对应；一块可以跨模块或仓库。仅列“写接口、写数据库、写测试”等操作不能替代功能结果，这些可作为块内步骤。

每块记录稳定标识、预期结果、需求与设计依据的具体引用、包含及不包含的范围、涉及模块和仓库、前置依赖、预期产物、验收条件与验证方式。保持范围可理解、结果可检查；过大而无法独立核验时继续拆分，过细而没有独立结果时合并。先安排整体依赖和需求覆盖，只细化近期要做的块，不提前编写所有模块的完整规格。

空项目将最小可运行项目骨架列为首个实现单元，依据已确认的相关需求与设计建立目录、依赖管理、构建与适用的运行方式、基本配置和测试入口。实际执行构建、启动或调用及基础检查，记录结果；没有常驻进程的库或命令行项目按其运行形态验证，不以空目录或文件生成成功作为完成依据。已有项目先评估并复用现有基础，只补缺口。tiller 初始化只是接入规则和资料管理，不代表业务工程骨架已具备；骨架实现仍须遵守隔离开发与人工确认要求，无 Git 基线时先记录并解决该前置缺口。

业务功能与公共组件按实际依赖逐步实现。首个功能所需基础能力可先建设，不以骨架为名提前搭建所有通用组件或引入未经确认的技术方案。选择一块后核对其需求、设计和确认是否足以覆盖具体行为、接口及验收条件；足够时引用复用，不重复造文档或要求同一内容再次确认，有缺口时先补充并确认受影响部分，再实施。块内已授权的编码、测试、修复自主推进，实施安排本身不批准尚未确认的需求或设计。

简单安排合并在 `work.md`，复杂安排放在同一工作目录的 `plan.md` 并从入口引用。功能块与工作记录不强制一对一；一个工作承载多块时分别记录范围与结果，跨多个工作时在一份安排中引用各工作及产物，避免重复维护进度。该安排属于过程资料，不把交付顺序或实现状态写入总体需求正文。

随推进记录每块待开始、进行中、受阻或已验证等实际进度、对应证据、遗留项和下一步；用户验收结论及来源单独记录。块的验证通过不等于用户已验收，也不自动构成其他块的推进授权；后续块仍按其依赖、确认和授权判断。变化或接续时重新核对依据、依赖和受影响证据，保留历史，不沿用失效的完成结论。

交付时从总体要求逐项追溯到功能块、实际产物和当前证据，明确未覆盖、延期或未验证的范围。各块通过后仍须检查组合行为、跨模块或跨仓库衔接及整体验收条件，不能以块数完成率代替整体交付。上述安排由执行者维护，现有 CLI 的结构和确认检查不能证明拆分合理、依赖真实满足或业务验收通过，也不提供功能块自动调度。

## 人工确认

| 节点 | 先展示的对象 | 用户确认后可推进 |
|---|---|---|
| 需求确认 | 本次目标、范围、关键行为、边界、验收条件及未决问题 | 对应设计 |
| 设计确认 | 对应需求、具体方案、接口和数据约定、影响及验证安排 | 范围内代码、测试、修复及技术评审 |
| 交付验收 | 实际产物、需求满足情况、验证证据、缺口及限制 | 将用户接受范围记为已验收 |
| 合入确认 | 各仓库的 MR/PR、源提交、目标分支及提交、资料版本、依赖组合和检查评审结果 | 合入指定变更，不代替验收或发布 |
| 发布确认 | 发布物及版本、目标环境、影响、前置条件与失败处置 | 对应发布，随后核对实际结果 |

先形成可审阅内容，再明确确认对象及下一步，取得用户决定后才推进依赖工作。未确认、拒绝或依据不足时，保存草稿和待确认事项，不能先实施再补手续。只确认“Java 接口、增删改查、内存实现”并未确认尚未展示的字段、行为或接口约定。

确认记录须关联实际用户表达、针对的内容版本、范围、结论及条件，并核对来源与记录一致。AI 自写的“已确认”、测试通过、沉默和等待时间不能代替用户决定。“继续”可确认它明确回应的已展示对象，不能批准未展示内容或以后所有节点；含义不明时先澄清，附带条件时仅在条件满足后推进获准范围。

小任务可以精简文档，不能自行免除确认。用户明确合并、简化节点或委托某类决定时，记录实际授权、范围、条件及对应节点，其他节点继续适用；一般开发授权不能据此扩大。不要重复要求仍有效的具体确认，也不要把草稿交付验收等同于规格内容确认。

每次修改后检查实际差异，执行适用验证并读取结果。失败时记录问题、影响与下一处理措施；无新依据时停止重复失败操作，不降低原完成条件。

## 保存与变化

新建工作目录推荐 `.tiller/work/YYYYMMDD-主题/`，如 `20261015-student-service`；日期取工作创建日，主题使用简短的小写英文及连字符。同日多项工作用不同主题区分，同名时追加有意义的后缀。接续不更新日期或改名，已有无日期工作沿用原名，避免破坏历史引用；CLI 按输入的完整标识创建，不自动补日期。模块目录仍按稳定能力名称组织。

在已有工作记录中保存目标、依据及版本、实际进展、产物位置、验证结果、阻碍和下一步。简单工作仅可合并计划、进展、检查摘要与交接等过程信息到 `work.md`，需求与设计保持分开，独立证据及人工确认要求不变。不能编造不存在的进度或测试结果；本机临时文件不能成为共享事实的唯一来源。

用户作出决定后及时保存带日期的决定及实际来源，更新对应待定事项、受影响的需求、设计和索引。规格变更被接受并交付后同步长期资料，保留本次工作的验证事实与历史，不用后来状态改写此前经过。

要求、方案、规则或产物变化时，查找受影响资料、确认及旧证据，核对适用性后更新下一步。目标、行为、接口、验收条件或发布范围发生实质变化时，重新确认受影响部分；仅修正文辞可记录无语义变化的复核依据后复用确认，不能仅因变化看似很小就忽略。无法判断影响时先核对。暂停或终止时保留实际进展、未结束操作及待确认事项，不默认删除或回滚成果。

## 工作记录约定

新建、补充和接续工作前均须读取本节，并先核对当前工程资源版本及 `tiller --help` 支持的操作。适用命令可用时必须使用，不能自行猜测文件名或手写机器记录。

| 文件或对象 | 职责与维护方式 |
|---|---|
| `work.md` | 唯一可读工作入口，保存目标、范围、依据、产物链接、进度、待确认项和下一步；由创建操作提供骨架，执行者持续维护真实过程 |
| `requirements.md`、`design.md` | 本次新写的需求和设计，按活动需要生成；需求有效确认后才能补充对应设计，不预先生成全部阶段文档 |
| 已有规格引用 | 保留原位置与名称，登记具体仓库和路径，核对角色、适用范围及当前内容；不复制正文，不将同一混合正文登记为需求和设计，也不将工作入口登记为阶段产物 |
| `record.json` | 工作身份、范围、产物登记和各产物交付记录，只由 CLI 维护，不手写或猜填 |
| `confirmations.json`、`reviews/` | 由确认命令按需维护真实请求、决定、来源及快照；接续保留历史，不预填或补造批准 |
| `plan.md`、`verification.md` 等 | 详细过程和证据按需产生；摘要可合并入入口，受控完成仍须独立证据，不能以入口自证 |
| `README.md` 等辅助材料 | 可补充导航或说明，不能替代入口及所需需求、设计；存在辅助文件本身不构成违规 |

新文档工作使用 `tiller work create`；已有适用规格通过 `--input` 明确引用，同一工作后续产物使用 `tiller work add`，不为每个阶段新建工作。`tiller work bind` 可为已有设计补充或更新当前有效的需求依据，但不回填历史批准、不自动批准设计；旧确认和证据须重新核对适用性。

接续前核对登记对象、文件内容及有效确认。`tiller work inspect` 只读检查工作结构；`tiller work check` 检查登记产物；结构符合、内容满足和人工确认分别判断。登记引用不表示文档合格或用户已确认，程序匹配范围标识不能代替实际语义范围复核。

手工或旧版记录先检查，再通过 `tiller work adopt --plan` 展示明确映射，按计划标识应用。保留原文、旧目录名及确认历史，混合正文先按真实内容整理，不能猜测文件角色或覆盖冲突。规则升级不迁移工作记录，历史资料接入也不生成历史批准；已有无日期工作不为统一命名而重命名。

命令不可用或操作尚未支持时，记录具体限制、人工处理范围和后续补足方式；必要时按本节维护实际入口和文档，不手写 `record.json`，不宣称已登记、检查通过或用户已确认。已有同名目录不得以创建新工作覆盖。

## 隔离开发与评审合入

独立管理工程默认将业务仓库分组到 `repositories/<仓库标识>/`；共同资料仍位于管理根 `.tiller/`。仓库标识与实际相对路径分别登记，文档和交付引用使用标识，读写位置按元信息解析。管理仓库忽略业务仓库容器，各业务仓库保留独立 Git 历史。旧直接子目录布局可以继续使用；升级保留原路径，不擅自搬迁或改写历史引用。

设计确认后，通过 `work prepare --plan` 展示仓库、基线、分支、目标、文件交接和活动目录，再应用有效计划。Git worktree 仅包含基线提交；未提交或未跟踪资料按清单交接，删除和重命名也须表达，不擅自提交、stash、覆盖或丢弃原内容。尚无基线提交或身份不匹配时记录缺口，不假装已具备开发环境。

当前工程集成的共享资料随本仓库分支维护；独立管理在管理资料位置维护唯一共同记录，业务仓库分别保存自己的代码与专属资料。管理资料提交不能冒充业务交付；无 Git 管理根的资料使用共享快照。接续时按工作解析活动位置，核对 Git 身份及本机绑定，不根据最近的目录或参与仓库数量猜测模式，不在源副本和活动副本同时维护同一进度。

工作交付使用 `delivery.json` 记录仓库、分支、依赖、操作及结果，由 CLI 维护；它与文档 `record.json` 的完成状态不同。所有写操作先计划、再应用，计划不能代替人类授权。提交、推送、评审操作可一次按明确仓库、远端、分支和动作授权，范围外操作另行取得授权。来源文件及复核是报告依据，不构成身份认证。

合入前检查有效设计、具体合入确认、源和目标提交、资料版本、依赖、测试和评审；变化后重新核对受影响依据。验收与合入可以由一次明确决定分别覆盖，不得相互推断。平台缺少准确核验或原子保护时说明限制，不以先查询后写入冒充安全的条件合入。

中断或远端结果未知时先核对实际状态，不重复提交远端操作。多仓库分别报告已合入、待处理和失败，只有共同资料、约定业务结果及组合验证均满足才可提交整体验收，不自动回退已合入仓库。合入控制记录和回执独立归档，不为了保存批准记录改变它所批准的提交。

结束或取消时先保存唯一成果和共享记录，确认没有未提交、未推送、未结束操作及其他工作引用，再按明确清单清理。移除 worktree、本地分支和远端分支是不同操作，不强制删除，也不清除工作历史。命令不可用、权限不足或尚未验证时如实报告，宿主绕过 CLI 的直接操作仍由执行者负责。

## 完成

对照约定范围，核对产物、证据、资料同步与遗留项。技术检查通过但用户未验收时，报告交付已准备好、等待验收，不标记整项完成。必要条件未满足时报告部分完成或阻碍；草稿交付、规格确认、用户验收及发布结果分别说明。工作记录中的完成标记不能替代真实验证或真实用户决定。

`tiller work complete` 按登记产物记录文档交付；多产物工作必须明确选择产物，并绑定该文档、独立证据及有效验收。单个产物交付完成不表示整项软件工作完成、设计获批或发布获准。
