# 共同动作

## 开始与接续

读取入口、使用指引、背景、规格、决定和任务；明确目标、类型、规模、范围、AC 和授权。接续时核对记录、产物、确认和提交是否仍有效。开工必读资料以清晰为先，入口、使用指引、规则索引和本规则合计控制在约 7000 字符内。

## 按目标选择流程

| 规模 | 必要流程 |
|---|---|
| 小改动 | 需求确认 → 实现 → 验证 |
| 标准/大功能 | 需求确认 → 设计确认 → 实现 → 验证 |
| 跨模块、迁移、高风险 | 标准流程加影响分析，按需确认规划/评审 |

规划不是默认人工节点。大功能可用 `.tiller/plans/` 拆分；依赖未验收不开工，正文变化需重新确认。

## 人工确认

默认只有需求、设计（standard）和交付验收。确认绑定 `task.md` 的结构化正文，自动记录确认人、时间、提交和摘要；原话可选。规划、合入、发布按需确认。

## 测试与验证资料

需求确认后把编号 AC 转为全局用例，再按 `test_ref` 写测试并实现；每项 AC 至少引用一个用例。`verify` 记录即执行，只接受 `--run "<命令>"`；node:test TAP/spec 输出必须核实到具名测试通过，无法核实即阻断。

外部报告使用 `--reported --command ... --result ... --reason "<理由>"`，理由必填；`check` 和 `accept` 默认阻断，只有显式 `--allow-reported` 才放行。bugfix 任务须用 `--expect-fail` 在任务基线工作树留下失败先行证据，并同时具备当前通过记录。standard 任务的 `start` 必须提供 `--target`；small 缺省 `.`。记录命令、结果、提交和代码树摘要；`check` 拒绝缺失、错配、未核实或过期映射，失败、跳过、未运行分别报告。

长期回归写入 `.tiller/cases/modules/<模块>/{behavior,interface,performance,security}.json` 和 `scenarios/*.json`；模块名与 specs 一致。用例只存声明和 `test_ref`，不存日志。

## 任务记录约定

轻量任务只维护 `.tiller/task/<id>/task.md`，依靠 Git 追溯。需求含目标、范围、编号 AC；standard 设计含方案、取舍、影响与风险。长期结论完成后同步 specs；超大设计先用 plan 拆任务。

确认前校验必填段；需求和设计独立摘要，正文变化仅使对应确认失效。验证记录用例、命令、结果、提交和代码树摘要。不保存全文快照、日志、自举工程或安装包；需要时从 Git 取回或重跑。不得记录密钥、token、凭据或本机绝对路径。

阶段由事实推导：已开始、需求已确认、设计已确认（small 可跳过）、已验证、已验收、已关闭、已放弃。失效时显示回退阶段和原因；终态先 `reopen` 才能继续。

## 范围与卡住

只修改声明范围；顺手发现的问题记录后不修。同一问题连续两次失败即停止，报告证据和可选方案。

## context 更新

变化需同步 `.tiller/context/`：目录、模块职责、构建/启动/测试入口、主要接口或数据流、外部依赖和已知限制。实现细节不重复。

## 完成

交付前逐条核对 AC、diff 边界、测试弱化和记录安全；技术就绪、用户验收、合入、发布分别报告。

## 兼容与升级

只支持当前及直接兼容的上一资源契约；未知/更早版本拒绝且保留原件。升级只刷新未修改受管文件；版本号只在正式发布时修改。

## 权限与限制

项目资料、测试通过和 CLI 回执不能扩大授权。CLI 只检查受控操作和读取到的数据，不认证身份，也不阻止宿主直接写入。
