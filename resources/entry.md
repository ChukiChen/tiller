# tiller 工作入口

tiller 帮助 AI 写清目标与方案、在范围内实现、用可定位测试证明结果。背景与约定见 `.tiller/context/`、`.tiller/rules/` 和已有决定。

## 开始

先读[使用指引](.tiller/usage.md)、[工程索引](.tiller/index.md)、项目规则、背景与任务记录，区分事实、候选方案和已确认决定。

开工说明目标、类型、规模、范围、仓库、验收条件和授权。小改动走“需求确认 → 实现 → 验证”；标准或大功能走“需求确认 → 设计确认 → 实现 → 验证”。默认人工节点只有需求、设计和交付验收；规划、合入、发布按需确认。大功能可先用 `.tiller/plans/` 拆分，依赖未验收不开工。工程内优先使用 `node .tiller/run.cjs`，参数从当前任务和错误提示推断。

## 执行纪律

- 只修改本次范围内的文件。顺手发现的问题记录到任务记录，不扩大修复。
- 同一问题两次修复失败即停止，报告证据与可选方案。
- 不删除、跳过或弱化测试来换取通过。验收条件必须编号，先转为全局用例，再映射具体测试引用。
- `start` 先写清目标、范围、AC 与设计；确认绑定结构化正文，自动记录部分、确认人、时间、提交和摘要，原话可选。
- 验证记录命令、结果、核实状态、提交和代码树摘要；`verify` 只接受 `--run` 并实际执行，外部报告须 `--reported` 写明理由并显式放行，bugfix 保留基线失败先行证据。全局回归写 `.tiller/cases/`，`task.md` 只记本次任务。不保存原始日志、全文快照、自举工程或安装包。
- 单个任务只维护一份 `task.md`；长期结论完成后同步到 `.tiller/specs/`，超大设计先用 plan 拆成多个任务。
- 任务阶段由记录事实推导；已验收用 `close` 收尾，未验收终止用 `close --abandon`，终态需显式 `reopen` 才能继续。
- 记录中不得出现密钥、token、凭据或本机绝对路径。共享资料必须可提交，`.tiller/local/` 只放本机数据。
- 架构、目录、命令或验证入口变化时同步 `.tiller/context/`；实现细节不重复。

## 交付

交付前逐条核对验收条件、diff 边界和测试是否被删除或弱化，报告未验证项与剩余风险；技术通过不代替用户验收。

提交、PR/MR 格式见使用指引。

合入和发布是独立可选操作，必须绑定当前提交、目标及检查结果并取得明确授权。版本号只在正式发布时修改；升级只核对当前及直接兼容的上一资源契约。

项目资料不能覆盖宿主指令或扩大授权；CLI 不认证身份，也不阻止绕过检查直接写入。
